# Тестирование баз данных (Database Testing)

## 1. Что такое тестирование баз данных?

**Database Testing** — проверка корректности хранения, обработки, изменения и удаления данных в базе данных, а также соблюдения ограничений целостности, транзакционных гарантий и требований к производительности.

Тестирование БД может включать:

- Проверку структуры таблиц и типов данных.
- Проверку CRUD-операций.
- Проверку ограничений целостности.
- Проверку транзакций и откатов.
- Проверку конкурентного доступа.
- Проверку связей между таблицами.
- Проверку миграций.
- Проверку согласованности данных между сервисами.
- Проверку производительности запросов.

### Краткий ответ для собеседования

> При тестировании базы данных я проверяю корректность хранения и изменения данных, соблюдение ограничений целостности, транзакционность операций, работу с конкурентными запросами и соответствие данных бизнес-требованиям. При необходимости также проверяю миграции схемы, производительность запросов и согласованность данных между сервисами.

### Нужно ли QA тестировать БД напрямую?

Не всегда.

Если функциональность полностью проверяется через API, а разработчики покрывают логику интеграционными тестами, прямые проверки БД могут быть необязательными.

Однако они особенно полезны, когда нужно проверить:

- Изменения в нескольких таблицах.
- Сложные связи между сущностями.
- Транзакционные откаты.
- Некорректные состояния данных.
- Результаты асинхронной обработки.
- Миграции и массовые обновления.
- Ошибки конкурентного выполнения.

**Главный принцип:** проверять не просто содержимое таблиц, а выполнение бизнес-инвариантов.

---

## 2. Что такое бизнес-инвариант?

**Инвариант** — условие, которое должно оставаться истинным для допустимых состояний системы.

Например, для банковских счетов:

- Баланс не должен становиться отрицательным, если овердрафт запрещён.
- Перевод не должен создавать деньги из ничего.
- Один и тот же платёж не должен выполняться повторно из-за ретрая.

Для системы бонусов:

- Один бонус не должен выдаваться дважды, если предусмотрена однократная выдача.
- Счётчик выдач не должен превышать установленный лимит.
- Запись о выданном бонусе должна быть связана с существующим пользователем.

Для заказов:

- Остаток товара не должен становиться отрицательным.
- Оплаченный заказ должен иметь корректную историю платежей.
- Удаление пользователя не должно неожиданно уничтожать финансовую историю.

### Пример

Есть таблица `accounts`:

```sql
CREATE TABLE accounts (
    id BIGINT PRIMARY KEY,
    balance DECIMAL(15, 2) NOT NULL,
    CHECK (balance >= 0)
);
```

Проверка:

```sql
SELECT *
FROM accounts
WHERE balance < 0;
```

**Ожидаемый результат:** 0 строк.

Но важно понимать, что такой запрос проверяет лишь один инвариант.

Например, положительный баланс сам по себе ещё не гарантирует правильность всей истории операций.

## 3. Тестирование CRUD-операций

CRUD — четыре базовые операции с данными:

- Create — создание.
- Read — чтение.
- Update — обновление.
- Delete — удаление.

### 3.1. Create

Проверяем создание новой сущности.

**Основные сценарии:**

1. Создание с корректными данными.
2. Создание с минимально допустимыми значениями.
3. Создание с максимально допустимыми значениями.
4. Попытка создания с обязательным полем NULL.
5. Попытка создания дубликата.
6. Создание со ссылкой на несуществующую сущность.
7. Повтор одного и того же запроса.
8. Два одновременных запроса создания.

Пример проверки:

```sql
SELECT *
FROM users
WHERE id = 100;
```

**Ожидаемый результат:** создана ровно одна запись с правильными значениями.

Дополнительно проверяем связанные таблицы, значения по умолчанию и автоматически заполняемые поля.

### 3.2. Read

Проверяем получение данных.

**Основные сценарии:**

- Получение существующей записи.
- Получение несуществующей записи.
- Поиск по различным фильтрам.
- Сортировка.
- Пагинация.
- Обработка NULL.
- Проверка прав доступа.
- Получение большого количества данных.

Например:

```sql
SELECT *
FROM orders
WHERE user_id = 10
ORDER BY created_at DESC, id DESC;
```

Проверяем, что API возвращает ожидаемые заказы в правильном порядке.

**Важно:** при отсутствии уникального ключа в ORDER BY порядок записей с одинаковыми значениями сортировки не гарантирован.

### 3.3. Update

Проверяем изменение существующей сущности.

**Основные сценарии:**

- Изменение одного поля.
- Изменение нескольких полей.
- Передача того же значения.
- Попытка изменения запрещённого поля.
- Обновление несуществующей записи.
- Конкурентное обновление.
- Проверка изменения связанных данных.

Пример:

```sql
SELECT id, status, updated_at
FROM orders
WHERE id = 101;
```

После изменения статуса через API проверяем:

- Новый статус.
- Обновление `updated_at`, если это предусмотрено.
- Отсутствие неожиданных изменений других полей.
- Корректность связанных сущностей.

### 3.4. Delete

Проверяем удаление данных.

Возможны два основных подхода.

**Hard Delete** — физическое удаление записи.

**Soft Delete** — логическое удаление, например через `deleted_at` или `is_deleted`.

Для Soft Delete:

```sql
SELECT
    id,
    deleted_at
FROM users
WHERE id = 100;
```

Проверяем:

- Что запись помечена удалённой.
- Что она не возвращается в обычных пользовательских запросах.
- Что связанные данные обрабатываются согласно требованиям.
- Что повторное удаление имеет ожидаемое поведение.

## 4. Проверка ограничений целостности

### PRIMARY KEY

Попытка создать запись с уже существующим первичным ключом.

**Ожидаемый результат:** БД отклоняет вставку.

### UNIQUE

Попытка зарегистрировать двух пользователей с одинаковым email.

**Ожидаемый результат:** если email должен быть уникален согласно требованиям, дубликат не сохраняется.

Особое внимание:

- NULL.
- Регистр символов.
- Пробелы.
- Нормализация email.
- Параллельные регистрации.

### NOT NULL

Попытка сохранить NULL в обязательное поле.

**Ожидаемый результат:** БД отклоняет изменение.

Но пустая строка `''` и NULL — разные значения. NOT NULL само по себе не запрещает пустую строку.

### FOREIGN KEY

Попытка создать заказ для несуществующего пользователя:

```sql
INSERT INTO orders (id, user_id, amount)
VALUES (101, 999999, 100);
```

Если существует активное ограничение FOREIGN KEY и соответствующего пользователя нет, вставка должна завершиться ошибкой.

### CHECK

Попытка установить отрицательный баланс:

```sql
UPDATE accounts
SET balance = -100
WHERE id = 1;
```

Если определён `CHECK (balance >= 0)`, изменение должно быть отклонено.

**Важно для QA:** ограничение БД и API-валидация решают разные задачи. API может возвращать понятную бизнес-ошибку, а БД обеспечивает дополнительную защиту целостности.

## 5. Проверка ссылочной целостности

Ссылочная целостность означает, что ссылки между связанными записями должны оставаться корректными.

### Сценарий 1. Создание дочерней записи

Создаём заказ с существующим `user_id`.

**Ожидаемый результат:** заказ сохраняется и правильно связан с пользователем.

### Сценарий 2. Несуществующий родитель

Создаём заказ с несуществующим `user_id`.

**Ожидаемый результат:** создание отклоняется либо обрабатывается по предусмотренным бизнес-правилам.

### Сценарий 3. Удаление родителя

Удаляем пользователя, у которого есть заказы.

В зависимости от схемы:

- Удаление запрещается.
- Заказы удаляются каскадно.
- Внешний ключ устанавливается в NULL.
- Выполняется другая предусмотренная бизнес-операция.

**Важно:** для финансовых систем каскадное удаление истории платежей часто недопустимо с точки зрения бизнес-требований.

### SQL-проверка осиротевших записей

```sql
SELECT o.*
FROM orders o
LEFT JOIN users u
    ON u.id = o.user_id
WHERE u.id IS NULL;
```

Если каждый заказ обязательно должен иметь существующего пользователя, результат должен содержать 0 строк.

## 6. Тестирование транзакций

При тестировании транзакций нужно проверять атомарность операции и правильность состояния данных после успеха или ошибки.

### Пример: банковский перевод

Есть два счёта:

| account_id | balance |
|---|---|
| 1 | 1000 |
| 2 | 500 |

Нужно перевести 100 со счёта 1 на счёт 2.

### Сценарий 1. Успешный перевод

Шаги:

1. Выполнить перевод через API.
2. Проверить успешный результат.
3. Проверить балансы обоих счетов.
4. Проверить запись в истории операций.

**Ожидаемый результат:**

- Баланс первого счёта — 900.
- Баланс второго счёта — 600.
- Суммарный баланс не изменился.
- История содержит корректную операцию.

### Сценарий 2. Ошибка после списания

Предположим, после списания происходит ошибка перед зачислением.

Если операция должна выполняться в одной локальной транзакции, проверяем, что вся транзакция откатилась.

**Ожидаемый результат:**

- Первый баланс — 1000.
- Второй баланс — 500.
- Нет зафиксированного частичного перевода.

### Сценарий 3. Недостаточно средств

Попытка перевода 1500 при балансе 1000.

**Ожидаемый результат:**

- Операция отклонена.
- Балансы не изменились.
- Не создана успешная запись перевода.

### Сценарий 4. Ошибка во время COMMIT

Клиент потерял соединение в момент фиксации.

Результат операции может оказаться неизвестным клиенту.

**Важно:** отсутствие успешного HTTP-ответа не означает, что транзакция обязательно откатилась.

Нужно проверить фактическое состояние операции и поведение повторного запроса.

### Как моделировать сбои?

В зависимости от доступной инфраструктуры:

- Специальные test hooks.
- Fault injection.
- Управляемые ошибки зависимостей.
- Отключение соединения.
- Таймауты.
- Тестовые конфигурации сервисов.

Простое закрытие соединения клиентом не гарантирует, что ошибка произошла до COMMIT. Поэтому нужно контролировать точку сбоя.

## 7. Тестирование конкурентного доступа

Конкурентное тестирование проверяет поведение системы при одновременном выполнении операций над общими данными.

### Сценарий: последний товар

В БД:

```text
product_id = 1
stock = 1
```

Два пользователя одновременно пытаются купить товар.

**Шаги:**

1. Подготовить товар с остатком 1.
2. Подготовить двух разных пользователей.
3. Отправить два запроса практически одновременно.
4. Проверить ответы API.
5. Проверить состояние БД.

**Ожидаемый результат:**

- Не больше одной успешной покупки единственной единицы товара.
- Остаток неотрицательный.
- Нет двух активных резервирований одной единицы.
- Ошибка второго запроса соответствует требованиям.

### Сценарий: Lost Update

Исходное значение:

```text
balance = 1000
```

Два запроса одновременно увеличивают баланс:

- Первый на 100.
- Второй на 200.

Если оба изменения должны примениться, ожидаемый итог — 1300.

Получение 1100 или 1200 может свидетельствовать о потерянном обновлении.

### Сценарий: ограничение количества бонусов

У бонуса лимит 1000 выдач.

Текущее количество выдач — 999.

Одновременно поступают два запроса на выдачу.

**Ожидаемый результат:**

- Не более одной дополнительной успешной выдачи.
- Итоговый счётчик не превышает 1000.
- Записи о выдаче и счётчик согласованы.

### Как запускать конкурентные проверки?

Можно использовать:

- Параллельные API-запросы.
- Несколько независимых SQL-соединений.
- Интеграционные тесты.
- Специализированные тестовые хуки.
- k6 или другой инструмент генерации нагрузки.

**Важный нюанс:** два запроса, отправленных одновременно с клиента, не обязательно пересекутся в критическом участке кода. Для воспроизводимых race condition лучше управлять моментом выполнения операций.

## 8. Тестирование идемпотентности

**Идемпотентность** означает, что повторное применение одной и той же операции не меняет итоговый эффект после первого успешного применения.

Для бизнес-операций это часто означает защиту от повторного выполнения одного логического действия.

### Пример

```http
POST /payments
Idempotency-Key: payment-123
```

Клиент отправляет запрос на оплату.

Из-за сетевого таймаута он не получает ответ и повторяет тот же запрос с тем же ключом.

**Ожидаемый результат:** не происходит нежелательное второе списание.

### Основные проверки

1. Первый запрос с новым ключом.
2. Повтор идентичного запроса с тем же ключом.
3. Повтор с тем же ключом, но другим телом.
4. Параллельные запросы с одинаковым ключом.
5. Повтор после ошибки.
6. Повтор после таймаута.
7. Повтор после истечения срока хранения ключа.

**Важно:** точные HTTP-статусы и формат повторного ответа зависят от контракта API.

Например, сервер может вернуть сохранённый результат первого запроса либо специальную ошибку конфликта для несовместимого повторного использования ключа.

### Что проверить в БД?

- Количество созданных платежей.
- Количество фактических списаний.
- Уникальность идентификатора операции.
- Статусы операций.
- Отсутствие нежелательных повторных побочных эффектов.

## 9. Тестирование асинхронной обработки и брокеров сообщений

В микросервисных системах данные часто изменяются после обработки сообщений из Kafka или RabbitMQ.

Например:

1. Сервис платежей создаёт операцию.
2. Публикует событие `PaymentCompleted`.
3. Сервис заказов обрабатывает событие.
4. Обновляет статус заказа в БД.

### Позитивный сценарий

Сообщение успешно обработано.

Проверяем:

- Правильность обновления БД.
- Связь с исходной операцией.
- Корректность статуса.
- Отсутствие непредусмотренных изменений.

### Повторная доставка сообщения

Одно событие доставляется обработчику повторно.

**Ожидаемый результат:** если событие описывает одну логическую операцию, её бизнес-эффект не должен нежелательно дублироваться.

Например, один платёж не должен дважды увеличивать оплаченную сумму заказа.

### Ошибка во время обработки

Consumer изменил БД, но завершился до подтверждения обработки сообщения.

При повторной доставке проверяем:

- Распознавание уже обработанного события.
- Корректность идемпотентности.
- Отсутствие повторного бизнес-эффекта.

### Нарушение порядка событий

Например, поступают:

- `OrderCreated`
- `OrderPaid`
- `OrderCancelled`

Если архитектура допускает доставку или обработку событий не по порядку, нужно проверить, как система обрабатывает такие ситуации.

**Важно:** Kafka гарантирует порядок сообщений в пределах одной партиции, но это не означает глобального порядка между всеми партициями и сервисами.

### Eventual Consistency

При асинхронном взаимодействии обновления между сервисами могут происходить не мгновенно.

Поэтому для проверки лучше использовать ожидание конечного состояния с ограниченным таймаутом, а не фиксированный `sleep`.

## 10. Тестирование миграций БД

**Миграция БД** — контролируемое изменение структуры или данных базы данных.

Примеры:

- Добавление колонки.
- Изменение типа данных.
- Создание индекса.
- Добавление ограничения.
- Перенос данных.
- Разделение таблицы.
- Удаление устаревших колонок.

### Сценарий 1. Добавление новой колонки

Проверяем:

- Успешность миграции.
- Тип данных.
- NULL/NOT NULL.
- Значение по умолчанию.
- Совместимость с существующим кодом.

### Сценарий 2. Добавление NOT NULL

Если таблица уже содержит NULL, миграция может завершиться ошибкой.

Проверяем:

1. Состояние данных до миграции.
2. Наличие процедуры заполнения старых записей.
3. Добавление ограничения.
4. Работу API после изменения схемы.

### Сценарий 3. Добавление UNIQUE

Перед созданием уникального индекса проверяем наличие дубликатов.

```sql
SELECT
    email,
    COUNT(*)
FROM users
WHERE email IS NOT NULL
GROUP BY email
HAVING COUNT(*) > 1;
```

Если дубликаты существуют, миграция может завершиться ошибкой.

### Сценарий 4. Добавление индекса на большую таблицу

Проверяем:

- Время создания индекса.
- Наличие блокировок.
- Влияние на параллельные запросы.
- Использование диска.
- Корректность завершения.
- План выполнения запросов после миграции.

**Нюанс MySQL:** многие DDL-команды вызывают неявный COMMIT. Откат схемы обычным ROLLBACK может быть невозможен.

### Сценарий 5. Совместимость старой и новой версии сервиса

При rolling deployment некоторое время одновременно могут работать несколько версий приложения.

Проверяем, что:

- Старый код продолжает работать с новой схемой.
- Новая версия корректно обрабатывает старые данные.
- Изменения не нарушают интеграции.
- Удаление старой колонки происходит только после прекращения её использования.

Для этого часто применяют подход Expand and Contract.

## 11. Тестирование производительности БД

Задача QA — не обязательно самостоятельно оптимизировать SQL, но уметь обнаруживать деградацию и предоставлять разработчикам полезные данные.

### Основные показатели

- Время выполнения запросов.
- p95/p99 latency.
- Количество запросов в секунду.
- CPU.
- Использование памяти.
- Disk I/O.
- Количество активных соединений.
- Время ожидания блокировок.
- Частота deadlock.
- Количество ошибок и таймаутов.

### EXPLAIN

Позволяет изучить план выполнения SQL-запроса.

PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE user_id = 100;
```

**Важно:** EXPLAIN ANALYZE действительно выполняет запрос.

### На что обращать внимание?

- Полный просмотр большой таблицы.
- Большое количество прочитанных строк.
- Неэффективные JOIN.
- Дополнительные сортировки.
- Устаревшая статистика.
- Неподходящие индексы.
- Большое расхождение между оценкой и фактическим количеством строк.

### Типичный дефект: N+1 Queries

Приложение сначала получает список из 100 заказов, затем для каждого отдельно запрашивает пользователя.

Вместо нескольких эффективных запросов выполняется 101 обращение.

На небольших данных проблема может быть незаметна, но под нагрузкой время ответа значительно увеличивается.

**Для QA:** полезно сравнивать количество SQL-запросов и latency при увеличении объёма возвращаемых данных.

## 12. Тестирование больших объёмов данных

При большом количестве записей могут проявляться проблемы, незаметные на небольшом тестовом наборе.

### Основные сценарии

- Миллионы строк в таблице.
- Пользователь с тысячами связанных записей.
- Большое количество элементов в одном запросе.
- Пагинация глубоко в наборе данных.
- Массовое создание записей.
- Массовое обновление.
- Работа с партиционированными таблицами.

### Что проверять?

- Корректность результата.
- Время выполнения.
- Потребление ресурсов.
- Таймауты.
- Работа индексов.
- Размер транзакций.
- Блокировки.
- Корректность пагинации.

### Пример: глубокая пагинация

```sql
SELECT *
FROM orders
ORDER BY id
LIMIT 100 OFFSET 1000000;
```

Большой OFFSET может приводить к дорогостоящему пропуску множества строк.

Альтернативой может быть keyset pagination:

```sql
SELECT *
FROM orders
WHERE id > 1000000
ORDER BY id
LIMIT 100;
```

Но этот подход требует соответствующего контракта пагинации и подходящего ключа сортировки.

## 13. Тестирование партиционирования

Допустим, таблица истории бонусов разделена на месячные партиции.

### Позитивный сценарий

Создаём запись с датой внутри существующего диапазона.

**Ожидаемый результат:** запись доступна через родительскую таблицу и физически находится в правильной партиции.

### Граничные даты

Проверяем:

- Последнюю допустимую дату текущей партиции.
- Первую дату следующей партиции.
- Переход месяца.
- Переход года.
- Особенности часовых поясов.

Для PostgreSQL:

```sql
SELECT
    tableoid::regclass AS partition_name,
    id,
    created_at
FROM bonus_history
WHERE id = 100;
```

`tableoid::regclass` позволяет определить физическую таблицу, содержащую строку.

### Отсутствующая партиция

Пытаемся сохранить запись с датой, для которой нет подходящей партиции и default partition.

**Ожидаемый результат:** БД отклоняет операцию.

Приложение должно корректно обработать эту ошибку.

### Проверка Partition Pruning

```sql
EXPLAIN
SELECT *
FROM bonus_history
WHERE created_at >= '2026-05-01'
  AND created_at < '2026-06-01';
```

Проверяем, что план не включает ненужные партиции, если ожидается эффективное отсечение.

## 14. Тестирование репликации и согласованности

В некоторых архитектурах запись выполняется в Primary, а чтение — с Replica.

### Сценарий: Read After Write

1. Пользователь обновляет профиль.
2. API подтверждает успешное обновление.
3. Пользователь немедленно выполняет GET.
4. Запрос попадает на реплику.

Если используется асинхронная репликация, GET может временно вернуть старые данные.

### Что важно выяснить?

- Допускается ли eventual consistency?
- Какая задержка считается приемлемой?
- Требуется ли read-your-writes consistency?
- Есть ли возможность читать с Primary после записи?
- Как приложение обрабатывает отставание реплики?

**Важно:** устаревшие данные после записи не всегда являются дефектом. Это зависит от согласованности, обещанной контрактом системы.

## 15. Тестирование безопасности данных

### SQL Injection

SQL Injection возникает, когда недоверенные входные данные влияют на структуру SQL-запроса.

Основная защита — параметризованные запросы и корректное управление доступом к БД.

Для QA важно проверять, что ввод пользователя не позволяет изменить предполагаемую семантику запроса.

### Доступ к чужим данным

Пример:

```http
GET /orders/101
```

Пользователь A пытается получить заказ пользователя B.

Проверяем не только HTTP-ответ, но при необходимости и отсутствие несанкционированного изменения данных.

### Чувствительные данные

Проверяем:

- Не хранятся ли секреты в открытом виде без необходимости.
- Не попадают ли пароли и токены в логи.
- Ограничены ли права сервисных учётных записей.
- Не раскрываются ли персональные данные через API.
- Корректно ли реализованы правила удаления или обезличивания данных.

## 16. Полный пример тестирования backend-функциональности

### Задача

Разработана ручка:

```http
POST /bonuses/issue
```

Она выдаёт пользователю бонус.

Условия:

- Бонус должен существовать.
- Пользователь должен существовать.
- Бонус можно выдать только один раз на пользователя.
- У бонуса есть общий лимит выдач.
- При выдаче создаётся запись в истории.
- При ошибке данные должны оставаться согласованными.

### Позитивные проверки

1. Успешная выдача бонуса.
2. Проверка записи в таблице выдач.
3. Проверка обновления счётчика.
4. Проверка правильности идентификаторов.
5. Проверка дат и статусов.

### Негативные проверки

1. Несуществующий пользователь.
2. Несуществующий бонус.
3. Повторная выдача.
4. Исчерпанный лимит.
5. Некорректные входные данные.
6. Ошибка БД.
7. Таймаут зависимости.

### Конкурентные проверки

1. Два запроса на выдачу одного бонуса одному пользователю.
2. Параллельные выдачи разным пользователям при почти исчерпанном лимите.
3. Повтор после таймаута.
4. Конкурентное изменение лимита и выдача бонусов, если такая операция поддерживается.

### Проверки согласованности

Предположим, есть:

- `users_to_bonuses` — выданные бонусы.
- `bonus_issue_counters` — счётчики выдач.

Проверяем:

- Нет нежелательных повторных выдач.
- Счётчик соответствует предусмотренной модели учёта.
- Количество успешных операций не превышает лимит.
- Нет частично сохранённых операций.
- Не возникает рассинхронизация после повторных запросов.

**Важно:** нельзя автоматически считать, что значение счётчика обязано равняться количеству строк в истории. Сначала нужно понять назначение счётчика, правила отмен и повторных выдач.

## 17. Как выбирать глубину тестирования БД?

Не каждую операцию необходимо проверять одновременно через API, интеграционные тесты разработчиков и ручные SQL-запросы.

Глубина проверок зависит от риска.

### Низкий риск

Например, получение справочного списка без изменения данных.

Обычно достаточно:

- Проверки API.
- Валидации схемы ответа.
- Проверки основных фильтров.
- Проверки обработки ошибок.

### Средний риск

Например, изменение пользовательских настроек.

Дополнительно полезны:

- Проверки сохранения данных.
- Проверки повторных запросов.
- Проверки конкурентного изменения, если оно возможно.
- Проверки корректности обновления связанных сущностей.

### Высокий риск

Например, выдача бонусов, списание денег или изменение лимитов.

Могут потребоваться:

- Транзакционные проверки.
- Fault injection.
- Тестирование идемпотентности.
- Конкурентные сценарии.
- Проверки ограничений БД.
- Интеграционные проверки.
- Нагрузочное тестирование.

### Как ответить на вопрос: «Нужно ли руками проверять API, если разработчик уже написал интеграционные тесты?»

> Я бы сначала оценил, какие сценарии уже покрыты, на каком уровне выполняются тесты и какие риски остаются. Если интеграционные тесты действительно проверяют критичную бизнес-логику, нет необходимости вручную дублировать все случаи. Но я могу выполнить независимую проверку наиболее рискованных сценариев, проверить контракт API, интеграции, данные и поведение в условиях, которые не покрываются существующими тестами.

Это демонстрирует риск-ориентированный подход, а не стремление проверить всё одинаковое количество раз.

## 18. Типичные вопросы на собеседовании

### 1. Что проверять при тестировании базы данных?

Корректность данных, ограничения целостности, связи, транзакции, конкурентные операции, миграции и производительность в зависимости от риска.

### 2. Как проверить транзакционность операции?

Создать ситуацию ошибки внутри транзакционной последовательности и убедиться, что итоговое состояние соответствует требуемой атомарности.

### 3. Как проверить конкурентный доступ?

Запустить параллельные операции над общими данными и проверить соблюдение инвариантов и корректность обработки конфликтов.

### 4. Как проверить идемпотентность?

Повторить одну логическую операцию, в том числе после таймаута и параллельно, и проверить отсутствие нежелательных повторных эффектов.

### 5. Как найти осиротевшие записи?

Использовать LEFT JOIN с проверкой отсутствия родительской строки либо NOT EXISTS.

### 6. Как проверить, что миграция прошла успешно?

Проверить структуру, данные, ограничения, совместимость версий приложения и отсутствие критичных побочных эффектов.

### 7. Что делать, если после UPDATE пользователь видит старые данные?

Проверить кэширование, использование реплик, задержку репликации, транзакции и контракт согласованности.

### 8. Что такое Race Condition?

Ситуация, при которой результат работы системы зависит от порядка или времени выполнения конкурентных операций.

### 9. Почему при конкурентном тестировании недостаточно отправить два запроса последовательно?

Потому что нужно создать пересечение операций, способное проявить конфликт. Последовательные запросы обычно не воспроизводят race condition.

### 10. Как проверить, что два запроса не создадут одну сущность дважды?

В зависимости от требований использовать параллельные проверки, повторные запросы, проверку уникальных ограничений и итогового состояния БД.

### 11. Как проверить производительность SQL?

Изучить план выполнения, фактические метрики, индексы, объём данных, статистику, влияние конкурентной нагрузки и возможную деградацию.

### 12. Как проверить большое количество данных?

Использовать репрезентативные объёмы, оценивать корректность результатов, время ответа, потребление ресурсов, пагинацию и конкурентные операции.

### 13. Как проверить каскадное удаление?

Удалить родительскую запись и проверить, что зависимые строки изменились или удалились строго согласно определённым ограничениям и бизнес-правилам.

### 14. Как проверить обработку сообщения из Kafka на уровне БД?

Проверить итоговые изменения, обработку дубликатов, повторную обработку после ошибок, порядок событий и согласованность данных.

### 15. Как понять, нужны ли прямые проверки БД?

Оценить критичность данных, покрытие существующих тестов, наблюдаемость результата через API и риск скрытых ошибок хранения или конкурентного изменения.

## 19. Частые ошибки на собеседовании

**Ошибка:** «Тестирование БД — это просто проверить, что запись появилась в таблице».

Правильно: нужно также оценивать корректность связей, ограничений, транзакций и бизнес-инвариантов.

**Ошибка:** «Если API вернул 500, изменения точно откатились».

Правильно: HTTP-ошибка сама по себе не доказывает откат. Операция могла быть частично выполнена или даже полностью зафиксирована до ошибки формирования ответа.

**Ошибка:** «Если API вернул 200, данные точно сохранены».

Правильно: значение успешного ответа зависит от контракта. Например, асинхронная операция могла быть только принята к обработке.

**Ошибка:** «Для проверки конкурентности достаточно дважды вызвать API».

Правильно: важно обеспечить наложение операций во времени и проверить конечные инварианты.

**Ошибка:** «Все проверки БД QA обязан выполнять вручную».

Правильно: уровень и способ проверки выбираются исходя из рисков и существующего автоматизированного покрытия.

**Ошибка:** «Если используется Kafka, сообщение будет обработано ровно один раз».

Правильно: гарантии доставки и обработки требуют понимания конфигурации Kafka, управления offset и бизнес-идемпотентности.
