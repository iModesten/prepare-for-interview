# Индексы в базах данных (Database Indexes)

## 1. Что такое индекс?

**Индекс (Index)** — это дополнительная структура данных, которая позволяет СУБД быстрее находить строки по определённым значениям, не просматривая каждый раз всю таблицу.

Индекс можно сравнить с предметным указателем в книге: вместо последовательного просмотра всех страниц можно найти нужный термин и перейти к соответствующему месту.

Индексы особенно полезны для:

- Поиска по `WHERE`.
- Соединения таблиц через `JOIN`.
- Сортировки через `ORDER BY`.
- Поиска по диапазонам значений.
- Проверки уникальности данных.

### Краткий ответ для собеседования

> Индекс — дополнительная структура данных, ускоряющая поиск и извлечение строк из таблицы. Чаще всего используются B-tree индексы. Они позволяют эффективно искать значения и диапазоны. При этом индексы занимают дополнительное место и увеличивают стоимость операций изменения данных, поэтому создавать их на каждый столбец нецелесообразно.

---

## 2. Как работает индекс?

Представим таблицу `users` с миллионом записей:

| id | email | name |
|---|---|---|
| 1 | anna@example.com | Anna |
| 2 | bob@example.com | Bob |
| 3 | kate@example.com | Kate |
| ... | ... | ... |

Выполняем запрос:

```sql
SELECT *
FROM users
WHERE email = 'kate@example.com';
```

### Без индекса

СУБД может последовательно проверять строки, пока не найдёт нужную.

Такой способ называется **Sequential Scan (Seq Scan)** в PostgreSQL или Full Table Scan в MySQL.

При большом объёме данных это может быть дорого.

### С индексом

Создадим индекс:

```sql
CREATE INDEX idx_users_email
ON users (email);
```

Теперь СУБД может использовать индекс, чтобы быстрее определить расположение подходящей записи.

**Важно:** наличие индекса не гарантирует его использование. Оптимизатор выбирает план выполнения исходя из предполагаемой стоимости.

Для маленькой таблицы полный просмотр может оказаться быстрее обращения к индексу.

## 3. B-tree индекс

**B-tree (Balanced Tree)** — наиболее распространённый тип индекса в реляционных СУБД.

В PostgreSQL и MySQL InnoDB B-tree-подобные структуры используются для эффективного поиска значений и диапазонов.

В InnoDB фактически используется B+tree.

### Как устроен B-tree?

Упрощённо структура состоит из:

- Корневого узла (Root).
- Промежуточных узлов (Internal nodes).
- Листовых узлов (Leaf nodes).

Например:

```text
                [50]
               /    \
           [20]      [80]
          /    \     /    \
       [10]  [30] [60]  [90]
```

Это схематичная иллюстрация поиска, а не точная физическая структура страниц индекса.

При поиске значения 60 СУБД последовательно выбирает нужные ветви дерева вместо просмотра всех записей.

### Для каких операций полезен B-tree?

```sql
-- Точное совпадение
SELECT * FROM users WHERE id = 100;

-- Диапазон
SELECT * FROM orders WHERE amount > 1000;

-- BETWEEN
SELECT * FROM orders
WHERE amount BETWEEN 100 AND 500;

-- IN
SELECT * FROM users WHERE id IN (1, 5, 10);

-- Сортировка
SELECT * FROM orders ORDER BY created_at;
```

B-tree также может поддерживать некоторые префиксные поиски по строкам, например:

```sql
SELECT *
FROM users
WHERE name LIKE 'Ann%';
```

Но фактическая применимость зависит от СУБД, collation и типа индексного оператора.

### Почему B-tree эффективен?

Он поддерживает упорядоченное хранение индексных ключей и обеспечивает логарифмическую глубину поиска.

Это позволяет эффективно работать даже с большими таблицами.

## 4. Основные типы индексов

### 4.1. Primary Key Index

Индекс, связанный с первичным ключом.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    email VARCHAR(255)
);
```

Первичный ключ обеспечивает:

- Уникальность.
- Запрет NULL.
- Эффективный поиск по ключу.

**PostgreSQL:** для PRIMARY KEY автоматически создаётся уникальный B-tree индекс.

**MySQL InnoDB:** PRIMARY KEY является кластеризованным индексом.

### 4.2. Unique Index

Обеспечивает уникальность индексируемых значений согласно правилам СУБД.

```sql
CREATE UNIQUE INDEX idx_users_email
ON users (email);
```

Попытка вставить повторяющийся email приведёт к ошибке уникальности.

**Нюанс:** поведение UNIQUE относительно NULL зависит от СУБД и настройки ограничения. В PostgreSQL по умолчанию несколько NULL допустимы, но есть возможность `NULLS NOT DISTINCT`.

### 4.3. Composite Index — составной индекс

Индекс, созданный по нескольким колонкам.

```sql
CREATE INDEX idx_orders_user_status
ON orders (user_id, status);
```

В таком индексе порядок колонок имеет значение.

Подробно разберём это ниже.

### 4.4. Partial Index — частичный индекс

Позволяет индексировать только строки, удовлетворяющие определённому условию.

Пример для PostgreSQL:

```sql
CREATE INDEX idx_active_users
ON users (email)
WHERE status = 'ACTIVE';
```

В индекс попадут только активные пользователи.

Это может уменьшить его размер и стоимость обслуживания.

**Важно:** MySQL InnoDB не поддерживает partial indexes в таком же виде, как PostgreSQL.

### 4.5. Expression / Functional Index

Индекс по результату выражения.

Например, в PostgreSQL:

```sql
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));
```

Он может ускорить поиск:

```sql
SELECT *
FROM users
WHERE LOWER(email) = 'anna@example.com';
```

MySQL 8.0+ также поддерживает функциональные части индексов, но синтаксис и ограничения отличаются.

### 4.6. Другие типы индексов PostgreSQL

| Тип | Основное применение |
|---|---|
| B-tree | Равенство, диапазоны, сортировка |
| Hash | Проверки равенства |
| GIN | Массивы, JSONB, полнотекстовый поиск |
| GiST | Пространственные и другие специализированные операции |
| BRIN | Очень большие таблицы с корреляцией значений и физического расположения |
| SP-GiST | Специализированные структуры разбиения пространства |

Для обычного QA-собеседования достаточно хорошо понимать B-tree и назначение остальных на базовом уровне.

## 5. Составные индексы и порядок колонок

Это одна из самых важных тем для собеседования.

Создадим индекс:

```sql
CREATE INDEX idx_orders_user_status_date
ON orders (user_id, status, created_at);
```

Внутри индекс упорядочен сначала по `user_id`, затем по `status`, затем по `created_at`.

### Пример 1. Поиск по user_id

```sql
SELECT *
FROM orders
WHERE user_id = 100;
```

Индекс хорошо подходит, поскольку условие использует первую колонку.

### Пример 2. Поиск по user_id и status

```sql
SELECT *
FROM orders
WHERE user_id = 100
  AND status = 'PAID';
```

Индекс также хорошо подходит.

### Пример 3. Поиск по всем трём колонкам

```sql
SELECT *
FROM orders
WHERE user_id = 100
  AND status = 'PAID'
  AND created_at >= '2026-01-01';
```

Условия по двум первым колонкам задают точные значения, а третья ограничивает диапазон.

Это типичный эффективный сценарий для составного B-tree индекса.

### Пример 4. Поиск только по status

```sql
SELECT *
FROM orders
WHERE status = 'PAID';
```

Индекс обычно значительно менее эффективен для этого запроса, поскольку отсутствует ограничение по первой колонке.

Оптимизатор может предпочесть полный просмотр или другой индекс.

Однако современные оптимизаторы могут применять дополнительные механизмы, например skip scan, поэтому утверждение «индекс вообще невозможно использовать» было бы слишком категоричным.

### Leftmost Prefix Rule

Для составного B-tree индекса наиболее эффективными обычно являются условия на начальные (левые) колонки индекса.

Например, для индекса `(A, B, C)`:

| Условия WHERE | Типичная эффективность |
|---|---|
| A | Хорошая |
| A, B | Хорошая |
| A, B, C | Хорошая |
| B | Часто низкая |
| C | Часто низкая |
| B, C | Часто низкая |

Это не абсолютный запрет на использование индекса без первой колонки. Результат зависит от оптимизатора, статистики и распределения данных.

### Важный нюанс: диапазонные условия

Для составного индекса:

```sql
CREATE INDEX idx_example
ON orders (user_id, created_at, status);
```

Запрос:

```sql
SELECT *
FROM orders
WHERE user_id = 100
  AND created_at > '2026-01-01'
  AND status = 'PAID';
```

После диапазонного условия на `created_at` последующие колонки часто уже не помогают сузить диапазон сканирования настолько эффективно, как при равенстве.

Но они всё ещё могут использоваться для фильтрации на уровне индекса или других оптимизаций.

**Практическое правило:** при проектировании составных индексов нужно учитывать реальные фильтры, равенства, диапазоны и сортировки, а не просто добавлять все колонки из WHERE.

## 6. Селективность и кардинальность

### Кардинальность (Cardinality)

В контексте статистики индексируемого столбца под кардинальностью часто понимают количество различных значений.

Например:

**Таблица users: 1 миллион строк.**

Поле `id`:

- 1 миллион уникальных значений.
- Высокая кардинальность.

Поле `gender` или `status`:

- Несколько различных значений.
- Низкая кардинальность.

### Селективность (Selectivity)

Селективность показывает, какую долю строк выбирает условие.

Например:

```sql
SELECT *
FROM users
WHERE id = 123;
```

Вероятно, вернёт одну строку из миллиона — условие очень селективно.

А запрос:

```sql
SELECT *
FROM users
WHERE status = 'ACTIVE';
```

может вернуть 900 тысяч строк — условие слабо селективно.

### Почему это важно?

Если условие возвращает почти всю таблицу, индекс может быть невыгоден.

Обращения к индексу и последующее чтение большого количества строк могут стоить дороже последовательного просмотра таблицы.

**Важно:** высокая кардинальность колонки сама по себе не гарантирует, что конкретное условие будет высокоселективным. Например, условие диапазона может выбирать большую часть значений уникального столбца.

## 7. Почему СУБД не использует индекс?

Это один из типичных вопросов технического интервью.

Возможные причины:

### 1. Таблица маленькая

Для небольшой таблицы полный просмотр может быть быстрее.

### 2. Условие возвращает слишком много строк

Если запрос выбирает большую часть таблицы, использование индекса может оказаться дороже.

### 3. Индекс не соответствует условию

Есть индекс:

```sql
CREATE INDEX idx_orders_user
ON orders (user_id);
```

Но запрос фильтрует по другому полю:

```sql
SELECT *
FROM orders
WHERE status = 'PAID';
```

### 4. Функция над индексируемой колонкой

```sql
SELECT *
FROM users
WHERE LOWER(email) = 'test@example.com';
```

Обычный индекс по `email` может не подходить для такого выражения.

Возможное решение — функциональный индекс.

### 5. Преобразование типов

Неявные преобразования иногда мешают эффективному использованию индекса.

Конкретное поведение зависит от СУБД и типов выражений.

### 6. Устаревшая статистика

Оптимизатор принимает решения на основании статистики распределения данных.

Если статистика устарела, план может быть неоптимальным.

Для PostgreSQL:

```sql
ANALYZE orders;
```

Для MySQL:

```sql
ANALYZE TABLE orders;
```

### 7. Неудачная структура составного индекса

Запрос фильтрует по второй или третьей колонке, а первая не ограничена.

### 8. Индекс всё же не самый дешёвый вариант

Даже если индекс применим, оптимизатор может сознательно выбрать альтернативный способ доступа.

**Ключевая мысль:** отсутствие Index Scan не обязательно означает проблему. Нужно сравнивать реальную стоимость и время выполнения.

## 8. EXPLAIN и EXPLAIN ANALYZE

**EXPLAIN** показывает, какой план выполнения запроса выбрал оптимизатор.

Это один из основных инструментов анализа производительности SQL.

### PostgreSQL

```sql
EXPLAIN
SELECT *
FROM users
WHERE email = 'test@example.com';
```

Возможный результат:

```text
Index Scan using idx_users_email on users
  Index Cond: (email = 'test@example.com')
```

Это означает, что оптимизатор планирует использовать индекс.

### Основные операции PostgreSQL

| Операция | Значение |
|---|---|
| Seq Scan | Последовательный просмотр таблицы |
| Index Scan | Поиск через индекс с обращением к таблице |
| Index Only Scan | Попытка получить данные преимущественно из индекса |
| Bitmap Index Scan | Создание набора указателей подходящих строк |
| Bitmap Heap Scan | Чтение строк таблицы по bitmap |
| Nested Loop | Соединение через вложенные циклы |
| Hash Join | Соединение с использованием хеш-таблицы |
| Merge Join | Соединение упорядоченных наборов |
| Sort | Сортировка |
| Aggregate | Агрегация |

### EXPLAIN ANALYZE

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'test@example.com';
```

В отличие от обычного EXPLAIN, эта команда действительно выполняет запрос и показывает фактическую информацию.

В том числе:

- Время выполнения.
- Фактическое количество строк.
- Количество выполнений узлов.
- Отличия между оценками оптимизатора и реальностью.

Для более подробного анализа:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM users
WHERE email = 'test@example.com';
```

`BUFFERS` позволяет получить информацию об обращениях к буферам.

**Осторожно:** `EXPLAIN ANALYZE` действительно выполняет SQL. Если применить его к UPDATE или DELETE, данные могут измениться.

Для безопасного изучения плана изменяющего запроса в PostgreSQL можно использовать транзакцию с откатом:

```sql
BEGIN;

EXPLAIN ANALYZE
UPDATE users
SET status = 'ACTIVE'
WHERE id = 1;

ROLLBACK;
```

При этом триггеры и внешние побочные эффекты не обязательно отменяются откатом.

### MySQL

```sql
EXPLAIN
SELECT *
FROM users
WHERE email = 'test@example.com';
```

Основные поля традиционного табличного представления:

| Поле | Что показывает |
|---|---|
| type | Способ доступа к данным |
| possible_keys | Потенциально подходящие индексы |
| key | Выбранный индекс |
| rows | Оценка количества просматриваемых строк |
| filtered | Оценка процента строк, проходящих фильтр |
| Extra | Дополнительная информация |

Возможные значения `type`:

- `const`
- `eq_ref`
- `ref`
- `range`
- `index`
- `ALL`

`ALL` обычно обозначает полный просмотр таблицы, но это не всегда плохой план.

Для фактической информации в MySQL 8.4:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'test@example.com';
```

## 9. Index Scan, Index Only Scan и Covering Index

### Index Scan

СУБД использует индекс для поиска подходящих записей, а затем при необходимости обращается к основной таблице за остальными значениями.

### Covering Index

**Покрывающий индекс** — индекс, содержащий все столбцы, необходимые для выполнения определённого запроса.

Например, есть запрос:

```sql
SELECT status, created_at
FROM orders
WHERE user_id = 100;
```

Для него потенциально подходит индекс:

```sql
CREATE INDEX idx_orders_cover
ON orders (user_id, status, created_at);
```

Поскольку все необходимые колонки содержатся в индексе, часть или все обращения к основной таблице можно избежать.

### PostgreSQL: INCLUDE

PostgreSQL позволяет добавлять неключевые столбцы:

```sql
CREATE INDEX idx_orders_cover
ON orders (user_id)
INCLUDE (status, created_at);
```

`user_id` участвует в поиске, а `status` и `created_at` хранятся в индексе как дополнительные данные.

Это может позволить использовать Index Only Scan.

Однако из-за MVCC PostgreSQL иногда всё равно обращается к таблице, чтобы проверить видимость строк.

### MySQL InnoDB

В InnoDB вторичные индексы содержат также значение первичного ключа, позволяющее найти строку в кластеризованном индексе.

Если все необходимые данные доступны из вторичного индекса, дополнительное обращение к кластеризованному индексу может не понадобиться.

Это может отображаться как `Using index` в EXPLAIN.

## 10. Clustered и Non-Clustered Index

### Clustered Index

Кластеризованный индекс определяет организацию хранения основных данных таблицы.

**MySQL InnoDB** хранит данные таблицы в структуре кластеризованного индекса.

Обычно в качестве него используется PRIMARY KEY.

Если подходящего первичного или уникального ключа нет, InnoDB может использовать внутренний скрытый идентификатор строки.

### Secondary Index

Вторичный индекс — дополнительная структура для поиска по другим колонкам.

В MySQL InnoDB вторичные индексы содержат значения первичного ключа для доступа к основной записи.

### PostgreSQL

В PostgreSQL таблицы обычно хранятся отдельно от индексов в heap-структуре.

Индексы ссылаются на расположение версий строк в таблице.

Команда `CLUSTER` может физически переупорядочить таблицу по индексу, но PostgreSQL не поддерживает автоматическое постоянное поддержание этого порядка, аналогичное кластеризованному индексу InnoDB.

### Сравнение

| Характеристика | PostgreSQL | MySQL InnoDB |
|---|---|---|
| Основное хранение строк | Heap | Clustered Index |
| PRIMARY KEY | Уникальный индекс | Обычно кластеризованный индекс |
| Вторичные индексы | Ссылки на строки таблицы | Хранят ключ для доступа к clustered index |
| Порядок данных | Не гарантируется индексом | Организован по clustered key |

## 11. Как индексы влияют на INSERT, UPDATE и DELETE?

Индекс — не бесплатная оптимизация.

### INSERT

При добавлении строки СУБД должна обновить необходимые индексы.

Чем больше индексов, тем выше потенциальные затраты на вставку.

### UPDATE

Если изменяется индексируемое значение, индекс также может потребовать обновления.

В PostgreSQL механизм HOT (Heap-Only Tuple) в некоторых случаях позволяет избежать создания новых записей в индексах при обновлении.

### DELETE

При удалении строк необходимо корректно обслуживать связанные индексные структуры.

Физическая очистка может происходить не сразу и зависит от реализации СУБД.

### Основные недостатки индексов

- Дополнительное дисковое пространство.
- Увеличение стоимости записи.
- Дополнительные затраты на обслуживание.
- Возможная фрагментация и увеличение размера индексов.
- Более сложный выбор плана оптимизатором.

**Вывод:** создавать индексы следует исходя из реальных запросов и характера нагрузки.

## 12. Практический пример оптимизации запроса

Представим таблицу `orders` с 10 миллионами записей.

Частый запрос:

```sql
SELECT id, amount, created_at
FROM orders
WHERE user_id = 100
  AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 20;
```

### Шаг 1. Проверяем план

```sql
EXPLAIN
SELECT id, amount, created_at
FROM orders
WHERE user_id = 100
  AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 20;
```

Предположим, что запрос выполняется медленно и использует полный просмотр с сортировкой.

### Шаг 2. Анализируем условия

В запросе используются:

- Равенство по `user_id`.
- Равенство по `status`.
- Сортировка по `created_at`.
- Ограничение результата через `LIMIT`.

### Шаг 3. Создаём составной индекс

```sql
CREATE INDEX idx_orders_user_status_date
ON orders (user_id, status, created_at DESC);
```

Такой индекс потенциально позволит найти нужного пользователя, нужный статус и получать строки в подходящем порядке.

### Шаг 4. Повторно проверяем план

Сравниваем:

- Выбранный способ доступа.
- Фактическое время выполнения.
- Количество прочитанных строк.
- Количество обращений к буферам.
- Необходимость отдельной сортировки.

### Шаг 5. Проверяем побочные эффекты

Измеряем влияние нового индекса на:

- INSERT новых заказов.
- UPDATE статуса.
- Использование диска.
- Другие частые запросы.

**Важно:** индекс следует оценивать на данных и нагрузке, близких к реальным, а не только на небольшой тестовой таблице.

## 13. Что важно QA при тестировании индексов?

Индексы в основном влияют на производительность, но уникальные индексы и ограничения также обеспечивают целостность данных.

### Функциональные проверки

- Уникальные ограничения действительно работают.
- Дубликаты корректно отклоняются.
- NULL обрабатывается согласно требованиям и СУБД.
- Запросы возвращают правильные данные после изменения схемы.
- Изменения структуры не нарушают работу приложения.

### Нагрузочные проверки

- Снизилось ли время ответа запросов.
- Улучшился ли p95 или p99.
- Не ухудшилась ли производительность INSERT/UPDATE.
- Не увеличились ли чрезмерно затраты ресурсов.
- Как ведёт себя система при параллельной работе.

### Проверки миграций

Если в релизе добавляется индекс на большую таблицу, важно проверить:

- Сколько времени занимает создание.
- Блокирует ли оно операции приложения.
- Достаточно ли свободного диска.
- Корректно ли обрабатываются ошибки миграции.
- Можно ли безопасно откатить изменение.

В PostgreSQL существует `CREATE INDEX CONCURRENTLY`, позволяющий существенно снизить блокирование обычных операций записи, но он имеет ограничения и дополнительные затраты.

В MySQL InnoDB доступные online DDL-операции зависят от конкретного изменения структуры и возможностей версии СУБД.

## 14. Типичные вопросы на собеседовании

### 1. Что такое индекс?

Дополнительная структура данных, ускоряющая поиск и доступ к строкам таблицы.

### 2. Какие бывают индексы?

B-tree, Hash, GIN, GiST, BRIN и другие. Доступность зависит от СУБД.

### 3. Почему нельзя создать индекс на каждую колонку?

Потому что индексы занимают место, увеличивают стоимость записи и требуют обслуживания.

### 4. Что такое составной индекс?

Индекс по нескольким колонкам, в котором порядок колонок может влиять на эффективность поиска.

### 5. Что такое Leftmost Prefix Rule?

Принцип, согласно которому составной B-tree индекс обычно наиболее эффективен при использовании его начальных колонок.

### 6. Почему запрос не использует индекс?

Возможные причины: маленькая таблица, низкая селективность, неподходящий индекс, функции над колонками, устаревшая статистика или более дешёвый альтернативный план.

### 7. Что такое EXPLAIN?

Инструмент для получения плана выполнения SQL-запроса.

### 8. Чем EXPLAIN отличается от EXPLAIN ANALYZE?

EXPLAIN показывает план и оценки, а EXPLAIN ANALYZE выполняет запрос и собирает фактические показатели.

### 9. Что такое селективность?

Характеристика того, насколько сильно условие сокращает количество подходящих строк.

### 10. Может ли индекс замедлить запрос?

Да. Неподходящий план с индексным доступом может быть дороже полного просмотра. Кроме того, индексы замедляют некоторые операции записи.

### 11. Что такое Covering Index?

Индекс, содержащий все необходимые для конкретного запроса столбцы и позволяющий избежать части обращений к основной таблице.

### 12. Чем индекс по PRIMARY KEY отличается в PostgreSQL и MySQL InnoDB?

В PostgreSQL PRIMARY KEY обеспечивается отдельным уникальным индексом. В InnoDB PRIMARY KEY обычно служит кластеризованным индексом, в котором организовано хранение основных данных.

### 13. Как оптимизировать медленный SQL-запрос?

Изучить план выполнения, фактические показатели, количество прочитанных строк, фильтры, JOIN, сортировки, индексы и статистику. Затем изменить запрос или индексы и повторно измерить результат.

### 14. Может ли составной индекс (A, B) помочь запросу только по B?

Иногда да, в зависимости от СУБД, оптимизатора и распределения данных. Но обычно такой индекс менее эффективен для поиска только по B, чем индекс с B в начале.

### 15. Что произойдёт при создании уникального индекса, если в таблице уже есть дубликаты?

Создание индекса завершится ошибкой, поскольку существующие данные нарушают требование уникальности.

## 15. Частые ошибки на собеседовании

**Ошибка:** «Если есть индекс, запрос обязательно будет быстрее».

Правильно: оптимизатор может не использовать индекс, а индексный доступ не всегда выгоднее полного просмотра.

**Ошибка:** «Индекс всегда работает только по одному полю».

Правильно: существуют составные индексы по нескольким колонкам.

**Ошибка:** «Индекс хранит все данные таблицы».

Правильно: обычный вторичный индекс хранит индексные ключи и информацию для доступа к строкам. Физическая организация отличается между СУБД.

**Ошибка:** «EXPLAIN ANALYZE только показывает план и ничего не выполняет».

Правильно: он реально выполняет запрос.

**Ошибка:** «Высокая кардинальность гарантирует использование индекса».

Правильно: оптимизатор учитывает селективность конкретного условия, стоимость доступа и другие факторы.

**Ошибка:** «Составной индекс (A, B, C) нельзя использовать без условия по A».

Правильно: это зависит от реализации оптимизатора, хотя без ограничений по начальным колонкам он часто менее эффективен.
