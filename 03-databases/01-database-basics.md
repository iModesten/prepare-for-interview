# Основы реляционных баз данных (Database Basics)

## 1. Что такое база данных и СУБД?

**База данных (Database)** — организованная совокупность данных, предназначенная для хранения, поиска, изменения и обработки информации.

**СУБД (Database Management System, DBMS)** — программная система для управления базами данных.

Примеры СУБД:

- PostgreSQL
- MySQL
- Microsoft SQL Server
- Oracle Database
- SQLite

СУБД обеспечивает механизмы хранения, обработки запросов, управления транзакциями, конкурентного доступа, целостности и восстановления данных.

### Краткий ответ для собеседования

> База данных — организованное хранилище данных. СУБД — программное обеспечение, которое управляет этим хранилищем и предоставляет инструменты для работы с данными, выполнения запросов, управления транзакциями и обеспечения целостности.

---

## 2. Реляционная модель данных

**Реляционная модель** — модель организации данных, основанная на отношениях (relations).

В реляционных СУБД данные представлены в виде таблиц.

Таблица состоит из:

- Столбцов (Columns) — атрибутов.
- Строк (Rows) — записей.
- Типов данных.
- Ограничений целостности.

Например, таблица `users`:

| id | name | email |
|---|---|---|
| 1 | Anna | anna@example.com |
| 2 | Bob | bob@example.com |
| 3 | Kate | kate@example.com |

### Важные свойства

1. Каждая колонка имеет определённый тип данных.
2. В рамках таблицы имена колонок уникальны.
3. Логический порядок строк не гарантируется.
4. Для идентификации записей обычно используют первичные ключи.
5. Связи между таблицами могут задаваться внешними ключами.

**Важно:** первичный ключ не является обязательным синтаксическим требованием для создания таблицы в PostgreSQL или MySQL, но отсутствие подходящего ключа часто осложняет работу с данными.

## 3. Основные типы данных

Типы определяют, какие значения можно хранить в колонках.

| Тип | Назначение |
|---|---|
| INTEGER / INT | Целые числа |
| BIGINT | Большие целые числа |
| DECIMAL / NUMERIC | Числа с заданной точностью |
| FLOAT / DOUBLE | Числа с плавающей точкой |
| VARCHAR(n) | Строки переменной длины |
| CHAR(n) | Строки фиксированной длины |
| TEXT | Текстовые данные |
| BOOLEAN | Логические значения |
| DATE | Дата |
| TIME | Время |
| TIMESTAMP | Дата и время |
| JSON | JSON-документы |

### DECIMAL vs FLOAT

**DECIMAL** хранит точные десятичные значения в рамках заданной точности.

**FLOAT/DOUBLE** использует приближённое двоичное представление чисел.

Для финансовых расчётов обычно используют DECIMAL либо целочисленное представление минимальных денежных единиц.

Например:

```sql
CREATE TABLE accounts (
    id BIGINT PRIMARY KEY,
    balance DECIMAL(15, 2) NOT NULL
);
```

`DECIMAL(15, 2)` означает до 15 десятичных цифр всего, из них 2 после запятой.

### TIMESTAMP и часовые пояса

Здесь есть важные различия:

- В PostgreSQL `TIMESTAMP WITHOUT TIME ZONE` не хранит информацию о часовом поясе.
- PostgreSQL `TIMESTAMPTZ` представляет момент времени, нормализуемый относительно UTC, но не сохраняет исходное имя часового пояса.
- В MySQL `TIMESTAMP` выполняет преобразования между часовым поясом сессии и UTC.
- В MySQL `DATETIME` хранит дату и время без автоматической привязки к часовому поясу.

**Для QA:** проверять правильность хранения и отображения времени, особенно в системах с пользователями из разных часовых поясов.

## 4. Первичный ключ (Primary Key)

**Primary Key (PK)** — ограничение, однозначно идентифицирующее каждую строку таблицы.

Основные свойства:

- Уникальность.
- Запрет NULL.
- Одна конструкция PRIMARY KEY на таблицу.
- Может состоять из нескольких колонок.

Пример:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100)
);
```

Попытка вставить две строки с одинаковым id завершится ошибкой.

### Составной первичный ключ

```sql
CREATE TABLE user_roles (
    user_id BIGINT,
    role_id BIGINT,
    PRIMARY KEY (user_id, role_id)
);
```

Это означает, что комбинация `user_id + role_id` должна быть уникальной.

При этом один пользователь может иметь несколько ролей, а одна роль — принадлежать нескольким пользователям.

### Natural Key vs Surrogate Key

**Natural Key** — ключ, основанный на бизнес-данных.

Примеры:

- Артикул товара.
- Уникальный идентификатор внешней системы.

**Surrogate Key** — искусственно созданный технический идентификатор.

Примеры:

- BIGINT с автоинкрементом.
- UUID.

Для многих систем удобнее использовать технический первичный ключ, а бизнес-уникальность дополнительно защищать UNIQUE-ограничениями.

## 5. Внешний ключ (Foreign Key)

**Foreign Key (FK)** — ограничение, обеспечивающее ссылочную целостность между таблицами.

Например:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100)
);

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10, 2),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Здесь:

- `users` — родительская таблица.
- `orders` — дочерняя таблица.
- `orders.user_id` ссылается на `users.id`.

Если внешние ключи включены и корректно определены, нельзя создать заказ с несуществующим `user_id`.

### Что обеспечивает Foreign Key?

- Защиту от ссылок на несуществующие записи.
- Контроль удаления или изменения родительских записей.
- Поддержание ссылочной целостности.

**Важно:** логическая связь между таблицами может существовать и без ограничения FOREIGN KEY. Но тогда БД сама не гарантирует ссылочную целостность такой связи.

## 6. ON DELETE и ON UPDATE

Для внешних ключей можно задавать поведение при удалении или изменении родительской записи.

### RESTRICT / NO ACTION

Запрещают операцию, если она нарушает ссылочную целостность.

Пример: нельзя удалить пользователя, если у него существуют заказы, ссылающиеся на него.

### CASCADE

Автоматически распространяет изменение на зависимые записи.

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
);
```

При удалении пользователя его связанные заказы также будут удалены.

**Осторожно:** каскадное удаление может затронуть большое количество данных.

### SET NULL

При удалении родительской записи внешний ключ дочерней строки устанавливается в NULL.

```sql
FOREIGN KEY (user_id)
    REFERENCES users(id)
    ON DELETE SET NULL
```

Для этого колонка `user_id` должна допускать NULL.

### SET DEFAULT

Предполагает установку значения по умолчанию, если оно допустимо для ограничения.

Однако поддержка зависит от СУБД. Например, InnoDB в MySQL 8.4 не поддерживает `SET DEFAULT` как действие внешнего ключа.

### Отличие NO ACTION от RESTRICT

В PostgreSQL некоторые ограничения FOREIGN KEY могут быть отложены до конца транзакции с помощью `DEFERRABLE`. Для `NO ACTION` такая отложенная проверка возможна, а `RESTRICT` проверяется немедленно.

В MySQL InnoDB проверки внешних ключей не откладываются: `NO ACTION` фактически ведёт себя как `RESTRICT`.

## 7. Типы связей между таблицами

### One-to-One (1:1)

Одной записи таблицы A соответствует не более одной записи таблицы B.

Пример:

- Пользователь.
- Профиль пользователя.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY
);

CREATE TABLE profiles (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL UNIQUE,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Ограничение UNIQUE на `user_id` не позволяет создать несколько профилей для одного пользователя.

### One-to-Many (1:N)

Одной записи таблицы A может соответствовать несколько записей таблицы B.

Пример:

- Один пользователь.
- Множество заказов.

```text
users
  1
  |
  |---- order 101
  |---- order 102
  |---- order 103
```

Обычно реализуется с помощью внешнего ключа на стороне «многие».

### Many-to-Many (M:N)

Одной записи таблицы A может соответствовать множество записей B, и наоборот.

Пример:

- Пользователи.
- Роли.

Обычно создаётся промежуточная таблица:

```sql
CREATE TABLE user_roles (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    PRIMARY KEY (user_id, role_id),
    FOREIGN KEY (user_id) REFERENCES users(id),
    FOREIGN KEY (role_id) REFERENCES roles(id)
);
```

### Важный вопрос для QA

Как проверить, что пользователь не получит одну и ту же роль дважды?

Один из способов — составной PRIMARY KEY или UNIQUE по комбинации `user_id, role_id`.

## 8. Ограничения целостности (Constraints)

Ограничения помогают обеспечивать корректность данных непосредственно на уровне БД.

### NOT NULL

```sql
name VARCHAR(100) NOT NULL
```

Запрещает сохранять NULL.

### UNIQUE

```sql
email VARCHAR(255) UNIQUE
```

Запрещает дублирование определённых значений.

Следует учитывать особенности сравнения строк и обработки NULL.

### CHECK

```sql
CREATE TABLE accounts (
    id BIGINT PRIMARY KEY,
    balance DECIMAL(15, 2) NOT NULL,
    CHECK (balance >= 0)
);
```

Запрещает отрицательное значение balance.

**Нюанс:** CHECK обычно не отклоняет UNKNOWN, поэтому для полноценного запрета NULL часто нужно отдельное NOT NULL.

### DEFAULT

```sql
status VARCHAR(20) DEFAULT 'NEW'
```

Если значение колонки при INSERT не указано, может использоваться значение по умолчанию.

DEFAULT сам по себе не гарантирует, что колонка не будет содержать NULL.

### FOREIGN KEY

Обеспечивает ссылочную целостность.

### PRIMARY KEY

Обеспечивает уникальную идентификацию строк.

### Почему ограничения важны?

Проверки на уровне приложения не всегда достаточно.

Например, два параллельных запроса могут одновременно проверить, что email свободен, и попытаться зарегистрировать его.

UNIQUE-ограничение на уровне БД предотвращает появление дубликатов даже при конкурентном выполнении.

## 9. Что такое нормализация БД?

**Нормализация** — процесс организации данных в реляционной базе с целью уменьшения избыточности и предотвращения аномалий изменения данных.

Обычно нормализация предполагает разделение информации по связанным таблицам в соответствии с функциональными зависимостями.

### Зачем нужна нормализация?

- Сократить нежелательное дублирование.
- Упростить поддержание согласованности.
- Предотвратить аномалии вставки.
- Предотвратить аномалии обновления.
- Предотвратить аномалии удаления.

### Пример ненормализованной структуры

| order_id | user_name | user_email | product |
|---|---|---|---|
| 101 | Anna | anna@mail.com | Mouse |
| 102 | Anna | anna@mail.com | Keyboard |
| 103 | Bob | bob@mail.com | Monitor |

Имя и email Anna повторяются в каждой строке заказа.

При изменении email придётся обновлять несколько записей.

Если обновить только одну, данные станут противоречивыми.

### Нормализованная структура

**users**

| id | name | email |
|---|---|---|
| 1 | Anna | anna@mail.com |
| 2 | Bob | bob@mail.com |

**orders**

| id | user_id | product |
|---|---|---|
| 101 | 1 | Mouse |
| 102 | 1 | Keyboard |
| 103 | 2 | Monitor |

Теперь сведения о пользователе хранятся отдельно.

Заказы ссылаются на пользователя через внешний ключ.

При изменении email достаточно обновить одну запись.

---

## 10. Аномалии ненормализованных данных

### Update Anomaly — аномалия обновления

Одинаковые сведения хранятся в нескольких строках.

При изменении можно обновить только часть записей и получить противоречивые данные.

### Insert Anomaly — аномалия вставки

Структура таблицы мешает добавить информацию независимо от другой сущности.

Например, невозможно зарегистрировать пользователя без создания фиктивного заказа, если информация о пользователях хранится только в таблице заказов.

### Delete Anomaly — аномалия удаления

Удаление одной сущности случайно приводит к потере информации о другой.

Например, удаление единственного заказа пользователя одновременно уничтожает его контактные данные, если они хранятся только в строке заказа.

## 11. Нормальные формы

### Первая нормальная форма (1NF)

Таблица находится в 1NF, если значения атрибутов представлены в соответствии с атомарной структурой выбранной реляционной модели, а повторяющиеся группы не объединены в один атрибут.

Практический пример нарушения принципа:

| user_id | phones |
|---|---|
| 1 | 111, 222, 333 |

Если нужно полноценно работать с несколькими номерами, лучше вынести их в отдельную таблицу:

**user_phones**

| user_id | phone |
|---|---|
| 1 | 111 |
| 1 | 222 |
| 1 | 333 |

Стоит помнить, что понятие атомарности зависит от выбранного типа данных и модели. Например, JSON как значение колонки сам по себе не всегда означает нарушение 1NF.

### Вторая нормальная форма (2NF)

Таблица находится во 2NF, если:

1. Она находится в 1NF.
2. Каждый неключевой атрибут полностью функционально зависит от каждого кандидатного ключа, а не только от его части.

Пример:

| order_id | product_id | product_name | quantity |
|---|---|---|---|
| 101 | 1 | Mouse | 2 |
| 101 | 2 | Keyboard | 1 |

Предположим, ключ — `(order_id, product_id)`.

- `quantity` зависит от комбинации заказа и товара.
- `product_name` зависит только от `product_id`.

Получается частичная зависимость.

Решение — хранить информацию о товаре в отдельной таблице products, а в строках заказа оставлять product_id и quantity.

### Третья нормальная форма (3NF)

Третья нормальная форма устраняет определённые зависимости неключевых атрибутов от других неключевых атрибутов.

Упрощённо: неключевые атрибуты должны описывать сущность, определяемую ключом, а не другую независимую сущность.

Пример:

| employee_id | department_id | department_name |
|---|---|---|
| 1 | 10 | IT |
| 2 | 10 | IT |

Здесь:

- `employee_id` определяет `department_id`.
- `department_id` определяет `department_name`.

Получается транзитивная зависимость.

Лучше разделить:

**employees**

| employee_id | department_id |
|---|---|
| 1 | 10 |
| 2 | 10 |

**departments**

| department_id | department_name |
|---|---|
| 10 | IT |

### BCNF — Boyce–Codd Normal Form

Более строгая нормальная форма.

Для каждой нетривиальной функциональной зависимости `X → Y` детерминант X должен быть суперключом.

Для обычного QA-интервью обычно достаточно понимать 1NF, 2NF и 3NF.

BCNF полезно знать на уровне определения и общего назначения.

## 12. Денормализация

**Денормализация** — осознанное добавление избыточных данных или изменение структуры хранения, часто ради ускорения чтения или упрощения определённых запросов.

Пример:

Есть таблица orders и отдельная таблица order_items.

Сумму заказа можно каждый раз вычислять:

```sql
SELECT SUM(quantity * price)
FROM order_items
WHERE order_id = 101;
```

Но система может дополнительно хранить:

```text
orders.total_amount
```

Это позволяет быстрее получать сумму заказа, но появляется риск рассинхронизации.

### Преимущества

- Потенциально более быстрые запросы чтения.
- Меньше JOIN или агрегаций.
- Удобство для аналитических и отчётных систем.

### Недостатки

- Дублирование данных.
- Усложнение обновлений.
- Дополнительные требования к согласованности.
- Вероятность устаревших значений.

### Что важно тестировать QA?

Если сумма заказа хранится отдельно, нужно проверить, что она корректно изменяется при:

- Добавлении позиции.
- Удалении позиции.
- Изменении количества.
- Применении скидки.
- Частичном возврате.
- Параллельных изменениях.

## 13. OLTP vs OLAP

### OLTP — Online Transaction Processing

Системы, ориентированные на большое количество относительно небольших транзакционных операций.

Примеры:

- Банковские операции.
- Оформление заказов.
- Регистрация пользователей.
- Управление остатками товаров.

Характеристики:

- Частые INSERT, UPDATE, DELETE.
- Важность транзакционной целостности.
- Обычно короткие запросы.
- Высокая конкурентность.

Типичные СУБД: PostgreSQL, MySQL.

### OLAP — Online Analytical Processing

Системы, ориентированные на аналитические запросы по большим объёмам данных.

Примеры:

- Аналитика продаж.
- Статистика пользовательской активности.
- Финансовая отчётность.
- Построение дашбордов.

Характеристики:

- Сложные агрегирующие запросы.
- Обработка больших наборов данных.
- Часто колоночное хранение.
- Оптимизация под аналитическое чтение.

Пример аналитической СУБД: ClickHouse.

### Сравнение

| Характеристика | OLTP | OLAP |
|---|---|---|
| Основное назначение | Транзакционные операции | Аналитика |
| Типичные запросы | Короткие чтения и изменения | Агрегации больших наборов |
| Изменение данных | Частое | Зависит от архитектуры |
| Приоритет | Корректность и скорость транзакций | Скорость аналитических вычислений |
| Примеры | MySQL, PostgreSQL | ClickHouse |

**Для MarfaTech:** в вакансии присутствуют одновременно MySQL и ClickHouse. Полезно понимать, почему приложение может использовать разные БД для транзакционных операций и аналитики.

## 14. Репликация и шардирование

### Репликация (Replication)

Репликация — копирование изменений данных между экземплярами БД.

Пример архитектуры:

```text
          Primary
         /       \
     Replica 1  Replica 2
```

В одной из распространённых схем:

- Primary принимает операции записи.
- Реплики обслуживают часть запросов чтения.
- Изменения передаются на реплики.

### Зачем нужна репликация?

- Масштабирование чтений.
- Повышение доступности.
- Организация резервных узлов.
- Разгрузка основного сервера.

### Replication Lag

При асинхронной репликации изменения появляются на репликах с задержкой.

Пример:

1. Пользователь изменил профиль.
2. Primary зафиксировал изменения.
3. Следующий GET попал на реплику.
4. Реплика ещё не получила обновление.
5. Пользователь увидел старые данные.

Это называется задержкой репликации.

**Для QA:** важно понимать ожидаемую модель согласованности и проверять пользовательские сценарии после операций записи.

### Шардирование (Sharding)

Шардирование — горизонтальное распределение данных между несколькими независимыми хранилищами.

Например:

```text
Shard 1: users 1–1000000
Shard 2: users 1000001–2000000
Shard 3: users 2000001–3000000
```

Или по хешу идентификатора пользователя.

### Репликация vs шардирование

- Репликация создаёт копии данных.
- Шардирование распределяет данные между отдельными хранилищами.

Эти механизмы могут использоваться одновременно.

**Важно:** шардирование усложняет JOIN, транзакции между шардами, миграцию данных и балансировку нагрузки.

## 15. Партиционирование (Partitioning)

**Партиционирование** — разделение большой логической таблицы на физические части по определённому правилу.

В отличие от шардирования, партиции обычно остаются частью одной логической БД.

### Range Partitioning

Разделение по диапазонам.

Например, история бонусов по месяцам:

```text
bonus_history
├── bonus_history_2026_01
├── bonus_history_2026_02
├── bonus_history_2026_03
└── bonus_history_2026_04
```

### List Partitioning

Разделение по определённым значениям.

Например, по региону или типу события.

### Hash Partitioning

Распределение по результату хеш-функции.

### Зачем нужно партиционирование?

- Упрощение обслуживания больших таблиц.
- Быстрое удаление или архивирование целых диапазонов.
- Улучшение отдельных сценариев чтения.
- Управление объёмами данных.

### Partition Pruning

Оптимизатор может исключать ненужные партиции из плана выполнения.

Например, запрос:

```sql
SELECT *
FROM bonus_history
WHERE created_at >= '2026-05-01'
  AND created_at < '2026-06-01';
```

Если таблица правильно партиционирована по created_at, СУБД может ограничить чтение только подходящими партициями.

**Важно:** партиционирование не гарантирует ускорение любого запроса.

## 16. Что важно QA при тестировании структуры БД?

### Проверка ограничений

- Нельзя вставить дублирующий PRIMARY KEY.
- Нельзя нарушить UNIQUE.
- Нельзя записать NULL в NOT NULL.
- Нельзя нарушить CHECK.
- Нельзя создать некорректную ссылку по FOREIGN KEY.

### Проверка связей

- Правильно создаются связанные записи.
- Не появляются нежелательные дубликаты.
- Корректно работает каскадное удаление.
- Не возникают осиротевшие записи.
- Удаление родительской сущности соответствует бизнес-правилам.

### Проверка типов данных

- Граничные значения чисел.
- Переполнение диапазона.
- Длина строк.
- Точность десятичных значений.
- Работа с NULL.
- Корректность даты и времени.
- Часовые пояса.

### Проверка нормализованных и денормализованных данных

- Изменения отражаются во всех необходимых местах.
- Сохраняется согласованность связанных сущностей.
- Не возникают противоречивые копии данных.

### Проверка репликации

- Обновления доходят до реплик.
- Задержки соответствуют допустимым требованиям.
- Приложение корректно работает с временно устаревшими данными.
- Нет неожиданной потери подтверждённых операций при переключениях.

### Проверка партиционирования

- Строки попадают в нужные партиции.
- Корректно обрабатываются граничные даты.
- Данные не теряются при создании новых партиций.
- Запросы корректно работают через границы партиций.
- Архивирование и удаление старых партиций не затрагивают актуальные данные.

## 17. Типичные вопросы на собеседовании

### 1. Чем база данных отличается от СУБД?

База данных — организованная совокупность данных. СУБД — система управления ими.

### 2. Что такое реляционная БД?

База данных, организованная в соответствии с реляционной моделью, где информация представляется отношениями, обычно в виде таблиц.

### 3. Что такое Primary Key?

Ограничение, однозначно идентифицирующее строки таблицы и запрещающее NULL в ключевых колонках.

### 4. Что такое Foreign Key?

Ограничение, обеспечивающее ссылочную целостность между таблицами.

### 5. Чем Primary Key отличается от Unique?

Primary Key является основным идентификатором строки и не допускает NULL. UNIQUE обеспечивает уникальность определённых значений, причём поведение с NULL зависит от СУБД.

### 6. Какие бывают связи между таблицами?

One-to-One, One-to-Many и Many-to-Many.

### 7. Как реализовать Many-to-Many?

Через промежуточную таблицу, содержащую внешние ключи на обе сущности.

### 8. Что такое нормализация?

Процесс организации данных для уменьшения нежелательной избыточности и предотвращения аномалий обновления, вставки и удаления.

### 9. Какие нормальные формы ты знаешь?

1NF, 2NF, 3NF, BCNF и более высокие нормальные формы.

### 10. Чем 2NF отличается от 3NF?

2NF устраняет частичные зависимости неключевых атрибутов от кандидатных ключей. 3NF дополнительно ограничивает функциональные зависимости, способные создавать аномалии.

### 11. Что такое денормализация?

Осознанное добавление избыточности для оптимизации доступа к данным или упрощения отдельных сценариев.

### 12. Что такое ссылочная целостность?

Свойство данных, при котором ссылки между связанными записями удовлетворяют установленным ограничениям.

### 13. Что такое каскадное удаление?

Автоматическое удаление зависимых строк при удалении родительской записи в соответствии с ON DELETE CASCADE.

### 14. Чем OLTP отличается от OLAP?

OLTP ориентирован на транзакционные операции, OLAP — на аналитическую обработку больших наборов данных.

### 15. Чем репликация отличается от шардирования?

Репликация создаёт копии данных, а шардирование распределяет набор данных между отдельными хранилищами.

### 16. Что такое партиционирование?

Разделение большой логической таблицы на части по заданному правилу.

### 17. Что такое Partition Pruning?

Оптимизация, при которой СУБД исключает ненужные партиции из обработки запроса.

### 18. Как проверить целостность данных после удаления пользователя?

Проверить связанные записи, ограничения внешних ключей, предусмотренные каскадные действия и бизнес-правила хранения данных.

### 19. Почему нельзя всегда использовать FLOAT для денег?

Потому что двоичная арифметика с плавающей точкой может представлять десятичные значения приближённо, приводя к погрешностям.

### 20. Почему один пользователь может увидеть старые данные сразу после обновления?

Одна из возможных причин — чтение с асинхронной реплики, которая ещё не получила изменения. Также причиной может быть кэширование.

## 18. Типичные ошибки на собеседовании

**Ошибка:** «В каждой таблице обязательно должен быть Primary Key».

Правильно: технически таблица может существовать без него, но часто это нежелательно.

**Ошибка:** «Foreign Key автоматически создаёт индекс в любой СУБД».

Правильно: поведение отличается. Например, InnoDB требует подходящий индекс на стороне дочерней таблицы и может создать его автоматически, а PostgreSQL не создаёт индекс на ссылающейся колонке автоматически.

**Ошибка:** «Нормализация всегда ускоряет запросы».

Правильно: нормализация уменьшает избыточность и аномалии данных, но дополнительные JOIN могут увеличивать стоимость отдельных запросов.

**Ошибка:** «Денормализация — это неправильное проектирование».

Правильно: она может быть осознанным архитектурным решением.

**Ошибка:** «Репликация гарантирует мгновенную синхронизацию данных».

Правильно: асинхронные реплики могут отставать.

**Ошибка:** «Шардирование и партиционирование — одно и то же».

Правильно: партиционирование обычно разделяет таблицу внутри логической БД, а шардирование распределяет данные между самостоятельными хранилищами.

**Ошибка:** «UNIQUE всегда запрещает несколько NULL».

Правильно: поведение зависит от СУБД и определения ограничения.
