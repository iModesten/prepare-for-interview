## 1. VIEW простыми словами

**VIEW (представление)** — объект БД, который хранит **определение SQL-запроса** и позволяет обращаться к его результату как к таблице.

Представь: есть таблица со всеми бонусами, а приложению нужен список только активных. Можно повторять один и тот же `SELECT ... WHERE status = 'ACTIVE'` в десятках мест. А можно назвать этот запрос `active_bonuses` и обращаться к нему по имени.

**Важно:** обычный VIEW в PostgreSQL **не хранит отдельную копию строк**. При обращении к нему СУБД выполняет запрос с учётом актуальных данных базовых таблиц (и правил видимости текущей транзакции).

Схема:

```text
Таблица bonuses: все бонусы
       |
       | VIEW active_bonuses задаёт условие status = 'ACTIVE'
       v
SELECT * FROM active_bonuses
       |
       v
Результат: только активные бонусы
```

VIEW полезен, чтобы:
- не дублировать сложные JOIN и фильтры;
- дать приложению понятный стабильный интерфейс чтения;
- показывать только нужные столбцы и строки;
- централизовать логику отчётного запроса.

Но VIEW — **не автоматический кэш**, и сам по себе не ускоряет SQL.

## 2. Создаём обычное VIEW

Допустим, в PostgreSQL есть таблица:

```sql
CREATE TABLE bonuses (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    title TEXT NOT NULL,
    status TEXT NOT NULL,
    amount NUMERIC(12, 2) NOT NULL
);

INSERT INTO bonuses (id, user_id, title, status, amount) VALUES
    (101, 1, 'Кешбэк 5%', 'ACTIVE', 50.00),
    (102, 1, 'Бонус за покупку', 'USED', 100.00),
    (103, 2, 'Скидка', 'ACTIVE', 20.00);
```

Создадим VIEW:

```sql
CREATE VIEW active_bonuses AS
SELECT id, user_id, title, amount
FROM bonuses
WHERE status = 'ACTIVE';
```

Теперь его можно читать почти так же, как таблицу:

```sql
SELECT *
FROM active_bonuses
WHERE user_id = 1;
```

Результат:

| id | user_id | title | amount |
|---|---|---|---|
| 101 | 1 | Кешбэк 5% | 50.00 |

Что важно понять: VIEW не содержит физически сохранённую строку `101`. В нём хранится **определение выборки**, а PostgreSQL получает подходящие строки из `bonuses`.

Если нужны данные из нескольких таблиц, в определении VIEW можно использовать `JOIN`, агрегаты `GROUP BY`, вычисляемые поля и другие конструкции SQL.

## 3. Что произойдёт при изменении таблицы

Представим, что бонус `101` использован:

```sql
UPDATE bonuses
SET status = 'USED'
WHERE id = 101;
```

Снова выполняем:

```sql
SELECT * FROM active_bonuses;
```

Теперь результат содержит только бонус `103`. Бонус `101` перестал соответствовать условию `status = 'ACTIVE'`.

**Почему не понадобилось обновлять VIEW?** Потому что обычное представление читает актуальные данные базовой таблицы при выполнении запроса. При этом в конкурентных транзакциях результат зависит от уровня изоляции и доступного снимка данных (**MVCC**).

## 4. VIEW, таблица, CTE и подзапрос

| Механизм | Что собой представляет | Хранит собственные строки? | Область применения |
|---|---|---|---|
| Таблица (`TABLE`) | Объект с данными | Да | Хранение записей |
| Обычное VIEW | Сохранённое определение SELECT | Нет, отдельной копии результатов нет | Повторное использование именованной выборки |
| MATERIALIZED VIEW | Сохранённый результат SELECT | Да | Отчёты, дорогие агрегаты, допускающие устаревание |
| CTE (`WITH`) | Именованное выражение в запросе | Не постоянно; план может материализовать промежуточный результат | Структурирование одного SQL-оператора |
| Подзапрос | SQL-запрос внутри другого запроса | Не как самостоятельный постоянный объект | Разовая логика внутри SQL |

Например, CTE:

```sql
WITH active_bonuses AS (
    SELECT * FROM bonuses WHERE status = 'ACTIVE'
)
SELECT * FROM active_bonuses WHERE user_id = 1;
```

**Разница:** CTE существует только в пределах данного SQL-оператора, а VIEW создаётся один раз как объект схемы БД и может использоваться в следующих запросах.

Подробно о CTE — в [разделе SQL](02-sql.md).

## 5. Можно ли менять данные через VIEW

**Иногда да.** В PostgreSQL простое представление на основе одной таблицы может быть **автоматически обновляемым (updatable view)**.

Например, для `active_bonuses`:

```sql
UPDATE active_bonuses
SET amount = 75.00
WHERE id = 103;
```

Такой `UPDATE` может изменить строку **в базовой таблице `bonuses`**, а не в отдельном хранилище VIEW.

Но не каждое VIEW обновляемое: конструкции вроде `GROUP BY`, `DISTINCT`, агрегатов и некоторых JOIN могут мешать автоматическим `INSERT`, `UPDATE` и `DELETE`. Для сложных случаев возможны специальные механизмы, например `INSTEAD OF`-триггеры.

**Ловушка — `WITH CHECK OPTION`.** Если простой VIEW фильтрует строки, обновление через него без дополнительного ограничения может привести к тому, что изменённая строка больше не видна в этом VIEW. `WITH CHECK OPTION` помогает запретить записи, нарушающие условие выборки:

```sql
CREATE VIEW checked_active_bonuses AS
SELECT id, user_id, title, status, amount
FROM bonuses
WHERE status = 'ACTIVE'
WITH LOCAL CHECK OPTION;
```

Тогда попытка через это VIEW изменить `status` на `USED` будет отклонена. Это правило относится к операциям через представление, а не к произвольному обновлению исходной таблицы.

## 6. MATERIALIZED VIEW

**MATERIALIZED VIEW (материализованное представление)** похоже на обычное VIEW, но **хранит результат запроса физически**.

Например, хотим показать количество активных бонусов у каждого пользователя:

```sql
CREATE MATERIALIZED VIEW active_bonus_counts AS
SELECT user_id, COUNT(*) AS active_count
FROM bonuses
WHERE status = 'ACTIVE'
GROUP BY user_id;
```

Читаем:

```sql
SELECT * FROM active_bonus_counts;
```

Теперь в базовую таблицу добавили бонус:

```sql
INSERT INTO bonuses (id, user_id, title, status, amount)
VALUES (104, 2, 'Новый бонус', 'ACTIVE', 30.00);
```

**Материализованное представление само не обновится.** Оно по-прежнему показывает данные на момент последнего заполнения.

Обновим его явно:

```sql
REFRESH MATERIALIZED VIEW active_bonus_counts;
```

После завершения обновления запрос к нему увидит новые значения.

**В чём выгода?** Вместо повторного пересчёта тяжёлого `GROUP BY` при каждом обращении можно читать сохранённый результат.

**В чём цена?** Данные могут устаревать между обновлениями, требуется место на диске, а сам `REFRESH` создаёт дополнительную нагрузку.

### CONCURRENTLY в PostgreSQL

Обычный `REFRESH MATERIALIZED VIEW` может блокировать чтение материализованного представления на время обновления.

PostgreSQL предоставляет:

```sql
CREATE UNIQUE INDEX ux_active_bonus_counts_user_id
ON active_bonus_counts (user_id);

REFRESH MATERIALIZED VIEW CONCURRENTLY active_bonus_counts;
```

`CONCURRENTLY` позволяет продолжать чтение во время обновления, но имеет условия: материализованное представление уже должно быть заполнено, нужен подходящий `UNIQUE`-индекс на обычных столбцах, охватывающий все строки. Одновременно выполнять несколько обновлений одного materialized view нельзя.

**Важный нюанс:** `REFRESH MATERIALIZED VIEW` **не выполняется автоматически по расписанию**. Если нужно обновлять отчёт каждые 5 минут, расписание или механизм запуска настраивается отдельно.

## 7. Производительность: что ускоряется, а что нет

**Обычное VIEW** не делает медленный запрос быстрым только потому, что ты дал ему имя.

Представление:

```sql
CREATE VIEW user_bonus_history AS
SELECT user_id, id, title, status
FROM bonuses;
```

При запросе `SELECT * FROM user_bonus_history WHERE user_id = 1` PostgreSQL может оптимизировать выражение и использовать индекс базовой таблицы. Отдельный индекс на обычный VIEW создать нельзя — индексируют базовые таблицы.

**Материализованное VIEW** хранит строки отдельно; для него можно создавать собственные индексы:

```sql
CREATE INDEX idx_active_bonus_counts_count
ON active_bonus_counts (active_count);
```

Но материализация — компромисс: чтение иногда быстрее, а актуальность хуже, и обновление требует ресурсов.

Для оценки SQL полезно использовать `EXPLAIN` и, на безопасном стенде, `EXPLAIN (ANALYZE, BUFFERS)`. Не делай вывод, что VIEW быстрее таблицы, без измерений на сопоставимых условиях.

## 8. Права доступа и безопасность

VIEW можно использовать, чтобы дать роли доступ только к определённым колонкам или строкам:

```sql
CREATE VIEW public_bonus_info AS
SELECT id, title, status
FROM bonuses;

GRANT SELECT ON public_bonus_info TO reporting_role;
```

В этом примере роль `reporting_role` — заранее созданная роль БД.

Но **VIEW само по себе не гарантирует безопасную изоляцию данных**. Результат зависит от прав владельца, настроек безопасности представления, Row Level Security (**RLS — безопасность на уровне строк**) и других правил PostgreSQL.

При необходимости в PostgreSQL доступны `security_invoker` (проверка прав вызывающего пользователя) и `security_barrier` для отдельных сценариев безопасной фильтрации. Для защиты данных проверяют реальные права, а не только текст `WHERE` внутри представления.

## 9. Что тестировать QA

Представим, что API списка бонусов начинает читать данные из VIEW вместо базовой таблицы.

| Проверка | Что проверяем |
|---|---|
| Корректность фильтрации | Не попадают `USED` и другие неактивные бонусы |
| Актуальность | Изменения в базовой таблице отражаются в обычном VIEW с учётом транзакций |
| JOIN и агрегаты | Нет потери или дублирования строк, верно рассчитаны количества |
| Права | Пользователь/роль не видит запрещённые данные |
| Изменения схемы | Миграция базовой таблицы не ломает VIEW и API |
| Быстродействие | План запроса и время ответа не ухудшились |
| Materialized view | До `REFRESH` данные могут быть старыми, после — соответствуют исходным таблицам |
| Конкурентное обновление | `REFRESH` не создаёт недопустимые задержки или ошибки чтения |

### Практический сценарий

У пользователя два активных бонуса. API читает `active_bonus_counts`, который обновляется раз в 5 минут.

1. Проверить, что после очередного `REFRESH` счётчик равен 2.
2. Выдать новый бонус: в `bonuses` теперь три активных.
3. До следующего `REFRESH` агрегат может оставаться равным 2 — это допустимо **только если требования разрешают задержку**.
4. После обновления агрегат должен стать равным 3.
5. Проверить поведение при ошибке обновления: не должен появиться частично пересчитанный результат.

**Связь с API:** ответ `200 OK` не гарантирует актуальность данных, если приложение берёт их из материализованного представления.

## 10. Ответ на собеседовании

> VIEW — это представление, то есть сохранённый SQL-запрос, к которому можно обращаться как к таблице. Обычное VIEW в PostgreSQL не хранит собственную копию строк: при SELECT оно читает данные базовых таблиц. Его используют для повторного применения сложных выборок, упрощения запросов и управления доступом.
>
> MATERIALIZED VIEW хранит результаты запроса физически, поэтому может ускорять чтение тяжёлых агрегатов. Но после изменения исходных таблиц его данные не обновляются автоматически — нужен REFRESH.
>
> Простые VIEW иногда позволяют INSERT, UPDATE и DELETE через представление, но это зависит от его определения. Для QA важно проверить корректность выборки, актуальность, права доступа и влияние на производительность.

## 11. Вопросы для самопроверки

### 1. Обычное VIEW хранит данные отдельно от таблицы?
<details><summary>Показать ответ</summary>

Нет. Оно хранит определение запроса. При чтении результат строится из базовых таблиц в соответствии с видимостью данных в транзакции.

</details>

### 2. Если изменить базовую таблицу, что будет с VIEW и MATERIALIZED VIEW?
<details><summary>Показать ответ</summary>

Обычное VIEW при следующем запросе может увидеть изменения, если они видны текущей транзакции. MATERIALIZED VIEW останется на ранее сохранённых данных до REFRESH.

</details>

### 3. Можно ли сделать UPDATE через VIEW?
<details><summary>Показать ответ</summary>

Да, если это автоматически обновляемое VIEW либо настроен специальный механизм обновления. В PostgreSQL простые представления одной таблицы часто обновляемые, но агрегаты, DISTINCT и другие операции могут исключать такую возможность.

</details>

### 4. Чем VIEW отличается от CTE?
<details><summary>Показать ответ</summary>

VIEW — постоянный объект схемы БД с именованным SQL-запросом. CTE (`WITH`) — именованное выражение внутри одного SQL-оператора.

</details>

### 5. Может ли обычное VIEW ускорить запрос?
<details><summary>Показать ответ</summary>

Само по себе — нет. Оно не хранит готовые результаты. Скорость определяется итоговым планом выполнения, индексами и объёмом данных.

</details>

### 6. Что требуется для REFRESH MATERIALIZED VIEW CONCURRENTLY?
<details><summary>Показать ответ</summary>

Уже заполненное материализованное представление и подходящий уникальный индекс, использующий только имена столбцов и охватывающий все строки. CONCURRENTLY уменьшает блокировку чтения при обновлении.

</details>

### 7. Почему API может возвращать устаревшие данные, хотя в таблице всё обновлено?
<details><summary>Показать ответ</summary>

Например, API читает MATERIALIZED VIEW, который ещё не обновлялся. Также возможны кэширование приложения и особенности чтения в транзакции — нужно проверить фактический источник данных.

</details>
