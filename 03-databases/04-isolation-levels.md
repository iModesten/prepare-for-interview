# Уровни изоляции транзакций (Transaction Isolation Levels)

## 1. Что такое изоляция транзакций?

**Изоляция (Isolation)** — одно из свойств ACID, которое определяет, как параллельно выполняющиеся транзакции влияют друг на друга и какие изменения данных они могут наблюдать.

Представим, что одновременно происходят две операции:

- Транзакция A читает баланс пользователя.
- Транзакция B изменяет баланс этого же пользователя.

Возникают вопросы:

- Увидит ли транзакция A незавершённые изменения B?
- Что произойдёт, если A прочитает баланс повторно?
- Может ли A работать с устаревшими данными?
- Что произойдёт, если обе транзакции одновременно изменят баланс?

Ответы зависят от уровня изоляции, реализации СУБД и характера SQL-операций.

### Краткий ответ для собеседования

> Уровень изоляции транзакций определяет, какие аномалии могут возникать при параллельной работе с данными. Существуют четыре стандартных уровня: Read Uncommitted, Read Committed, Repeatable Read и Serializable. Чем сильнее гарантии изоляции, тем больше ограничений накладывается на допустимое взаимодействие транзакций. Это может увеличивать накладные расходы, вероятность ожиданий, конфликтов и повторных попыток.

## 2. Какие проблемы возникают при параллельных транзакциях?

Для понимания уровней изоляции сначала нужно разобрать аномалии конкурентного доступа.

### 2.1. Dirty Read — грязное чтение

**Dirty Read** — ситуация, когда одна транзакция читает изменения другой транзакции, которые ещё не были зафиксированы через COMMIT.

Пример:

Изначальный баланс пользователя — 1000.

| Шаг | Транзакция A | Транзакция B |
|---|---|---|
| 1 | BEGIN | |
| 2 | UPDATE balance = 500 | |
| 3 | | BEGIN |
| 4 | | SELECT balance → 500 |
| 5 | ROLLBACK | |
| 6 | | COMMIT |

Транзакция B прочитала значение 500, хотя транзакция A впоследствии отменила изменение.

Фактически B прочитала данные, которые никогда не были зафиксированы.

**Чем опасно:** приложение может принимать решения на основании изменений, которые впоследствии исчезнут.

**Как предотвращается:** уровень Read Committed и выше исключает Dirty Read.

Важно: показанный сценарий не воспроизводится в PostgreSQL даже на Read Uncommitted, поскольку PostgreSQL не допускает грязного чтения.

### 2.2. Non-repeatable Read — неповторяемое чтение

**Non-repeatable Read** — ситуация, когда внутри одной транзакции повторное чтение одной и той же строки возвращает другое значение, поскольку другая транзакция изменила данные и зафиксировала изменения.

Изначальный баланс — 1000.

| Шаг | Транзакция A | Транзакция B |
|---|---|---|
| 1 | BEGIN | |
| 2 | SELECT balance → 1000 | |
| 3 | | BEGIN |
| 4 | | UPDATE balance = 500 |
| 5 | | COMMIT |
| 6 | SELECT balance → 500 | |
| 7 | COMMIT | |

Два одинаковых SELECT внутри одной транзакции вернули разные результаты.

**Чем опасно:** логика приложения может рассчитывать на неизменность прочитанных данных, хотя они изменились.

**Как предотвращается:** Repeatable Read и Serializable.

### 2.3. Phantom Read — фантомное чтение

**Phantom Read** — ситуация, когда повторное выполнение запроса с одинаковым условием возвращает изменившийся набор строк из-за изменений, зафиксированных другой транзакцией.

Например, есть таблица заказов:

| id | status |
|---|---|
| 1 | NEW |
| 2 | NEW |
| 3 | COMPLETED |

Транзакция A выполняет:

```sql
SELECT COUNT(*)
FROM orders
WHERE status = 'NEW';
```

Результат — 2.

После этого транзакция B добавляет новый заказ:

```sql
INSERT INTO orders (id, status)
VALUES (4, 'NEW');

COMMIT;
```

Транзакция A повторяет запрос и получает 3.

Это и есть фантомное чтение: набор строк, удовлетворяющих условию, изменился.

**Отличие от Non-repeatable Read:**

- Non-repeatable Read — изменилось значение уже прочитанной строки.
- Phantom Read — изменился набор строк, соответствующих условию запроса.

В PostgreSQL Repeatable Read предотвращает фантомные чтения, хотя минимальные требования стандарта SQL допускают их на данном уровне.

### 2.4. Lost Update — потерянное обновление

**Lost Update** — ситуация, когда одно обновление теряется в результате конкурентных действий нескольких транзакций.

Представим, что в БД находится:

```text
balance = 1000
```

Два запроса одновременно пытаются увеличить баланс:

- Транзакция A — на 100.
- Транзакция B — на 200.

Возможное развитие событий:

| Шаг | Транзакция A | Транзакция B |
|---|---|---|
| 1 | SELECT → 1000 | |
| 2 | | SELECT → 1000 |
| 3 | Рассчитывает 1100 | |
| 4 | | Рассчитывает 1200 |
| 5 | UPDATE balance = 1100 | |
| 6 | COMMIT | |
| 7 | | UPDATE balance = 1200 |
| 8 | | COMMIT |

Итоговый баланс — 1200 вместо ожидаемых 1300.

Изменение транзакции A оказалось потеряно.

Такой сценарий возможен, например, когда приложение сначала читает значение, рассчитывает результат у себя и затем записывает его обратно, не проверяя конкурентные изменения.

**Способы предотвращения:**

- Атомарные операции `UPDATE balance = balance + 100`.
- Пессимистические блокировки (`SELECT ... FOR UPDATE`).
- Оптимистическая блокировка через версию записи.
- Подходящий уровень изоляции и обработка конфликтов.

**Важно:** Lost Update не следует автоматически считать допустимым или невозможным на каком-либо уровне без учёта конкретной СУБД и используемого способа обновления.

### 2.5. Write Skew — аномалия конкурентной записи

Это более сложная аномалия, которую могут спросить на Senior-собеседовании.

Представим систему дежурств.

Есть два сотрудника:

| employee | on_duty |
|---|---|
| Alice | true |
| Bob | true |

Бизнес-правило: хотя бы один сотрудник должен оставаться на дежурстве.

Две транзакции одновременно проверяют, что на дежурстве находятся два человека.

- Транзакция A снимает с дежурства Alice.
- Транзакция B снимает с дежурства Bob.

Каждая транзакция изменяет свою строку.

В результате обе могут успешно завершиться, и дежурных не останется.

Причина: каждая транзакция принимала решение на основании состояния данных, которое уже не отражает результат конкурентной операции.

Это пример Write Skew.

**Важный нюанс:** такая аномалия возможна при Snapshot Isolation, например на уровне Repeatable Read в PostgreSQL.

Serializable предотвращает успешное завершение обеих транзакций с таким несериализуемым результатом.

## 3. Четыре уровня изоляции

### 3.1. Read Uncommitted

Самый слабый из четырёх стандартных уровней изоляции.

В системах, поддерживающих его обычную семантику, транзакция может видеть изменения других транзакций до их фиксации.

Может допускать:

- Dirty Read.
- Non-repeatable Read.
- Phantom Read.
- Другие аномалии конкурентного выполнения.

**Преимущество:** потенциально меньше ограничений на чтение.

**Недостаток:** высокая вероятность работы с несогласованными или незавершёнными данными.

**PostgreSQL:** фактически использует поведение Read Committed.

**MySQL InnoDB:** поддерживает Read Uncommitted и допускает грязные чтения.

### 3.2. Read Committed

Транзакция не должна видеть незафиксированные изменения других транзакций.

При этом повторный запрос внутри той же транзакции может вернуть другое значение, если конкурентная транзакция успела зафиксировать изменения.

В PostgreSQL каждый оператор получает новый снимок зафиксированных данных на начало своего выполнения (с учётом собственных изменений транзакции).

**Предотвращает:**

- Dirty Read.

**Может допускать:**

- Non-repeatable Read.
- Phantom Read.
- Аномалии при конкурентном изменении данных.

**Используется по умолчанию в PostgreSQL.**

Пример:

```sql
BEGIN;

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SELECT balance
FROM accounts
WHERE id = 1;

-- Другая транзакция меняет balance и выполняет COMMIT.

SELECT balance
FROM accounts
WHERE id = 1;

COMMIT;
```

Два SELECT могут вернуть разные значения.

### 3.3. Repeatable Read

Обеспечивает более стабильное чтение данных внутри транзакции.

В PostgreSQL запросы внутри такой транзакции работают с одним снимком данных, сформированным на момент начала первого оператора, требующего снимка.

Изменения, зафиксированные другими транзакциями после создания снимка, не становятся видимыми обычным последующим SELECT этой транзакции.

**Предотвращает:**

- Dirty Read.
- Non-repeatable Read.

**В PostgreSQL дополнительно предотвращает Phantom Read.**

При этом остаются возможными некоторые аномалии сериализации, например Write Skew.

Пример для PostgreSQL:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance
FROM accounts
WHERE id = 1;

-- Другая транзакция обновляет balance и делает COMMIT.

SELECT balance
FROM accounts
WHERE id = 1;

COMMIT;
```

Повторный SELECT вернёт то же значение, если сама транзакция его не меняла.

**В MySQL InnoDB Repeatable Read — уровень по умолчанию.**

Обычные неблокирующие SELECT используют согласованный снимок данных, тогда как блокирующие чтения и DML-операции имеют другую семантику.

Поэтому нельзя считать, что все виды чтений в MySQL Repeatable Read обязательно работают с одним и тем же состоянием данных.

### 3.4. Serializable

Самый строгий стандартный уровень изоляции.

**Serializable** гарантирует, что результат успешно завершённых конкурентных транзакций эквивалентен некоторому последовательному порядку их выполнения.

Это не значит, что СУБД физически выполняет все транзакции по одной.

Она может использовать блокировки, отслеживать зависимости между транзакциями и отклонять операции, которые привели бы к недопустимому результату.

В PostgreSQL используется механизм Serializable Snapshot Isolation (SSI).

При обнаружении опасной ситуации одна из транзакций может завершиться ошибкой сериализации.

Приложение должно быть готово повторить транзакцию целиком.

**Преимущества:**

- Наиболее сильные гарантии корректности конкурентного выполнения.
- Предотвращение аномалий сериализации.

**Недостатки:**

- Дополнительные накладные расходы.
- Возможные ожидания блокировок.
- Ошибки сериализации или конкуренции, требующие обработки и повторных попыток.

## 4. Сравнение уровней изоляции

Таблица ниже отражает минимальные гарантии уровней согласно стандартной модели SQL, а не все особенности конкретных СУБД.

| Уровень | Dirty Read | Non-repeatable Read | Phantom Read |
|---|---|---|---|
| Read Uncommitted | Возможен | Возможен | Возможен |
| Read Committed | Нет | Возможен | Возможен |
| Repeatable Read | Нет | Нет | Допускается стандартом |
| Serializable | Нет | Нет | Нет |

**Важно:** отсутствие перечисленных аномалий ещё не означает полную сериализуемость. Например, Write Skew — отдельная возможная проблема.

## 5. PostgreSQL vs MySQL: основные отличия

| Характеристика | PostgreSQL | MySQL InnoDB |
|---|---|---|
| Уровень по умолчанию | Read Committed | Repeatable Read |
| Read Uncommitted | Работает как Read Committed | Поддерживается |
| Repeatable Read | Snapshot Isolation | Consistent reads + locking |
| Phantom Read на Repeatable Read | Не возникает | Обычные consistent reads защищены снимком; для блокирующих чтений используются другие механизмы |
| Serializable | SSI | Преимущественно усиленная блокировочная изоляция |

### Почему это важно?

Одинаковое название уровня изоляции не всегда означает полностью одинаковое поведение между СУБД.

Например, при переходе с PostgreSQL на MySQL могут измениться:

- Поведение повторных чтений.
- Механизмы блокировки диапазонов.
- Реакция на конкурентные UPDATE.
- Вероятность конфликтов и deadlock.
- Способы обработки ошибок конкурентного выполнения.

В MySQL InnoDB для диапазонных блокировок могут использоваться gap locks и next-key locks.

Эти механизмы рассмотрим отдельно в `05-locks-and-mvcc.md`.

## 6. Как установить и проверить уровень изоляции

### PostgreSQL

Проверить текущий уровень:

```sql
SHOW transaction_isolation;
```

Начать транзакцию с нужным уровнем:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT *
FROM users;

COMMIT;
```

Либо:

```sql
BEGIN;

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT *
FROM users;

COMMIT;
```

Уровень изоляции необходимо устанавливать до выполнения запросов, для которых он должен применяться.

### MySQL

Проверить уровень изоляции текущей сессии:

```sql
SELECT @@transaction_isolation;
```

Установить уровень для следующей транзакции:

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

START TRANSACTION;

SELECT *
FROM users;

COMMIT;
```

Установить уровень для всей текущей сессии:

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

## 7. Практическое тестирование уровней изоляции

Для проверки конкурентного поведения удобно открыть два независимых соединения с базой данных.

Например, два SQL-окна в DBeaver, каждое с отдельным подключением.

### Сценарий: Non-repeatable Read

СУБД: PostgreSQL.

Исходные данные:

```sql
CREATE TABLE accounts (
    id INT PRIMARY KEY,
    balance INT NOT NULL
);

INSERT INTO accounts (id, balance)
VALUES (1, 1000);
```

**Соединение A**

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;

SELECT balance
FROM accounts
WHERE id = 1;
-- 1000
```

Оставляем транзакцию открытой.

**Соединение B**

```sql
BEGIN;

UPDATE accounts
SET balance = 500
WHERE id = 1;

COMMIT;
```

**Возвращаемся в соединение A**

```sql
SELECT balance
FROM accounts
WHERE id = 1;
-- 500

COMMIT;
```

**Результат:** значение изменилось внутри транзакции A.

Повторяем эксперимент, предварительно восстановив исходный баланс и заменив `READ COMMITTED` на `REPEATABLE READ`.

Теперь обычный повторный SELECT в A продолжит возвращать старое значение.

### Что проверять QA?

1. Какие результаты возвращаются при разных уровнях изоляции.
2. Не нарушаются ли бизнес-правила.
3. Как система обрабатывает конкурентные обновления.
4. Возникают ли блокировки или ошибки сериализации.
5. Корректно ли приложение повторяет транзакции после допустимых к повтору ошибок.

## 8. Вопросы для собеседования

### 1. Что такое уровень изоляции транзакции?

Уровень изоляции определяет гарантии при одновременной работе нескольких транзакций и допустимые аномалии конкурентного выполнения.

### 2. Какие существуют уровни изоляции?

Read Uncommitted, Read Committed, Repeatable Read, Serializable.

### 3. Что такое Dirty Read?

Чтение изменений другой транзакции до их фиксации.

### 4. Чем Non-repeatable Read отличается от Phantom Read?

При Non-repeatable Read меняется результат повторного чтения ранее прочитанной строки.

При Phantom Read меняется набор строк, удовлетворяющих одному условию.

### 5. Какой уровень изоляции по умолчанию в PostgreSQL?

Read Committed.

### 6. Какой уровень изоляции по умолчанию в MySQL InnoDB?

Repeatable Read.

### 7. Почему Repeatable Read не всегда гарантирует полную согласованность бизнес-операций?

Потому что он может допускать аномалии сериализации, например Write Skew. Кроме того, бизнес-инварианты требуют корректной реализации самой операции.

### 8. Что такое Serializable?

Уровень изоляции, при котором результат конкурентного выполнения эквивалентен некоторому последовательному порядку выполнения транзакций.

### 9. Всегда ли Serializable означает выполнение транзакций по очереди?

Нет. Транзакции могут выполняться параллельно, если СУБД обеспечивает сериализуемый результат.

### 10. Что произойдёт при конфликте сериализации?

В некоторых СУБД одна из транзакций может завершиться ошибкой. Приложение должно корректно обработать её и при необходимости повторить всю транзакцию.

### 11. Какой уровень изоляции лучше использовать?

Универсального ответа нет. Выбор зависит от требований к целостности данных, характера конкурентной нагрузки и реализации СУБД.

### 12. Поможет ли Serializable избежать повторного списания при двух одинаковых API-запросах?

Не обязательно. Serializable обеспечивает сериализуемость транзакций, но не распознаёт автоматически два запроса как одну бизнес-операцию. Для этого нужны дополнительные механизмы, например идемпотентность и уникальные ограничения.

## 9. Типичные ошибки

**Ошибка:** «Read Committed означает, что внутри транзакции данные не меняются».

Правильно: этот уровень запрещает грязное чтение, но допускает неповторяемые чтения.

**Ошибка:** «Repeatable Read и Serializable — одно и то же».

Правильно: Repeatable Read в ряде СУБД может допускать аномалии сериализации.

**Ошибка:** «Serializable полностью исключает любые ошибки конкурентной работы».

Правильно: при таком уровне могут возникать ошибки сериализации, deadlock или необходимость повторного выполнения транзакции.

**Ошибка:** «PostgreSQL и MySQL реализуют все уровни изоляции одинаково».

Правильно: у них есть различия в реализации снимков данных, блокировок и поведении конкурентных операций.

**Ошибка:** «Более высокий уровень изоляции всегда лучше».

Правильно: он предоставляет более строгие гарантии, но может увеличивать затраты ресурсов и количество конфликтов. Уровень выбирают исходя из требований системы.
