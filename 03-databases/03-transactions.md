# Транзакции в базах данных (Transactions)

## 1. Что такое транзакция?

**Транзакция** — это логическая единица работы с базой данных, объединяющая одну или несколько операций, которые должны выполняться как единое целое.

Транзакция гарантирует, что либо все изменения будут успешно зафиксированы, либо ни одно из них не будет применено окончательно.

Например, при переводе денег между банковскими счетами нужно:

1. Списать деньги со счёта отправителя.
2. Зачислить деньги на счёт получателя.

Если первая операция выполнится, а вторая завершится ошибкой, данные окажутся в некорректном состоянии. Использование транзакции позволяет избежать частичного выполнения операции.

### Краткий ответ для собеседования

> Транзакция — это набор операций с базой данных, который выполняется как единое целое. Она необходима для обеспечения атомарности, согласованности, изоляции и долговечности изменений — свойств ACID. Если транзакция успешно завершается, изменения фиксируются через COMMIT, а при необходимости отмены используется ROLLBACK.

## 2. Основные команды управления транзакциями

| Команда | Назначение |
|---|---|
| `BEGIN` | Начинает транзакцию |
| `START TRANSACTION` | Альтернативный способ начать транзакцию |
| `COMMIT` | Фиксирует изменения |
| `ROLLBACK` | Отменяет незафиксированные изменения |
| `SAVEPOINT` | Создаёт точку сохранения |
| `ROLLBACK TO SAVEPOINT` | Откатывает изменения до точки сохранения |
| `RELEASE SAVEPOINT` | Удаляет точку сохранения |

### Пример транзакции

Допустим, существует таблица `accounts`:

| id | balance |
|---|---|
| 1 | 1000 |
| 2 | 500 |

Необходимо перевести 100 единиц со счёта 1 на счёт 2.

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

После успешного выполнения:

| id | balance |
|---|---|
| 1 | 900 |
| 2 | 600 |

Если вместо `COMMIT` выполнить `ROLLBACK`, изменения будут отменены, и балансы вернутся к исходным значениям.

**Важно:** это упрощённый пример. В реальной системе нужно дополнительно проверять существование обоих счетов, достаточность средств и результаты `UPDATE`. Транзакция сама по себе не проверяет бизнес-правила.

## 3. Свойства ACID

ACID — четыре свойства, определяющие надёжность транзакционной обработки данных.

### A — Atomicity (Атомарность)

Транзакция выполняется по принципу «всё или ничего».

Если одна из обязательных операций не может быть выполнена, изменения всей транзакции должны быть отменены.

**Пример:** при переводе денег успешно произошло списание, но зачисление не выполнилось. При откате транзакции списание отменяется.

**Важный нюанс:** не каждая SQL-ошибка автоматически вызывает откат всей транзакции во всех СУБД. Например, поведение PostgreSQL и MySQL при ошибках внутри транзакций различается. Приложение должно корректно обрабатывать ошибки и управлять завершением транзакции.

### C — Consistency (Согласованность)

Транзакция должна переводить базу данных из одного корректного состояния в другое, сохраняя определённые правила и ограничения целостности.

Примеры ограничений:

- `PRIMARY KEY` — уникальность первичного ключа.
- `FOREIGN KEY` — ссылочная целостность.
- `UNIQUE` — уникальность значений.
- `CHECK` — проверка заданного условия.
- `NOT NULL` — запрет отсутствующего значения.

**Пример:** если в БД установлено ограничение `CHECK (balance >= 0)`, транзакция не сможет успешно зафиксировать изменение, нарушающее его.

При этом бизнес-правила, не закреплённые ограничениями или корректной логикой приложения, база данных не обеспечит автоматически.

### I — Isolation (Изолированность)

Параллельно выполняющиеся транзакции должны взаимодействовать в соответствии с выбранным уровнем изоляции.

Например, два пользователя одновременно пытаются изменить остаток одного товара.

Без корректной обработки конкурентного доступа возможны потерянные обновления, некорректные проверки доступности и другие аномалии.

Степень защиты зависит от уровня изоляции:

- Read Uncommitted
- Read Committed
- Repeatable Read
- Serializable

**Важно:** Isolation не означает, что параллельные транзакции вообще не влияют друг на друга или всегда выполняются строго последовательно.

### D — Durability (Долговечность)

После успешной фиксации транзакции её изменения должны сохраняться даже при сбоях системы в пределах гарантий используемой СУБД и её конфигурации.

Для этого применяются механизмы журналирования и восстановления.

Например:

- PostgreSQL использует WAL (Write-Ahead Logging).
- MySQL InnoDB использует redo log.

После подтверждённого `COMMIT` изменения должны переживать предусмотренные моделью долговечности сбои, например перезапуск сервера БД.

## 4. COMMIT и ROLLBACK

### COMMIT

`COMMIT` завершает транзакцию и фиксирует внесённые изменения.

```sql
BEGIN;

UPDATE users
SET status = 'ACTIVE'
WHERE id = 10;

COMMIT;
```

После успешного коммита изменения становятся зафиксированными.

Видимость этих изменений для других транзакций зависит от их уровней изоляции и используемых снимков данных.

### ROLLBACK

`ROLLBACK` отменяет изменения, выполненные внутри текущей транзакции с момента её начала, если они ещё не зафиксированы.

```sql
BEGIN;

DELETE FROM users
WHERE id = 10;

ROLLBACK;
```

После отката удалённая запись останется в таблице.

**Важный момент:** обычный `ROLLBACK` не отменяет транзакцию, для которой уже успешно выполнен `COMMIT`.

Также следует помнить, что откат изменений в БД не обязательно отменяет внешние действия — например, отправленное электронное письмо или HTTP-запрос в другой сервис.

## 5. SAVEPOINT — точки сохранения

`SAVEPOINT` позволяет создать промежуточную точку внутри транзакции.

Это полезно, если нужно отменить только часть операций.

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

SAVEPOINT before_credit;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

ROLLBACK TO SAVEPOINT before_credit;

UPDATE accounts
SET balance = balance + 100
WHERE id = 3;

COMMIT;
```

Что произошло:

1. Со счёта 1 списали 100.
2. Создали точку сохранения.
3. Зачислили 100 на счёт 2.
4. Отменили зачисление на счёт 2.
5. Зачислили 100 на счёт 3.
6. Зафиксировали итоговые изменения.

**Отличие от обычного ROLLBACK:** откат до SAVEPOINT не завершает всю транзакцию.

## 6. Что такое Autocommit?

Autocommit — режим, при котором отдельные SQL-операторы автоматически выполняются и фиксируются как самостоятельные транзакции, если они не находятся внутри явно управляемой транзакции.

Например:

```sql
UPDATE users
SET status = 'BLOCKED'
WHERE id = 5;
```

При включённом autocommit изменение будет зафиксировано после успешного завершения оператора.

Если выполнить несколько отдельных `UPDATE` без явной транзакции, между ними может произойти ошибка, и ранее зафиксированные изменения уже нельзя будет отменить общим `ROLLBACK`.

### PostgreSQL и MySQL

- В PostgreSQL отдельные команды вне явного блока транзакции выполняются в неявных транзакциях. Клиентские инструменты и драйверы могут управлять этим по-своему.
- В MySQL InnoDB autocommit по умолчанию включён. Режим можно изменять, например с помощью `SET autocommit = 0`.

## 7. Транзакции и параллельные запросы

Транзакции особенно важны при конкурентном доступе.

Представим, что на счёте находится 1000 рублей.

Два параллельных запроса пытаются снять по 700 рублей.

Оба приложения выполняют:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

Оба получают значение 1000 и решают, что средств достаточно.

Если дальнейшие изменения реализованы неправильно, возможны некорректное списание или потерянное обновление.

Один из вариантов защиты — использовать блокировку строки:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

-- Проверка достаточности средств
-- и изменение баланса

COMMIT;
```

`FOR UPDATE` блокирует выбранную строку для конфликтующих изменений на время транзакции.

Второй конкурентный запрос, пытающийся получить несовместимую блокировку, будет ожидать её освобождения или завершится ошибкой при соответствующих условиях.

Альтернативный подход — атомарное условное обновление:

```sql
UPDATE accounts
SET balance = balance - 700
WHERE id = 1
  AND balance >= 700;
```

После выполнения приложение должно проверить количество изменённых строк.

Если изменена одна строка — списание прошло.

Если ноль строк — условие не выполнено, либо запись не найдена. В рамках полноценной транзакции приложение должно решить, можно ли продолжать остальные операции.

## 8. Транзакции и уровни изоляции

Уровень изоляции определяет, какие изменения других транзакций могут быть видны текущей транзакции и какие аномалии конкурентного выполнения допускаются.

| Уровень | Основная идея |
|---|---|
| Read Uncommitted | Может допускать чтение незафиксированных изменений |
| Read Committed | Не допускает грязное чтение |
| Repeatable Read | Защищает от неповторяемого чтения |
| Serializable | Гарантирует результат, эквивалентный некоторому последовательному выполнению транзакций |

Важные отличия:

**PostgreSQL:**

- По умолчанию используется `READ COMMITTED`.
- `READ UNCOMMITTED` фактически работает как `READ COMMITTED`.
- `REPEATABLE READ` также предотвращает phantom reads.
- На `SERIALIZABLE` возможны ошибки сериализации, требующие повторного выполнения транзакции.

**MySQL InnoDB:**

- По умолчанию используется `REPEATABLE READ`.
- Для согласованного чтения используется механизм снимков данных.
- Поведение обычных `SELECT` и блокирующих запросов может отличаться.

Подробно уровни изоляции и аномалии разберём в отдельном файле `04-isolation-levels.md`.

## 9. Что важно знать QA при тестировании транзакций

### Позитивный сценарий

Все операции завершились успешно, изменения зафиксировались.

Проверяем:

- Данные в связанных таблицах.
- Итоговое состояние сущностей.
- Правильность бизнес-ограничений.

### Ошибка в середине транзакции

Одна из операций завершается ошибкой.

Проверяем:

- Произошёл ли откат, если он предусмотрен логикой.
- Не осталось ли частично применённых изменений.
- Не нарушены ли ограничения целостности.

### Конкурентное выполнение

Два или больше запроса одновременно изменяют связанные данные.

Проверяем:

- Нет ли потерянных обновлений.
- Не нарушаются ли бизнес-инварианты.
- Правильно ли обрабатываются конфликты и ожидание блокировок.

### Повтор запроса

Клиент повторяет запрос после таймаута.

Проверяем:

- Не происходит ли двойное списание.
- Реализована ли идемпотентность, если она требуется.
- Корректно ли обрабатывается неопределённость результата первой попытки.

### Сбой во время выполнения

Соединение или приложение аварийно завершается до фиксации транзакции.

Проверяем ожидаемый откат незавершённой транзакции и отсутствие частичного результата.

Если соединение потеряно во время `COMMIT`, клиент может не знать, была ли операция зафиксирована. Для таких случаев особенно важны идемпотентность и проверка фактического результата.

## 10. Типичные вопросы на собеседовании

### 1. Что такое транзакция?

Логическая единица работы с базой данных, объединяющая связанные операции с общими гарантиями ACID.

### 2. Что такое ACID?

Atomicity, Consistency, Isolation, Durability — атомарность, согласованность, изоляция, долговечность.

### 3. Чем отличается COMMIT от ROLLBACK?

`COMMIT` фиксирует изменения, а `ROLLBACK` отменяет ещё не зафиксированные изменения транзакции.

### 4. Можно ли откатить транзакцию после COMMIT?

Обычным `ROLLBACK` нельзя. Для компенсации потребуется новая операция или восстановление данных другими средствами.

### 5. Что будет, если транзакция завершится ошибкой?

Зависит от СУБД, характера ошибки и логики приложения. Транзакция может перейти в состояние ошибки, отдельный оператор может быть отменён или вся транзакция может быть откатана.

### 6. Может ли транзакция состоять из одного SQL-запроса?

Да. Одна SQL-операция также может выполняться в рамках транзакции.

### 7. Решают ли транзакции все проблемы конкурентного доступа?

Нет. Это зависит от уровня изоляции, блокировок, бизнес-логики и способа обновления данных.

### 8. Что произойдёт, если приложение упадёт до COMMIT?

Открытая незавершённая транзакция при разрыве соединения обычно откатывается СУБД. Если же COMMIT уже был отправлен и его результат неизвестен клиенту, нужно отдельно выяснять, была ли фиксация успешной.

### 9. Может ли транзакция охватывать несколько микросервисов?

Обычная локальная транзакция БД не обеспечивает атомарность операций между независимыми сервисами. Для таких сценариев применяют распределённые транзакции (например, XA/2PC в поддерживаемых системах) или паттерны вроде Saga.

### 10. Чем SAVEPOINT отличается от COMMIT?

SAVEPOINT создаёт точку для частичного отката внутри транзакции, а COMMIT фиксирует всю транзакцию.

## 11. Частые ошибки в ответах

**Ошибка:** «Если SQL-запрос внутри транзакции упал, все операции всегда автоматически откатятся».

Правильнее: поведение зависит от СУБД и конкретной ошибки. Приложение должно корректно обрабатывать неудачные операции.

**Ошибка:** «Изоляция означает, что транзакции выполняются по очереди».

Правильнее: транзакции могут выполняться параллельно. Уровень изоляции определяет допустимое взаимодействие и гарантии результата.

**Ошибка:** «Если используется транзакция, двойное списание невозможно».

Правильнее: транзакции не заменяют идемпотентность и корректную обработку конкурентных запросов.

**Ошибка:** «ROLLBACK отменяет вообще все действия, совершённые приложением».

Правильнее: локальный откат БД не отменяет автоматически внешние побочные эффекты, например отправленное сообщение или HTTP-запрос.
