# Блокировки и MVCC в базах данных

## 1. Что такое блокировки?

**Блокировка (Lock)** — механизм управления конкурентным доступом к данным, который помогает нескольким транзакциям безопасно работать с одними и теми же ресурсами.

Блокировки позволяют предотвращать конфликты между операциями чтения и изменения данных.

Например, два пользователя одновременно пытаются купить последний товар на складе. Если приложение неправильно обрабатывает конкурентные запросы, оба пользователя могут успешно оформить покупку.

Блокировки — один из механизмов предотвращения таких ситуаций.

### Краткий ответ для собеседования

> Блокировки — это механизм контроля конкурентного доступа к данным. Они позволяют ограничивать выполнение конфликтующих операций над одними и теми же ресурсами. Блокировки могут применяться к строкам, таблицам и другим объектам. В зависимости от режима одна транзакция может ожидать завершения другой. Блокировки используются вместе с механизмами изоляции транзакций и MVCC.

---

## 2. Основные виды блокировок

Блокировки можно классифицировать по нескольким признакам.

### 2.1. Shared Lock — разделяемая блокировка

**Shared Lock (S-lock)** разрешает нескольким транзакциям одновременно получать совместимые разделяемые блокировки.

Однако эксклюзивная блокировка на том же ресурсе обычно конфликтует с разделяемой.

Пример:

- Транзакция A получает Shared Lock.
- Транзакция B также может получить Shared Lock.
- Транзакция C хочет получить Exclusive Lock и должна ожидать освобождения конфликтующих блокировок.

В MySQL InnoDB для явного разделяемого блокирующего чтения используется:

```sql
SELECT *
FROM users
WHERE id = 1
FOR SHARE;
```

В PostgreSQL также поддерживается `FOR SHARE`.

**Важно:** обычный SELECT в PostgreSQL и типичный неблокирующий SELECT в InnoDB не требуют разделяемой блокировки каждой читаемой строки. Благодаря MVCC чтение часто выполняется без блокирования записывающих транзакций.

### 2.2. Exclusive Lock — эксклюзивная блокировка

**Exclusive Lock (X-lock)** используется для операций, требующих исключительного доступа к определённому ресурсу относительно конфликтующих блокировок.

Например:

```sql
UPDATE users
SET balance = balance - 100
WHERE id = 1;
```

При изменении строки СУБД применяет необходимые блокировки, препятствующие конфликтующим изменениям этой же строки другой транзакцией.

**Важный момент:** Exclusive Lock на строку обычно не означает, что другие транзакции вообще не смогут прочитать эту строку.

В PostgreSQL и InnoDB обычное чтение через MVCC может получать ранее зафиксированную версию данных.

## 3. Row-Level Lock и Table-Level Lock

### Row-Level Lock — блокировка строки

Блокируется конкретная строка либо набор строк, затронутых операцией.

Например:

```sql
BEGIN;

SELECT *
FROM users
WHERE id = 10
FOR UPDATE;

-- Работа с выбранным пользователем

COMMIT;
```

Другие транзакции не смогут выполнить конфликтующее изменение заблокированной строки до освобождения блокировки.

При этом операции с другими строками могут продолжать выполняться.

### Table-Level Lock — блокировка таблицы

Блокировка устанавливается на уровне таблицы.

Она может использоваться при операциях с данными или структурой БД.

Примеры:

- `ALTER TABLE`
- `DROP TABLE`
- `TRUNCATE`
- Некоторые варианты создания индексов
- Явная команда `LOCK TABLE`

**Важно:** блокировка уровня таблицы не всегда означает полный запрет работы с таблицей.

В PostgreSQL существует несколько режимов табличных блокировок, совместимость которых различается.

Например, обычный `SELECT` получает `ACCESS SHARE`, а `ACCESS EXCLUSIVE` блокирует даже такое чтение.

### Сравнение

| Характеристика | Row-Level | Table-Level |
|---|---|---|
| Область действия | Отдельные строки | Таблица |
| Параллельность | Обычно выше | Зависит от режима |
| Пример | `SELECT FOR UPDATE` | `LOCK TABLE` |
| Основное применение | Конкурентное изменение записей | Операции со структурой и координация доступа |

## 4. Пессимистические блокировки (Pessimistic Locking)

Пессимистический подход предполагает, что конфликт между транзакциями возможен, поэтому данные блокируются до выполнения критических операций.

Обычно используется при операциях, где важно не допустить конкурентного изменения данных между чтением и последующей записью.

### Пример: покупка последнего товара

В таблице `products`:

| id | name | stock |
|---|---|---|
| 1 | Keyboard | 1 |

Покупатель A начинает транзакцию:

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 1
FOR UPDATE;
```

Получает:

```text
stock = 1
```

В этот момент покупатель B также пытается выполнить:

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 1
FOR UPDATE;
```

Вторая транзакция будет ожидать освобождения конфликтующей блокировки.

Покупатель A списывает товар:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 1;

COMMIT;
```

После освобождения блокировки покупатель B сможет продолжить выполнение (при обычном `READ COMMITTED` в PostgreSQL), увидит актуальный остаток 0 и должен получить отказ в покупке.

**Вывод:** блокировка позволяет сериализовать критическую последовательность чтения и изменения одной записи.

### Преимущества

- Позволяет контролировать конкурентное изменение данных.
- Подходит для критичных операций.
- Защищает участок между чтением и последующим обновлением.

### Недостатки

- Транзакции могут ожидать друг друга.
- Снижается параллельность при высокой конкуренции.
- Возможны deadlock.
- Длительные транзакции способны вызывать задержки.

## 5. SELECT FOR UPDATE

`SELECT ... FOR UPDATE` — SQL-конструкция, которая позволяет прочитать строки и одновременно получить блокировки для их последующего изменения.

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

### Что происходит?

1. Начинается транзакция.
2. СУБД находит нужную строку.
3. Получает блокировку для последующего изменения.
4. Другие транзакции, запрашивающие конфликтующие блокировки, ожидают.
5. Первая транзакция изменяет данные.
6. После COMMIT блокировка освобождается.

### NOWAIT

Можно указать, что при невозможности немедленно получить блокировку запрос должен завершиться ошибкой:

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE NOWAIT;
```

Это полезно, когда приложение не должно долго ожидать освобождения ресурса.

### SKIP LOCKED

Позволяет пропускать строки, уже заблокированные другими транзакциями:

```sql
SELECT *
FROM jobs
WHERE status = 'PENDING'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

Типичный пример — несколько обработчиков, которые забирают задачи из таблицы.

Каждый обработчик получает доступные незаблокированные строки.

**Нюанс:** `SKIP LOCKED` возвращает неполное представление данных и подходит не для всех бизнес-сценариев. Особенно полезен для очередей задач, реализованных на базе таблицы.

### Важные особенности

- Блокировки обычно удерживаются до завершения транзакции.
- `FOR UPDATE` нужно использовать внутри правильно организованной транзакции.
- Поведение зависит от уровня изоляции и СУБД.
- В MySQL InnoDB диапазонный запрос может затрагивать блокировками не только найденные строки, но и индексные интервалы.

## 6. Оптимистические блокировки (Optimistic Locking)

Оптимистический подход исходит из того, что конфликты редки.

Вместо предварительной блокировки приложение проверяет, не изменились ли данные с момента их чтения.

Для этого часто используют поле `version`.

### Пример

Таблица:

| id | balance | version |
|---|---|---|
| 1 | 1000 | 1 |

Два запроса читают одну строку:

```sql
SELECT balance, version
FROM accounts
WHERE id = 1;
```

Оба получают:

```text
balance = 1000
version = 1
```

Первый запрос обновляет:

```sql
UPDATE accounts
SET balance = 900,
    version = version + 1
WHERE id = 1
  AND version = 1;
```

Обновление успешно.

Теперь:

```text
balance = 900
version = 2
```

Второй запрос пытается обновить данные со старой версией:

```sql
UPDATE accounts
SET balance = 800,
    version = version + 1
WHERE id = 1
  AND version = 1;
```

Количество обновлённых строк — 0.

Это означает, что условие не выполнилось: запись изменилась или отсутствует.

Приложение должно обработать конфликт — например, перечитать данные, сообщить пользователю об изменении или повторить операцию с пересчётом.

### Преимущества

- Нет необходимости удерживать блокировку между чтением и проверяемым обновлением.
- Хорошо подходит, если конфликты редки.
- Удобен для REST API и редактирования сущностей.

### Недостатки

- Нужно явно обрабатывать конфликты.
- При высокой конкуренции возможно много повторных попыток.
- Повторять операции нужно осторожно, чтобы не нарушать бизнес-логику.

### Сравнение подходов

| | Пессимистический | Оптимистический |
|---|---|---|
| Основная идея | Предотвратить конфликт блокировкой | Обнаружить конфликт при записи |
| Механизм | Locks | Version / conditional update |
| Ожидание | Возможно | Часто вместо ожидания — конфликт |
| Подходит | Высокий риск конфликтов | Редкие конфликты |
| Риск | Ожидания, deadlock | Повторные попытки |

**Важно:** Optimistic Locking — это подход к контролю конкурентных изменений, а не гарантия полного отсутствия внутренних блокировок СУБД.

## 7. Что такое Deadlock?

**Deadlock (взаимная блокировка)** — ситуация, когда две или более транзакции ожидают освобождения ресурсов друг другом и ни одна не может продолжить выполнение.

### Пример

Есть два банковских счёта:

| id | balance |
|---|---|
| 1 | 1000 |
| 2 | 2000 |

Транзакция A:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

-- Позже пытается изменить счёт 2
UPDATE accounts
SET balance = balance + 100
WHERE id = 2;
```

Транзакция B:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 200
WHERE id = 2;

-- Позже пытается изменить счёт 1
UPDATE accounts
SET balance = balance + 200
WHERE id = 1;
```

Если операции выполняются в нужном порядке:

1. A блокирует счёт 1.
2. B блокирует счёт 2.
3. A пытается изменить счёт 2 и ожидает B.
4. B пытается изменить счёт 1 и ожидает A.

Получается взаимное ожидание.

### Как СУБД обрабатывает Deadlock?

PostgreSQL и MySQL InnoDB умеют обнаруживать deadlock.

Когда обнаруживается взаимная блокировка, СУБД выбирает одну из транзакций и отменяет её, чтобы другая могла продолжить выполнение.

В PostgreSQL deadlock обычно приводит к ошибке с SQLSTATE `40P01`.

В MySQL InnoDB типичная ошибка — `1213`, SQLSTATE `40001`.

### Как уменьшить вероятность Deadlock?

- Захватывать ресурсы в одинаковом порядке.
- Делать транзакции короткими.
- Использовать подходящие индексы.
- Избегать лишних блокировок.
- Не выполнять длительные внешние операции внутри транзакции.
- Корректно повторять транзакцию после ошибки deadlock.

### Deadlock vs Lock Wait

**Lock Wait** — транзакция ожидает освобождения ресурса. Это нормальная ситуация, которая может успешно разрешиться.

**Deadlock** — транзакции образовали цикл взаимного ожидания. Без вмешательства ни одна не сможет продолжить выполнение.

**Lock Wait Timeout** — ожидание блокировки превысило настроенный лимит времени. Это не обязательно deadlock.

## 8. Что такое MVCC?

**MVCC (Multi-Version Concurrency Control)** — механизм управления конкурентным доступом, при котором СУБД использует несколько версий данных, чтобы обеспечить согласованное чтение в условиях параллельных изменений.

Вместо того чтобы заставлять все читающие транзакции ожидать завершения записывающих, система может предоставить подходящую версию строки.

### Пример

Изначальное значение:

```text
balance = 1000
```

Транзакция A изменяет его:

```sql
BEGIN;

UPDATE accounts
SET balance = 500
WHERE id = 1;
```

Но пока не выполняет COMMIT.

В это время транзакция B делает обычный SELECT:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

В PostgreSQL на уровне Read Committed транзакция B увидит:

```text
balance = 1000
```

Она не увидит незавершённое изменение A.

После фиксации транзакции A новый SELECT в B (если B использует Read Committed) сможет увидеть:

```text
balance = 500
```

### Как работает MVCC в общем виде?

1. Транзакция изменяет строку.
2. СУБД сохраняет информацию, необходимую для доступа к разным версиям данных.
3. Читающая транзакция определяет, какая версия строки видима ей согласно правилам изоляции.
4. Старые версии могут оставаться доступными для активных транзакций.
5. Когда версии больше не нужны, они могут быть очищены механизмами обслуживания СУБД.

### MVCC в PostgreSQL

PostgreSQL хранит версии строк непосредственно в таблицах.

Для определения видимости используются служебные сведения, включая идентификаторы транзакций `xmin` и `xmax`.

Когда выполняется UPDATE, обычно создаётся новая версия строки, а старая со временем становится ненужной.

Очисткой устаревших версий занимается VACUUM, а автоматическое обслуживание выполняет autovacuum.

**Важный нюанс:** долгоживущие транзакции могут мешать очистке старых версий строк и способствовать увеличению размеров таблиц.

### MVCC в MySQL InnoDB

InnoDB применяет MVCC вместе с undo logs.

Undo records позволяют восстанавливать более ранние версии данных для согласованного чтения.

Старые версии удаляются механизмом purge, когда они больше не нужны.

В InnoDB используются read views, которые помогают определять видимые версии строк.

### MVCC не отменяет блокировки

Частое заблуждение: если СУБД использует MVCC, блокировки ей не нужны.

Это неверно.

MVCC помогает сократить конфликты между чтением и записью, но конкурентные изменения одних и тех же строк всё равно требуют координации.

Например:

- Два UPDATE одной строки могут конфликтовать.
- SELECT FOR UPDATE использует блокировки.
- Операции изменения структуры таблиц могут блокировать другие действия.
- Deadlock возможны даже при использовании MVCC.

## 9. Gap Locks и Next-Key Locks в MySQL InnoDB

Эта тема особенно актуальна для MarfaTech, поскольку в вакансии указан MySQL.

### Gap Lock

**Gap Lock** — блокировка промежутка между индексными значениями.

Она может предотвращать вставку новых записей в определённый индексный диапазон.

Например, в индексе есть значения:

```text
10, 20, 30
```

Gap Lock может запрещать вставку новых значений между 10 и 20.

Это применяется в InnoDB для контроля конкурентных изменений диапазонов.

### Next-Key Lock

**Next-Key Lock** сочетает блокировку индексной записи и предшествующего ей промежутка.

Например, для индексного значения 20 соответствующий интервал можно представить как:

```text
(10, 20]
```

Это помогает предотвращать появление новых строк в защищённом диапазоне при определённых режимах изоляции.

### Пример

```sql
BEGIN;

SELECT *
FROM orders
WHERE amount BETWEEN 100 AND 200
FOR UPDATE;
```

На уровне Repeatable Read InnoDB может заблокировать просканированные индексные диапазоны, включая промежутки, чтобы другие транзакции не могли вставить конфликтующие записи.

Точный набор блокировок зависит от:

- Индексов.
- Условия WHERE.
- Плана выполнения запроса.
- Уровня изоляции.
- Типа операции.

**Особенность:** на Read Committed InnoDB обычно отключает gap locking для поисковых и индексных сканирований, но сохраняет его для некоторых проверок, например внешних ключей и уникальности.

## 10. Как посмотреть блокировки в PostgreSQL и MySQL

### PostgreSQL

Информация о блокировках:

```sql
SELECT
    pid,
    locktype,
    relation::regclass,
    mode,
    granted
FROM pg_locks;
```

- `pid` — идентификатор процесса.
- `locktype` — тип блокируемого объекта.
- `mode` — режим блокировки.
- `granted` — получена ли блокировка.

Посмотреть активные запросы:

```sql
SELECT
    pid,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity;
```

Найти процессы, которые блокируют другие:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

### MySQL InnoDB

Просмотреть информацию о состоянии InnoDB:

```sql
SHOW ENGINE INNODB STATUS;
```

Для анализа ожиданий блокировок можно использовать представления:

```sql
SELECT *
FROM performance_schema.data_lock_waits;
```

```sql
SELECT *
FROM performance_schema.data_locks;
```

Доступность диагностических данных зависит от версии MySQL, конфигурации и прав пользователя.

## 11. Практический сценарий для QA

Предположим, существует API:

```http
POST /orders
```

Операция уменьшает остаток товара на складе и создаёт заказ.

В наличии один товар.

Два пользователя одновременно отправляют запрос на покупку.

### Что нужно проверить?

**Сценарий 1. Обычная покупка**

Один запрос успешно создаёт заказ, остаток уменьшается с 1 до 0.

**Сценарий 2. Две одновременные покупки**

Ожидаем:

- Не больше одного успешного резервирования единственного товара.
- Остаток не становится отрицательным.
- Количество заказов соответствует бизнес-правилам.
- Второй запрос получает корректный ответ.

**Сценарий 3. Ошибка при создании заказа**

Операция создания заказа завершается ошибкой после изменения остатка.

Проверяем, что система не оставляет некорректное частично изменённое состояние.

**Сценарий 4. Повтор после таймаута**

Клиент не получил ответ и повторил запрос.

Проверяем, что повтор не создаёт нежелательный второй заказ.

Для защиты от повторов могут потребоваться идемпотентные операции или idempotency key.

**Сценарий 5. Высокая конкурентная нагрузка**

Одновременно отправляем большое количество запросов.

Проверяем:

- Корректность данных.
- Количество успешных операций.
- Ошибки блокировок и deadlock.
- Время ответа.
- Работу повторных попыток.

## 12. Вопросы на собеседовании

### 1. Что такое блокировка в БД?

Механизм, который позволяет координировать конкурентный доступ транзакций к данным и другим ресурсам.

### 2. Чем Shared Lock отличается от Exclusive Lock?

Shared Lock допускает совместимые разделяемые блокировки, а Exclusive Lock конфликтует с определёнными другими блокировками и используется для исключительного доступа к ресурсу.

### 3. Что делает SELECT FOR UPDATE?

Читает строки и получает блокировки, препятствующие конфликтующим изменениям до завершения транзакции.

### 4. Чем оптимистическая блокировка отличается от пессимистической?

При пессимистическом подходе ресурс блокируется заранее. При оптимистическом конфликт обнаруживается при попытке изменения, например проверкой версии записи.

### 5. Что такое Deadlock?

Ситуация взаимного ожидания ресурсов между транзакциями, образующая цикл зависимостей.

### 6. Как избежать Deadlock?

Упорядочивать захват ресурсов, сокращать длительность транзакций, использовать подходящие индексы и корректно обрабатывать ошибки конкурентного выполнения.

### 7. Что такое MVCC?

Механизм управления конкурентным доступом, позволяющий транзакциям читать подходящие версии данных в соответствии с правилами видимости.

### 8. Зачем нужен MVCC?

Для согласованного чтения и уменьшения конфликтов между операциями чтения и записи.

### 9. Нужны ли блокировки, если используется MVCC?

Да. MVCC не устраняет необходимость координации конфликтующих изменений.

### 10. Что такое Gap Lock?

Механизм InnoDB, предотвращающий вставку записей в определённые индексные промежутки.

### 11. Что произойдёт, если две транзакции одновременно изменят одну строку?

Поведение зависит от СУБД, уровня изоляции и SQL-операций. Обычно возникает ожидание блокировки, а в некоторых сценариях одна транзакция может получить ошибку конкурентного обновления.

### 12. Когда использовать Optimistic Locking?

Когда конфликты ожидаются редко и приложение может обнаруживать их при записи и корректно обрабатывать.

### 13. Почему долгие транзакции опасны?

Они могут удерживать блокировки, увеличивать время ожидания других транзакций и мешать очистке устаревших версий данных.

### 14. Что такое SKIP LOCKED?

Режим блокирующего чтения, при котором уже заблокированные строки пропускаются. Полезен при конкурентной обработке задач.

### 15. Чем отличается Deadlock от Lock Wait Timeout?

Deadlock означает цикл взаимного ожидания, а Lock Wait Timeout — превышение допустимого времени ожидания блокировки без обязательного наличия цикла.

## 13. Частые ошибки на собеседовании

**Ошибка:** «SELECT FOR UPDATE блокирует всю таблицу».

Правильно: обычно он устанавливает блокировки на выбранные строки или индексные записи. В MySQL при диапазонных запросах блокировки могут затрагивать дополнительные индексные интервалы.

**Ошибка:** «MVCC полностью избавляет от блокировок».

Правильно: MVCC позволяет выполнять многие чтения без блокирования изменений, но не исключает блокировки при конкурентной записи.

**Ошибка:** «Deadlock — это когда один запрос долго выполняется».

Правильно: Deadlock предполагает взаимное ожидание транзакций. Долгое выполнение само по себе не означает deadlock.

**Ошибка:** «Оптимистическая блокировка всегда быстрее».

Правильно: её эффективность зависит от частоты конфликтов и стоимости повторных попыток.

**Ошибка:** «При использовании транзакций двойное списание невозможно».

Правильно: транзакции не заменяют идемпотентность и корректную логику обработки повторных запросов.
