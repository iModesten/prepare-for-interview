## 2. Основные понятия

**Linux** — семейство ОС на базе ядра Linux; Ubuntu и Debian — дистрибутивы. **Terminal** — окно для ввода команд, **Shell** (например, Bash) — программа, которая их выполняет.

**Файловая система:** `/` — корень, `/home` — домашние каталоги, `/etc` — конфигурации, `/var/log` — распространённое место для логов, `/tmp` — временные файлы.

**Права доступа:** `r` — чтение, `w` — запись, `x` — выполнение файла или проход через каталог. Например, `chmod 755 script.sh` даёт владельцу `rwx`, группе и остальным — `r-x`. `chmod 777` не стоит использовать как универсальное «исправление».

**Процесс** — запущенная программа с PID. **SIGTERM** просит корректно завершиться, **SIGKILL** завершает принудительно. Exit Code `137` часто связан с SIGKILL, но **сам по себе не доказывает OOM**.

**DNS** помогает получить IP-адрес сервера по имени. **TCP-порт** позволяет обратиться к конкретной службе по адресу. Рабочий TCP-порт не означает, что API корректно обрабатывает запросы.

**HTTP 500** — серверная ошибка. **502/504** часто формирует промежуточный Proxy/Gateway. Если POST вернул timeout, это **не доказывает**, что бизнес-операция не выполнилась.

## 3. Команды для работы

В примерах `app.log` — доступный тебе лог-файл, `api.example.com` — пример хоста. Команды для systemd и Docker работают, если приложение действительно запущено там и у тебя есть доступ.

| Что нужно сделать | Команда |
|---|---|
| Где я нахожусь? | `pwd` |
| Что в директории? | `ls -lah` |
| Перейти в папку | `cd /var/log` |
| Посмотреть файл | `less app.log` |
| Последние строки | `tail -n 100 app.log` |
| Смотреть новые строки | `tail -f app.log` |
| Найти текст | `grep -n 'ERROR' app.log` |
| Найти точный Request ID | `grep -F 'req-101' app.log` |
| Найти файлы | `find . -name '*.log'` |
| Посчитать ошибки | `grep -c 'ERROR' app.log` |
| Посмотреть процесс | `ps aux` |
| Найти процесс | `pgrep -af 'bonus-service'` |
| CPU/память процессов | `top` |
| Память системы | `free -h` |
| Проверить DNS | `getent ahosts api.example.com` |
| Посмотреть слушающие TCP-порты | `ss -lntp` |
| Проверить TCP-порт | `nc -vz -w 3 api.example.com 443` |
| Посмотреть HTTP-ответ | `curl -i https://api.example.com/health` |
| Подробности соединения | `curl -v https://api.example.com/health` |
| Посмотреть логи systemd | `journalctl -u bonus-service.service -n 100` |
| Логи Docker-контейнера | `docker logs --tail 100 bonus-service` |

**Pipe `|`** передаёт вывод одной команды в другую:

```bash
grep 'ERROR' app.log | wc -l
```

Этот пример считает строки с ошибкой. Для JSON-логов иногда удобнее `jq`; для реальных проверок учитывай формат записей.

## 4. Четыре практических сценария

### Сценарий 1. API вернул HTTP 500

**Ситуация:** запрос на получение бонусов завершился ошибкой.

**Действия QA:**

1. Сохраняю время, URL, статус, тело ответа и Request ID (если есть).
2. По Request ID ищу запись в логах приложения.
3. Смотрю, есть ли исключение и не упала ли зависимость — PostgreSQL или другой сервис.
4. Проверяю, повлияла ли ошибка на данные.
5. Оформляю баг с подтверждёнными фактами, а не догадкой «сломалась БД».

```bash
grep -F 'requestId=req-101' app.log
```

### Сценарий 2. API вообще не открывается

**Ситуация:** клиент получает Connection refused или timeout, HTTP-статуса нет.

**Действия QA:** проверяю DNS → возможность TCP-подключения → HTTP/TLS. Если есть доступ к серверу, проверяю, слушает ли приложение нужный порт.

```bash
getent ahosts api.example.com
nc -vz -w 3 api.example.com 443
curl -v --connect-timeout 3 --max-time 10 https://api.example.com/health
```

**Важно:** Connection refused, timeout и HTTP 500 — разные симптомы, требующие разных проверок.

### Сценарий 3. После релиза приложение постоянно перезапускается

**Ситуация:** приложение то доступно, то нет.

```bash
pgrep -af 'bonus-service'
journalctl -u bonus-service.service -n 100
```

Если оно в Docker:

```bash
docker ps -a
docker logs --tail 100 bonus-service
```

Ищу причину завершения: ошибка конфигурации, недоступная зависимость, нехватка памяти. Не делаю вывод об OOM только по коду 137.

### Сценарий 4. POST вернул 504 — бонус выдан или нет?

**Ситуация:** клиент отправил POST на выдачу бонуса и получил 504.

504 означает, что Gateway не дождался ответа. Но Backend мог успеть **создать запись или опубликовать событие**.

**Что проверю:** логи по Request ID, факт выдачи в БД, событие в брокере, возможные дубликаты, поддержку Idempotency Key. Не стану бездумно повторять запрос.

## 5. Быстрые вопросы для собеседования

**Чем Shell отличается от Terminal?** Terminal предоставляет интерфейс, Shell разбирает и выполняет команды.

**Что значит `chmod 755`?** Владелец может читать, писать, выполнять; группа и остальные — читать и выполнять.

**Как найти ошибку в логах?** `grep 'ERROR' app.log`; если известен Request ID, ищу именно его.

**Как вывести последние 100 строк файла?** `tail -n 100 app.log`.

**Что означает `|`?** Передаёт стандартный вывод одной команды на стандартный ввод следующей.

**Чем `ps` отличается от `top`?** `ps` показывает снимок процессов, `top` — обновляемую информацию.

**Чем SIGTERM отличается от SIGKILL?** SIGTERM можно обработать для корректного завершения, SIGKILL — нельзя.

**Что проверяет `ping`?** Обычно ICMP-достижимость и задержку; не проверяет работу HTTP.

**Что проверяет `nc -vz host 443`?** Возможность установить TCP-соединение с этим портом, но не работу API.

**Чем отличаются 502 и 504?** 502 — Gateway получил непригодный ответ от upstream, 504 — не дождался ответа вовремя.

**Что делать при HTTP 500?** Найти запрос в логах и проверить причину и последствия, а не ограничиться статусом.

**Зачем Request ID?** Чтобы найти связанные записи одного запроса среди большого количества логов.
