# Часть 1. Основы сетевого взаимодействия

## 1. Как клиент подключается к Backend?

Рассмотрим запрос:

```http
GET https://api.example.com:443/api/bonuses
```

Упрощённая последовательность для HTTPS поверх TCP:

```text
Client
  |
  | 1. DNS lookup
  v
Resolve api.example.com → IP
  |
  | 2. TCP connection
  v
Connect to IP:443
  |
  | 3. TLS handshake
  v
Encrypted connection
  |
  | 4. HTTP request
  v
GET /api/bonuses
  |
  | 5. HTTP response
  v
200 OK
```

Для HTTP/3 последовательность отличается: он использует QUIC поверх UDP вместо TCP.

### На каком этапе может возникнуть ошибка?

| Этап | Пример проблемы |
|---|---|
| DNS | Не удалось определить IP-адрес |
| Routing | Отсутствует маршрут до сети |
| TCP | Connection refused или Timeout |
| TLS | Недействительный сертификат |
| HTTP | 401, 403, 404, 500 |
| Backend | Ошибка бизнес-логики |
| Dependency | Недоступна БД или другой сервис |

### Главный принцип диагностики

Проверять соединение последовательно, от нижних уровней к верхним.

Не имеет смысла сразу искать ошибку SQL, если клиент даже не установил TCP-соединение с сервером.

## 2. Что такое IP-адрес?

**IP address** — сетевой адрес интерфейса, используемый для доставки IP-пакетов.

Основные версии:

- IPv4.
- IPv6.

### IPv4

Пример:

```text
192.168.1.10
```

IPv4-адрес состоит из 32 бит.

### IPv6

Пример:

```text
2001:db8::1
```

IPv6-адрес состоит из 128 бит.

### Зачем нужны IPv6-адреса?

IPv6 предоставляет значительно большее адресное пространство и другие возможности сетевого протокола.

### Важный нюанс

Один сервер может иметь несколько IP-адресов.

Например:

- Внутренний IPv4.
- Внешний IPv4.
- IPv6.
- Адреса нескольких сетевых интерфейсов.

Поэтому «IP сервера» не всегда является единственным значением.

---

## 3. Что такое порт?

**Port** — числовой идентификатор транспортного endpoint, используемый TCP и UDP.

Он позволяет различать сетевые службы на одном IP-адресе.

Например:

```text
192.168.1.10:8080
```

Здесь:

- `192.168.1.10` — IP.
- `8080` — порт.

### Часто встречающиеся порты

| Сервис | Стандартный или распространённый порт |
|---|---:|
| HTTP | 80 |
| HTTPS | 443 |
| SSH | 22 |
| PostgreSQL | 5432 |
| MySQL | 3306 |
| Redis | 6379 |
| RabbitMQ AMQP | 5672 |
| RabbitMQ Management | 15672 |
| Kafka | 9092 |

Эти значения являются стандартными или распространёнными настройками, а не обязательными.

### Может ли несколько сервисов использовать один порт?

Обычно два независимых процесса не могут просто так слушать одну и ту же комбинацию IP, порта и протокола.

Но существуют исключения и специальные механизмы:

- Разные локальные IP.
- Разные транспортные протоколы.
- Socket reuse.
- Reverse Proxy.

Например, Nginx может принимать HTTPS на порту 443 и направлять запросы нескольким Backend-сервисам на разные внутренние порты.

## 4. Что такое Socket?

**Socket** — программный интерфейс и связанный с ним объект для сетевого взаимодействия.

TCP-соединение обычно идентифицируется комбинацией:

```text
Source IP
Source Port
Destination IP
Destination Port
Protocol
```

### Пример

```text
Client:  192.168.1.20:53214
Server:  192.168.1.10:8080
Protocol: TCP
```

### Почему порт клиента не равен 8080?

Клиент обычно использует временный локальный порт (ephemeral port), назначенный операционной системой.

Сервер слушает известный порт 8080.

### Для собеседования

> Socket — механизм сетевого взаимодействия. TCP-соединение связывает два endpoint, каждый из которых определяется IP-адресом и портом. Сервер обычно слушает известный порт, а клиент использует временный локальный порт.

---

## 5. TCP vs UDP

| Характеристика | TCP | UDP |
|---|---|---|
| Соединение | Connection-oriented | Connectionless |
| Доставка | Надёжный упорядоченный поток байтов при работающем соединении | Нет встроенной гарантии доставки |
| Порядок | Сохраняет порядок байтов | Нет встроенной гарантии порядка |
| Повторная передача | Реализована транспортом | Не предусмотрена самим UDP |
| Типичные примеры | HTTP/1.1, HTTP/2, PostgreSQL | DNS, QUIC/HTTP/3 |

### Важный нюанс

UDP не обязательно означает ненадёжность прикладного протокола.

Например, QUIC работает поверх UDP, но реализует собственные механизмы надёжности, управления потерями и соединением.

### Краткий ответ

> TCP предоставляет упорядоченный поток байтов с обнаружением потерь и повторной передачей. UDP передаёт датаграммы без встроенных гарантий доставки и порядка. Дополнительные гарантии могут быть реализованы на уровне приложения.

---

## 6. TCP Three-Way Handshake

Для установления TCP-соединения обычно используется трёхэтапное рукопожатие.

```text
Client                         Server
  |                               |
  |------------ SYN ------------->|
  |                               |
  |<--------- SYN-ACK ------------|
  |                               |
  |------------ ACK ------------->|
  |                               |
  |        TCP Established        |
```

### Что означает каждый этап?

**SYN**

Клиент запрашивает установление соединения.

**SYN-ACK**

Сервер подтверждает SYN и отправляет собственный SYN.

**ACK**

Клиент подтверждает SYN сервера.

### Что происходит дальше при HTTPS?

После установления TCP-соединения выполняется TLS handshake.

Только затем обычно передаются HTTP-сообщения.

### Важный нюанс

Успешный TCP handshake не означает, что HTTP API работает.

Он означает, что на соответствующем endpoint удалось установить TCP-соединение.

# Часть 2. Сетевые адреса и интерфейсы

## 7. localhost, 127.0.0.1 и 0.0.0.0

Эти адреса часто встречаются при запуске Backend-приложений.

### 127.0.0.1

IPv4-адрес loopback-интерфейса.

Обращение к нему остаётся внутри соответствующего сетевого пространства имён.

```text
http://127.0.0.1:8080
```

### localhost

Имя хоста, которое обычно разрешается в loopback-адреса:

```text
127.0.0.1
::1
```

Фактическое разрешение зависит от системы.

### 0.0.0.0

В контексте привязки IPv4 listening socket обычно означает все локальные IPv4-интерфейсы.

Например, приложение, слушающее:

```text
0.0.0.0:8080
```

обычно может принимать соединения на этом порту через разные IPv4-адреса соответствующего сетевого namespace, если сетевые политики разрешают доступ.

### Сравнение

| Bind Address | Что означает |
|---|---|
| `127.0.0.1:8080` | Только локальный IPv4 loopback |
| `192.168.1.10:8080` | Конкретный IPv4-интерфейс |
| `0.0.0.0:8080` | Все локальные IPv4-интерфейсы |
| `[::1]:8080` | IPv6 loopback |
| `[::]:8080` | Все локальные IPv6-интерфейсы |

### Важный вопрос

**Почему API работает через localhost на сервере, но недоступен с другого компьютера?**

Возможная причина: приложение слушает только `127.0.0.1`.

Другие возможные причины:

- Firewall.
- Неправильный IP.
- Отсутствие маршрута.
- Настройки контейнерной сети.
- Неправильный port mapping.

### Нюанс IPv6

Сокет, привязанный к `[::]`, на некоторых системах также может принимать IPv4-подключения через IPv4-mapped IPv6 addresses.

Это зависит от настроек, включая `IPV6_V6ONLY`.

## 8. ip addr — посмотреть сетевые интерфейсы

Команда:

```bash
ip addr
```

Показывает сетевые интерфейсы и назначенные им адреса.

### Более короткий вариант

```bash
ip -br addr
```

Пример:

```text
lo       UNKNOWN   127.0.0.1/8 ::1/128
eth0     UP        192.168.1.10/24
```

### Основные понятия

**lo**

Loopback interface.

**eth0**

Условное имя Ethernet-интерфейса.

На современных системах имена могут быть другими, например `ens160` или `enp0s3`.

**UP**

Интерфейс административно включён.

### Для QA

Если сервис недоступен по определённому IP, нужно убедиться, что нужный адрес действительно назначен интерфейсу.

---

## 9. ip route — таблица маршрутизации

Команда:

```bash
ip route
```

Показывает маршруты IPv4.

Пример:

```text
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link
```

### Что такое Default Gateway?

Маршрутизатор, через который система отправляет пакеты к адресам, для которых нет более специфичного маршрута.

### Проверить маршрут до конкретного IP

```bash
ip route get 192.0.2.10
```

Результат может содержать:

- Выбранный интерфейс.
- Следующий узел маршрута.
- Исходный IP-адрес.

### Когда полезно?

Если сервис недоступен из одного окружения, но доступен из другого.

Например:

- Изнутри VPN работает.
- Из локальной сети не работает.
- Из контейнера недоступен.
- На самом сервере доступен.

### Важный нюанс

Наличие маршрута ещё не гарантирует, что удалённая система доступна.

Между клиентом и сервером могут находиться firewall, ACL и другие ограничения.

# Часть 3. DNS

## 10. Что такое DNS?

**DNS (Domain Name System)** — распределённая система разрешения имён и получения связанных с ними DNS-записей.

Например:

```text
api.example.com → 192.0.2.10
```

### Зачем нужен DNS?

Чтобы клиент мог использовать доменное имя вместо непосредственного указания IP.

### Пример

```text
Client
   |
   | api.example.com?
   v
Resolver
   |
   | 192.0.2.10
   v
Client connects to 192.0.2.10
```

### Краткий ответ для собеседования

> DNS — распределённая система, позволяющая получать IP-адреса и другие данные, связанные с доменными именами. Для подключения к API клиент обычно должен определить адрес сервера через DNS или другой механизм разрешения имён.

---

## 11. Основные DNS Record Types

| Тип | Назначение |
|---|---|
| A | IPv4-адрес |
| AAAA | IPv6-адрес |
| CNAME | Каноническое имя / alias |
| MX | Почтовые серверы домена |
| NS | Авторитетные DNS-серверы зоны |
| TXT | Текстовые данные |
| PTR | Обратное сопоставление адреса с именем |
| SRV | Информация о службе, включая порт и приоритет |

### Пример A

```text
api.example.com → 192.0.2.10
```

### Пример AAAA

```text
api.example.com → 2001:db8::10
```

### Пример CNAME

```text
api.example.com → gateway.example.net
```

### Важный нюанс

CNAME — не непосредственное сопоставление домена с IP-адресом.

Он указывает другое DNS-имя, для которого затем получают соответствующие записи.

---

## 12. dig — DNS-диагностика

**dig** — утилита для выполнения DNS-запросов.

### Получить DNS-информацию

```bash
dig example.com
```

### Только краткий ответ

```bash
dig +short example.com
```

### Запрос A

```bash
dig example.com A
```

### Запрос AAAA

```bash
dig example.com AAAA
```

### Запрос MX

```bash
dig example.com MX
```

### Для QA

Если приложение не может подключиться к:

```text
database.internal.example
```

можно проверить, разрешается ли имя в текущей среде:

```bash
dig database.internal.example
```

### Важно

`dig` выполняет DNS-запросы, но не обязательно воспроизводит полностью тот же путь разрешения имён, который использует приложение.

Например, приложение может учитывать `/etc/hosts` или другие NSS-источники.

---

## 13. nslookup

Ещё одна утилита для DNS-запросов.

```bash
nslookup example.com
```

Также можно явно задать тип записи, если реализация поддерживает соответствующие параметры:

```bash
nslookup -type=AAAA example.com
```

### dig vs nslookup

Для базовой проверки подходят обе.

`dig` обычно предоставляет больше возможностей для анализа DNS-ответов.

Для собеседования достаточно уверенно объяснить их назначение.

---

## 14. getent — разрешение имён через систему

На Linux с glibc можно использовать:

```bash
getent hosts example.com
```

Или:

```bash
getent ahosts example.com
```

### Чем это отличается от dig?

`getent` использует настроенные механизмы Name Service Switch.

Они могут включать:

- `/etc/hosts`.
- DNS.
- Другие источники имён.

### Почему это важно?

Возможна ситуация:

```bash
dig service.internal
```

не возвращает нужный IP, но:

```bash
getent hosts service.internal
```

возвращает адрес из `/etc/hosts` или другого настроенного источника.

### Для Backend QA

Если приложение использует системный resolver, `getent` часто помогает приблизиться к тому, как хост разрешает имя.

Но отдельные программы могут использовать собственные DNS-библиотеки и правила.

---

## 15. /etc/hosts

Файл:

```text
/etc/hosts
```

Может содержать статические соответствия IP и имён.

Пример:

```text
127.0.0.1 localhost
192.0.2.10 api-test.internal
```

### Зачем используется?

- Локальное сопоставление имени с адресом.
- Работа в тестовых окружениях.
- Специальная маршрутизация по имени.
- Разработка и диагностика.

### Важный нюанс

Изменение `/etc/hosts` может повлиять на приложения, использующие системное разрешение имён.

Не стоит изменять его на общем тестовом сервере без необходимости и согласования.

---

## 16. /etc/resolv.conf

Файл:

```text
/etc/resolv.conf
```

обычно содержит настройки resolver, например DNS-серверы и параметры поиска доменов.

Посмотреть:

```bash
cat /etc/resolv.conf
```

### Важный нюанс

На системах с `systemd-resolved` файл может быть символической ссылкой на автоматически формируемую конфигурацию.

Поэтому его содержимое не всегда раскрывает всю схему DNS-разрешения.

### Если доступен systemd-resolved

Можно использовать:

```bash
resolvectl status
```

Для проверки разрешения имени:

```bash
resolvectl query example.com
```

# Часть 4. Проверка сетевой достижимости

## 17. ping

**ping** отправляет ICMP Echo Request и анализирует полученные Echo Reply.

Пример:

```bash
ping -c 4 192.0.2.10
```

`-c 4` ограничивает количество запросов четырьмя в распространённой Linux-реализации.

### Что можно узнать?

- Отвечает ли удалённая сторона на ICMP Echo.
- Есть ли потери ответов.
- Приблизительное Round-Trip Time.
- Есть ли базовая IP-достижимость для данного вида трафика.

### Пример

```text
64 bytes from 192.0.2.10: icmp_seq=1 ttl=55 time=12.4 ms
64 bytes from 192.0.2.10: icmp_seq=2 ttl=55 time=12.1 ms
```

### Что ping НЕ проверяет?

- Работает ли HTTP API.
- Открыт ли TCP-порт 443.
- Корректен ли TLS-сертификат.
- Доступна ли база данных.
- Исправна ли бизнес-логика.

### Очень важный вопрос

**Если ping не проходит, значит сервер недоступен?**

Не обязательно.

ICMP Echo может быть заблокирован firewall или политиками сети.

Сервер при этом может успешно принимать TCP-подключения.

### Краткий ответ

> ping позволяет проверить получение ICMP Echo Reply и измерить задержку ответов. Но отсутствие ответа не доказывает недоступность сервера, потому что ICMP может фильтроваться. Для проверки конкретного API нужно отдельно проверить TCP, TLS и HTTP.

---

## 18. traceroute

**traceroute** помогает исследовать маршрут IP-пакетов до назначения.

Например:

```bash
traceroute example.com
```

Показывает промежуточные сетевые узлы, которые отвечают на соответствующие диагностические пакеты.

### Для чего полезно?

Если запросы не доходят до удалённой сети.

Можно приблизительно определить, на каком участке пути прекращаются диагностические ответы.

### Важный нюанс

Символы `* * *` не обязательно означают неисправность маршрутизатора.

Промежуточные устройства могут не отвечать на используемые traceroute-пакеты, ограничивать ICMP или применять другие политики.

Поэтому traceroute не является абсолютным доказательством места сетевого сбоя.

### Дополнительные инструменты

В некоторых окружениях доступны:

```bash
tracepath example.com
```

```bash
mtr example.com
```

Утилиты могут отсутствовать в минимальных контейнерных образах.

# Часть 5. Проверка TCP-портов

## 19. Что такое Listening Port?

Чтобы принимать входящие TCP-соединения, сервер обычно создаёт socket, привязывает его к адресу и порту и переводит в состояние LISTEN.

Например:

```text
0.0.0.0:8080 LISTEN
```

Это означает, что процесс слушает TCP-порт 8080 на локальных IPv4-интерфейсах в соответствующем сетевом namespace.

### Важно

Listening Port не гарантирует исправности приложения.

Сервис может принять TCP-соединение, но не отвечать на HTTP-запрос.

---

## 20. ss — просмотр сокетов

**ss (Socket Statistics)** — одна из самых полезных команд Linux для сетевой диагностики.

Она показывает сведения о сокетах.

### Список слушающих TCP-портов

```bash
ss -lnt
```

### С информацией о процессах

```bash
ss -lntp
```

### Расшифровка

| Опция | Назначение |
|---|---|
| `-l` | Listening sockets |
| `-n` | Числовые IP и порты |
| `-t` | TCP |
| `-u` | UDP |
| `-p` | Процессы, использующие socket |
| `-a` | Все соответствующие sockets |
| `-s` | Сводная статистика |

### Пример вывода

```text
State   Recv-Q Send-Q Local Address:Port Peer Address:Port Process
LISTEN  0      128    127.0.0.1:8080     0.0.0.0:*       ...
LISTEN  0      4096   0.0.0.0:5432       0.0.0.0:*       ...
```

### Что это означает?

Первый сервис слушает порт 8080 только на loopback IPv4.

Второй слушает порт 5432 на всех локальных IPv4-интерфейсах.

### Важный нюанс

Для просмотра сведений о некоторых чужих процессах через `-p` могут потребоваться дополнительные права.

---

## 21. Как узнать, кто занял порт?

Допустим, приложение не запускается и сообщает:

```text
Address already in use
```

### Шаг 1. Найти порт

```bash
ss -lntp
```

Можно отфильтровать вывод:

```bash
ss -lntp | grep ':8080'
```

Для точного фильтра TCP listening sockets:

```bash
ss -lntp '( sport = :8080 )'
```

### Шаг 2. Определить процесс

Если отображён PID, можно посмотреть его:

```bash
ps -p 2500 -o pid,ppid,user,cmd
```

### Альтернатива через lsof

Если установлен `lsof`:

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

### Важный нюанс

Ошибка Address already in use не всегда означает, что один случайный процесс занял порт.

Возможны:

- Второй экземпляр того же сервиса.
- Неправильная конфигурация.
- Конфликт привязки IPv4/IPv6.
- Особенности socket reuse.

### Для QA

Не нужно сразу завершать найденный процесс.

Сначала следует определить, кому он принадлежит и должен ли он работать.

---

## 22. Просмотр установленных TCP-соединений

```bash
ss -tn state established
```

Показывает TCP-сокеты в состоянии ESTABLISHED.

### Пример

```text
192.168.1.10:8080 192.168.1.20:53214
```

Это может означать установленное соединение между клиентом и Backend.

### Что такое ESTABLISHED?

Состояние TCP-соединения, в котором стороны могут обмениваться данными.

### Другие состояния TCP

| State | Значение |
|---|---|
| LISTEN | Ожидание входящих подключений |
| SYN-SENT | Отправлен SYN, ожидается ответ |
| SYN-RECV | Получен SYN, выполняется установление |
| ESTABLISHED | Соединение установлено |
| FIN-WAIT-1 / FIN-WAIT-2 | Процесс закрытия соединения |
| CLOSE-WAIT | Получен FIN от удалённой стороны, локальная сторона ещё не закрыла соединение |
| TIME-WAIT | Ожидание после завершения соединения согласно правилам TCP |

### Senior-нюанс

Большое количество CLOSE-WAIT может свидетельствовать о проблеме с закрытием соединений приложением.

Но окончательный вывод требует анализа контекста, количества соединений и поведения сервиса.

---

## 23. nc — проверка TCP-подключения

**nc (netcat)** — утилита для сетевых операций, в том числе для проверки возможности установить TCP-соединение.

### Пример

```bash
nc -vz -w 3 192.0.2.10 8080
```

В распространённых реализациях:

- `-v` — подробный вывод.
- `-z` — проверка подключения без обычного обмена данными.
- `-w 3` — таймаут.

### Возможный успешный результат

```text
Connection to 192.0.2.10 8080 port [tcp/*] succeeded!
```

### Что означает успех?

С текущего клиента удалось установить TCP-соединение с указанным адресом и портом.

### Что он не гарантирует?

- Что HTTP API отвечает.
- Что TLS работает.
- Что есть авторизация.
- Что Backend подключён к БД.
- Что бизнес-операция выполняется.

### Важный нюанс

Существуют разные реализации netcat: OpenBSD nc, GNU netcat, BusyBox nc, Nmap ncat.

Некоторые опции и формат вывода могут отличаться.

---

## 24. Проверка PostgreSQL, Kafka или RabbitMQ

Допустим, приложение не может подключиться к PostgreSQL.

### Проверка TCP-порта

```bash
nc -vz -w 3 postgres.internal.example 5432
```

Для RabbitMQ AMQP:

```bash
nc -vz -w 3 rabbitmq.internal.example 5672
```

Для Kafka:

```bash
nc -vz -w 3 kafka.internal.example 9092
```

### Что можно понять?

Открыто ли TCP-соединение на соответствующий endpoint.

### Что нельзя понять?

Не получится подтвердить:

- Корректность логина в PostgreSQL.
- Успешный Kafka metadata request.
- Возможность прочитать Kafka topic.
- Корректность AMQP-аутентификации.
- Права доступа к RabbitMQ queue.

### Kafka-нюанс

Успешный TCP connect к одному Kafka bootstrap broker не гарантирует полноценную работу Kafka Client.

Клиент получает metadata и может пытаться подключаться к другим брокерам по адресам из `advertised.listeners`.

Если эти адреса недоступны из сети клиента, работа Kafka будет нарушена.

Это важный пример того, почему проверка одного TCP-порта не равна проверке всей интеграции.

# Часть 6. curl — HTTP-запросы из терминала

## 25. Что такое curl?

**curl** — инструмент передачи данных с использованием различных сетевых протоколов.

Для Backend QA он особенно полезен для проверки HTTP и HTTPS API.

### Основные задачи

- Отправка GET.
- Отправка POST, PUT, PATCH и DELETE.
- Передача Headers.
- Передача JSON.
- Проверка HTTP-статусов.
- Проверка TLS.
- Диагностика соединения.
- Измерение отдельных этапов запроса.

### Краткий ответ для собеседования

> curl — утилита командной строки для сетевых запросов. В Backend QA её используют для проверки HTTP API, передачи заголовков и тела запроса, получения ответов и диагностики DNS, TCP, TLS и HTTP.

---

## 26. Простой GET

```bash
curl https://example.com
```

По умолчанию curl использует GET для обычного HTTP-запроса без дополнительных параметров, меняющих метод.

### Более реалистичный пример

```bash
curl https://api.example.com/health
```

Это учебный адрес. Фактический endpoint зависит от системы.

### Показать заголовки ответа вместе с телом

```bash
curl -i https://api.example.com/health
```

Здесь `-i` добавляет HTTP response headers к выводу.

---

## 27. curl -I vs curl -i

Эти команды важно не путать.

### curl -I

```bash
curl -I https://example.com
```

Использует HEAD для HTTP-запроса и выводит заголовки ответа.

### curl -i

```bash
curl -i https://example.com
```

Обычно выполняет GET и показывает заголовки вместе с телом.

### Важный нюанс

Если endpoint не поддерживает HEAD, команда `curl -I` может вернуть 405, хотя GET работает.

Поэтому для проверки именно GET удобнее:

```bash
curl -D - -o /dev/null https://example.com
```

Здесь выполняется обычный GET, но тело ответа не выводится, а заголовки показываются в терминале.

---

## 28. curl -v — подробная диагностика

```bash
curl -v https://api.example.com/health
```

Verbose-режим помогает увидеть:

- Разрешение имени.
- Попытки подключения.
- Выбранный IP.
- Установление соединения.
- Детали TLS.
- HTTP-запрос.
- HTTP-ответ.

### Типичный сценарий

API не отвечает.

Запускаем:

```bash
curl -v --max-time 10 https://api.example.com/health
```

По выводу можно определить, на каком этапе возникла проблема.

### Важный момент безопасности

Verbose-вывод может содержать чувствительную информацию, включая HTTP-заголовки.

Не следует без очистки прикладывать его к публичным задачам или сообщениям.

Особенно важно защищать:

- Authorization.
- Cookie.
- Set-Cookie.
- Токены.
- Персональные данные.

## 29. Передача Headers

Пример:

```bash
curl \
  -H 'Accept: application/json' \
  https://api.example.com/bonuses
```

### Несколько Headers

```bash
curl \
  -H 'Accept: application/json' \
  -H 'X-Request-ID: qa-test-001' \
  https://api.example.com/bonuses
```

### Authorization

```bash
curl \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  https://api.example.com/profile
```

### Важный нюанс

При работе с токенами нужно учитывать:

- Историю Shell.
- Логи CI.
- Отладочный вывод.
- Список аргументов процесса.
- Правила хранения секретов.

Для реальных секретов следует использовать предусмотренные компанией безопасные способы передачи конфигурации и credentials.

---

## 30. POST с JSON

Пример:

```bash
curl \
  -X POST \
  https://api.example.com/bonuses/issue \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  -d '{
    "userId": "user-100",
    "bonusId": 777
  }'
```

### Что здесь происходит?

`-X POST` задаёт метод.

`-H` передаёт заголовки.

`-d` передаёт тело запроса.

### Важный нюанс

Использование `-d` для HTTP по умолчанию предполагает POST, если не задан другой метод.

Но `-d` само по себе не устанавливает Content-Type: application/json.

Поэтому заголовок Content-Type нужно задавать явно для JSON.

### Отправить содержимое файла

```bash
curl \
  https://api.example.com/bonuses/issue \
  -H 'Content-Type: application/json' \
  --data-binary @request.json
```

Так удобнее выполнять тесты с большими телами запросов.

## 31. PUT, PATCH и DELETE

### PUT

```bash
curl -X PUT \
  https://api.example.com/users/100 \
  -H 'Content-Type: application/json' \
  -d '{"name":"Anna"}'
```

### PATCH

```bash
curl -X PATCH \
  https://api.example.com/users/100 \
  -H 'Content-Type: application/merge-patch+json' \
  -d '{"city":"Minsk"}'
```

### DELETE

```bash
curl -X DELETE \
  https://api.example.com/users/100
```

### Для QA

Можно быстро проверить:

- Поддерживается ли метод.
- Какой статус возвращается.
- Корректно ли обрабатывается тело.
- Есть ли ошибки авторизации.
- Выполняется ли ожидаемая бизнес-операция.

## 32. Как получить только HTTP Status?

Очень полезная команда:

```bash
curl -sS \
  -o /dev/null \
  -w '%{http_code}\n' \
  https://api.example.com/health
```

### Опции

| Опция | Значение |
|---|---|
| `-s` | Убрать progress meter и обычные сообщения |
| `-S` | Показывать ошибки при silent mode |
| `-o /dev/null` | Не выводить тело |
| `-w` | Вывести заданную информацию о запросе |
| `%{http_code}` | HTTP response code |

### Возможный результат

```text
200
```

### Важный нюанс

Если HTTP-ответ вообще не был получен, curl может вывести:

```text
000
```

Это не настоящий HTTP-статус.

Он означает отсутствие доступного HTTP response code в данном результате curl.

Для диагностики нужно также проверять exit code и сообщение об ошибке.

---

## 33. HTTP Status vs curl Exit Code

Это важное различие.

Предположим, сервер вернул:

```http
HTTP/1.1 500 Internal Server Error
```

По умолчанию curl может успешно завершить передачу HTTP-ответа и вернуть exit code 0.

Хотя HTTP-статус — 500.

### Почему?

Потому что:

- HTTP Status характеризует результат HTTP-запроса на уровне протокола.
- curl Exit Code характеризует результат выполнения операции самой утилитой.

### Пример

```bash
curl -sS -o /dev/null \
  -w '%{http_code}\n' \
  https://api.example.com/health

echo $?
```

При полученном HTTP 500 команда без специальных опций может вернуть:

```text
500
0
```

### Как считать HTTP 4xx/5xx ошибкой curl?

```bash
curl --fail-with-body \
  https://api.example.com/health
```

В поддерживающих эту опцию версиях curl она позволяет сохранить тело ответа, но вернуть ошибку для соответствующих HTTP 4xx/5xx.

Есть также:

```bash
curl -f https://api.example.com/health
```

Но `-f` обычно подавляет тело такого ответа.

### Для CI

Нужно явно понимать, что считается успешным результатом:

- Установление соединения?
- HTTP 2xx?
- Определённый статус?
- Корректное тело?
- Успешная бизнес-операция?

---

## 34. Основные curl Exit Codes

| Exit Code | Типичное значение |
|---|---|
| 0 | curl успешно выполнил операцию |
| 6 | Не удалось разрешить имя хоста |
| 7 | Не удалось подключиться к серверу |
| 22 | HTTP-ошибка при использовании fail-режима |
| 28 | Истёк timeout операции |
| 35 | Ошибка TLS/SSL-соединения |
| 52 | Empty reply from server |
| 60 | Ошибка проверки сертификата |
| 56 | Ошибка получения сетевых данных |

### Важный нюанс

Exit code сам по себе не всегда определяет точную первопричину.

Например, код 7 может возникнуть по разным причинам сбоя соединения.

Необходимо анализировать текст ошибки и контекст запроса.

---

## 35. Timeout в curl

### Connection Timeout

```bash
curl --connect-timeout 3 \
  https://api.example.com/health
```

Ограничивает время фазы соединения согласно правилам curl, включая необходимые этапы установления соединения.

### Общий Timeout

```bash
curl --max-time 10 \
  https://api.example.com/health
```

Ограничивает общее время операции.

### Использовать вместе

```bash
curl \
  --connect-timeout 3 \
  --max-time 10 \
  https://api.example.com/health
```

### Почему полезно задавать оба?

Чтобы различать:

- Невозможность установить соединение.
- Слишком длительный запрос после успешного подключения.

### Важный нюанс

Если запрос завершился по общему timeout, это не обязательно ошибка сети.

Причина может быть в длительной обработке на Backend или медленной передаче данных.

---

## 36. Измерение времени запроса через curl

Одна из самых полезных возможностей для диагностики.

```bash
curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup}\nconnect=%{time_connect}\ntls=%{time_appconnect}\nttfb=%{time_starttransfer}\ntotal=%{time_total}\n' \
  https://api.example.com/health
```

### Основные метрики

| Метрика | Значение |
|---|---|
| time_namelookup | Время до завершения разрешения имени |
| time_connect | Время от старта до завершения TCP-соединения |
| time_appconnect | Время до завершения TLS/другого прикладного handshake |
| time_starttransfer | Время до получения первого байта ответа |
| time_total | Общее время операции |

### Важный нюанс

Эти метрики обычно являются накопительными временными отметками от начала операции, а не независимыми длительностями этапов.

Например:

```text
dns=0.010
connect=0.030
tls=0.080
ttfb=0.400
total=0.450
```

Можно приблизительно оценить:

```text
DNS             ≈ 10 ms
TCP после DNS   ≈ 20 ms
TLS после TCP   ≈ 50 ms
До первого байта после TLS ≈ 320 ms
Оставшаяся передача ≈ 50 ms
```

Это упрощённая интерпретация. На реальные измерения влияют соединения, прокси, повторное использование соединений и другие детали.

### Для Backend QA

Если TTFB сильно больше времени установления соединения, возможная задержка находится на этапе после соединения:

- Reverse Proxy.
- Backend.
- База данных.
- Внешняя зависимость.
- Очередь обработки.

Но одной метрики недостаточно для точной локализации.

---

## 37. Проверка Redirect

По умолчанию curl обычно не переходит автоматически по HTTP-redirect.

### Следовать перенаправлениям

```bash
curl -L https://example.com
```

### Посмотреть подробности

```bash
curl -v -L https://example.com
```

### Для QA

Проверять:

- 301 / 302.
- 307 / 308.
- Location.
- Корректность конечного URL.
- Отсутствие нежелательных циклов.
- Безопасность перенаправления.
- Сохранение HTTP-метода, где это требуется.

### Важный нюанс

Автоматическое следование redirect может изменять метод при определённых статусах и сценариях.

Поэтому при проверке POST и Redirect нужно внимательно смотреть фактические запросы.

# Часть 7. HTTPS и TLS

## 38. Что такое TLS?

**TLS (Transport Layer Security)** — протокол защиты сетевого соединения.

Для HTTPS он обеспечивает:

- Шифрование.
- Контроль целостности.
- Аутентификацию сервера через сертификат при корректной проверке.

### Упрощённая схема

```text
Client
   |
   | TCP connection
   v
Server
   |
   | TLS handshake
   v
Protected connection
   |
   | HTTPS request
   v
HTTP response
```

### Что проверяет клиент?

В зависимости от конфигурации:

- Доверие к цепочке сертификатов.
- Срок действия.
- Соответствие имени сервера.
- Допустимость криптографических параметров.
- Другие ограничения безопасности.

---

## 39. Почему curl может не доверять сертификату?

Пример:

```text
curl: (60) SSL certificate problem
```

Возможные причины:

- Самоподписанный сертификат.
- Отсутствует доверенный CA.
- Неполная цепочка сертификатов.
- Неверное имя сервера.
- Истёкший сертификат.
- Другие проблемы верификации.

### Что делать QA?

1. Проверить точный текст ошибки.
2. Убедиться в правильности доменного имени.
3. Проверить сертификат.
4. Проверить доверенную CA-конфигурацию.
5. Убедиться, что проблема не связана с тестовым окружением.

### Опасная практика

```bash
curl -k https://api.example.com
```

Опция `-k` отключает проверку сертификата в соответствующем режиме.

Она может быть полезна для строго контролируемой диагностики, но не должна рассматриваться как исправление TLS-проблемы.

**Не использовать отключение проверки сертификатов для обхода проблем безопасности в рабочей среде.**

---

## 40. openssl s_client

Для более глубокой проверки TLS можно использовать OpenSSL.

Например:

```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com \
  -verify_return_error \
  </dev/null
```

### Что это позволяет исследовать?

- Установление TLS-соединения.
- Сертификаты сервера.
- Параметры соединения.
- Ошибки проверки.
- Поддерживаемый механизм TLS.

### Зачем нужен -servername?

Он задаёт имя для SNI — Server Name Indication.

Это важно, когда на одном IP располагается несколько HTTPS-сайтов.

### Важный нюанс

Даже успешный TLS handshake не означает успешную HTTP-операцию.

После TLS приложение ещё должно корректно обработать HTTP-запрос.

# Часть 8. Диагностика DNS и конкретного IP

## 41. curl --resolve

Иногда нужно проверить конкретный Backend IP, сохранив доменное имя в HTTPS-запросе.

Например, DNS возвращает неправильный IP, а нам известен предполагаемый адрес:

```text
192.0.2.10
```

Можно выполнить:

```bash
curl \
  --resolve api.example.com:443:192.0.2.10 \
  https://api.example.com/health
```

### Что делает --resolve?

Для указанной пары домен/порт curl использует заданный IP вместо обычного результата разрешения имени.

При этом URL остаётся:

```text
https://api.example.com/health
```

### Почему это полезно?

Можно проверить:

- Определённый сервер за DNS.
- Отдельный экземпляр API.
- Проблему DNS.
- Влияние балансировщика или маршрутизации.

### Важный нюанс

Для HTTPS важно сохранять ожидаемое доменное имя, поскольку оно участвует в SNI и проверке сертификата.

Простой вызов:

```bash
curl https://192.0.2.10
```

может вести себя иначе.

### Для Backend QA

`--resolve` особенно полезен при сравнении работы приложения через DNS и напрямую через конкретный IP.

# Часть 9. Connection Refused vs Timeout

## 42. Connection Refused

Пример ошибки:

```text
Connection refused
```

Обычно означает, что попытка TCP-соединения была явно отклонена.

Возможные причины:

- На порту никто не слушает.
- Приложение слушает другой IP.
- Сервис не запущен.
- Firewall или другое сетевое устройство явно отклоняет соединение.
- Неправильный порт.

### Что проверить?

На сервере:

```bash
ss -lntp
```

С клиента:

```bash
nc -vz -w 3 api.example.com 8080
```

### Пример

Приложение слушает:

```text
127.0.0.1:8080
```

Клиент пытается подключиться к:

```text
192.168.1.10:8080
```

В такой ситуации соединение может быть отклонено.

### Краткий ответ

> Connection refused обычно означает, что соединение было активно отклонено. Частая причина — отсутствие listening socket на нужном IP и порту, но отказ также может исходить от сетевой инфраструктуры.

---

## 43. Connection Timed Out

Пример:

```text
Connection timed out
```

Означает, что соединение не было установлено в отведённое время.

Возможные причины:

- Сетевые пакеты фильтруются.
- Недоступен маршрут.
- Потеря пакетов.
- Удалённая сторона не отвечает.
- Сетевое устройство отбрасывает запрос.
- Проблема с VPN или сетевыми правилами.

### Refused vs Timed Out

| Характеристика | Refused | Timed Out |
|---|---|---|
| Был явный отказ | Часто да | Обычно нет |
| Нет слушателя | Частая причина | Не обязательно |
| Firewall | Может активно отклонить | Может молча отбросить |
| Диагностика | Адрес, порт, listener | Маршрут, firewall, сеть, доступность |

### Важный нюанс

Нельзя утверждать, что Timeout всегда означает firewall.

Это лишь одна из возможных причин.

---

## 44. Connection Reset

Ошибка:

```text
Connection reset by peer
```

Обычно связана с получением TCP RST и аварийным прекращением соединения.

Возможные причины:

- Удалённая сторона закрыла соединение через reset.
- Сетевая инфраструктура сбросила соединение.
- Проблема приложения.
- Проблема протокола или таймаута.

### Чем отличается от Refused?

Connection refused относится к неуспешной попытке установления соединения.

Connection reset часто возникает, когда соединение уже было установлено или находилось в процессе взаимодействия.

### Для QA

Нужно определить, в какой момент произошёл reset:

- При подключении.
- Во время TLS.
- Во время отправки запроса.
- Во время чтения ответа.

# Часть 10. HTTP-ошибки инфраструктуры

## 45. 502, 503 и 504

### 502 Bad Gateway

Gateway/Proxy получил непригодный ответ от upstream.

Пример:

```text
Client
   |
   v
Nginx
   |
   | Invalid upstream response
   v
Backend
```

### 503 Service Unavailable

Сервис временно не может обработать запрос.

Причины могут включать:

- Перегрузку.
- Maintenance.
- Недоступность обслуживающих компонентов.

### 504 Gateway Timeout

Gateway/Proxy не получил своевременный ответ от upstream.

### Почему это важно?

Если клиент получил 504, нельзя автоматически считать, что бизнес-операция не выполнилась.

Backend мог успешно изменить БД, но не вернуть ответ до истечения таймаута Gateway.

Это особенно важно для:

- Платежей.
- Выдачи бонусов.
- Создания заказов.
- Неидемпотентных операций.


```bash

```


- Внешние зависимости.
- Retry.
- Очереди задач.

## 51. Сценарий: в контейнере API работает, с хоста — нет

- Совпадает ли внутренний порт контейнера с ожидаемым.

- Используется ли правильный network namespace.

Контейнер запущен с параметром:

```bash

```

Это одна из распространённых причин ошибок при работе с API и БД в Docker.

# Часть 13. Вопросы для собеседования

## 54. Что такое IP-адрес?

Сетевой адрес интерфейса, используемый IP для доставки пакетов.

## 55. Чем IPv4 отличается от IPv6?

IPv4 использует 32-битные адреса, IPv6 — 128-битные.

## 56. Что такое TCP Port?

Числовой идентификатор транспортного endpoint, позволяющий различать соединения с приложениями.

## 57. Что такое Socket?

Интерфейс и объект сетевого взаимодействия, через который процесс обменивается данными.

## 58. Чем TCP отличается от UDP?

TCP предоставляет упорядоченный надёжный поток байтов. UDP передаёт датаграммы без встроенных гарантий доставки и порядка.

## 59. Как работает TCP Three-Way Handshake?

SYN → SYN-ACK → ACK.

## 60. Что такое DNS?

Распределённая система разрешения доменных имён и получения связанных DNS-записей.

## 61. Что такое A и AAAA Records?

A содержит IPv4-адрес, AAAA — IPv6-адрес.

## 62. Что такое CNAME?

DNS-запись, указывающая каноническое имя.

## 63. Как проверить DNS из Linux?

```bash
dig example.com
```

Или:

```bash
getent ahosts example.com
```

## 64. Чем dig отличается от getent?

dig выполняет DNS-запросы. getent использует настроенные системные NSS-механизмы.

## 65. Что такое localhost?

Имя, которое обычно разрешается в loopback-адреса.

## 66. Чем 127.0.0.1 отличается от 0.0.0.0?

127.0.0.1 — конкретный loopback IPv4-адрес. 0.0.0.0 при bind обычно означает все локальные IPv4-интерфейсы.

## 67. Как посмотреть сетевые интерфейсы?

```bash
ip -br addr
```

## 68. Как посмотреть маршруты?

```bash
ip route
```

## 69. Как проверить ICMP-доступность сервера?

```bash
ping -c 4 example.com
```

## 70. Если ping не проходит, значит сервер недоступен?

Нет. ICMP может фильтроваться.

## 71. Как проверить TCP-порт?

```bash
nc -vz -w 3 example.com 443
```

## 72. Как посмотреть слушающие порты?

```bash
ss -lntp
```

## 73. Как найти процесс, слушающий порт 8080?

```bash
ss -lntp '( sport = :8080 )'
```

Или:

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

## 74. Что означает LISTEN?

TCP socket ожидает входящие подключения.

## 75. Что означает ESTABLISHED?

TCP-соединение установлено.

## 76. Что такое curl?

Утилита для передачи данных по сетевым протоколам, широко используемая для HTTP API.

## 77. Как отправить GET через curl?

```bash
curl https://example.com
```

## 78. Как отправить POST с JSON?

```bash
curl -X POST \
  https://api.example.com/orders \
  -H 'Content-Type: application/json' \
  -d '{"productId":10}'
```

## 79. Чем curl -I отличается от curl -i?

-I выполняет HEAD. -i показывает заголовки ответа вместе с содержимым обычного запроса.

## 80. Как посмотреть подробности соединения?

```bash
curl -v https://example.com
```

## 81. Как получить только HTTP Status?

```bash
curl -sS -o /dev/null \
  -w '%{http_code}\n' \
  https://example.com
```

## 82. Чем HTTP Status отличается от curl Exit Code?

HTTP Status — результат HTTP-обработки. curl Exit Code — результат выполнения сетевой операции утилитой.

## 83. Что означает curl Exit Code 6?

Не удалось разрешить имя хоста.

## 84. Что означает curl Exit Code 7?

Не удалось установить соединение с сервером.

## 85. Что означает curl Exit Code 28?

Истёк установленный timeout curl.

## 86. Что означает curl Exit Code 60?

Ошибка проверки сертификата.

## 87. Чем Connection Refused отличается от Timed Out?

Refused — обычно явный отказ при подключении. Timed Out — отсутствие успешного подключения за установленное время.

## 88. Что означает Connection Reset?

Соединение аварийно сброшено, например через TCP RST.

## 89. Что такое TLS?

Протокол защиты сетевого соединения, обеспечивающий шифрование, целостность и аутентификацию стороны в соответствующей конфигурации.

## 90. Как посмотреть этапы HTTP-запроса по времени?

Использовать curl `-w` с `time_namelookup`, `time_connect`, `time_appconnect`, `time_starttransfer`, `time_total`.

## 91. Почему Backend может работать локально, но не извне?

Проблема может быть связана с bind address, firewall, маршрутизацией, Proxy или контейнерной сетью.

## 92. Может ли открытый TCP-порт гарантировать успешную работу API?

Нет. Нужно отдельно проверить TLS, HTTP, авторизацию, приложение и зависимости.

## 93. Почему 504 не гарантирует, что POST не выполнился?

Потому что Backend мог выполнить операцию, но не вернуть ответ Gateway в установленное время.

# Часть 14. Частые ошибки на собеседовании

**Ошибка:** «ping проверяет доступность HTTP-сервера».

Правильно: ping использует ICMP и не проверяет HTTP API.

**Ошибка:** «Если ping не проходит, сервер точно выключен».

Правильно: ICMP может фильтроваться.

**Ошибка:** «0.0.0.0 означает IP конкретного удалённого сервера».

Правильно: при bind это обычно все локальные IPv4-интерфейсы.

**Ошибка:** «localhost внутри контейнера — это Docker Host».

Правильно: localhost относится к соответствующему сетевому namespace.

**Ошибка:** «Если порт 443 открыт, HTTPS работает».

Правильно: открытый TCP-порт не гарантирует успешный TLS handshake.

**Ошибка:** «curl Exit Code 0 означает HTTP 200».

Правильно: curl может успешно получить HTTP 404 или 500.

**Ошибка:** «Connection refused и Connection timeout — одно и то же».

Правильно: это разные виды неуспешного соединения.

**Ошибка:** «Если TCP-соединение с PostgreSQL успешно, значит БД работает правильно».

Правильно: дополнительно нужны проверки PostgreSQL-протокола, аутентификации, прав и функциональности.

**Ошибка:** «TLS и HTTP — один протокол».

Правильно: HTTPS объединяет HTTP и TLS, а сами механизмы имеют разные задачи.

**Ошибка:** «504 означает, что Backend ничего не выполнил».

Правильно: результат бизнес-операции может быть неизвестен клиенту.

**Ошибка:** «dig и системное разрешение имени всегда возвращают одно и то же».

Правильно: приложение может использовать `/etc/hosts`, NSS и другие механизмы.

# Часть 15. Практика

Все команды ниже предназначены для собственной или разрешённой тестовой среды. Некоторые из них требуют установленного программного обеспечения.

## Задание 1. Посмотреть сетевые интерфейсы

```bash
ip -br addr
```

Найти:

- Loopback.
- Основной интерфейс.
- IPv4.
- IPv6, если используется.

## Задание 2. Посмотреть маршруты

```bash
ip route
```

Определить Default Gateway, если он настроен.

## Задание 3. Проверить DNS

```bash
getent ahosts example.com
```

```bash
dig +short example.com
```

Сравнить результаты.

## Задание 4. Проверить ICMP

```bash
ping -c 4 example.com
```

Определить:

- Есть ли ответы.
- RTT.
- Packet Loss.

Помнить, что отсутствие ответов не доказывает недоступность HTTP.

## Задание 5. Проверить HTTPS через curl

```bash
curl -v --max-time 10 https://example.com
```

Найти в выводе:

- IP.
- TCP-подключение.
- TLS.
- HTTP status.

## Задание 6. Получить только HTTP Status

```bash
curl -sS -o /dev/null \
  -w '%{http_code}\n' \
  https://example.com
```

## Задание 7. Измерить время

```bash
curl -sS -o /dev/null \
  -w 'DNS: %{time_namelookup}\nTCP: %{time_connect}\nTLS: %{time_appconnect}\nTTFB: %{time_starttransfer}\nTotal: %{time_total}\n' \
  https://example.com
```

Сравнить значения.

## Задание 8. Посмотреть слушающие TCP-порты

```bash
ss -lntp
```

Найти:

- LISTEN.
- Local Address.
- Port.
- Process, если информация доступна.

## Задание 9. Проверить порт

```bash
nc -vz -w 3 example.com 443
```

При успешном соединении помнить, что это ещё не функциональная проверка HTTPS.

## Задание 10. Сравнить HEAD и GET

```bash
curl -I https://example.com
```

```bash
curl -D - -o /dev/null https://example.com
```

Понять различия методов и содержимого.

|---|---|
| Посмотреть IP-адреса | `ip -br addr` |

| Посмотреть LISTEN | `ss -lntp` |
| Посмотреть TCP-соединения | `ss -tn state established` |
| Найти процесс на порту | `ss -lntp '( sport = :8080 )'` |
| GET | `curl https://example.com` |
| Подробный HTTP/TLS | `curl -v https://example.com` |
| Заголовки HEAD | `curl -I https://example.com` |
| Заголовки GET | `curl -D - -o /dev/null https://example.com` |
| Только статус | `curl -sS -o /dev/null -w '%{http_code}\n' URL` |
| Timeout | `curl --connect-timeout 3 --max-time 10 URL` |
| Redirect | `curl -L URL` |
| Конкретный IP для домена | `curl --resolve host:443:IP https://host/` |
| Проверка TLS | `openssl s_client -connect host:443 -servername host` |
