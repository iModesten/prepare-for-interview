# Часть 1. Основы Linux и файловая система

## 1. Что такое Linux?

**Middle**

Linux — ядро операционной системы, на основе которого создаются различные дистрибутивы.

Примеры дистрибутивов:

- Ubuntu.
- Debian.
- Fedora.
- Red Hat Enterprise Linux.
- Alpine Linux.

Для Backend QA Linux используется при работе с серверами, тестовыми стендами, Docker, CI/CD, логами и сетевыми соединениями.

## 2. Чем Terminal отличается от Shell?

**Middle**

Terminal — приложение, предоставляющее интерфейс командной строки.

Shell — интерпретатор, который принимает и выполняет команды.

Bash и Zsh — примеры Shell.

**Уточнение:** `cd` обычно является встроенной командой оболочки, поскольку меняет её текущую рабочую директорию.

## 3. Какие основные директории Linux ты знаешь?

**Middle**

| Директория | Назначение |
|---|---|
| `/` | Корень файловой системы |
| `/home` | Домашние директории пользователей |
| `/etc` | Системные конфигурации |
| `/var/log` | Распространённое расположение логов |
| `/var/lib` | Изменяемые данные сервисов |
| `/tmp` | Временные файлы |
| `/usr/bin` | Многие исполняемые команды |
| `/opt` | Дополнительное ПО |
| `/proc` | Виртуальная информация о процессах и ядре |
| `/dev` | Файлы устройств |

Не все сервисы записывают логи в `/var/log`. Например, контейнерные приложения часто используют stdout/stderr.

## 4. Чем абсолютный путь отличается от относительного?

**Middle**

Абсолютный путь начинается с корня файловой системы:

```bash
/var/log/app.log
```

Относительный путь определяется от текущей рабочей директории:

```bash
logs/app.log
```

Основные обозначения:

- `.` — текущая директория.
- `..` — родительская директория.
- `~` — домашняя директория в контексте расширения Shell.

## 5. Какие команды используются для навигации?

**Middle**

```bash
pwd                 # текущая директория
ls                  # содержимое
ls -lah             # подробный список
cd /var/log         # перейти в директорию
cd ..               # на уровень выше
cd ~                # домой
cd -                # предыдущая директория
```

Для быстрого просмотра прав, владельца и размеров файлов удобно использовать `ls -lah`.

## 6. Как создать, скопировать, переместить и удалить файл?

**Middle**

```bash
touch file.txt
cp file.txt backup.txt
mv file.txt renamed.txt
rm renamed.txt
```

Создать вложенные директории:

```bash
mkdir -p project/config/dev
```

**Важно:** `rm` обычно удаляет файл без перемещения в корзину. На общих серверах следует избегать непроверенных рекурсивных удалений.

## 7. Что означает chmod 755?

**Middle**

Права записываются для трёх категорий:

- Owner.
- Group.
- Others.

Числовые значения:

```text
Read    = 4
Write   = 2
Execute = 1
```

`755` означает:

```text
Owner:  rwx = 7
Group:  r-x = 5
Others: r-x = 5
```

Команда:

```bash
chmod 755 script.sh
```

## 8. Что означают chmod 644 и chmod 600?

**Middle**

`644`:

```text
rw-r--r--
```

Владелец может читать и изменять, остальные получают право чтения.

`600`:

```text
rw-------
```

Только владелец получает базовые права на чтение и запись.

Примеры:

```bash
chmod 644 config.json
chmod 600 private.txt
```

Дополнительные механизмы, например ACL, могут влиять на фактический доступ.

## 9. Чем права на файл отличаются от прав на директорию?

**Middle / Senior**

Для обычного файла:

- `r` — чтение.
- `w` — запись.
- `x` — выполнение.

Для директории:

- `r` — просмотр списка имён.
- `w` — изменение записей при соблюдении дополнительных условий.
- `x` — проход через директорию и доступ к известным именам.

**Важный нюанс:** даже если у пользователя есть право чтения файла, он может не суметь открыть его без права `x` на родительских директориях.

## 10. Как диагностировать Permission denied?

**Middle / Senior**

Проверить:

```bash
whoami
id
ls -l /path/to/file
ls -ld /path/to/directory
```

На Linux, если утилита доступна:

```bash
namei -l /path/to/file
```

Возможные причины:

- Неправильный владелец.
- Неподходящая группа.
- Недостаточные права файла.
- Нет права прохода через директорию.
- Дополнительные ограничения ACL или SELinux/AppArmor.

**Не следует автоматически применять `chmod 777`.**

## 11. Что такое Symbolic Link?

**Middle**

Symbolic Link — файловый объект, указывающий на другой путь.

Создать:

```bash
ln -s releases/v2 current
```

Проверить:

```bash
ls -l current
readlink current
```

Если цель переместится или исчезнет, ссылка может стать нерабочей.

Hard Link отличается тем, что является ещё одним именем того же inode файла.

## 12. Что такое Environment Variables и PATH?

**Middle**

Environment Variables используются для передачи настроек процессам.

Примеры:

```bash
echo "$HOME"
echo "$PATH"
printenv
```

Создать переменную окружения для дочерних процессов:

```bash
export APP_ENV=test
```

`PATH` содержит список директорий, в которых Shell ищет команды.

**Важно:** `export` в текущем Shell не делает переменную постоянной глобальной настройкой системы.

# Часть 2. Поиск и обработка текста

## 13. Что такое grep?

**Middle**

`grep` используется для поиска строк, соответствующих текстовому шаблону или регулярному выражению.

Например:

```bash
grep 'ERROR' app.log
```

Для Backend QA это одна из самых полезных команд при поиске ошибок.

## 14. Какие основные опции grep ты знаешь?

**Middle**

| Опция | Назначение |
|---|---|
| `-i` | Игнорировать регистр |
| `-n` | Показывать номера строк |
| `-c` | Считать строки с совпадениями |
| `-v` | Исключать совпадающие строки |
| `-F` | Буквальный поиск |
| `-E` | Расширенные регулярные выражения |
| `-r` | Рекурсивный поиск |
| `-C 5` | Пять строк контекста до и после |

Примеры:

```bash
grep -in 'error' app.log
grep -c 'ERROR' app.log
grep -E 'ERROR|WARN' app.log
```

## 15. Чем grep -F отличается от grep -E?

**Middle**

`grep -F` ищет буквальную строку без интерпретации регулярных выражений.

`grep -E` использует расширенные регулярные выражения.

Например:

```bash
grep -F 'requestId=req-101' app.log
```

Подходит для поиска конкретного Request ID.

```bash
grep -E 'ERROR|WARN' app.log
```

Позволяет найти один из нескольких шаблонов.

## 16. Как найти все HTTP 500 в логах?

**Middle**

Если лог содержит поле:

```text
status=500
```

Можно использовать:

```bash
grep -F 'status=500' app.log
```

Подсчитать строки:

```bash
grep -cF 'status=500' app.log
```

Для HTTP 5xx:

```bash
grep -E 'status=5[0-9]{2}([[:space:]]|$)' app.log
```

**Senior:** сначала нужно убедиться в реальном формате логов. Если это JSON, лучше использовать структурированный поиск.

## 17. Чем grep отличается от find?

**Middle**

`grep` ищет совпадения внутри текстовых данных.

`find` ищет файловые объекты по имени и атрибутам.

Например:

```bash
find . -type f -name '*.log'
```

Найти ERROR во всех найденных файлах:

```bash
find . -type f -name '*.log' \
  -exec grep -nH 'ERROR' {} +
```

## 18. Чем head отличается от tail?

**Middle**

`head` показывает начало файла.

`tail` показывает конец файла.

```bash
head -n 20 app.log
tail -n 50 app.log
```

`tail -f` позволяет наблюдать добавление новых записей:

```bash
tail -f app.log
```

В GNU Linux `tail -F` удобен при ротации файла, поскольку следит за именем и пытается открыть файл повторно.

## 19. Что такое Pipe?

**Middle**

Pipe (`|`) передаёт STDOUT одной команды на STDIN следующей.

Например:

```bash
grep 'ERROR' app.log | wc -l
```

Сначала находятся строки с ERROR, затем подсчитывается их количество.

### Пример цепочки

```bash
grep -oE 'status=[0-9]{3}' app.log |
  cut -d= -f2 |
  sort |
  uniq -c
```

Она позволяет посчитать частоту HTTP-статусов при соответствующем формате логов.

## 20. Что означают STDIN, STDOUT и STDERR?

**Middle**

Три стандартных потока процесса:

| Поток | Дескриптор | Назначение |
|---|---:|---|
| STDIN | 0 | Ввод |
| STDOUT | 1 | Обычный вывод |
| STDERR | 2 | Ошибки и диагностика |

Перенаправление:

```bash
command > output.log
command >> output.log
command 2> error.log
command > combined.log 2>&1
```

Последняя команда направляет STDOUT и STDERR в один файл.

**Уточнение:** порядок перенаправлений имеет значение.

## 21. Чем sort отличается от uniq?

**Middle**

`sort` сортирует строки.

`uniq` работает с соседними одинаковыми строками.

Поэтому для общего подсчёта повторений обычно используют:

```bash
sort file.txt | uniq -c
```

Отсортировать результат по количеству:

```bash
sort file.txt | uniq -c | sort -nr
```

## 22. Что такое sed?

**Middle**

`sed` — потоковый редактор для поиска, выбора строк и преобразования текста.

Пример замены:

```bash
echo 'status=500' | sed 's/status=/HTTP /'
```

Результат:

```text
HTTP 500
```

Вывести строки с десятой по двадцатую:

```bash
sed -n '10,20p' app.log
```

Для диагностики лучше сначала выполнять преобразования без изменения оригинального файла.

## 23. Что такое awk?

**Middle / Senior**

`awk` — инструмент обработки записей и полей текста.

Позволяет:

- Выводить поля.
- Фильтровать записи.
- Считать значения.
- Выполнять простые агрегации.

Пример:

```bash
awk '{print $2}' app.log
```

Выводит второе поле каждой строки при стандартном разделении.

Посчитать строки, где второе поле равно ERROR:

```bash
awk '$2 == "ERROR" {n++} END {print n+0}' app.log
```

## 24. Для чего используется jq?

**Middle / Senior**

`jq` используется для обработки JSON в командной строке.

Например:

```bash
echo '{"status":500,"requestId":"req-101"}' |
  jq '.status'
```

Результат:

```text
500
```

Для JSON Lines:

```bash
jq -c 'select(.status >= 500 and .status < 600)' \
  structured.log
```

Это надёжнее поиска подстроки, если данные действительно представлены корректным JSON.

# Часть 3. Процессы и сигналы

## 25. Что такое Process?

**Middle**

Process — выполняющийся экземпляр программы.

Он имеет:

- PID.
- Состояние.
- Адресное пространство.
- Потоки.
- Файловые дескрипторы.
- Переменные окружения.
- Учётные данные и ограничения.

Одна и та же программа может иметь несколько запущенных экземпляров.

## 26. Что такое PID и PPID?

**Middle**

PID — идентификатор процесса.

PPID — идентификатор родительского процесса.

Посмотреть:

```bash
ps -ef
```

Для определённого процесса:

```bash
ps -p 2500 -o pid,ppid,user,cmd
```

PID может повторно использоваться после завершения процесса.

## 27. Чем Process отличается от Thread?

**Middle**

Process — отдельный контекст выполнения с собственным виртуальным адресным пространством.

Thread — поток выполнения внутри процесса.

Потоки одного процесса используют общую память, но имеют собственные стеки и состояние выполнения.

Для Backend это важно при анализе:

- Deadlock.
- Thread starvation.
- Thread Pool.
- Конкурентности.
- Потребления CPU.

## 28. Как посмотреть все процессы?

**Middle**

```bash
ps aux
```

Или:

```bash
ps -ef
```

Для интерактивного мониторинга:

```bash
top
```

## 29. Как найти процесс приложения?

**Middle**

```bash
pgrep -af 'bonus-service'
```

Или:

```bash
ps aux | grep 'bonus-service'
```

Первый вариант обычно удобнее, поскольку не создаёт дополнительного совпадения с самим процессом grep.

**Важно:** перед действиями с PID нужно убедиться, что найден правильный процесс.

## 30. Что означают состояния R, S, D, T и Z?

**Middle / Senior**

| Код | Состояние |
|---|---|
| R | Running / Runnable |
| S | Interruptible Sleep |
| D | Uninterruptible Sleep |
| T | Stopped |
| Z | Zombie |

**Уточнение:** S — нормальное состояние ожидания. Оно не означает, что процесс завис.

## 31. Что такое Zombie Process?

**Middle / Senior**

Zombie — завершившийся процесс, чей родитель ещё не получил информацию о завершении.

Он уже не выполняет пользовательский код.

Обычно его нельзя устранить с помощью `kill -9`, поскольку он уже завершился.

Нужно изучать поведение родительского процесса.

## 32. Что делает команда kill?

**Middle**

`kill` отправляет сигнал процессу или группе процессов в зависимости от аргументов.

По умолчанию обычно отправляется SIGTERM.

Пример:

```bash
kill -TERM 2500
```

Команда не гарантирует немедленное завершение.

## 33. Чем SIGTERM отличается от SIGKILL?

**Middle**

SIGTERM — запрос завершения, который приложение может обработать.

SIGKILL — принудительное завершение без выполнения пользовательских shutdown handlers.

```bash
kill -TERM 2500
```

```bash
kill -KILL 2500
```

**Senior:** для Backend-приложений важно корректно реализовывать Graceful Shutdown.

## 34. Что такое Graceful Shutdown?

**Middle / Senior**

Контролируемое завершение приложения.

Обычно включает:

- Прекращение приёма новых запросов.
- Завершение или корректную отмену текущих операций.
- Закрытие соединений.
- Сохранение необходимого состояния.
- Корректную остановку Consumers.

SIGTERM позволяет начать такое завершение, но приложение должно поддерживать соответствующую логику.

## 35. Что означает Exit Code 137?

**Middle / Senior**

Часто связан с завершением через SIGKILL:

```text
128 + 9 = 137
```

Возможные причины:

- OOM Killer.
- Принудительная остановка контейнера.
- Действие администратора.
- Другой источник SIGKILL.

**Важно:** 137 не доказывает OOM.

Нужно проверить системные логи и сведения контейнерной платформы.

## 36. Как проверить потребление CPU и памяти?

**Middle**

```bash
top
```

```bash
free -h
```

Для процесса:

```bash
ps -p 2500 -o pid,%cpu,%mem,rss,vsz,cmd
```

Показатель RSS отражает резидентную память процесса, а VSZ/VIRT — виртуальное адресное пространство.

## 37. Что такое Load Average?

**Middle / Senior**

Load Average показывает усреднённую нагрузку на систему за 1, 5 и 15 минут.

Проверить:

```bash
uptime
```

В Linux показатель учитывает runnable задачи и определённые виды непрерываемого ожидания.

Он не равен проценту CPU.

## 38. Что такое OOM Killer?

**Middle / Senior**

Механизм Linux, который при определённых условиях нехватки памяти может завершать процессы.

Причины OOM могут быть связаны с:

- Памятью всего хоста.
- Ограничениями cgroup.
- Лимитом контейнера.

Поэтому даже при наличии свободной памяти на хосте контейнер может быть завершён из-за собственного лимита.

## 39. Что такое File Descriptor?

**Middle / Senior**

Числовой дескриптор, через который процесс работает с открытыми ресурсами.

Примеры:

- Файлы.
- Сокеты.
- Каналы.

Посмотреть:

```bash
ls -l /proc/2500/fd
```

Если установлен lsof:

```bash
lsof -p 2500
```

Большое количество неосвобождённых дескрипторов может привести к ошибке `Too many open files`.

# Часть 4. Сетевые команды и диагностика

## 40. Чем TCP отличается от UDP?

**Middle**

TCP предоставляет упорядоченный поток байтов и механизмы обнаружения потерь и повторной передачи.

UDP передаёт датаграммы без встроенных гарантий доставки и порядка.

Примеры:

- HTTP/1.1 и HTTP/2 обычно используют TCP.
- HTTP/3 использует QUIC поверх UDP.
- PostgreSQL обычно использует TCP.
- DNS может использовать UDP или TCP.

## 41. Как устанавливается TCP-соединение?

**Middle**

Three-Way Handshake:

```text
Client                  Server
  |                        |
  |------- SYN ----------->|
  |<----- SYN-ACK ---------|
  |------- ACK ----------->|
```

После этого TCP-соединение установлено.

Для HTTPS поверх TCP затем выполняется TLS handshake.

## 42. Что такое localhost, 127.0.0.1 и 0.0.0.0?

**Middle**

`127.0.0.1` — IPv4 loopback.

`localhost` — имя, которое обычно разрешается в loopback-адреса.

`0.0.0.0` при bind IPv4 socket обычно означает прослушивание всех локальных IPv4-интерфейсов.

**Важно:** приложение, слушающее только `127.0.0.1`, обычно недоступно напрямую по внешнему IPv4-адресу.

## 43. Как узнать IP-адрес сервера?

**Middle**

```bash
ip -br addr
```

Или:

```bash
ip addr
```

Для просмотра маршрутов:

```bash
ip route
```

## 44. Как проверить DNS?

**Middle**

```bash
dig example.com
```

```bash
nslookup example.com
```

Если нужно проверить системное разрешение имён:

```bash
getent ahosts example.com
```

**Уточнение:** dig выполняет DNS-запросы, а getent использует настроенные системные механизмы разрешения имён, которые могут учитывать `/etc/hosts`.

## 45. Что проверяет ping?

**Middle**

`ping` отправляет ICMP Echo Request и анализирует ответы.

Например:

```bash
ping -c 4 example.com
```

Он помогает оценить ICMP-достижимость и RTT.

**Важно:** отсутствие ответа не означает, что сервер недоступен по TCP. ICMP может быть заблокирован.

## 46. Как проверить открытый TCP-порт?

**Middle**

```bash
nc -vz -w 3 example.com 443
```

При успешном подключении можно утверждать, что TCP-соединение установилось.

Но нельзя утверждать, что HTTPS или бизнес-API работают правильно.

## 47. Как посмотреть, какие порты слушает сервер?

**Middle**

```bash
ss -lntp
```

Основные опции:

- `-l` — Listening.
- `-n` — числовые адреса.
- `-t` — TCP.
- `-p` — информация о процессах.

Проверить конкретный порт:

```bash
ss -lntp '( sport = :8080 )'
```

## 48. Чем Connection refused отличается от Connection timed out?

**Middle / Senior**

**Connection refused** — попытка подключения получила явный отказ.

Возможные причины:

- Нет listening socket.
- Неверный порт.
- Неправильный bind address.
- Активный отказ firewall.

**Connection timed out** — соединение не установилось за заданное время.

Возможные причины:

- Фильтрация.
- Сетевые потери.
- Проблемы маршрутизации.
- Удалённая сторона не отвечает.

## 49. Как отправить HTTP-запрос через curl?

**Middle**

GET:

```bash
curl https://example.com
```

POST:

```bash
curl -X POST \
  https://api.example.com/orders \
  -H 'Content-Type: application/json' \
  -d '{"productId":10}'
```

Подробный вывод:

```bash
curl -v https://example.com
```

## 50. Чем curl -I отличается от curl -i?

**Middle**

`curl -I` для HTTP выполняет HEAD и выводит заголовки.

`curl -i` включает заголовки ответа в вывод обычного запроса.

Для GET без вывода тела:

```bash
curl -D - -o /dev/null https://example.com
```

## 51. Чем HTTP Status отличается от curl Exit Code?

**Middle / Senior**

HTTP Status описывает результат HTTP-обработки.

Curl Exit Code описывает выполнение сетевой операции самой утилитой.

Например, при HTTP 500 curl без fail-режима может вернуть exit code 0, если получил HTTP-ответ успешно.

Для проверки HTTP-ошибок в сценариях автоматизации можно использовать:

```bash
curl --fail-with-body https://example.com
```

## 52. Как измерить время HTTP-запроса через curl?

**Senior**

```bash
curl -sS -o /dev/null \
  -w 'DNS=%{time_namelookup}\nTCP=%{time_connect}\nTLS=%{time_appconnect}\nTTFB=%{time_starttransfer}\nTotal=%{time_total}\n' \
  https://example.com
```

Эти показатели позволяют оценить, на каком этапе появилась задержка.

**Важно:** это в основном накопительные отметки времени, а не независимые продолжительности этапов.

# Часть 5. Логи, сервисы и диагностика

## 53. Как проверить состояние systemd-сервиса?

**Middle**

```bash
systemctl status bonus-service.service
```

Проверить активность:

```bash
systemctl is-active bonus-service.service
```

Проверить включение:

```bash
systemctl is-enabled bonus-service.service
```

**Важно:** активность сервиса не гарантирует функциональную исправность HTTP API.

## 54. Как посмотреть логи systemd-сервиса?

**Middle**

Последние 100 записей:

```bash
journalctl -u bonus-service.service -n 100
```

Следить за новыми:

```bash
journalctl -u bonus-service.service -f
```

За конкретный период:

```bash
journalctl -u bonus-service.service \
  --since "2026-10-09 10:00:00"
```

## 55. Чем restart отличается от reload и daemon-reload?

**Middle / Senior**

`restart` — перезапускает сервис.

`reload` — запрашивает перечитывание конфигурации у поддерживающего это сервиса.

`daemon-reload` — заставляет systemd перечитать собственную конфигурацию unit-файлов.

**Важно:** `daemon-reload` не равен рестарту приложения.

## 56. Как посмотреть логи Docker-контейнера?

**Middle**

```bash
docker logs --tail 100 bonus-service
```

Следить за логами:

```bash
docker logs -f bonus-service
```

Для Docker Compose:

```bash
docker compose logs -f bonus-service
```

## 57. Как посмотреть логи предыдущего контейнера Kubernetes?

**Middle / Senior**

```bash
kubectl logs bonus-service-pod \
  -n qa --previous
```

Это полезно, если контейнер перезапустился и причина завершения осталась в логах предыдущего экземпляра.

Также проверить:

```bash
kubectl describe pod bonus-service-pod -n qa
```

## 58. Что такое CrashLoopBackOff?

**Middle / Senior**

Состояние Kubernetes, при котором контейнер повторно неуспешно запускается, а платформа увеличивает задержку между попытками.

Возможные причины:

- Ошибка конфигурации.
- Исключение при старте.
- Нехватка памяти.
- Недоступная зависимость.
- Ошибка probes.

CrashLoopBackOff — симптом, а не первопричина.

## 59. Что такое Request ID и Trace ID?

**Middle**

Request ID обычно связывает записи отдельного запроса.

Trace ID используется для корреляции выполнения распределённой операции через сервисы.

Например:

```text
Gateway → Bonus Service → User Service → PostgreSQL
```

Общий Trace ID помогает исследовать цепочку.

## 60. Что делать, если API вернул HTTP 500?

**Senior**

Мой порядок действий:

1. Зафиксировать запрос и ответ.
2. Сохранить время и Request ID.
3. Найти соответствующие Backend-логи.
4. Проверить исключение и зависимости.
5. Определить, произошёл ли бизнес-эффект.
6. Сформулировать подтверждённые факты.
7. Создать баг-репорт с диагностической информацией.

**Важно:** HTTP 500 не означает автоматически, что изменения в БД были отменены.

## 61. Чем отличаются 502, 503 и 504?

**Middle**

- **502** — шлюз или прокси получил непригодный ответ от upstream.
- **503** — сервис временно недоступен или не может обработать запрос.
- **504** — Gateway не дождался своевременного ответа upstream.

Для расследования важно определить, какой компонент сформировал ответ.

## 62. Как диагностировать Database Timeout?

**Senior**

Проверить:

- Состояние PostgreSQL.
- Сетевую доступность.
- Connection Pool.
- Активные запросы.
- Длительные транзакции.
- Блокировки.
- Метрики CPU и I/O.
- Настройки timeout.

Например:

```sql
SELECT
    pid,
    state,
    wait_event_type,
    wait_event,
    now() - query_start AS duration
FROM pg_stat_activity
WHERE state <> 'idle';
```

**Главное:** Database Timeout не означает автоматически медленный SQL.

## 63. Почему Kafka Consumer Lag может расти?

**Senior**

Возможные причины:

- Consumer медленно обрабатывает сообщения.
- БД или внешний сервис тормозит обработку.
- Недостаточно эффективного параллелизма.
- Происходят ошибки и повторные попытки.
- Consumer Group нестабильна.
- Поступает больше сообщений, чем обрабатывается.

Проверять нужно не только брокер, но и скорость бизнес-обработки.

## 64. Чем RabbitMQ Ready отличается от Unacked?

**Middle / Senior**

Ready — сообщения, доступные для доставки Consumer.

Unacked — сообщения, уже доставленные, но ещё не подтверждённые.

Большой Ready может означать нехватку обработки.

Большой Unacked может быть связан с медленной обработкой, зависанием Consumer или настройками Prefetch.

## 65. Чем Logs отличаются от Metrics и Traces?

**Middle / Senior**

| Источник | Что показывает |
|---|---|
| Logs | Конкретные события |
| Metrics | Численные показатели во времени |
| Traces | Путь выполнения операции через компоненты |

Например:

- Лог: `Database timeout`.
- Метрика: p95 вырос до 2 секунд.
- Trace: основное время потрачено на PostgreSQL span.

Для точной диагностики полезно сопоставлять все три источника.


Цель — определить, на каком уровне произошёл сбой.

### Пример ответа

Само существование процесса не доказывает его исправность.

## Сценарий 4. Сервис возвращает 504 после POST

**Вопрос:** Пользователь получил 504 при выдаче бонуса. Что проверять?

### Пример ответа

504 означает, что Gateway не дождался ответа upstream.

Но Backend мог успеть выполнить бизнес-операцию.

Поэтому нужно проверить:

1. Request ID.
2. Логи Gateway.
3. Логи Backend.
4. Состояние выдачи в БД.
5. Наличие события Kafka.
6. Возможные повторные запросы.
7. Идемпотентность операции.

**Главное:** не считать timeout доказательством отсутствия бизнес-эффекта.

## Сценарий 5. После нагрузки сервис завершился с кодом 137

**Вопрос:** Что это означает?

### Пример ответа

Код 137 часто связан с SIGKILL.

OOM является одной из возможных причин.

Я бы проверил:

```bash
free -h
```

```bash
journalctl -k -b
```

Если приложение в Docker:

```bash
docker inspect \
  --format '{{.State.ExitCode}} {{.State.OOMKilled}}' \
  bonus-service
```

Также нужно проверить лимит памяти контейнера и изменение потребления памяти во времени.

**Главное:** не объявлять OOM без подтверждения.

## Сценарий 6. PostgreSQL доступна по TCP, но приложение не может подключиться

**Вопрос:** `nc` на порт 5432 проходит успешно. Почему Backend всё равно получает ошибку?

### Возможные причины

- Неверный пользователь или пароль.
- Неверная база данных.
- Ошибка TLS.
- Ограничения доступа PostgreSQL.
- Исчерпание Connection Pool.
- Ошибка протокольной конфигурации.

### Что проверять?

```bash
nc -vz -w 3 postgres.internal 5432
```

При наличии утилиты:

```bash
pg_isready -h postgres.internal -p 5432
```

Далее — реальные ошибки клиента PostgreSQL и настройки подключения.

**Главный принцип:** TCP connectivity и успешная аутентификация в БД — разные проверки.

## Сценарий 7. После релиза появился большой Kafka Consumer Lag

**Вопрос:** Как будешь расследовать?

### Пример ответа

Сначала проверю, действительно ли скорость обработки отстаёт от скорости публикации.

Затем посмотрю:

- Lag по партициям.
- Consumer Group.
- Логи Consumer.
- Время обработки сообщений.
- PostgreSQL.
- CPU/RAM.
- Ошибки и retry.
- Изменения после релиза.

Команда:

```bash
kafka-consumer-groups.sh \
  --bootstrap-server kafka.internal:9092 \
  --describe \
  --group bonus-consumer-group
```

**Важно:** увеличение числа Consumer поможет не всегда. Параллелизм группы ограничивается в том числе количеством партиций.

## Сценарий 8. RabbitMQ Queue растёт, хотя Consumer запущены

**Вопрос:** Что проверять?

### Пример ответа

Проверю:

- Messages Ready.
- Messages Unacked.
- Количество Consumer.
- Скорость публикации.
- Скорость обработки.
- Prefetch.
- ACK/NACK.
- Ошибки бизнес-операций.
- Доступность зависимостей.

Команда:

```bash
rabbitmqctl list_queues \
  name messages_ready messages_unacknowledged consumers
```

Если Unacked велик, нужно исследовать текущую обработку и подтверждения.

Если Ready растёт, нужно выяснить, почему Consumer не успевают за Producer.

# Часть 8. Частые ошибки на собеседовании

| Ошибочное утверждение | Правильный ответ |
|---|---|
| Linux — это Ubuntu | Ubuntu — дистрибутив на основе ядра Linux |
| Terminal и Bash — одно и то же | Terminal — интерфейс, Bash — оболочка |
| chmod 755 позволяет всем изменять файл | Запись разрешена только владельцу через эти базовые биты |
| chmod 777 — нормальное решение Permission denied | Нужно предоставлять минимальные необходимые права |
| grep и find делают одно и то же | grep ищет в содержимом, find — файловые объекты |
| uniq убирает все повторения автоматически | uniq работает с соседними одинаковыми строками |
| Sleeping означает зависание | S часто является нормальным ожиданием |
| kill всегда принудительно завершает процесс | kill отправляет сигнал; обычно по умолчанию SIGTERM |
| SIGTERM и SIGKILL одинаковы | SIGTERM можно обработать, SIGKILL — нет |
| 137 всегда означает OOM | Это часто связано с SIGKILL, причины могут отличаться |
| Мало free RAM — значит закончилась память | Нужно учитывать available, кэш и другие метрики |
| Ping проверяет HTTP | Ping использует ICMP |
| Если порт открыт, API исправен | TCP connect не проверяет бизнес-логику |
| Curl exit code 0 означает HTTP 200 | Curl может получить HTTP 4xx/5xx и завершиться с кодом 0 |
| localhost внутри Docker — адрес хоста | Это loopback соответствующего сетевого namespace |
| `systemctl active` гарантирует рабочее API | Нужны health и функциональные проверки |
| 504 означает откат операции | Backend мог выполнить операцию до таймаута |
| HTTP 500 всегда связан с багом в коде | Возможны ошибки зависимостей и конфигурации |
| Kafka Lag всегда проблема брокера | Причина часто в скорости Consumer или его зависимостях |
| CrashLoopBackOff — первопричина сбоя | Это состояние повторных неуспешных запусков |

# Часть 10. Как отвечать на практические вопросы

Для ситуационных вопросов удобно использовать единую схему.

### 1. Уточнить симптомы

Что именно не работает?

Например:

```text
API returns HTTP 504
```

### 2. Определить возможные уровни сбоя

```text
Client
  ↓
Network
  ↓
Proxy
  ↓
Backend
  ↓
Database / Broker
```

### 3. Назвать конкретные проверки

Например:

```bash
curl -v URL
ss -lntp
journalctl -u service.service -n 100
```

### 4. Проверить гипотезы

Не объявлять причину без подтверждения.

### 5. Проверить бизнес-последствия

Особенно при изменяющих операциях:

- Нет ли дубликатов?
- Не потерялись ли данные?
- Не осталось ли неконсистентного состояния?
- Безопасен ли повтор запроса?

### Пример полного ответа

**Вопрос: Backend начал возвращать HTTP 504. Что будешь делать?**

> Сначала проверю, какой компонент вернул 504 и какой timeout сработал. Затем по Request ID найду связанные логи Gateway и Backend. Посмотрю длительность обработки, обращения к БД и внешним сервисам. Если обнаружится database timeout, отдельно проверю активные запросы, блокировки и Connection Pool. Для POST дополнительно проверю фактический бизнес-результат, потому что сервер мог выполнить операцию, несмотря на потерянный ответ. После этого сформулирую подтверждённую причину или передам разработчику собранные данные для дальнейшего расследования.
