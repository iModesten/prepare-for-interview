**Уровень:** Middle / Senior QA Engineer  
**Темы:** Process, PID, PPID, ps, top, pgrep, kill, signals, jobs, systemd, systemctl, journalctl, CPU, Memory, OOM

# Часть 1. Что такое процесс?

## 1. Process vs Program

**Program** — программа, представленная исполняемым кодом и другими необходимыми данными.

**Process** — выполняющийся экземпляр программы, которым управляет операционная система.

Например, на сервере установлено приложение:

```text
/opt/bonus-service/app
```

Когда оно запускается, Linux создаёт процесс.

```text
Program
   |
   | Execute
   v
Process
   |
   +-- PID
   +-- Memory
   +-- Threads
   +-- File Descriptors
   +-- Environment Variables
   +-- Security Credentials
   +-- Execution State
```

Одна программа может быть запущена несколько раз.

Каждый запущенный экземпляр обычно имеет свой PID.

### Что содержит процесс?

- Идентификатор процесса.
- Состояние выполнения.
- Виртуальное адресное пространство.
- Открытые файловые дескрипторы.
- Информацию о пользователе и группах.
- Переменные окружения.
- Один или несколько потоков.
- Связи с другими процессами.

### Краткий ответ для собеседования

> Процесс — это экземпляр выполняющейся программы. Операционная система выделяет ему идентификатор PID, управляет его состоянием, ресурсами и правами доступа. В Linux информацию о процессах можно получить с помощью ps, top, pgrep и виртуальной файловой системы /proc.

---

## 2. PID и PPID

**PID (Process ID)** — идентификатор процесса.

**PPID (Parent Process ID)** — идентификатор родительского процесса.

### Пример

```text
PID   PPID   COMMAND
1000     1   systemd
2500  1000   bonus-service
2600  2500   worker
```

Это условный пример, а не реальная таблица процессов.

Здесь:

- Процесс 2500 имеет родителя 1000.
- Процесс 2600 запущен процессом 2500.

### Зачем нужен PID?

Чтобы:

- Найти процесс.
- Проверить его состояние.
- Получить сведения о ресурсах.
- Отправить сигнал.
- Изучить связанные файлы и дескрипторы.

### Важные нюансы

1. PID уникален среди процессов в соответствующем PID namespace на момент использования.
2. После завершения процесса его PID может быть использован повторно.
3. В контейнере процесс может иметь другой PID, чем на хосте.
4. PID не является постоянным идентификатором приложения.

### Что такое PID 1?

В обычной Linux-системе PID 1 часто принадлежит системному init-процессу, например systemd.

В контейнере PID 1 может принадлежать самому приложению или контейнерному init-процессу.

Это важно для обработки сигналов и завершения дочерних процессов.

---

## 3. Process vs Thread

**Process** — отдельный контекст выполнения программы.

**Thread** — поток выполнения внутри процесса.

У одного процесса может быть несколько потоков.

### Пример

```text
Backend Process (PID 2500)
       |
       +-- Thread 1: HTTP requests
       +-- Thread 2: Background task
       +-- Thread 3: Worker
       +-- Thread 4: Worker
```

Потоки одного процесса используют общее адресное пространство, но имеют собственные состояния выполнения и стеки.

### Зачем это QA?

При высокой нагрузке Backend-приложение может создавать множество потоков.

Возможные проблемы:

- Блокировки.
- Deadlock.
- Thread starvation.
- Исчерпание Thread Pool.
- Повышенное потребление CPU.
- Зависание обработки запросов.

### Краткий ответ

> Процесс представляет выполняющееся приложение с собственным адресным пространством. Потоки — единицы выполнения внутри процесса, использующие общую память процесса. Поэтому потоки могут эффективно взаимодействовать, но требуют корректной синхронизации при доступе к общим данным.

# Часть 2. Просмотр процессов

## 4. ps — информация о процессах

**ps (Process Status)** показывает снимок состояния процессов.

### Посмотреть процессы текущего терминала

```bash
ps
```

### Посмотреть все процессы

```bash
ps -ef
```

Пример:

```text
UID       PID   PPID  C STIME TTY      TIME CMD
root        1      0  0 10:00 ?    00:00:03 /sbin/init
app      2500      1  2 10:01 ?    00:00:24 /opt/bonus-service/app
qa       3000   2900  0 10:05 pts/0 00:00:00 bash
```

### Основные поля

| Поле | Значение |
|---|---|
| UID | Пользователь процесса |
| PID | Идентификатор процесса |
| PPID | Родительский PID |
| C | Показатель использования CPU в данном формате |
| STIME | Время запуска |
| TTY | Связанный терминал |
| TIME | Накопленное CPU-время |
| CMD | Команда запуска |

### Другой распространённый вариант

```bash
ps aux
```

Он показывает процессы в BSD-формате с колонками вроде:

- USER.
- PID.
- %CPU.
- %MEM.
- VSZ.
- RSS.
- STAT.
- COMMAND.

### Какой вариант нужно знать?

Оба:

```bash
ps -ef
```

```bash
ps aux
```

**Важно:** `ps aux` и `ps -aux` не следует считать полностью эквивалентными формами. У procps есть различия между BSD- и UNIX-синтаксисом.

---

## 5. Найти процесс приложения

Предположим, на сервере запущен сервис:

```text
bonus-service
```

Можно попробовать:

```bash
ps aux | grep 'bonus-service'
```

Но здесь есть проблема.

В результат может попасть сам процесс `grep`.

### Более удобный вариант

```bash
pgrep -af 'bonus-service'
```

Где:

- `pgrep` — поиск процессов по имени или другим атрибутам.
- `-a` — показать командную строку.
- `-f` — искать по полной командной строке.

Пример результата:

```text
2500 /opt/bonus-service/app --env=test
```

### Что важно?

Поиск по полному имени команды может найти несколько процессов.

Например:

- Основной сервис.
- Worker того же приложения.
- Тестовый экземпляр.
- Другую команду с совпадающим аргументом.

Поэтому перед дальнейшими действиями следует убедиться, что найден правильный PID.

---

## 6. pgrep vs pkill

### pgrep

Ищет процессы.

```bash
pgrep -af 'bonus-service'
```

### pkill

Отправляет сигнал подходящим процессам.

Например:

```bash
pkill -TERM -f 'bonus-service'
```

**Важное предупреждение:** эта команда приведена для понимания синтаксиса, а не как рекомендация выполнять её на сервере.

`pkill -f` может совпасть сразу с несколькими процессами.

Поэтому на общих стендах безопаснее сначала определить конкретный PID и понять, кто управляет приложением.

### Для собеседования

> pgrep используется для поиска процессов, а pkill — для отправки сигналов процессам, соответствующим заданному условию. При использовании pkill нужно быть осторожным, поскольку один шаблон может соответствовать нескольким процессам.

---

## 7. Посмотреть конкретный PID

Если известен PID:

```text
2500
```

Можно выполнить:

```bash
ps -p 2500
```

### Подробная информация

```bash
ps -p 2500 -o pid,ppid,user,stat,etime,%cpu,%mem,cmd
```

### Что означают поля?

| Поле | Значение |
|---|---|
| pid | PID |
| ppid | Родительский PID |
| user | Пользователь |
| stat | Состояние |
| etime | Время с запуска процесса |
| %cpu | Использование CPU по методике ps |
| %mem | Доля физической памяти |
| cmd | Команда запуска |

### Для Backend QA

Это полезно, когда нужно узнать:

- Работает ли процесс.
- Как давно он запущен.
- Под каким пользователем.
- Не изменился ли PID после рестарта.
- Сколько CPU и памяти он потребляет.

## 8. Process Tree

Процессы образуют иерархию родительских и дочерних процессов.

Например:

```text
systemd
  |
  +-- bonus-service
  |      |
  |      +-- worker-1
  |      +-- worker-2
  |
  +-- nginx
  |
  +-- postgresql
```

### Посмотреть дерево

Если установлен `pstree`:

```bash
pstree -ap
```

### Для определённого процесса

```bash
pstree -ap 2500
```

### Через ps

```bash
ps -ejH
```

### Когда полезно?

Если приложение запускает дочерние процессы и один из них:

- Завис.
- Завершился.
- Потребляет слишком много ресурсов.
- Не завершился после остановки родителя.

# Часть 3. Состояния процессов

## 9. Основные состояния

В выводе ps можно увидеть поле STAT.

Основные состояния:

| Код | Состояние | Значение |
|---|---|---|
| R | Running / Runnable | Выполняется или готов к выполнению |
| S | Interruptible Sleep | Ожидает событие, может быть пробуждён |
| D | Uninterruptible Sleep | Ожидает операцию, часто связанную с I/O |
| T | Stopped | Остановлен сигналом управления заданиями |
| Z | Zombie | Завершился, но родитель ещё не забрал статус |
| I | Idle | Бездействующий поток ядра |

### Дополнительные символы

Иногда STAT содержит несколько символов:

```text
Sl
Ss
R+
```

Дополнительные символы могут описывать:

- Многопоточность.
- Статус лидера сессии.
- Принадлежность foreground process group.
- Особенности приоритета.

Для собеседования важнее всего понимать основные буквы.

---

## 10. Состояние R — Running

Процесс выполняется на CPU или готов к выполнению.

Пример:

```text
PID   STAT   COMMAND
2500  R      worker
```

### Важный нюанс

R не означает, что процесс непрерывно выполняется прямо сейчас.

Он может находиться в очереди планировщика и ожидать CPU.

### Для QA

Если много процессов постоянно находятся в R, это может свидетельствовать о нагрузке на CPU.

Но один показатель STAT недостаточен для полноценной диагностики.

---

## 11. Состояние S — Sleeping

Процесс ожидает некоторого события.

Например:

- Сетевые данные.
- Таймер.
- Новую задачу.
- Разблокировку ожидания.
- Сигнал.

### Пример

```text
PID   STAT   COMMAND
2500  S      bonus-service
```

### Нужно ли считать S ошибкой?

Нет.

Множество совершенно исправных процессов большую часть времени находятся в состоянии Sleeping.

Например, HTTP-сервис может ожидать новый запрос.

### Типичный вопрос

**Если процесс находится в S, значит он завис?**

Нет.

Это нормальное состояние ожидания. Для вывода о зависании нужны дополнительные признаки: отсутствие ответов, аномальные задержки, проблемы с потоками, логами или зависимостями.

---

## 12. Состояние D — Uninterruptible Sleep

D — состояние ожидания, часто связанное с операциями ввода-вывода.

Например:

- Доступ к диску.
- Проблемы с некоторыми файловыми системами.
- Зависшее I/O.
- Ожидание определённых операций ядра.

### Почему это важно?

Процесс в состоянии D может не реагировать немедленно даже на SIGKILL.

Сигнал может быть обработан только после выхода из соответствующего непрерываемого ожидания.

### Что проверять?

- Состояние файловой системы.
- Доступность сетевого хранилища.
- I/O delays.
- Системные логи.
- Ошибки диска.
- Состояние зависимостей.

### Важно

Нельзя автоматически считать любую задачу в D признаком неисправности диска.

Нужно анализировать контекст.

---

## 13. Zombie Process

**Zombie** — процесс, который уже завершил выполнение, но его родитель ещё не получил информацию о завершении через механизм ожидания.

В ps обозначается:

```text
Z
```

Или:

```text
<defunct>
```

### Как возникает?

```text
Parent Process
      |
      v
Child Process
      |
      v
Child exits
      |
      v
Parent has not collected exit status
      |
      v
Zombie
```

### Работает ли Zombie?

Нет.

Процесс уже не выполняет пользовательский код.

От него остаётся минимальная информация, необходимая для получения родителем статуса завершения.

### Можно ли устранить Zombie через kill -9?

Обычно нет.

Он уже завершился.

Нужно разобраться, почему родитель не забирает статус завершения дочернего процесса.

### Как найти Zombie?

```bash
ps -eo pid,ppid,stat,cmd |
  awk '$3 ~ /^Z/ {print}'
```

### Senior-нюанс

Массовое накопление Zombie может указывать на ошибку управления дочерними процессами.

Особенно важно это в контейнерах, где PID 1 должен корректно обрабатывать завершение дочерних процессов.

# Часть 4. top и анализ ресурсов

## 14. Что такое top?

**top** — интерактивная утилита мониторинга процессов и использования системных ресурсов.

Запуск:

```bash
top
```

Она позволяет наблюдать:

- CPU.
- Memory.
- Load Average.
- Количество процессов.
- Состояния процессов.
- Использование ресурсов отдельными процессами.

### Основные клавиши

| Клавиша | Действие |
|---|---|
| `q` | Выйти |
| `P` | Сортировать по CPU |
| `M` | Сортировать по памяти |
| `T` | Сортировать по накопленному CPU-времени |
| `1` | Переключить отображение CPU |
| `c` | Переключить формат отображения команды |

Поведение отдельных клавиш зависит от реализации top.

### Следить за конкретным PID

```bash
top -p 2500
```

### Для QA

Полезно во время нагрузочного тестирования или воспроизведения дефекта.

Можно наблюдать, не начинает ли приложение потреблять необычно много CPU или памяти.

---

## 15. Как читать вывод top?

Типичный вывод содержит информацию вида:

```text
top - 12:00:00 up 3 days
load average: 1.20, 0.80, 0.50

%Cpu(s): ...
MiB Mem : ...

PID   USER   PR  NI   VIRT   RES   SHR   S   %CPU   %MEM   TIME+  COMMAND
2500  app    20   0   1500m  250m   20m  S   75.0    3.2   10:20  bonus-service
```

### Важные поля

**PID**

Идентификатор процесса.

**%CPU**

Использование процессорного времени.

**%MEM**

Доля физической памяти системы.

**VIRT**

Размер виртуального адресного пространства процесса.

**RES**

Резидентная память, находящаяся в физической памяти.

**SHR**

Память, учитываемая как разделяемая.

**S**

Состояние процесса.

**TIME+**

Накопленное CPU-время.

### Важный нюанс

`%CPU` в top обычно оценивается на интервале обновления, а в ps показатель `%CPU` может представлять усреднение за время существования процесса.

Поэтому значения не обязательно совпадают.

---

## 16. Почему CPU может быть больше 100%?

В Linux процесс может иметь несколько потоков.

На многопроцессорной системе эти потоки могут выполняться параллельно.

В распространённом режиме отображения top:

```text
100% ≈ одно полностью занятое логическое CPU
```

Многопоточный процесс может показывать:

```text
250%
```

Это означает использование приблизительно 2,5 логических CPU в выбранном режиме отображения.

### Важно

top поддерживает разные режимы нормализации CPU.

Поэтому интерпретация процентов зависит от его настроек.

### Для QA

Если после запуска нагрузки использование CPU резко увеличилось, это повод проверить:

- Соответствует ли нагрузка ожидаемой.
- Не возникли ли циклы повторных попыток.
- Нет ли бесконечного цикла.
- Не происходит ли дорогая сериализация.
- Не увеличилось ли количество работающих потоков.
- Не изменилась ли производительность системы.

---

## 17. free — оперативная память

Команда:

```bash
free -h
```

Показывает использование RAM и Swap.

Пример:

```text
               total   used   free   shared  buff/cache  available
Mem:            16Gi    8Gi   1Gi       ...       7Gi        7Gi
Swap:            2Gi    0Gi   2Gi
```

### Поля

**total**

Общий объём памяти.

**used**

Оценка используемой памяти.

**free**

Свободная память, не занятая другими видами использования.

**buff/cache**

Память, используемая для буферизации и кэширования.

**available**

Оценка памяти, доступной новым приложениям без существенного использования Swap.

### Важный вопрос

**Если free показывает мало свободной памяти, значит на сервере проблема?**

Не обязательно.

Linux активно использует RAM для кэшей.

Поэтому нужно смотреть в том числе `available`, использование Swap и другие метрики.

---

## 18. RSS vs VIRT

### VIRT

Виртуальное адресное пространство процесса.

Может включать:

- Отображённые файлы.
- Зарезервированную память.
- Библиотеки.
- Выделенные области, не обязательно полностью находящиеся в RAM.

### RSS / RES

Резидентные страницы процесса, находящиеся в физической памяти.

### Пример

```text
VIRT = 2 GB
RES  = 300 MB
```

Это не означает, что приложение обязательно занимает 2 GB физической RAM.

### Важный нюанс

RES может включать разделяемые страницы.

Поэтому суммирование RES многих процессов не всегда даёт точную оценку уникально используемой ими памяти.

Для более детального анализа существуют PSS и другие метрики.

---

## 19. Что такое Load Average?

Load Average показывает усреднённую нагрузку на систему за периоды:

- 1 минута.
- 5 минут.
- 15 минут.

Посмотреть:

```bash
uptime
```

Пример:

```text
load average: 1.20, 0.80, 0.50
```

### Что учитывается?

В Linux Load Average учитывает задачи, готовые к выполнению, и задачи в некоторых состояниях непрерываемого ожидания.

Это не просто процент использования CPU.

### Пример интерпретации

Для системы с четырьмя доступными логическими CPU нагрузка 4 может соответствовать ситуации, когда система примерно полностью занята исполняемыми задачами.

Но высокая Load Average может быть связана и с I/O wait.

### Что важно?

Сравнивать Load Average с:

- Доступной вычислительной мощностью.
- CPU utilization.
- I/O.
- Количеством runnable задач.
- Наличием ограничений контейнера.

**Нельзя трактовать Load Average 5 как 5% CPU.**

---

# Часть 5. Сигналы и завершение процессов

## 20. Что такое Signal?

**Signal** — механизм уведомления процесса о событии.

Сигнал может передаваться:

- Ядром.
- Другим процессом.
- Командой пользователя.
- Терминалом.

Например, сигнал может означать:

- Требование завершиться.
- Прерывание.
- Остановку.
- Возобновление.
- Ошибку выполнения.

### Основные сигналы

| Сигнал | Номер на распространённых Linux-архитектурах | Назначение |
|---|---:|---|
| SIGTERM | 15 | Запросить завершение |
| SIGKILL | 9 | Принудительно завершить |
| SIGINT | 2 | Прерывание, часто Ctrl+C |
| SIGHUP | 1 | Исторически потеря терминала; приложение может трактовать как запрос reload |
| SIGSTOP | 19 | Приостановить выполнение |
| SIGCONT | 18 | Возобновить выполнение |

Числовые значения отдельных сигналов могут отличаться на разных архитектурах, поэтому в командах удобнее использовать символьные имена.

### Краткий ответ

> Signal — механизм уведомления процесса о событии. Например, SIGTERM запрашивает завершение, SIGKILL принудительно завершает процесс, а SIGINT часто отправляется при Ctrl+C. Процесс может обрабатывать некоторые сигналы, но SIGKILL и SIGSTOP нельзя перехватить или игнорировать.

---

## 21. Что делает kill?

Название команды может вводить в заблуждение.

**kill отправляет сигнал процессу.**

Команда не всегда означает немедленное принудительное завершение.

### По умолчанию

```bash
kill 2500
```

Обычно отправляет SIGTERM.

Эквивалентно:

```bash
kill -TERM 2500
```

Или на распространённых Linux-архитектурах:

```bash
kill -15 2500
```

### Важный нюанс

Успешная отправка SIGTERM не гарантирует мгновенное завершение.

Приложение может:

- Обработать сигнал.
- Начать корректное завершение.
- Завершать текущие запросы.
- Закрывать соединения.
- Фиксировать состояние.
- Игнорировать сигнал, если это допустимо.

---

## 22. SIGTERM — корректное завершение

**SIGTERM** обычно используется для запроса завершения процесса.

### Типичная последовательность

```text
Running Application
        |
        | SIGTERM
        v
Shutdown Handler
        |
        +-- Stop accepting new requests
        +-- Finish in-flight requests
        +-- Close connections
        +-- Release resources
        |
        v
Process exits
```

Это пример корректно реализованного graceful shutdown.

### Что такое Graceful Shutdown?

Это контролируемое завершение приложения с попыткой корректно закончить или отменить незавершённую работу.

### Для Backend QA

При остановке сервиса важно проверить:

- Перестаёт ли сервис принимать новые запросы.
- Что происходит с текущими запросами.
- Закрываются ли соединения.
- Сохраняются ли необходимые данные.
- Не возникают ли дубликаты после перезапуска.
- Корректно ли завершаются Consumer.

### Важный нюанс

SIGTERM не гарантирует graceful shutdown сам по себе.

Нужно, чтобы приложение реализовало соответствующую обработку.

---

## 23. SIGKILL — принудительное завершение

**SIGKILL** нельзя перехватить, заблокировать или игнорировать обычным способом.

Команда:

```bash
kill -KILL 2500
```

Распространённая запись:

```bash
kill -9 2500
```

### Что происходит?

Процесс не получает возможности выполнить обычный пользовательский shutdown handler.

Вследствие этого могут остаться:

- Незавершённые бизнес-операции.
- Неотправленные подтверждения.
- Неочищенное временное состояние.
- Незавершённые внешние действия.

При этом ресурсы процесса, управляемые ядром, обычно освобождаются при его окончательном завершении.

### Почему SIGKILL опасен?

Потому что он не позволяет приложению корректно завершить работу.

Например:

```text
Kafka Consumer
      |
      v
DB COMMIT successful
      |
      v
SIGKILL
      |
      v
Kafka offset not committed
      |
      v
Message may be processed again
```

### Для QA

SIGKILL иногда используют для проверки отказоустойчивости, но только в контролируемом тестовом окружении.

На общем сервере нельзя отправлять его без согласования.

---

## 24. SIGTERM vs SIGKILL

| Характеристика | SIGTERM | SIGKILL |
|---|---|---|
| Назначение | Запросить завершение | Принудительно завершить |
| Можно обработать приложением | Да | Нет |
| Можно игнорировать | Да | Нет |
| Позволяет graceful shutdown | При правильной реализации | Нет |
| Рекомендуемость | Обычный первый вариант | Последняя мера |
| Риск нарушения бизнес-обработки | Есть | Обычно выше |

### Готовый ответ для собеседования

> SIGTERM запрашивает у процесса завершение и позволяет приложению корректно закрыть соединения и закончить работу. SIGKILL принудительно завершает процесс без выполнения пользовательских обработчиков завершения. Поэтому сначала обычно используют SIGTERM, а SIGKILL — только при необходимости.

---

## 25. SIGINT и Ctrl+C

В интерактивном терминале:

```text
Ctrl+C
```

обычно отправляет SIGINT foreground process group.

Это не буквально то же самое, что SIGTERM.

Приложение может по-разному обрабатывать SIGINT и SIGTERM.

### Когда полезно?

Например, остановить:

```bash
tail -f app.log
```

или собственный тестовый процесс.

### Важно

Ctrl+C действует в контексте терминала и foreground process group.

Он не является универсальным способом завершить произвольный серверный процесс.

---

## 26. Проверить существование PID без завершения

Можно использовать:

```bash
kill -0 2500
```

Здесь сигнал 0 фактически не отправляется.

Выполняются проверки существования процесса и прав на отправку сигнала.

### Возможные результаты

Успешная проверка означает, что соответствующая цель существует и операция разрешена в данном контексте.

Ошибка может означать:

- Процесс отсутствует.
- Недостаточно прав.

### Важный нюанс

Это не полноценный health check приложения.

Процесс может существовать, но не отвечать на HTTP-запросы.

Также между проверкой и последующим действием PID может завершиться или быть использован повторно.

# Часть 6. Фоновые процессы

## 27. Запуск команды в Background

В Bash оператор `&` запускает команду в фоне относительно текущей оболочки.

Пример:

```bash
sleep 120 &
```

Команда создаёт процесс, который ожидает 120 секунд.

Shell может сразу вернуть управление терминалу.

### Получить PID

```bash
echo $!
```

`$!` — PID последней асинхронной команды или задания, запущенного текущей оболочкой, с нюансами для составных команд.

### Пример

```bash
sleep 120 &
PID=$!
echo "$PID"
```

Эту конструкцию используем в безопасной практике.

---

## 28. jobs, fg и bg

### jobs

Показывает задания, которыми управляет текущая интерактивная оболочка.

```bash
jobs -l
```

### Ctrl+Z

Обычно отправляет SIGTSTP foreground-заданию, из-за чего оно может остановиться.

### bg

Продолжает остановленное задание в фоне.

```bash
bg
```

### fg

Возвращает задание на передний план.

```bash
fg
```

### Пример

```text
Запущен процесс
      |
      v
Ctrl+Z
      |
      v
Stopped
      |
      v
bg
      |
      v
Running in background
      |
      v
fg
      |
      v
Running in foreground
```

### Важный нюанс

`jobs` относится к заданиям текущего Shell.

Он не показывает все процессы операционной системы.

Для этого используют `ps` и другие инструменты.

---

## 29. nohup

**nohup** запускает команду с игнорированием SIGHUP.

Например:

```bash
nohup ./test-script.sh > test-script.log 2>&1 &
```

### Для чего?

Чтобы процесс не завершался только из-за получения SIGHUP при определённых сценариях закрытия терминала.

### Но гарантирует ли nohup, что процесс переживёт всё?

Нет.

Он не защищает от:

- SIGKILL.
- Сбоя системы.
- Ограничений systemd.
- Политик контейнера.
- Других сигналов и проблем.

Для постоянно работающих сервисов лучше использовать штатный менеджер сервисов или оркестратор.

# Часть 7. Exit Codes

## 30. Что такое Exit Code?

**Exit Code** — код завершения процесса.

В Shell обычно:

```text
0 — успешное завершение
не 0 — иной результат, часто ошибка
```

Но точное значение зависит от команды.

### Пример

```bash
ls /tmp
echo $?
```

`$?` содержит exit status предыдущей команды.

### Важный нюанс

Код завершения `0` не гарантирует, что бизнес-операция корректна.

Например, скрипт может завершиться успешно, но не выполнить всех ожидаемых проверок из-за логической ошибки.

---

## 31. Exit Code 137 и 143

В Bash при завершении процесса сигналом часто используется соглашение:

```text
Exit Status = 128 + Signal Number
```

### SIGKILL

На распространённых Linux-архитектурах:

```text
128 + 9 = 137
```

### SIGTERM

```text
128 + 15 = 143
```

### Важный вопрос

**Если процесс завершился с кодом 137, значит его убил OOM Killer?**

Не обязательно.

137 часто указывает на завершение через SIGKILL.

SIGKILL мог быть отправлен:

- Linux OOM Killer.
- Контейнерным runtime или оркестратором.
- Администратором.
- Другим процессом.

Кроме того, приложение может завершиться самостоятельно с определённым кодом.

Поэтому код 137 сам по себе не является доказательством OOM.

### Как проверить?

- Логи приложения.
- Системные логи.
- Kernel messages.
- События оркестратора.
- Метрики памяти.
- Сведения о завершении процесса.

# Часть 8. systemd и systemctl

## 32. Что такое systemd?

**systemd** — набор компонентов управления системой и сервисами, используемый во многих Linux-дистрибутивах.

Одна из основных задач systemd — управление жизненным циклом служб.

Например:

- Запуск.
- Остановка.
- Перезапуск.
- Контроль состояния.
- Управление зависимостями.
- Автоматический рестарт.
- Интеграция с журналированием.

### Что такое Unit?

Unit — объект конфигурации, которым управляет systemd.

Примеры типов:

- service.
- socket.
- timer.
- mount.
- target.

Для Backend QA чаще всего интересны Service Units.

### Важный нюанс

Не каждый Linux-сервер или контейнер использует systemd.

Например, внутри минимального Docker-контейнера PID 1 часто принадлежит приложению, а не systemd.

Поэтому `systemctl` может быть недоступен или не работать.

---

## 33. systemctl status

Команда:

```bash
systemctl status bonus-service.service
```

Показывает состояние сервиса.

Пример:

```text
● bonus-service.service - Bonus Service
     Loaded: loaded
     Active: active (running)
   Main PID: 2500
```

### Что нужно смотреть?

- Loaded.
- Active.
- Main PID.
- Причины ошибок.
- Недавние сообщения журнала.
- Информацию о рестартах, если доступна.

### Возможные состояния

| Состояние | Значение |
|---|---|
| active | Unit активен |
| inactive | Unit неактивен |
| failed | Unit завершился с ошибкой или не смог успешно запуститься |
| activating | Выполняется запуск |
| deactivating | Выполняется остановка |

Для service-unit также могут отображаться уточняющие состояния, например running или exited.

### Важно

`active (running)` не гарантирует, что HTTP API отвечает корректно.

Процесс может существовать, но:

- Не принимать запросы.
- Не иметь соединения с БД.
- Находиться в deadlock.
- Возвращать HTTP 500.

Поэтому необходимы дополнительные проверки работоспособности.

---

## 34. systemctl is-active

```bash
systemctl is-active bonus-service.service
```

Проверяет, активен ли сервис.

Пример:

```text
active
```

### Для чего полезно?

- Быстрая диагностика.
- Использование в скриптах.
- Проверка состояния после развёртывания.

### Важный нюанс

Команда проверяет состояние systemd unit, а не полную функциональную исправность приложения.

---

## 35. systemctl is-enabled

```bash
systemctl is-enabled bonus-service.service
```

Проверяет конфигурацию включения unit, например его участие в автоматическом запуске.

### Отличие от is-active

**is-active** — состояние сейчас.

**is-enabled** — конфигурация включения unit.

### Пример

Сервис может быть:

```text
active
disabled
```

Это означает, что он работает сейчас, но не обязательно включён для запуска через соответствующую конфигурацию.

### Типичный вопрос

**Может ли disabled service работать?**

Да.

Его могли запустить вручную или через другой механизм.

---

## 36. Основные команды systemctl

| Команда | Назначение |
|---|---|
| `status` | Посмотреть состояние |
| `is-active` | Проверить активность |
| `is-enabled` | Проверить конфигурацию включения |
| `start` | Запустить |
| `stop` | Остановить |
| `restart` | Перезапустить |
| `reload` | Перезагрузить конфигурацию в поддерживаемых сервисах |
| `cat` | Показать конфигурацию unit |
| `show` | Показать свойства unit |
| `list-units` | Показать units |

### Примеры диагностических команд

```bash
systemctl status bonus-service.service
```

```bash
systemctl cat bonus-service.service
```

```bash
systemctl show bonus-service.service \
  -p MainPID -p ActiveState -p SubState
```

### Команды, изменяющие состояние

```bash
sudo systemctl restart bonus-service.service
```

```bash
sudo systemctl stop bonus-service.service
```

**Не выполняй команды управления чужими сервисами без разрешения.**

На общих тестовых стендах это может прервать тесты других команд.

---

## 37. Restart vs Reload vs Daemon-Reload

Эти команды часто путают.

### restart

```bash
systemctl restart bonus-service.service
```

Останавливает и снова запускает сервис.

### reload

```bash
systemctl reload bonus-service.service
```

Запрашивает перезагрузку конфигурации работающего сервиса, если он поддерживает такую операцию.

### daemon-reload

```bash
systemctl daemon-reload
```

Перечитывает конфигурацию менеджера systemd, включая unit-файлы.

### Главное отличие

**daemon-reload не означает restart приложения.**

Если был изменён unit-файл, может понадобиться перечитать конфигурацию systemd.

Но для применения изменений приложением может дополнительно понадобиться его перезапуск или поддерживаемый reload.

### Готовый ответ

> restart перезапускает сервис, reload просит сам сервис перечитать конфигурацию, а daemon-reload заставляет systemd перечитать собственные unit-файлы. Это разные операции.

---

## 38. Что такое Service Unit File?

Это конфигурационный файл, описывающий управление сервисом.

Пример:

```ini
[Unit]
Description=Bonus Service
After=network.target

[Service]
Type=simple
User=app
WorkingDirectory=/opt/bonus-service
ExecStart=/opt/bonus-service/app
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

### Основные параметры

**Description**

Описание сервиса.

**After**

Порядок запуска относительно других units.

**User**

Пользователь, под которым запускается сервис.

**WorkingDirectory**

Рабочая директория процесса.

**ExecStart**

Команда запуска.

**Restart**

Политика перезапуска.

**RestartSec**

Задержка перед повторным запуском.

### Важный нюанс

`After=network.target` задаёт порядок, но само по себе не гарантирует, что внешняя сеть или удалённая база данных уже доступны.

Также `After=` не означает жёсткую зависимость существования другого unit.

Для зависимостей используются дополнительные параметры, например `Requires=` и `Wants=`.

# Часть 9. journalctl — логи сервисов

## 39. Что такое journalctl?

**journalctl** — утилита просмотра записей systemd journal.

Она позволяет просматривать:

- Сообщения сервисов.
- Системные события.
- Сообщения ядра.
- Журналы определённого периода.

### Посмотреть логи сервиса

```bash
journalctl -u bonus-service.service
```

### Последние 100 записей

```bash
journalctl -u bonus-service.service -n 100
```

### Следить за новыми записями

```bash
journalctl -u bonus-service.service -f
```

### Логи с определённого времени

```bash
journalctl -u bonus-service.service \
  --since "2026-10-09 10:00:00"
```

### Только текущая загрузка системы

```bash
journalctl -b -u bonus-service.service
```

### Без интерактивного постраничного просмотра

```bash
journalctl -u bonus-service.service \
  -n 100 --no-pager
```

### Важный нюанс

Доступ к журналу может быть ограничен правами.

Также не все приложения пишут логи в systemd journal.

Например, сервис в Docker может писать в stdout/stderr контейнера, а его журналы будут доступны через механизмы контейнерной платформы.

---

## 40. systemctl status vs journalctl

### systemctl status

Показывает текущее состояние сервиса и часть недавних диагностических записей.

### journalctl

Предоставляет более гибкую работу с журналами.

Например:

- Фильтрация по времени.
- Поиск определённого сервиса.
- Наблюдение в реальном времени.
- Просмотр записей предыдущей загрузки, если они сохранились.

### Для Backend QA

Обычно удобно начать с:

```bash
systemctl status bonus-service.service
```

А затем:

```bash
journalctl -u bonus-service.service -n 100
```

Это часто быстрее, чем сразу пытаться найти произвольный файл логов.

# Часть 10. /proc — информация о процессах

## 41. Что такое /proc?

`/proc` — виртуальная файловая система, предоставляющая информацию о процессах и ядре Linux.

Для процесса с PID 2500 может существовать:

```text
/proc/2500/
```

### Что там можно найти?

| Путь | Информация |
|---|---|
| `/proc/PID/status` | Состояние и сведения о процессе |
| `/proc/PID/cmdline` | Аргументы запуска |
| `/proc/PID/environ` | Переменные окружения |
| `/proc/PID/fd` | Открытые файловые дескрипторы |
| `/proc/PID/limits` | Ограничения ресурсов |

### Пример

```bash
cat /proc/2500/status
```

Можно увидеть:

```text
Name:   bonus-service
State:  S (sleeping)
Pid:    2500
PPid:   1
Threads: 12
```

### Важный нюанс

Процесс может завершиться между проверками.

Тогда директория `/proc/PID` исчезнет.

Доступ к отдельным данным `/proc` также может быть ограничен настройками безопасности.

## 42. Открытые File Descriptors

**File Descriptor (FD)** — числовой дескриптор, через который процесс обращается к открытым объектам.

Это могут быть:

- Файлы.
- Сокеты.
- Каналы.
- Другие файловые объекты.

### Типичные значения

```text
0 — STDIN
1 — STDOUT
2 — STDERR
```

### Посмотреть дескрипторы

```bash
ls -l /proc/2500/fd
```

### Если установлен lsof

```bash
lsof -p 2500
```

### Когда это полезно?

Например, приложение постепенно перестаёт создавать новые сетевые соединения.

Возможная причина — утечка файловых дескрипторов.

### Что проверить?

- Количество открытых дескрипторов.
- Растёт ли оно со временем.
- Какие объекты остаются открытыми.
- Ограничения процесса.

### Посмотреть лимиты

```bash
cat /proc/2500/limits
```

Или для текущей оболочки:

```bash
ulimit -n
```

### Важно

Значение `ulimit -n` текущего Shell не обязательно совпадает с ограничением уже запущенного systemd-сервиса.

# Часть 11. OOM и проблемы памяти

## 43. Что такое OOM?

**OOM (Out Of Memory)** — ситуация, при которой система или ограниченная область памяти не может удовлетворить требования к выделению памяти.

В Linux существуют механизмы OOM handling, включая OOM Killer.

### Что делает OOM Killer?

При определённых условиях ядро может завершить выбранный процесс для освобождения памяти.

### Типичные симптомы

- Приложение неожиданно завершилось.
- PID изменился после рестарта.
- Контейнер перезапустился.
- В логах есть сообщения о нехватке памяти.
- В Kubernetes указан Reason: OOMKilled.
- Приложение завершилось через SIGKILL.

### Важный нюанс

OOM может возникать:

- На уровне всего хоста.
- В пределах cgroup.
- При превышении лимита памяти контейнера.

Поэтому свободная память хоста не всегда объясняет, почему контейнер был убит.

---

## 44. Как диагностировать подозрение на OOM?

### Проверить память

```bash
free -h
```

### Проверить процесс

```bash
ps -p 2500 -o pid,%mem,rss,vsz,cmd
```

### Проверить системные сообщения

На системе с systemd:

```bash
journalctl -k -b
```

При наличии прав можно искать сообщения об OOM:

```bash
journalctl -k -b --no-pager |
  grep -Ei 'out of memory|oom|killed process'
```

### Проверить платформу

Если приложение находится в контейнере или Kubernetes, нужно проверить соответствующие события и ограничения.

### Что важно для QA?

Одного сообщения:

```text
Exit code 137
```

недостаточно для уверенного заключения об OOM.

Нужно собрать подтверждающие данные.

## 45. Что такое Memory Leak?

**Memory Leak** — ситуация, когда приложение сохраняет или теряет возможность освобождать больше памяти, чем необходимо, что приводит к нежелательному росту её использования.

### Пример

```text
Start:   200 MB
10 min:  300 MB
20 min:  450 MB
30 min:  700 MB
```

Такой рост может быть признаком проблемы.

Но не всегда.

### Почему рост RSS не обязательно означает утечку?

Причины могут быть другими:

- Кэширование.
- Прогрев приложения.
- Создание новых соединений.
- Работа сборщика мусора.
- Буферизация.
- Изменение нагрузки.

### Как тестировать?

1. Зафиксировать начальное состояние.
2. Создать контролируемую нагрузку.
3. Наблюдать память.
4. Снизить нагрузку.
5. Проверить поведение после стабилизации.
6. Повторить сценарий.
7. Сопоставить наблюдения с метриками приложения.

### Senior QA-подход

Нельзя объявлять memory leak только по одному снимку top.

Нужны временной ряд и понимание характера использования памяти.

## 50. Сценарий: после SIGTERM Consumer повторно обработал событие

### Условие

Kafka Consumer получил сообщение, обновил БД и завершился после SIGTERM.

После перезапуска то же событие снова обработалось.

### Возможная последовательность

```text
Kafka Message
     |
     v
Consumer receives
     |
     v
DB COMMIT
     |
     v
SIGTERM
     |
     v
Consumer exits
     |
     v
Kafka offset not committed
     |
     v
Message redelivered after restart
```

### Что здесь проверять?

- Реализован ли graceful shutdown.
- Завершаются ли текущие обработки.
- Фиксируются ли безопасные offsets.
- Есть ли идемпотентность.
- Не создаётся ли повторный бизнес-эффект.
- Корректно ли обрабатывается rebalance.

### Главный вывод

Даже корректное завершение процесса не всегда исключает повторное получение сообщений.

Систему нужно проектировать и тестировать с учётом выбранных гарантий доставки.

# Часть 13. Docker и Kubernetes — базовая связь с процессами

## 51. Процессы внутри Docker

Контейнеры используют механизмы изоляции Linux, включая namespaces и cgroups.

Процессы контейнера продолжают исполняться ядром хостовой системы.

### Полезные команды Docker

Если Docker установлен и есть права:

```bash

```

```bash
docker logs container-name
```

Посмотреть логи.

```bash

```

Посмотреть процессы контейнера.

```bash

```

Посмотреть статистику ресурсов.

### Важный нюанс

PID процесса внутри контейнера может отличаться от PID на хосте из-за PID namespace.

---

## 52. SIGTERM и завершение контейнера

При обычной остановке контейнерная платформа обычно сначала запрашивает завершение основного процесса, затем после установленного времени ожидания может применить SIGKILL.

### Почему это важно?

Приложение должно корректно обрабатывать остановку:

- Завершать текущие запросы.
- Закрывать соединения.
- Прекращать получение новых сообщений.
- Сохранять безопасный прогресс обработки.

### Что особенно важно для Kafka Consumer?

Если контейнер завершился до Kafka offset commit, возможна повторная обработка.

Следовательно, нужно тестировать как штатное завершение, так и аварийное.

### Что особенно важно для RabbitMQ Consumer?

Если сообщение обработано, но ACK ещё не отправлен, RabbitMQ может повторно доставить его после потери соединения.

# Часть 14. Вопросы для собеседования

## 53. Что такое процесс?

Экземпляр выполняющейся программы, которым управляет операционная система.

## 54. Что такое PID?

Идентификатор процесса.

## 55. Что такое PPID?

Идентификатор родительского процесса.

## 56. Чем Process отличается от Thread?

Процесс имеет собственный контекст выполнения и адресное пространство, а потоки одного процесса разделяют его память и могут выполняться параллельно.

## 57. Как посмотреть все процессы?

```bash
ps -ef
```

Или:

```bash
ps aux
```

## 58. Как найти конкретный процесс?

```bash
pgrep -af 'bonus-service'
```

## 59. Как посмотреть процесс по PID?

```bash
ps -p 2500 -o pid,ppid,user,stat,%cpu,%mem,cmd
```

## 60. Что такое top?

Утилита интерактивного мониторинга процессов и ресурсов системы.

## 61. Что означают R, S, D, T и Z?

- R — Running/Runnable.
- S — Interruptible Sleep.
- D — Uninterruptible Sleep.
- T — Stopped.
- Z — Zombie.

## 62. Что такое Zombie Process?

Завершившийся процесс, информацию о завершении которого родитель ещё не забрал.

## 63. Можно ли исправить Zombie через kill -9?

Обычно нет. Процесс уже завершился. Нужно анализировать поведение родительского процесса.

## 64. Что делает команда kill?

Отправляет сигнал процессу или группе процессов в зависимости от аргументов.

## 65. Чем SIGTERM отличается от SIGKILL?

SIGTERM запрашивает завершение и может быть обработан приложением. SIGKILL принудительно завершает процесс и не может быть перехвачен.

## 66. Что делает Ctrl+C?

Обычно отправляет SIGINT foreground process group в терминале.

## 67. Что делает Ctrl+Z?

Обычно отправляет SIGTSTP, приостанавливая foreground-задание.

## 68. Как вернуть задачу на передний план?

```bash
fg
```

## 69. Что делает символ &?

Запускает команду в фоне относительно текущей оболочки.

## 70. Что такое Exit Code?

Числовой результат завершения процесса или команды.

## 71. Что может означать Exit Code 137?

Часто завершение через SIGKILL. Причиной может быть OOM или другое принудительное завершение.

## 72. Что такое OOM Killer?

Механизм Linux, который при определённых условиях нехватки памяти может завершать процессы для освобождения ресурсов.

## 73. Как посмотреть память?

```bash
free -h
```

## 74. Что такое RSS?

Оценка резидентной памяти процесса, находящейся в физической RAM.

## 75. Что такое Load Average?

Усреднённая системная нагрузка за 1, 5 и 15 минут, учитывающая runnable задачи и некоторые непрерываемые ожидания.

## 76. Что такое systemd?

Система и набор компонентов управления Linux-сервисами и другими units.

## 77. Как проверить состояние сервиса?

```bash
systemctl status bonus-service.service
```

## 78. Чем is-active отличается от is-enabled?

is-active проверяет текущее состояние, is-enabled — конфигурацию включения unit.

## 79. Чем restart отличается от reload?

restart перезапускает сервис, reload запрашивает перечитывание конфигурации в поддерживаемом режиме.

## 80. Что делает daemon-reload?

Заставляет systemd перечитать собственную конфигурацию units. Не перезапускает автоматически приложение.

## 81. Как посмотреть логи systemd-сервиса?

```bash
journalctl -u bonus-service.service
```

## 82. Как смотреть новые логи сервиса?

```bash
journalctl -u bonus-service.service -f
```

## 83. Что такое /proc?

Виртуальная файловая система Linux, содержащая информацию о процессах и ядре.

## 84. Что такое File Descriptor?

Числовой дескриптор, через который процесс работает с открытым файловым объектом, сокетом или другим ресурсом.

## 85. Почему работающий процесс может не отвечать на HTTP-запросы?

Из-за зависания, блокировки, недоступности зависимостей, неправильного сетевого порта, перегрузки или другой внутренней проблемы.

# Часть 15. Частые ошибки на собеседовании

**Ошибка:** «Если процесс найден через ps, приложение работает нормально».

Правильно: процесс может существовать, но не отвечать на запросы или быть в некорректном состоянии.

**Ошибка:** «kill всегда немедленно завершает процесс».

Правильно: kill отправляет сигнал. По умолчанию обычно SIGTERM.

**Ошибка:** «SIGTERM и SIGKILL одинаковые».

Правильно: SIGTERM позволяет приложению выполнить graceful shutdown, SIGKILL — нет.

**Ошибка:** «Процесс в Sleeping завис».

Правильно: состояние S часто является нормальным ожиданием.

**Ошибка:** «Zombie — это работающий процесс, который использует много CPU».

Правильно: Zombie уже завершился, но ещё не был окончательно обработан родителем.

**Ошибка:** «SIGKILL всегда мгновенно устраняет процесс в состоянии D».

Правильно: процесс в непрерываемом ожидании может не завершиться немедленно.

**Ошибка:** «137 точно означает OOM».

Правильно: 137 часто связан с SIGKILL, который может иметь разные причины.

**Ошибка:** «Если Linux показывает мало free memory, память закончилась».

Правильно: Linux использует RAM для кэширования; нужно учитывать available, swap и другие показатели.

**Ошибка:** «systemctl is-enabled показывает, работает ли сервис».

Правильно: is-enabled относится к конфигурации включения, is-active — к текущему состоянию.

**Ошибка:** «daemon-reload перезапускает сервис».

Правильно: daemon-reload перечитывает конфигурацию менеджера systemd.

**Ошибка:** «active (running) означает, что API полностью исправно».

Правильно: необходимы дополнительные health и функциональные проверки.

```bash
PID=$!
```

Показать PID:

```bash
echo "$PID"
```

Проверить процесс:

```bash
ps -p "$PID" -o pid,ppid,stat,etime,cmd
```

### Ожидаемый результат

Процесс `sleep` существует и обычно находится в состоянии ожидания.

---

## Задание 3. Посмотреть процесс через top

Пока sleep работает:

```bash
top -p "$PID"
```

Для выхода:

```text
q
```

### Что наблюдаем?

У sleep обычно очень низкое использование CPU, поскольку он ожидает завершения заданного интервала.

---

## Задание 4. Проверить процесс без завершения

```bash
kill -0 "$PID"
echo $?
```

При успешной проверке ожидается код 0.

---

## Задание 5. Отправить SIGTERM собственному процессу

```bash
kill -TERM "$PID"
```

Проверить:

```bash
ps -p "$PID"
```

Процесс должен завершиться, хотя Shell может ещё сохранять информацию о задании до вызова wait.

Убрать завершённое задание из таблицы заданий оболочки:

```bash
wait "$PID" || true
```

### Что важно понять?

SIGTERM отправляет запрос завершения.

В случае `sleep` обычное поведение — завершение процесса.

---

## Задание 6. Посмотреть общие ресурсы

```bash
uptime
```

```bash
free -h
```

```bash
top
```

Обратить внимание:

- Load Average.
- CPU.
- Memory.
- Swap.
- Process States.

## Задание 7. Посмотреть системные сервисы

Если доступен systemd:

```bash
systemctl list-units --type=service
```

Выбрать разрешённый для просмотра сервис и выполнить:

```bash
systemctl status service-name.service
```

**Важно:** это упражнение предполагает только просмотр состояния, без остановки или перезапуска сервиса.

---

## Задание 8. Посмотреть журнал сервиса

```bash
journalctl -u service-name.service -n 30
```

Если хватает прав, можно увидеть последние записи выбранного сервиса.

# Мини-шпаргалка Backend QA

| Задача | Команда |
|---|---|
| Все процессы | `ps aux` |
| Подробный список процессов | `ps -ef` |
| Найти сервис | `pgrep -af 'service-name'` |
| Проверить PID | `ps -p 2500 -o pid,ppid,stat,cmd` |
| Дерево процессов | `pstree -ap` |
| Мониторинг CPU/RAM | `top` |
| Мониторинг PID | `top -p 2500` |
| Общая память | `free -h` |
| Общая нагрузка | `uptime` |
| Отправить SIGTERM | `kill -TERM 2500` |
| Отправить SIGKILL | `kill -KILL 2500` |
| Проверить PID | `kill -0 2500` |
| Фоновые задания Shell | `jobs -l` |
| Состояние сервиса | `systemctl status service.service` |
| Проверить активность | `systemctl is-active service.service` |
| Посмотреть unit | `systemctl cat service.service` |
| Последние логи сервиса | `journalctl -u service.service -n 100` |
| Следить за логами | `journalctl -u service.service -f` |
| Информация о процессе | `cat /proc/2500/status` |
| Лимиты процесса | `cat /proc/2500/limits` |
| Открытые дескрипторы | `lsof -p 2500` |
