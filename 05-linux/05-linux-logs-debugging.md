# Часть 1. Основы диагностики

## 1. Что такое Troubleshooting?

**Troubleshooting** — систематический процесс поиска и локализации неисправности.

В работе Backend QA он включает:

1. Определение проблемы.
2. Сбор информации.
3. Формирование гипотез.
4. Проверку гипотез.
5. Локализацию причины.
6. Подтверждение исправления.

### Пример

При вызове:

```http
POST /api/bonuses/issue
```

получили:

```http
HTTP/1.1 500 Internal Server Error
```

Это только симптом.

Причиной могут быть:

- Исключение в коде.
- Недоступность PostgreSQL.
- Ошибка SQL.
- Исчерпание пула соединений.
- Неожиданное значение в данных.
- Нарушение бизнес-инварианта.
- Ошибка конфигурации.
- Ошибка внешнего сервиса.

### Правильный подход

Не стоит сразу делать вывод:

> Это баг Backend, потому что вернулся 500.

Лучше определить, на каком уровне возникла ошибка, что её вызвало и какие данные это подтверждают.

### Краткий ответ для собеседования

> При диагностике Backend-проблемы я сначала воспроизвожу её и фиксирую условия, затем определяю этап сбоя, анализирую HTTP-ответ, логи по Request ID и связанные зависимости. После этого проверяю гипотезы и фиксирую фактическую причину либо наиболее вероятную область проблемы с подтверждающими данными.

---

## 2. Симптом, причина и последствие

Эти понятия важно различать.

### Симптом

То, что наблюдает пользователь или QA.

Например:

```text
HTTP 504 Gateway Timeout
```

### Причина

Проблема, из-за которой возник симптом.

Например:

```text
SQL-запрос ожидал блокировку
```

### Последствие

Результат возникшей проблемы.

Например:

```text
Пользователь повторил POST, и возникла двойная выдача бонуса
```

### Схема

```text
Долгая транзакция
       |
       v
Блокировка в PostgreSQL
       |
       v
Backend долго ждёт SQL
       |
       v
Gateway возвращает 504
       |
       v
Клиент повторяет запрос
       |
       v
Возможен дублирующий бизнес-эффект
```

Здесь 504 — симптом.

Блокировка — одна из возможных причин задержки.

Повторная выдача — потенциальное последствие.

### Важный нюанс

Одна и та же ошибка HTTP может иметь совершенно разные причины.

Поэтому диагностировать необходимо не только статус-код, но и весь путь выполнения запроса.

---

## 3. Основной алгоритм диагностики

Для большинства Backend-проблем подходит следующий порядок.

### Шаг 1. Зафиксировать симптомы

- Что не работает?
- Какой endpoint?
- Какой HTTP-метод?
- Какой ответ?
- Когда возникла проблема?
- Воспроизводится ли повторно?
- Затронут один пользователь или многие?

### Шаг 2. Определить уровень ошибки

- DNS.
- TCP.
- TLS.
- Reverse Proxy.
- Backend.
- Database.
- Message Broker.
- Внешний сервис.

### Шаг 3. Найти связанные логи

- Request ID.
- Trace ID.
- Временной интервал.
- Название сервиса.
- Идентификатор операции.

### Шаг 4. Проверить состояние системы

- Работает ли процесс?
- Есть ли доступный порт?
- Хватает ли CPU и памяти?
- Не закончился ли диск?
- Работают ли зависимости?

### Шаг 5. Проверить бизнес-результат

Особенно важно для изменяющих операций:

- Создалась ли запись в БД?
- Изменился ли статус?
- Увеличился ли счётчик?
- Было ли опубликовано событие?
- Нет ли дубликатов?

### Шаг 6. Сформулировать вывод

Отделить подтверждённые факты от предположений.

Например:

**Факт:** API вернул 504.

**Факт:** в логах Backend обработка запроса завершилась после таймаута Gateway.

**Гипотеза:** запрос задержался из-за ожидания блокировки БД.

**Подтверждение:** в `pg_stat_activity` наблюдалось ожидание типа `Lock` для связанной транзакции.

# Часть 2. Где искать логи?

## 4. Основные источники логов

В Linux логи могут находиться в разных местах.

| Источник | Где искать |
|---|---|
| Обычный файл | `cat`, `less`, `tail`, `grep` |
| systemd journal | `journalctl` |
| Docker Container | `docker logs` |
| Docker Compose | `docker compose logs` |
| Kubernetes Pod | `kubectl logs` |
| Nginx | Настроенные access/error logs или journal |
| PostgreSQL | Настроенный logging destination |
| Централизованная система | Loki, OpenSearch, Elasticsearch и др. |

### Важный нюанс

Не стоит считать `/var/log` единственным местом хранения логов.

Современное приложение может:

- Писать в stdout.
- Писать в stderr.
- Передавать логи через sidecar или agent.
- Использовать systemd journal.
- Передавать логи в централизованную платформу.

### С чего начать?

С определения, **как именно запущено приложение**.

Если через systemd — начать с `systemctl` и `journalctl`.

Если через Docker — с `docker logs`.

Если через Kubernetes — с `kubectl logs`, `kubectl describe` и доступной системы наблюдаемости.

---

## 5. Уровни логирования

В приложениях часто встречаются:

| Level | Назначение |
|---|---|
| TRACE | Очень подробные события выполнения |
| DEBUG | Диагностическая информация |
| INFO | Обычные события работы |
| WARN | Необычная ситуация, не обязательно приводящая к отказу |
| ERROR | Ошибка выполнения операции |
| FATAL | Критичная ошибка, часто препятствующая продолжению работы |

Конкретные уровни и их смысл зависят от библиотеки логирования.

### Пример

```text
INFO  requestId=req-100 Request started
DEBUG requestId=req-100 Loading bonus configuration
ERROR requestId=req-100 Database timeout
INFO  requestId=req-100 Response status=500
```

### Можно ли искать только ERROR?

Не всегда.

Например:

- HTTP 500 может быть записан без уровня ERROR.
- Timeout может сопровождаться WARN.
- Ошибка может находиться в другом сервисе.
- Одно исключение может создать несколько записей.
- Часть ошибок обрабатывается приложением штатно.

Поэтому полезно искать не только уровень, но и идентификаторы запросов, коды ошибок и названия операций.

---

## 6. Structured Logging

**Structured Logging** — логирование в структурированном формате.

Например, JSON:

```json
{
  "timestamp": "2026-10-09T10:15:00Z",
  "level": "ERROR",
  "service": "bonus-service",
  "requestId": "req-101",
  "method": "POST",
  "path": "/api/bonuses/issue",
  "status": 500,
  "durationMs": 840,
  "errorCode": "DATABASE_TIMEOUT"
}
```

### Преимущества

- Удобная фильтрация.
- Поиск по отдельным полям.
- Агрегация.
- Использование в системах мониторинга.
- Меньшая зависимость от формулировок текста.

### Что особенно полезно Backend QA?

- timestamp.
- service.
- environment.
- requestId.
- traceId.
- operationId.
- errorCode.
- status.
- durationMs.
- Версия приложения.

### Чего не должно быть в обычных логах?

Без необходимости не следует записывать:

- Пароли.
- Access и Refresh Tokens.
- Session Cookies.
- Приватные ключи.
- Полные платёжные реквизиты.
- Избыточные персональные данные.

### Важный нюанс

В структурированном логе одно событие обычно представлено отдельной записью.

Это облегчает анализ по сравнению с многострочными произвольными сообщениями.

# Часть 3. Поиск логов в Linux

## 7. Просмотр файлов логов

### Последние 100 строк

```bash
tail -n 100 /var/log/my-service/app.log
```

### Наблюдать новые записи

```bash
tail -f /var/log/my-service/app.log
```

### Отслеживать файл при ротации

На GNU Linux:

```bash
tail -F /var/log/my-service/app.log
```

### Постраничный просмотр

```bash
less /var/log/my-service/app.log
```

### Найти ошибки

```bash
grep -n 'ERROR' /var/log/my-service/app.log
```

### Показать контекст

```bash
grep -C 5 'ERROR' /var/log/my-service/app.log
```

### Важный нюанс

Если запросы выполняются параллельно, соседние строки лога могут относиться к разным запросам.

Поэтому поиск по Request ID часто полезнее, чем просмотр пяти соседних строк.

---

## 8. Поиск по Request ID

Предположим, ответ API содержит:

```http
HTTP/1.1 500 Internal Server Error
X-Request-ID: req-101
```

Можно выполнить:

```bash
grep -F 'req-101' /var/log/my-service/app.log
```

### Пример результата

```text
10:15:00 INFO  req-101 Request started
10:15:00 DEBUG req-101 Bonus validation passed
10:15:01 ERROR req-101 Database timeout
10:15:01 INFO  req-101 Response status=500
```

### Что удалось выяснить?

- Запрос попал в Backend.
- Первичная валидация прошла.
- Ошибка произошла на этапе взаимодействия с БД.
- Клиент получил 500.

### Чего пока нельзя утверждать?

Что причиной является исключительно медленный SQL.

Database timeout мог возникнуть из-за:

- Ожидания соединения.
- Блокировки.
- Недоступности БД.
- Сетевой задержки.
- Длительного запроса.
- Ошибки настройки таймаутов.

---

## 9. Request ID, Trace ID и Operation ID

Эти идентификаторы не обязательно обозначают одно и то же.

### Request ID

Обычно связывает записи с отдельным запросом.

```text
requestId=req-101
```

### Trace ID

Связывает несколько операций в рамках распределённой трассировки.

Например:

```text
API Gateway
    |
    v
Bonus Service
    |
    v
User Service
    |
    v
PostgreSQL
```

Все части цепочки могут иметь общий Trace ID.

### Operation ID

Может обозначать длительную бизнес-операцию.

Например:

```text
operationId=bonus-issue-500
```

Одна бизнес-операция может включать:

- Несколько HTTP-запросов.
- Асинхронные сообщения.
- Повторные попытки.
- Несколько Trace ID.

### Важный вывод

**Request ID и Trace ID помогают найти техническое выполнение, а Operation ID — связать его с бизнес-результатом.**

Для асинхронных систем это особенно важно.

---

## 10. Поиск ошибок за определённое время

При наличии текстового timestamp можно сначала сузить интервал.

Например:

```bash
grep '2026-10-09T10:15' app.log
```

Но такой поиск зависит от формата логов.

### Что проверить до анализа?

- Часовой пояс логов.
- Часовой пояс рабочего компьютера.
- Используется ли UTC.
- Синхронизированы ли часы сервисов.
- Нет ли задержки доставки логов в централизованную систему.

### Пример проблемы

Пользователь сообщил:

```text
Ошибка в 13:15 по Минску
```

А Backend пишет время в UTC.

В период UTC+3 соответствующая запись будет около:

```text
10:15 UTC
```

### Важный нюанс

При сопоставлении логов нескольких сервисов лучше использовать единую временную шкалу.

Для этого особенно удобны timestamps с явным часовым поясом.

# Часть 4. journalctl

## 11. Диагностика systemd-сервиса

Если приложение запущено через systemd:

```bash
systemctl status bonus-service.service
```

Команда показывает состояние unit и часть недавних диагностических сведений.

### Пример

```text
Loaded: loaded
Active: failed
Main PID: 2500
```

### Что проверить?

- Состояние сервиса.
- Последний exit status.
- Время завершения.
- Причину ошибки.
- Количество перезапусков, если доступно.
- Последние журнальные сообщения.

### Важный нюанс

`Active: active (running)` означает, что systemd считает сервис активным.

Это не доказывает, что HTTP API успешно обрабатывает запросы.

---

## 12. Основные команды journalctl

### Последние 100 записей

```bash
journalctl -u bonus-service.service -n 100
```

### Следить за новыми событиями

```bash
journalctl -u bonus-service.service -f
```

### За конкретный период

```bash
journalctl -u bonus-service.service \
  --since "2026-10-09 10:00:00" \
  --until "2026-10-09 11:00:00"
```

### Только текущая загрузка

```bash
journalctl -b -u bonus-service.service
```

### Только сообщения с приоритетом error и выше

```bash
journalctl -u bonus-service.service -p err
```

### Без постраничного просмотрщика

```bash
journalctl -u bonus-service.service \
  -n 100 --no-pager
```

### Отображать время в UTC

```bash
journalctl --utc -u bonus-service.service -n 100
```

### Важный нюанс

Фильтр `-p err` относится к приоритету записей systemd journal.

Он не обязательно совпадает с текстовым значением `level=ERROR` внутри приложения.

---

## 13. JSON-вывод journalctl

Systemd journal хранит структурированные поля.

Для вывода в JSON:

```bash
journalctl -u bonus-service.service \
  -n 20 -o json
```

Если доступен jq:

```bash
journalctl -u bonus-service.service \
  -n 20 -o json |
  jq -r '.MESSAGE'
```

### Зачем полезно?

Можно работать с полями журнала, а не только с отформатированным текстом.

Например:

- Идентификатор процесса.
- Имя unit.
- Приоритет.
- Содержимое MESSAGE.

### Важный нюанс

`MESSAGE` может содержать обычный текст или сериализованный JSON приложения. Это разные уровни структуры, которые иногда приходится разбирать отдельно.

---

## 14. Посмотреть свойства завершения сервиса

```bash
systemctl show bonus-service.service \
  -p ActiveState \
  -p SubState \
  -p Result \
  -p ExecMainCode \
  -p ExecMainStatus \
  -p NRestarts
```

### Что можно узнать?

- Как systemd оценивает состояние unit.
- Как завершился основной процесс.
- Какие сведения о рестартах доступны.

### Важно

Не следует интерпретировать все поля без понимания типа сервиса и версии systemd.

Если сервис запускается через обёртку или shell script, состояние основного процесса может не полностью описывать состояние дочернего приложения.

# Часть 5. Docker и Kubernetes

## 15. Docker Logs

Если приложение работает в Docker:

```bash
docker ps
```

Показать контейнеры.

### Последние 100 строк

```bash
docker logs --tail 100 bonus-service
```

### Следить за логами

```bash
docker logs -f bonus-service
```

### Логи за последние 15 минут

```bash
docker logs --since 15m bonus-service
```

### Добавить timestamps

```bash
docker logs --timestamps bonus-service
```

### Удобная комбинация

```bash
docker logs \
  --since 15m \
  --tail 200 \
  --timestamps \
  bonus-service
```

### Важный нюанс

`docker logs` работает в рамках поддерживаемой конфигурации логирования контейнера.

Не стоит считать, что команда обязательно покажет все файлы логов, которые приложение создало внутри контейнера.

---

## 16. Диагностика перезапуска Docker-контейнера

Проверить состояние:

```bash
docker ps -a
```

Посмотреть подробности:

```bash
docker inspect bonus-service
```

### Вывести выбранные поля

```bash
docker inspect \
  --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}} RestartCount={{.RestartCount}}' \
  bonus-service
```

### Что проверить?

- Exit Code.
- OOMKilled.
- Restart Count.
- StartedAt.
- FinishedAt.
- Логи приложения.

### Пример

```text
ExitCode=137 OOMKilled=true RestartCount=4
```

Это серьёзное свидетельство завершения из-за OOM в контексте данных Docker.

### Важный нюанс

Сам по себе Exit Code 137 не доказывает OOM.

Он часто связан с SIGKILL, который может быть отправлен по разным причинам.

Если приложение развёрнуто через Docker Compose:

```bash
docker compose ps
```

Посмотреть сервисы.

### Логи конкретного сервиса

```bash
docker compose logs bonus-service
```

### Последние записи

```bash
docker compose logs --tail 100 bonus-service
```

### Следить за логами

```bash
docker compose logs -f bonus-service
```

### За последние 10 минут

```bash
docker compose logs --since 10m bonus-service
```

Название Compose-сервиса и имя Docker-контейнера могут отличаться.

## 18. Kubernetes: основные диагностические команды

В Kubernetes приложение обычно работает внутри Pod.

### Посмотреть Pod

```bash
kubectl get pods -n qa
```

Где `qa` — условное название namespace.

### Подробности Pod

```bash
kubectl describe pod bonus-service-abc123 -n qa
```

### Логи контейнера

```bash
kubectl logs bonus-service-abc123 -n qa
```

### Последние 100 строк

```bash
kubectl logs bonus-service-abc123 \
  -n qa --tail=100
```

### Следить за логами

```bash
kubectl logs bonus-service-abc123 \
  -n qa -f
```

### Логи за последние 10 минут

```bash
kubectl logs bonus-service-abc123 \
  -n qa --since=10m
```

### Логи предыдущего экземпляра контейнера

```bash
kubectl logs bonus-service-abc123 \
  -n qa --previous
```

### Почему --previous важен?

Если контейнер перезапустился, его текущие логи могут уже не содержать причину предыдущего падения.

`--previous` позволяет получить доступные логи предыдущего экземпляра контейнера в Pod.

### Важные нюансы

- Если в Pod несколько контейнеров, нужно указать `-c container-name`.
- Предыдущие логи могут быть уже недоступны.
- Доступ зависит от RBAC и настроек кластера.
- Минимальный контейнер может не содержать shell, grep, curl и других утилит.

## 19. CrashLoopBackOff

**CrashLoopBackOff** — состояние ожидания перед следующей попыткой запуска контейнера после повторяющихся неуспешных запусков.

Это не конкретная первопричина ошибки.

### Что проверять?

```bash
kubectl describe pod bonus-service-abc123 -n qa
```

Затем:

```bash
kubectl logs bonus-service-abc123 \
  -n qa --previous
```

### Возможные причины

- Ошибка конфигурации.
- Неправильная команда запуска.
- Недоступная зависимость.
- Ошибка приложения.
- Нехватка памяти.
- Проблема с секретами или volume.
- Некорректные health probes.

### Какие поля важны?

- State.
- Last State.
- Reason.
- Exit Code.
- Restart Count.
- Events.

### Важный нюанс

CrashLoopBackOff описывает повторные неуспешные запуски и задержку между ними.

Чтобы определить причину, нужны сведения о завершении контейнера и его логи.

---

## 20. Liveness и Readiness Probes

В Kubernetes используются механизмы проверки состояния контейнеров.

### Liveness Probe

Помогает определить, следует ли перезапустить контейнер, который больше не считается работоспособным.

### Readiness Probe

Определяет, готов ли контейнер обслуживать трафик через соответствующие механизмы Kubernetes.

### Startup Probe

Используется для проверки запуска, особенно если приложению необходимо значительное время для инициализации.

### Пример

Контейнер запущен, но не может подключиться к БД.

В зависимости от реализации readiness probe Pod может быть помечен как Not Ready.

### Что важно QA?

Проверять не только то, что процесс существует, но и то, правильно ли приложение сообщает свою готовность.

### Нюанс

Не каждую временную ошибку внешней зависимости следует превращать в неуспешную liveness probe.

Иначе система может создавать ненужные циклы рестарта.

# Часть 6. Диагностика HTTP 500, 502, 503 и 504

## 21. Сценарий: API возвращает HTTP 500

### Условие

```http
POST /api/bonuses/issue
```

Ответ:

```http
HTTP/1.1 500 Internal Server Error
X-Request-ID: req-101
```

### Алгоритм

**1. Зафиксировать запрос**

- Endpoint.
- Метод.
- Request Body без секретов.
- Заголовки, важные для воспроизведения.
- Время.
- Request ID.

**2. Найти логи**

```bash
grep -F 'req-101' app.log
```

**3. Найти ошибку**

Например:

```text
ERROR requestId=req-101 Database timeout
```

**4. Проверить зависимость**

- Доступность PostgreSQL.
- Connection Pool.
- Активные запросы.
- Блокировки.
- Таймауты.

**5. Проверить бизнес-состояние**

Не выдался ли бонус несмотря на HTTP 500?

**6. Сформулировать результат**

Например:

> При выдаче бонуса запрос завершается HTTP 500. В логах обнаружен database timeout. Для уточнения причины требуется проверить ожидания и состояние соединений PostgreSQL. Запись о выдаче в БД не появилась.

### Почему это лучше, чем «ручка падает»?

Потому что информация позволяет другому инженеру воспроизвести проблему и начать расследование с конкретных фактов.

## 24. Сценарий: HTTP 504 Gateway Timeout

```text
   |

   |

Backend
   |

PostgreSQL
   |
```

# Часть 7. Диагностика PostgreSQL

## 25. Connection Refused vs Authentication Failed

Предположим, Backend не может подключиться к PostgreSQL.

### Connection Refused

```text
Connection refused
```

Возможные причины:

- PostgreSQL не запущен.
- Не слушает нужный адрес.
- Неверный порт.
- Firewall отклоняет соединение.
- Ошибка сетевой конфигурации.

### Проверить TCP

```bash
nc -vz -w 3 postgres.internal 5432
```

### Authentication Failed

Пример:

```text
password authentication failed for user
```

TCP-соединение и протокольное взаимодействие дошли до этапа аутентификации, но учётные данные не были приняты.

Возможные причины:

- Неверный пароль.
- Неправильный пользователь.
- Ошибка конфигурации authentication.
- Неправильный источник учётных данных.

### Главный вывод

Это разные классы ошибок.

Не следует диагностировать неверный пароль как сетевую недоступность PostgreSQL.

## 26. pg_isready

Если утилита PostgreSQL доступна:

```bash
pg_isready -h postgres.internal -p 5432
```

Она проверяет, принимает ли PostgreSQL подключения в рамках возможностей этой утилиты.

### Важно

Успешный результат `pg_isready` не подтверждает:

- Корректность пользовательского пароля.
- Доступ к конкретной БД.
- Наличие прав на таблицы.
- Отсутствие блокировок.
- Корректность бизнес-запросов.

Для этого нужны дополнительные проверки.

---

## 27. Проблема: медленные SQL-запросы

Сценарий:

```text
API response time = 12 seconds
```

В логах:

```text
Database query timeout
```

### Что проверить?

- Время выполнения SQL.
- Использование индексов.
- Блокировки.
- Размер таблиц.
- Нагрузку на БД.
- Количество соединений.
- Состояние транзакций.

### PostgreSQL: pg_stat_activity

При наличии прав:

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    now() - query_start AS query_duration
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
```

### Что можно увидеть?

- Активные запросы.
- Длительные запросы.
- Ожидания.
- Состояния сессий.

### Важный нюанс

`state = 'active'` не означает, что PostgreSQL обязательно выполняет вычисления на CPU.

Активный запрос может ожидать блокировку или I/O.

Поле `wait_event_type` помогает уточнить ситуацию.

---

## 28. Как проверить блокировки PostgreSQL?

Можно использовать `pg_blocking_pids()`.

Пример:

```sql
SELECT
    pid,
    state,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blocking_pids
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

### Что показывает запрос?

Для сессий, ожидающих lock, можно получить PID процессов, которые блокируют их продвижение.

### Возможная причина API Timeout

```text
Transaction A
    |
    | Holds Lock
    v
Transaction B
    |
    | Waits
    v
API Timeout
```

### Важно

Обнаружение блокировки не означает, что нужно немедленно завершать блокирующую транзакцию.

Сначала необходимо понять:

- Что делает транзакция.
- Почему она длительная.
- Кому она принадлежит.
- Каким будет эффект её прерывания.

На общем стенде QA не должен самостоятельно завершать чужие транзакции без разрешения.

---

## 29. Connection Pool Exhaustion

**Connection Pool** — механизм повторного использования подключений к БД.

### Пример

Приложение имеет пул из 20 соединений.

При нагрузке все соединения заняты.

Новые запросы ожидают освобождения соединения.

Если ожидание слишком долгое, возникает timeout.

### Симптомы

- Рост HTTP latency.
- Ошибки получения соединения.
- Низкая скорость обработки.
- Большое количество активных запросов.
- Иногда повышенный Consumer Lag.

### Что проверить?

- Размер пула.
- Количество active/idle/pending connections.
- Время ожидания.
- Длительность SQL.
- Незавершённые транзакции.
- Утечки соединений.

### Важный нюанс

Увеличение размера пула — не универсальное решение.

Если сама PostgreSQL перегружена, дополнительные соединения могут ухудшить ситуацию.

# Часть 8. Диагностика Kafka

## 30. Сценарий: Kafka Consumer перестал обрабатывать сообщения

### Симптомы

- Не обновляется статус.

### Что проверить?

1. Работает ли Consumer.
2. Есть ли ошибки в логах.
3. Стабильна ли Consumer Group.
4. Не происходит ли постоянный rebalance.
5. Какое количество партиций назначено.
6. Не замедлилась ли обработка сообщений.
7. Доступны ли PostgreSQL и другие зависимости.
8. Не упирается ли приложение в ресурсы.

## 31. Kafka Consumer Group Diagnostics

В окружении с доступными Kafka CLI:

```bash
kafka-consumer-groups.sh \
  --bootstrap-server kafka.internal:9092 \
  --describe \
  --group bonus-consumer-group
```

В некоторых установках команда называется `kafka-consumer-groups` без `.sh`.

### Типичные поля

```text
GROUP
TOPIC
PARTITION
CURRENT-OFFSET
LOG-END-OFFSET
LAG
CONSUMER-ID
HOST
CLIENT-ID
```

### Что означает Lag?

В стандартном представлении CLI — разница между концом потока партиции и сохранённой позицией группы.

### Пример

```text
CURRENT-OFFSET = 1000
LOG-END-OFFSET = 1500
LAG = 500
```

Это означает отставание позиции группы на 500 offsets в соответствующей партиции.

### Важный нюанс

Lag не равен автоматически количеству незавершённых бизнес-операций.

Например, Consumer может коммитить offsets не в тот же момент, когда завершается бизнес-обработка.

---

## 32. Почему Consumer Lag растёт?

Возможные причины:

- Сообщения поступают быстрее, чем обрабатываются.
- Слишком мало эффективного параллелизма.
- Недостаточно партиций для желаемого масштабирования группы.
- Медленная БД.
- Ошибки внешних сервисов.
- Повторная обработка.
- Проблемы с Consumer Group.
- Длительный rebalance.
- Недостаток CPU или памяти.

### Как диагностировать?

Сопоставить:

- Скорость публикации сообщений.
- Скорость обработки.
- Lag по партициям.
- CPU/RAM.
- Длительность бизнес-операций.
- Ошибки в логах.
- Состояние БД.

### Важный вывод

Нельзя исправлять любой Lag простым добавлением Consumer.

Если у топика четыре партиции и одна Consumer Group, запуск десяти участников не означает десятикратный параллелизм чтения этого топика.

## 33. Сценарий: сообщение обработалось дважды

### Условие

Consumer получил событие начисления бонуса.

После рестарта то же событие обработалось повторно.

### Возможная последовательность

```text
Kafka Message
      |
      v
Consumer
      |
      v
DB COMMIT
      |
      v
Consumer crash
      |
      v
Offset not committed
      |
      v
Message processed again
```

### Что проверить?

- Когда выполняется offset commit.
- Успела ли завершиться БД-транзакция.
- Есть ли уникальный eventId.
- Как реализована идемпотентность.
- Не произошло ли повторного начисления.
- Не создаётся ли повторное событие.

### Основной бизнес-инвариант

```text

        =
One business effect
```

Даже если техническое событие доставляется несколько раз.

## 35. Messages Ready vs Messages Unacknowledged

### Ready

Сообщения, доступные для доставки Consumer.

### Unacknowledged

Сообщения, которые уже были доставлены, но ещё не получили соответствующего подтверждения.

### Пример

```text
Ready = 10
Unacked = 500
Consumers = 5
```

### Возможные причины

- Consumer медленно обрабатывают сообщения.
- Обработка зависла.
- Слишком большой prefetch.
- Не отправляются ACK.
- Недоступна БД.
- Длительные внешние запросы.

### Важный нюанс

Высокое Unacked не всегда автоматически означает дефект.

Нужно сопоставить его со скоростью обработки, настройками prefetch и ожидаемой нагрузкой.

- Отсутствием прогресса очереди.

### Что проверить?

- Причину ошибки.
- Количество попыток.

- DLQ.
- Идемпотентность.
- Поведение после восстановления зависимости.

## 38. OOM и Exit Code 137

### Симптом

После нагрузки приложение неожиданно завершилось.

Контейнер показывает:

```text
Exit Code: 137
```

### Что это может означать?

137 часто связано с SIGKILL.

Но SIGKILL не обязательно произошёл из-за OOM.

### Как проверить?

Для Docker:

```bash
docker inspect \
  --format '{{.State.OOMKilled}} {{.State.ExitCode}}' \
  bonus-service
```

Для systemd / Linux:

```bash
journalctl -k -b --no-pager |
  grep -Ei 'out of memory|oom|killed process'
```

Для Kubernetes:

```bash
kubectl describe pod bonus-service-abc123 -n qa
```

### Что ещё проверить?

- Лимит памяти контейнера.
- RSS.
- Memory usage over time.
- Нагрузку.
- Поведение после снижения нагрузки.
- Изменения конфигурации.

### Важный нюанс

Не стоит диагностировать Memory Leak только по одному высокому показателю памяти.

Нужны наблюдения во времени и понимание модели использования памяти.

## 39. Сценарий: No space left on device

Ошибка:

```text
No space left on device
```

### Что проверить?

```bash
df -h
```

Показывает использование дискового пространства.

```bash
df -i
```

Показывает использование inode.

### Почему важно df -i?

Файловая система может исчерпать доступные inode даже при наличии свободного пространства в байтах.

### Найти большие директории

В разрешённой области:

```bash
du -sh /var/log/*
```

### Возможные причины

- Логи не ротируются.
- Слишком большой объём временных файлов.
- Большое количество мелких файлов.
- Переполненное хранилище контейнера.
- Неудалённые временные данные.

### Важный нюанс

Если файл удалён, но ещё открыт процессом, занимаемое место может не освободиться до закрытия соответствующего файлового дескриптора.

Поэтому `df` и `du` иногда показывают неожиданно разные результаты.

### Безопасность

Не следует удалять неизвестные файлы и журналы на общем сервере только ради освобождения места.

Сначала выяснить, какие данные можно удалять по действующим правилам обслуживания.

## 40. Too many open files

Ошибка:

```text
Too many open files
```

### Что означает?

Процесс или система достигли соответствующего ограничения на количество открытых файловых дескрипторов.

### Что проверить?

Для процесса:

```bash
cat /proc/2500/limits
```

Если установлен lsof:

```bash
lsof -p 2500
```

Посмотреть количество доступных записей FD:

```bash
ls /proc/2500/fd | wc -l
```

### Возможные причины

- File Descriptor Leak.
- Не закрываются сетевые соединения.
- Слишком большое число одновременных соединений.
- Не закрываются открытые файлы.
- Неподходящие лимиты.

### Важный нюанс

Увеличение лимита может временно уменьшить симптомы, но не исправит утечку дескрипторов.

Нужно понять, почему количество FD растёт.

# Часть 11. Логи, метрики и трассировка

## 41. Logs vs Metrics vs Traces

Это три основных вида данных наблюдаемости.

### Logs

Описывают отдельные события.

Например:

```text
Database timeout
```

### Metrics

Показывают численные показатели во времени.

Например:

```text
http_requests_total
http_request_duration_seconds
cpu_usage
consumer_lag
```

### Traces

Показывают путь выполнения операции через компоненты системы.

Например:

```text
HTTP Request
   |
   +-- API Gateway: 5 ms
   |
   +-- Bonus Service: 40 ms
   |
   +-- PostgreSQL Query: 850 ms
```

### Сравнение

| Источник | Основной вопрос |
|---|---|
| Logs | Что произошло? |
| Metrics | Как меняется поведение системы? |
| Traces | Где запрос потратил время и через что прошёл? |

### Важный нюанс

Эти источники дополняют друг друга.

Один Trace может показать медленный SQL-span, но для установления причины может понадобиться анализ плана запроса или блокировок БД.

---

## 42. Что такое Correlation ID?

**Correlation ID** — идентификатор, позволяющий связывать записи разных компонентов с одной логической операцией.

### Пример

```text
API Gateway:
requestId=req-101 traceId=trace-500

Bonus Service:
requestId=req-101 traceId=trace-500

User Service:
traceId=trace-500

PostgreSQL instrumentation:
traceId=trace-500
```

### Почему важно?

Без корреляции в распределённой системе трудно отличать события разных запросов.

Особенно если сервис обрабатывает тысячи запросов одновременно.

### Что полезно QA?

При создании баг-репорта сохранять:

- Request ID.
- Trace ID.
- Operation ID.
- Timestamp.
- Название сервиса.
- Версию приложения.

При этом идентификаторы и связанные логи нужно передавать через разрешённые корпоративные каналы.

---

## 43. Что такое Golden Signals?

В мониторинге сервисов часто используют четыре основных сигнала:

**Latency**

Задержка обработки запросов.

**Traffic**

Интенсивность поступающих запросов.

**Errors**

Количество или доля ошибок.

**Saturation**

Степень использования и исчерпания ресурсов.

### Для Backend QA

Допустим, после релиза:

- RPS остался прежним.
- p95 вырос в три раза.
- CPU увеличился.
- Доля ошибок пока низкая.

Это может говорить о деградации производительности ещё до массовых отказов.

### Главный вывод

Диагностика должна учитывать не только сообщения ERROR, но и изменение поведения системы.

# Часть 12. Как определить причину проблемы?

## 44. Почему нельзя делать вывод только по одному логу?

Пример:

```text
ERROR Database timeout
```

Эта запись не объясняет, почему произошёл timeout.

### Возможные гипотезы

**Гипотеза A**

Медленный SQL.

Проверить длительность и план запроса.

**Гипотеза B**

Ожидание блокировки.

Проверить `pg_stat_activity`, `wait_event` и блокирующие транзакции.

**Гипотеза C**

Исчерпание Connection Pool.

Проверить метрики пула.

**Гипотеза D**

Сетевая проблема.

Проверить соединения и сетевые ошибки.

**Гипотеза E**

Перегрузка БД.

Проверить CPU, I/O и число выполняемых запросов.

### Правильный подход

Необходимо собирать независимые подтверждения.

Например:

```text
API latency high
       +
DB wait_event_type = Lock
       +
Long transaction holds lock
       =
Strong evidence of lock-related delay
```

---

## 45. Как проверить, что проблема появилась после релиза?

### Собрать информацию

- Время начала ошибок.
- Время развёртывания.
- Версия приложения до и после.
- Изменения конфигурации.
- Изменения нагрузки.
- Миграции БД.
- Изменения зависимостей.

### Сравнить

```text
Before Release:
5xx = 0.1%
p95 = 200 ms

After Release:
5xx = 3%
p95 = 900 ms
```

Это показывает корреляцию.

### Но доказывает ли она причину?

Нет.

Могли одновременно измениться:

- Нагрузка.
- Состояние БД.
- Внешняя зависимость.
- Сетевая инфраструктура.
- Тестовые данные.

### Senior-подход

Изменение после релиза — сильная гипотеза, но её нужно проверять.

Не следует автоматически считать последний релиз причиной всех проблем.

# Часть 13. Практический алгоритм для Backend QA

## 46. Универсальная схема расследования HTTP-ошибки

```text
Observed Failure
       |
       v
Is there an HTTP response?
       |
       +-- No
       |    |
       |    +-- Check DNS
       |    +-- Check TCP
       |    +-- Check TLS
       |    +-- Check listening port
       |
       +-- Yes
            |
            v
       Check HTTP Status
            |
            +-- 4xx
            |    |
            |    +-- Authentication
            |    +-- Authorization
            |    +-- Validation
            |    +-- Business constraints
            |
            +-- 5xx
                 |
                 +-- Proxy
                 +-- Backend logs
                 +-- Dependencies
                 +-- Resources
                 +-- Database
                 +-- Brokers
```

После технической локализации:

```text
Check Business State
       |
       +-- Did DB change?
       +-- Was event published?
       +-- Did retry occur?
       +-- Are there duplicates?
       +-- Is operation recoverable?
```

### Важное правило

Нельзя завершать расследование изменяющей операции только словами:

> Сервер вернул ошибку.

Нужно установить, что произошло с бизнес-данными, если у QA есть соответствующий доступ и это важно для риска.

## 47. Таблица: симптом → возможные причины → проверки

| Симптом | Возможные причины | Что проверить |
|---|---|---|
| Connection refused | Нет слушателя, неверный порт, активный reject | `ss`, `nc`, состояние сервиса |
| Connection timed out | Маршрут, firewall, сеть | `ip route`, `nc`, сетевые логи |
| TLS error | Сертификат, CA, SNI | `curl -v`, `openssl s_client` |
| HTTP 401 | Нет или неверная аутентификация | Authorization, срок токена |
| HTTP 403 | Недостаточные права | Roles, scopes, object access |
| HTTP 500 | Ошибка приложения или зависимости | Request ID, Backend logs |
| HTTP 502 | Некорректный upstream response | Proxy и Backend |
| HTTP 503 | Сервис недоступен или перегружен | Readiness, ресурсы, инфраструктура |
| HTTP 504 | Upstream timeout | Latency, traces, dependencies |
| DB timeout | SQL, locks, pool, сеть | `pg_stat_activity`, pool metrics |
| Kafka Lag растёт | Consumer не успевает | Consumer Group, throughput, dependencies |
| RabbitMQ Ready растёт | Нет достаточной обработки | Consumers, rate, ошибки |
| RabbitMQ Unacked растёт | Медленная обработка, ACK, prefetch | Consumer logs, prefetch |
| Exit Code 137 | SIGKILL, возможно OOM | Контейнерные события, OOM flags |
| No space left | Место или inode | `df -h`, `df -i` |
| Too many open files | FD exhaustion | `/proc/PID/limits`, `lsof` |

# Часть 14. Баг-репорт по Backend-проблеме

## 48. Что должно быть в техническом баг-репорте?

Для сложного Backend-дефекта полезно указывать:

1. Краткое название.
2. Окружение.
3. Версию приложения.
4. Предусловия.
5. Шаги воспроизведения.
6. Ожидаемый результат.
7. Фактический результат.
8. Время возникновения.
9. Request ID / Trace ID.
10. Подтверждающие данные.
11. Бизнес-последствия.
12. Частоту воспроизведения.

### Важно

Не всегда нужно собирать все двенадцать пунктов.

Баг-репорт должен быть достаточным для понимания и воспроизведения дефекта, а не максимально длинным.

---

## 49. Пример технического баг-репорта

### Title

`[Bonus API] HTTP 500 при выдаче бонуса из-за таймаута PostgreSQL`

### Environment

```text
Environment: QA
Service: bonus-service
Version: 1.24.0
Endpoint: POST /api/bonuses/issue
```

### Preconditions

- Пользователь активен.
- Бонус доступен для выдачи.
- У пользователя нет ранее выданного экземпляра этого бонуса.

### Steps

1. Подготовить пользователя и бонус с допустимыми параметрами.
2. Выполнить POST `/api/bonuses/issue`.
3. Проверить HTTP-ответ.
4. Проверить состояние выдачи в БД.

### Expected Result

```text
201 Created
```

Бонус выдан, запись создана, счётчики согласованы.

### Actual Result

```text
500 Internal Server Error
```

В логах обнаружен timeout при обращении к PostgreSQL.

### Diagnostics

```text
Timestamp: 2026-10-09T10:15:01Z
Request ID: req-101
Error Code: DATABASE_TIMEOUT
```

### Database State

Запись о выдаче отсутствует.

### Additional Information

Причина самого database timeout пока не подтверждена. Требуется анализ состояния соединений и ожиданий PostgreSQL.

### Почему такая формулировка лучше?

Она не утверждает неподтверждённую первопричину.

Если расследование покажет, что источник проблемы — блокировка БД, заголовок и описание можно уточнить.

## 50. Подготовка учебных логов

Создадим файл, используя свою учебную директорию:

```bash
mkdir -p ~/qa-linux-practice/debugging
cd ~/qa-linux-practice/debugging
```

```bash
cat > app.log <<'EOF'
2026-10-09T10:00:00Z INFO requestId=req-100 service=bonus-service event=request-started
2026-10-09T10:00:01Z INFO requestId=req-100 service=bonus-service event=request-completed status=200 durationMs=40
2026-10-09T10:01:00Z INFO requestId=req-101 service=bonus-service event=request-started
2026-10-09T10:01:01Z ERROR requestId=req-101 service=bonus-service event=db-timeout
2026-10-09T10:01:01Z INFO requestId=req-101 service=bonus-service event=request-completed status=500 durationMs=1000
2026-10-09T10:02:00Z INFO requestId=req-102 service=bonus-service event=request-started
2026-10-09T10:02:01Z WARN requestId=req-102 service=bonus-service event=bonus-already-issued
2026-10-09T10:02:01Z INFO requestId=req-102 service=bonus-service event=request-completed status=409 durationMs=45
2026-10-09T10:03:00Z INFO requestId=req-103 service=bonus-service event=request-started
2026-10-09T10:03:01Z ERROR requestId=req-103 service=bonus-service event=dependency-unavailable
2026-10-09T10:03:01Z INFO requestId=req-103 service=bonus-service event=request-completed status=503 durationMs=900
EOF
```

### Задание 1. Найти все ошибки

```bash
grep 'ERROR' app.log
```

Ожидается две строки.

### Задание 2. Найти все записи req-101

```bash
grep -F 'requestId=req-101' app.log
```

Ожидается три строки.

### Задание 3. Найти HTTP 5xx

```bash
grep -E 'status=5[0-9]{2}([[:space:]]|$)' app.log
```

Ожидается две строки с завершением запросов.

### Задание 4. Посчитать завершённые запросы

```bash
grep -cF 'event=request-completed' app.log
```

Ожидается:

```text
4
```

### Задание 5. Посчитать долю 5xx

```bash
awk '
/event=request-completed/ {
  total++;
  if ($0 ~ /status=5[0-9][0-9]([[:space:]]|$)/) {
    errors++;
  }
}
END {
  if (total > 0) {
    printf "5xx rate: %.2f%%\n", errors / total * 100;
  }
}' app.log
```

Ожидается:

```text
5xx rate: 50.00%
```

### Почему считаем только request-completed?

Потому что один запрос создаёт несколько строк.

Если считать все строки лога, error rate будет вычислен неправильно.

### Задание 6. Сохранить диагностическую выборку

```bash
grep -F 'requestId=req-101' app.log > req-101.log
```

Проверить:

```bash
cat req-101.log
```

# Часть 16. Вопросы для собеседования

## 51. С чего начинаешь диагностику HTTP 500?

С воспроизведения, фиксации запроса, времени и Request ID. Затем анализирую Backend-логи, зависимости и фактический бизнес-результат.

## 52. Что такое Structured Logging?

Логирование событий в структурированном формате, например JSON, позволяющем фильтровать и агрегировать данные по отдельным полям.

## 53. Зачем нужен Request ID?

Чтобы связывать записи лога с конкретным запросом.

## 54. Чем Request ID отличается от Trace ID?

Request ID обычно идентифицирует отдельный запрос, а Trace ID связывает выполнение распределённой операции через разные компоненты.

## 55. Как посмотреть логи systemd-сервиса?

```bash
journalctl -u service-name.service -n 100
```

## 56. Как следить за логами сервиса?

```bash
journalctl -u service-name.service -f
```

## 57. Как посмотреть логи Docker-контейнера?

```bash
docker logs --tail 100 container-name
```

## 58. Как посмотреть логи предыдущего контейнера в Kubernetes Pod?

```bash
kubectl logs pod-name -n qa --previous
```

Если необходимо, дополнительно указать имя контейнера.

## 59. Что такое CrashLoopBackOff?

Состояние повторяющихся неуспешных запусков контейнера с задержкой между попытками. Не является самостоятельной первопричиной.

## 60. Что проверять при HTTP 504?

Gateway timeout, задержки Backend, SQL, внешние зависимости и фактический результат бизнес-операции.

## 61. Что означает Database Timeout?

Превышение определённого времени ожидания при работе с БД. Причина зависит от этапа — соединение, пул, блокировка, SQL или сеть.

## 62. Что такое Connection Pool Exhaustion?

Состояние, при котором доступные соединения пула заняты, а новые операции вынуждены ждать.

## 63. Как найти блокировки PostgreSQL?

Например, через `pg_stat_activity`, `wait_event_type` и `pg_blocking_pids()`.

## 64. Почему Kafka Consumer Lag может расти?

Из-за недостаточной скорости обработки, медленных зависимостей, настроек параллелизма, ошибок и проблем Consumer Group.

## 65. Чем RabbitMQ Ready отличается от Unacked?

Ready — сообщения, доступные для доставки. Unacked — доставленные сообщения, ещё не подтверждённые Consumer.

## 66. Что может означать Exit Code 137?

Часто завершение через SIGKILL. OOM — одна из возможных причин, но её нужно подтвердить.

## 67. Что проверять при No space left on device?

Свободное пространство, inode, использование файловой системы и крупные файлы.

## 68. Что такое File Descriptor Leak?

Ситуация, когда приложение не освобождает файловые дескрипторы должным образом, что может привести к достижению лимитов.

## 69. Чем Logs отличаются от Metrics и Traces?

Logs описывают события, Metrics — численные показатели во времени, Traces — путь выполнения операции через компоненты.

## 70. Почему одного сообщения ERROR недостаточно для Root Cause Analysis?

Потому что оно может описывать симптом или следствие. Нужны проверенные факты о работе компонентов и зависимостей.

## 71. Как проверить, что проблема связана с релизом?

Сравнить время возникновения, версию, логи, метрики, изменения конфигурации и другие факторы. Временная корреляция сама по себе не доказывает причинность.

## 72. Что должно быть в хорошем Backend-баг-репорте?

Условия, шаги, ожидаемый и фактический результат, окружение, время, идентификаторы запросов, подтверждающие данные и последствия.

# Часть 17. Частые ошибки на собеседовании

**Ошибка:** «HTTP 500 — значит проблема в коде Backend».

Правильно: ошибка может быть связана с зависимостями, конфигурацией или инфраструктурой. Важно установить источник.

**Ошибка:** «Database timeout означает медленный SQL».

Правильно: timeout может быть связан с соединением, пулом, блокировкой, сетью или SQL.

**Ошибка:** «Если API вернул 504, операция не выполнилась».

Правильно: бизнес-операция могла завершиться, но ответ не дошёл до клиента вовремя.

**Ошибка:** «Exit Code 137 всегда означает OOM».

Правильно: это часто следствие SIGKILL, который может иметь разные причины.

**Ошибка:** «Большой Kafka Lag означает, что брокер неисправен».

Правильно: проблема может быть в Consumer, БД или недостаточной скорости обработки.

**Ошибка:** «RabbitMQ Unacked означает потерянные сообщения».

Правильно: Unacked означает, что сообщения доставлены, но ещё не подтверждены.

**Ошибка:** «Если Pod Running, API работает».

Правильно: состояние контейнера не гарантирует функциональную исправность приложения.

**Ошибка:** «Чтобы найти причину, достаточно посмотреть последние 20 строк».

Правильно: причина может находиться раньше, в другом сервисе или в метриках.

**Ошибка:** «После релиза возникла проблема — значит виноват релиз».

Правильно: это гипотеза, которую нужно проверять.

**Ошибка:** «Для баг-репорта нужно копировать все логи целиком».

Правильно: нужны релевантные сведения без лишних секретов и персональных данных.

# Мини-шпаргалка Backend QA

| Задача | Команда |
|---|---|
| Последние логи файла | `tail -n 100 app.log` |
| Поиск Request ID | `grep -F 'req-101' app.log` |
| Найти ERROR | `grep 'ERROR' app.log` |
| Состояние systemd-сервиса | `systemctl status service.service` |
| Логи systemd | `journalctl -u service.service -n 100` |
| Логи за период | `journalctl -u service.service --since "2026-10-09 10:00:00"` |
| Логи Docker | `docker logs --tail 100 container` |
| Docker restart/OOM | `docker inspect container` |
| Логи Pod | `kubectl logs pod -n qa` |
| Предыдущие логи Pod | `kubectl logs pod -n qa --previous` |
| Описание Pod | `kubectl describe pod pod -n qa` |
| Потребление ресурсов | `top` |
| Память | `free -h` |
| Диск | `df -h` |
| Inode | `df -i` |
| Сетевые порты | `ss -lntp` |
| Тест HTTP | `curl -v URL` |
| Тест TCP | `nc -vz host port` |
| Проверка PostgreSQL | `pg_isready -h host -p 5432` |
| Kafka Consumer Lag | `kafka-consumer-groups.sh --bootstrap-server host:9092 --describe --group group-name` |
| RabbitMQ Queues | `rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers` |
