## 1. Для чего Backend QA нужна обработка текста?

При тестировании Backend-приложений часто необходимо:

- Найти ошибки в логах.
- Найти конкретный запрос по Request ID.
- Посмотреть события перед ошибкой.
- Узнать, сколько раз возникла определённая ошибка.
- Найти все ответы со статусом 500.
- Проверить работу интеграции.
- Найти конфигурационный файл.
- Отфильтровать данные большого файла.
- Проанализировать результаты работы приложения.

Например, мы вызвали API:

```http
POST /api/bonuses/issue
```

И получили:

```http
HTTP/1.1 500 Internal Server Error
```

Наш дальнейший путь может выглядеть так:

```text
HTTP 500
   |
   v
Найти нужный Request ID
   |
   v
Найти его в логах
   |
   v
Посмотреть связанные события
   |
   v
Определить ошибку
   |
   v
Проверить зависимость
   |
   v
Локализовать причину
```

Для этого пригодятся команды из данного раздела.

# Часть 1. Подготовка учебных данных

## 2. Создадим собственный лог

Чтобы все команды можно было попробовать самостоятельно, создадим небольшой учебный файл.

Выполни:

```bash
mkdir -p ~/qa-linux-practice/logs
cd ~/qa-linux-practice
```

Теперь создадим файл:

```bash
cat > logs/app.log <<'EOF'
2026-10-09T10:00:00Z INFO requestId=req-100 method=GET path=/api/bonuses status=200 durationMs=35
2026-10-09T10:00:01Z ERROR requestId=req-101 method=POST path=/api/bonuses/issue status=500 durationMs=840 message="database timeout"
2026-10-09T10:00:02Z WARN requestId=req-102 method=POST path=/api/bonuses/issue status=409 durationMs=42 message="already issued"
2026-10-09T10:00:03Z INFO requestId=req-103 method=GET path=/api/bonuses status=200 durationMs=28
2026-10-09T10:00:04Z ERROR requestId=req-104 method=GET path=/api/users/bonuses status=503 durationMs=910 message="dependency unavailable"
2026-10-09T10:00:05Z INFO requestId=req-105 method=POST path=/api/bonuses/issue status=201 durationMs=63
2026-10-09T10:00:06Z ERROR requestId=req-106 method=POST path=/api/bonuses/issue status=500 durationMs=721 message="database timeout"
2026-10-09T10:00:07Z INFO requestId=req-107 method=GET path=/health status=200 durationMs=5
EOF
```

### Что здесь происходит?

Конструкция:

```bash
cat > file <<'EOF'
...
EOF
```

Передаёт многострочный текст команде `cat`, а затем записывает её вывод в файл.

В нашем случае:

- `>` — записать вывод в файл.
- `<<'EOF'` — передать многострочный ввод без подстановки Shell-переменных и выполнения подстановок команд.
- `EOF` — обозначает окончание вводимого текста.

**Важно:** `>` перезаписывает существующий файл.

Теперь:

```bash
cat logs/app.log
```

выведет восемь строк.

Все дальнейшие примеры используют именно этот файл, если не указано другое.

# Часть 2. Стандартные потоки

## 3. STDIN, STDOUT и STDERR

В Linux процессы обычно используют три стандартных потока.

| Поток | Номер | Назначение |
|---|---|---|
| STDIN | 0 | Стандартный ввод |
| STDOUT | 1 | Стандартный вывод |
| STDERR | 2 | Стандартный вывод ошибок |

### STDIN

Данные, которые программа получает на вход.

Например, ввод пользователя или данные другой команды.

### STDOUT

Обычный результат работы программы.

Пример:

```bash
echo "Hello"
```

Результат:

```text
Hello
```

### STDERR

Поток для диагностики и сообщений об ошибках.

Например:

```bash
ls /directory-that-does-not-exist
```

Сообщение об ошибке обычно попадёт в STDERR.

### Почему это важно?

Потому что стандартные потоки можно:

- Направлять в файлы.
- Передавать другим командам.
- Обрабатывать отдельно.
- Объединять.

Это основа работы с логами через командную строку.

### Краткий ответ для собеседования

> В Linux стандартный ввод называется STDIN, обычный вывод — STDOUT, а вывод ошибок — STDERR. Они имеют файловые дескрипторы 0, 1 и 2. Shell позволяет перенаправлять эти потоки и объединять команды через pipe.

# Часть 3. grep — поиск по содержимому

## 4. Что такое grep?

**grep** — команда для поиска строк, соответствующих заданному шаблону.

Её часто используют для:

- Поиска ошибок.
- Поиска Request ID.
- Фильтрации HTTP-статусов.
- Поиска отдельных событий.
- Анализа текстовых логов.

### Простейший пример

```bash
grep 'ERROR' logs/app.log
```

Результат:

```text
2026-10-09T10:00:01Z ERROR requestId=req-101 method=POST path=/api/bonuses/issue status=500 durationMs=840 message="database timeout"
2026-10-09T10:00:04Z ERROR requestId=req-104 method=GET path=/api/users/bonuses status=503 durationMs=910 message="dependency unavailable"
2026-10-09T10:00:06Z ERROR requestId=req-106 method=POST path=/api/bonuses/issue status=500 durationMs=721 message="database timeout"
```

grep напечатал только строки, содержащие `ERROR`.

### Синтаксис

```bash
grep [options] 'pattern' file
```

Где:

- `grep` — команда.
- `pattern` — шаблон поиска.
- `file` — файл.

---

## 5. Основные опции grep

| Опция | Назначение |
|---|---|
| `-i` | Игнорировать регистр |
| `-n` | Показать номера строк |
| `-c` | Посчитать строки с совпадениями |
| `-v` | Показать строки без совпадений |
| `-w` | Сопоставлять целое слово |
| `-F` | Искать буквальную строку |
| `-E` | Использовать расширенные регулярные выражения |
| `-r` | Рекурсивно искать в директориях |
| `-l` | Вывести имена файлов с совпадениями |
| `-A N` | Показать N строк после совпадения |
| `-B N` | Показать N строк до совпадения |
| `-C N` | Показать N строк до и после |
| `-q` | Не печатать совпадения, использовать код завершения |
| `-o` | Вывести только совпавшие части |

Разберём наиболее полезные.

---

## 6. grep -i — игнорировать регистр

```bash
grep -i 'error' logs/app.log
```

Найдёт `ERROR`, `Error` и `error` в соответствии с правилами выбранной локали.

### Когда полезно?

Когда формат логов не гарантирует одинаковый регистр.

Например:

```text
ERROR
Error
error
```

---

## 7. grep -n — номера строк

```bash
grep -n 'ERROR' logs/app.log
```

Результат начинается с номеров:

```text
2:2026-10-09T10:00:01Z ERROR ...
5:2026-10-09T10:00:04Z ERROR ...
7:2026-10-09T10:00:06Z ERROR ...
```

### Зачем это QA?

Номер строки помогает:

- Быстро перейти к нужному месту.
- Найти соседние события.
- Передать конкретное место в файле другому инженеру.

---

## 8. grep -c — количество строк с совпадением

```bash
grep -c 'ERROR' logs/app.log
```

Результат:

```text
3
```

### Важный нюанс

`grep -c` считает **строки с совпадениями**, а не общее количество вхождений.

Если одна строка содержит `ERROR` три раза, для `grep -c` это одна строка.

### Посчитать вхождения

В GNU grep можно использовать:

```bash
grep -o 'ERROR' logs/app.log | wc -l
```

Здесь `grep -o` выводит каждое найденное вхождение отдельно.

---

## 9. grep -v — исключить строки

```bash
grep -v 'INFO' logs/app.log
```

Выведет все строки, в которых нет `INFO`.

В нашем примере останутся:

- ERROR.
- WARN.

### Где полезно?

Например, убрать шум от информационных сообщений.

Но нужно учитывать, что `grep -v 'INFO'` исключает любую строку, содержащую такую последовательность, а не только строки с определённым уровнем логирования.

Для сложных логов лучше учитывать точную структуру полей.

---

## 10. grep -F — буквальный поиск

```bash
grep -F 'requestId=req-101' logs/app.log
```

Выведет запись конкретного запроса.

### Почему полезен -F?

По умолчанию grep интерпретирует шаблон как базовое регулярное выражение.

Некоторые символы имеют специальное значение.

Например:

```text
.
*
[
]
```

Опция `-F` отключает интерпретацию регулярных выражений и ищет буквальную строку.

### Практическое правило

**Если ищешь конкретный Request ID, URL или фрагмент текста без необходимости использовать шаблоны, удобно применять `grep -F`.**

---

## 11. grep -E — регулярные выражения

`-E` включает расширенные регулярные выражения.

Пример:

```bash
grep -E 'ERROR|WARN' logs/app.log
```

Найдёт строки с `ERROR` или `WARN`.

Символ `|` здесь означает логическое «или».

### Другой вариант

Для поиска нескольких буквальных строк:

```bash
grep -F -e 'ERROR' -e 'WARN' logs/app.log
```

Этот вариант не использует регулярные выражения.

### Когда нужен grep -E?

Когда требуется шаблон:

- Несколько вариантов.
- Числовые диапазоны.
- Якоря начала или конца строки.
- Повторения символов.
- Группировка выражений.

---

## 12. Поиск HTTP 500 в логах

В нашем логе статус записан как:

```text
status=500
```

Поэтому можно использовать:

```bash
grep -F 'status=500' logs/app.log
```

Результат — две строки:

```text
req-101
req-106
```

Конечно, команды выводят полные строки; здесь указаны соответствующие Request ID.

### Посчитать количество

```bash
grep -cF 'status=500' logs/app.log
```

Результат:

```text
2
```

### Найти все 5xx

```bash
grep -E 'status=5[0-9]{2}([[:space:]]|$)' logs/app.log
```

Шаблон означает:

- `status=5` — начало значения.
- `[0-9]{2}` — ещё две цифры.
- `([[:space:]]|$)` — после статуса должен быть пробел или конец строки.

Найдёт статусы:

- 500.
- 503.

Всего три строки.

### Важный нюанс

Команда зависит от формата логов.

Если приложение использует JSON logging, лучше обрабатывать поле `status` как JSON, например через `jq`.

---

## 13. grep -A, -B, -C — контекст ошибки

Иногда мало найти строку с ошибкой.

Нужно увидеть, что происходило рядом.

### Две строки после

```bash
grep -A 2 'ERROR' logs/app.log
```

### Две строки до

```bash
grep -B 2 'ERROR' logs/app.log
```

### Две строки до и после

```bash
grep -C 2 'ERROR' logs/app.log
```

### Где полезно?

Например, приложение логирует:

```text
Request started
Database query
ERROR
Stack trace
Request finished
```

Контекст помогает увидеть дополнительные события.

### Важный нюанс

Если разные запросы обрабатываются параллельно, соседние строки лога не обязательно относятся к одному запросу.

Поэтому поиск по Request ID обычно надёжнее простого просмотра соседних строк.

---

## 14. grep -r — рекурсивный поиск

Допустим, логи распределены по директориям:

```text
logs/
├── app.log
├── old/
│   └── app-1.log
└── integrations/
    └── kafka.log
```

Найти ERROR во всех файлах:

```bash
grep -rn 'ERROR' logs/
```

Здесь:

- `-r` — рекурсивно обходить директории.
- `-n` — показывать номера строк.

### Найти файлы, содержащие ошибку

```bash
grep -rl 'ERROR' logs/
```

Выведет имена файлов, где есть совпадение.

### Важный нюанс

Рекурсивный grep может наткнуться на бинарные файлы, большие архивы и специальные файлы.

В реальной системе желательно ограничивать область поиска.

---

## 15. grep и код завершения

Команды Linux возвращают exit status.

Для grep основные значения:

| Код | Значение |
|---|---|
| 0 | Найдено совпадение |
| 1 | Совпадений нет |
| 2 | Произошла ошибка (для GNU grep) |

### Пример

```bash
grep -qF 'ERROR' logs/app.log
echo $?
```

Результат:

```text
0
```

### Почему это важно для CI/CD?

Отсутствие совпадения — не обязательно ошибка самого grep.

Но код `1` может повлиять на выполнение Bash-скрипта, особенно при использовании `set -e`.

### Пример правильного использования

```bash
if grep -qF 'ERROR' logs/app.log; then
  echo "Errors found"
else
  echo "No errors found"
fi
```

Для production-grade скрипта при необходимости следует дополнительно различать отсутствие совпадений и техническую ошибку grep.

# Часть 4. Регулярные выражения

## 16. Основные элементы Regular Expressions

Регулярное выражение — шаблон для поиска или проверки текста.

Для большинства практических задач достаточно знать несколько символов.

| Символ | Значение |
|---|---|
| `.` | Любой отдельный символ в обычном текстовом режиме |
| `*` | Ноль или больше повторений предыдущего элемента |
| `+` | Одно или больше повторений в ERE |
| `?` | Ноль или одно повторение в ERE |
| `^` | Начало строки |
| `$` | Конец строки |
| `[0-9]` | Цифра |
| `[A-Z]` | Заглавная латинская буква |
| `{3}` | Ровно три повторения в ERE |
| `a|b` | a или b в ERE |

### Найти строки, начинающиеся с ERROR

```bash
grep '^ERROR' application.log
```

Это сработает, если уровень логирования действительно находится в начале строки.

В нашем учебном файле сначала стоит timestamp, поэтому совпадений не будет.

### Найти строки, заканчивающиеся на FAILED

```bash
grep 'FAILED$' application.log
```

### Найти 500, 501, 502 и другие 5xx

```bash
grep -E 'status=5[0-9]{2}([[:space:]]|$)' logs/app.log
```

### Найти ERROR или WARN

```bash
grep -E 'ERROR|WARN' logs/app.log
```

### Важное различие

Shell glob:

```bash
ls *.log
```

и регулярное выражение:

```bash
grep -E '.*\.log'
```

— это разные языки шаблонов.

В первом случае `*` обрабатывает Shell при подборе имён файлов.

Во втором регулярное выражение обрабатывает grep при анализе текста.

# Часть 5. find — поиск файлов

## 17. Что такое find?

**find** ищет файлы и директории по заданным условиям.

Например:

- Имя.
- Тип.
- Размер.
- Время изменения.
- Путь.
- Права.
- Владелец.

### Пример

```bash
find . -name 'app.log'
```

Ищет объект с именем `app.log` внутри текущей директории и её поддиректорий.

### Синтаксис

```bash
find PATH CONDITIONS ACTIONS
```

### Краткий ответ

> find используется для поиска файловых объектов по имени, типу, размеру, времени изменения и другим характеристикам. В отличие от grep, который обычно ищет строки в содержимом файлов, find в первую очередь работает с файловыми объектами и их атрибутами.

---

## 18. find -name

Найти файл:

```bash
find . -name 'application.yaml'
```

Найти все файлы `.log`:

```bash
find . -name '*.log'
```

### Почему '*.log' в кавычках?

Чтобы Shell не раскрыл шаблон до передачи команде find.

Правильно:

```bash
find . -name '*.log'
```

Нежелательно:

```bash
find . -name *.log
```

Во втором случае Shell может подставить имена файлов текущей директории, изменив смысл команды.

---

## 19. find -type

Ограничивает поиск типом объекта.

### Только обычные файлы

```bash
find . -type f
```

### Только директории

```bash
find . -type d
```

### Только символические ссылки

```bash
find . -type l
```

### Найти все лог-файлы

```bash
find . -type f -name '*.log'
```

Это распространённая комбинация.

---

## 20. find -size

Поиск по размеру.

Например, на GNU Linux:

```bash
find logs/ -type f -size +10M
```

Найдёт файлы, превышающие десять единиц по 1 МиБ согласно правилам округления `find -size`.

### Когда полезно?

Если логи занимают много дискового пространства.

### Пример QA-ситуации

Сервис перестал писать логи.

Одна из возможных причин — заполненный диск.

Можно проверить:

```bash
df -h
```

А затем найти крупные файлы в разрешённой директории логов:

```bash
find logs/ -type f -size +100M
```

---

## 21. find -mtime

Поиск по времени последней модификации файла.

### Файлы, изменённые менее суток назад

```bash
find logs/ -type f -mtime -1
```

### Важный нюанс

`-mtime -1` означает возраст изменения менее 24 часов, а не обязательно «сегодня по календарю».

GNU find также поддерживает:

```bash
find logs/ -type f -newermt '2026-10-09'
```

Здесь `-newermt` — удобное GNU-расширение для сравнения времени изменения с указанной датой.

Оно может отсутствовать в некоторых других реализациях find.

---

## 22. find + grep

Это очень полезная комбинация.

### Найти ERROR во всех .log файлах

```bash
find logs/ -type f -name '*.log' \
  -exec grep -nH 'ERROR' {} +
```

### Как работает?

`find` находит подходящие файлы.

`-exec` запускает grep для найденных файлов.

`{}` обозначает найденные пути.

`+` позволяет передавать несколько путей за один запуск команды.

### Почему удобно?

Так можно ограничить поиск только подходящими файлами, вместо рекурсивного анализа всего каталога.

### Важный нюанс

Если имена файлов содержат пробелы, конструкция `-exec ... {} +` корректно передаёт их как отдельные аргументы.

---

## 23. find и xargs

**xargs** строит аргументы команд из входных данных.

Например, можно передать найденные файлы другой команде.

### Безопасная передача имён файлов

```bash
find logs/ -type f -name '*.log' -print0 |
  xargs -0 -r grep -nH 'ERROR'
```

Здесь:

- `-print0` разделяет имена файлов нулевым байтом.
- `xargs -0` корректно обрабатывает такие разделители.
- `-r` в GNU xargs не запускает команду при пустом входе.

### Зачем нужен print0?

Имена файлов могут содержать:

- Пробелы.
- Табуляцию.
- Переводы строк.
- Специальные символы.

Поэтому передавать произвольные имена файлов через обычный текстовый поток небезопасно.

### Что лучше запомнить сначала?

Для большинства повседневных задач достаточно:

```bash
find logs/ -type f -name '*.log'
```

А для поиска текста:

```bash
find logs/ -type f -name '*.log' \
  -exec grep -nH 'ERROR' {} +
```

xargs можно изучать глубже позже.

# Часть 6. head, tail и просмотр логов

## 24. head — начало файла

```bash
head logs/app.log
```

По умолчанию показывает первые строки файла.

### Первые пять строк

```bash
head -n 5 logs/app.log
```

### Когда полезно?

- Посмотреть заголовки CSV.
- Проверить формат лога.
- Быстро оценить содержимое файла.
- Проверить начало конфигурации.

---

## 25. tail — конец файла

```bash
tail logs/app.log
```

### Последние пять строк

```bash
tail -n 5 logs/app.log
```

### Когда полезно?

Часто последние строки содержат наиболее свежие события.

Особенно если логи записываются последовательно.

---

## 26. tail -f — наблюдение в реальном времени

```bash
tail -f logs/app.log
```

Команда показывает последние строки и продолжает ожидать новые.

### Сценарий Backend QA

1. Открываем терминал.
2. Запускаем `tail -f`.
3. Отправляем HTTP-запрос через Postman.
4. Смотрим появившиеся записи.
5. Ищем нужный Request ID.

### Остановить

```text
Ctrl + C
```

### tail -F

На GNU Linux:

```bash
tail -F logs/app.log
```

Полезен при ротации логов, когда файл переименовывается и создаётся заново.

`tail -F` отслеживает имя файла и пытается переоткрывать его.

---

## 27. Последние 100 строк или последние 100 ошибок?

Это разные задачи.

### Найти ERROR среди последних 100 строк

```bash
tail -n 100 logs/app.log | grep 'ERROR'
```

Сначала берём последние сто строк, потом фильтруем ошибки.

### Найти последние 100 строк с ERROR

```bash
grep 'ERROR' logs/app.log | tail -n 100
```

Сначала находим все строки с ERROR, затем берём последние сто совпавших строк.

### Почему это важно?

Если ошибок мало, первая команда может не найти их вообще.

Вторая будет искать во всём доступном файле.

На очень больших файлах второй вариант может потребовать существенно больше чтения данных.

---

## 28. Следить только за новыми ошибками

Можно использовать:

```bash
tail -F logs/app.log | grep --line-buffered 'ERROR'
```

### Что происходит?

- `tail -F` следит за файлом.
- `grep` оставляет только ERROR.
- `--line-buffered` помогает выводить совпадения по мере получения строк.

### Важный нюанс

`--line-buffered` — опция GNU grep. В macOS и других реализациях могут быть отличия.

Без соответствующей буферизации вывод в pipeline иногда появляется с задержкой.

# Часть 7. Pipe — объединение команд

## 29. Что такое Pipe?

**Pipe (`|`)** позволяет передать стандартный вывод одной команды на стандартный ввод другой.

### Пример

```bash
cat logs/app.log | grep 'ERROR'
```

Схема:

```text
cat
 |
 | STDOUT
 v
grep
 |
 | STDOUT
 v
Terminal
```

### Более простой вариант

Для обычного поиска в файле лучше:

```bash
grep 'ERROR' logs/app.log
```

Необязательно использовать `cat` перед grep.

Но Pipe становится особенно полезен, когда нужно выполнить цепочку преобразований.

### Краткий ответ для собеседования

> Pipe позволяет объединить команды в конвейер: стандартный вывод предыдущей команды становится стандартным вводом следующей. Это удобно для фильтрации, сортировки и подсчёта данных.

---

## 30. Примеры Pipe

### Найти ошибки и посчитать строки

```bash
grep 'ERROR' logs/app.log | wc -l
```

Результат:

```text
3
```

### Найти HTTP 500 и показать только последнюю строку

```bash
grep -F 'status=500' logs/app.log | tail -n 1
```

### Найти ERROR и WARN

```bash
grep -E 'ERROR|WARN' logs/app.log
```

### Посчитать запросы выдачи бонуса

```bash
grep -cF 'path=/api/bonuses/issue' logs/app.log
```

Результат:

```text
4
```

# Часть 8. Перенаправление вывода

## 31. Оператор >

`>` перенаправляет STDOUT в файл.

Пример:

```bash
grep 'ERROR' logs/app.log > errors.log
```

Результат поиска сохранится в `errors.log`.

### Важное предупреждение

Если файл уже существует, `>` обычно перезаписывает его.

Поэтому при работе с важными данными нужно проверять целевой путь.

---

## 32. Оператор >>

`>>` добавляет вывод в конец файла.

Пример:

```bash
echo "New record" >> notes.txt
```

Если файл существует, старое содержимое сохраняется.

### Разница

| Оператор | Действие |
|---|---|
| `>` | Перезаписать файл выводом |
| `>>` | Добавить вывод в конец файла |

---

## 33. Оператор 2>

`2>` перенаправляет STDERR.

Например:

```bash
ls /not-existing-directory 2> command-errors.log
```

Сообщение об ошибке будет записано в файл.

### Почему именно 2?

Потому что стандартный поток ошибок имеет файловый дескриптор 2.

---

## 34. Что означает 2>&1?

Конструкция:

```bash
command > combined.log 2>&1
```

Направляет STDOUT и STDERR в один файл.

### Пошагово

```bash
> combined.log
```

Сначала STDOUT направляется в файл.

```bash
2>&1
```

Затем STDERR направляется туда же, куда в этот момент направлен STDOUT.

### Важный нюанс: порядок имеет значение

Эти команды не всегда эквивалентны:

```bash
command > combined.log 2>&1
```

```bash
command 2>&1 > combined.log
```

Во втором случае STDERR сначала связывается с прежним назначением STDOUT, и лишь затем STDOUT перенаправляется в файл.

### Для QA

Полезно, когда запускаешь тестовый скрипт и хочешь сохранить как обычный вывод, так и сообщения об ошибках.

---

## 35. /dev/null

`/dev/null` — специальное устройство, которое отбрасывает записываемые данные.

### Скрыть обычный вывод

```bash
command > /dev/null
```

### Скрыть ошибки

```bash
command 2> /dev/null
```

### Скрыть оба потока

```bash
command > /dev/null 2>&1
```

### Важный нюанс

Не следует подавлять ошибки при диагностике проблем.

Это полезно только тогда, когда такое поведение действительно предусмотрено.

---

## 36. Что такое tee?

**tee** одновременно выводит данные в терминал и записывает их в файл.

Пример:

```bash
grep 'ERROR' logs/app.log | tee errors.log
```

Данные:

- Отображаются в терминале.
- Сохраняются в errors.log.

### Добавить в существующий файл

```bash
grep 'ERROR' logs/app.log | tee -a errors.log
```

### Когда полезно?

При выполнении диагностики можно одновременно наблюдать результат и сохранять его для дальнейшего анализа.

Но перед сохранением логов необходимо учитывать наличие персональных данных, токенов и других секретов.

---

## 37. Exit Status и pipefail

В Bash по умолчанию exit status pipeline обычно определяется результатом последней команды.

Например:

```bash
grep 'SOMETHING_MISSING' logs/app.log | wc -l
```

Результат:

```text
0
```

Однако `wc -l` может завершиться успешно, хотя grep не нашёл совпадений и вернул код 1.

### pipefail

В Bash можно включить:

```bash
set -o pipefail
```

Тогда exit status конвейера отражает ошибку одного из его компонентов согласно правилам Bash, а не только последней команды.

### Зачем QA это знать?

Особенно при написании CI/CD скриптов.

Иначе ошибка промежуточной команды может быть незаметна.

### Важный нюанс

Отсутствие совпадений grep — обычная ситуация, и не всегда её нужно считать ошибкой теста.

Поэтому в скриптах следует явно задавать ожидаемое поведение.

# Часть 9. wc — подсчёт

**wc (Word Count)** считает строки, слова и байты.

wc -l logs/app.log

8 logs/app.log

### Количество слов

```bash
wc -w logs/app.log

### Количество байтов

wc -c logs/app.log
```

### Количество ошибок

grep 'ERROR' logs/app.log | wc -l

# Часть 10. sort и uniq

## 39. sort — сортировка

**sort** сортирует строки.

Пример:

```bash
printf '%s\n' 500 200 404 500 201 | sort
```

Результат:

```text
200
201
404
500
500
```

### Числовая сортировка

```bash
printf '%s\n' 2 10 100 | sort -n
```

Результат:

```text
2
10
100
```

### По убыванию

```bash
printf '%s\n' 2 10 100 | sort -nr
```

Результат:

```text
100
10
2
```

### Опции

- `-n` — числовая сортировка.
- `-r` — обратный порядок.
- `-u` — оставить уникальные строки.

---

## 40. uniq — уникальные соседние строки

**uniq** удаляет повторяющиеся соседние строки.

Например:

```bash
printf '%s\n' 500 500 404 500 | uniq
```

Результат:

```text
500
404
500
```

Почему 500 встретилось дважды?

Потому что uniq анализирует только соседние одинаковые строки.

### Правильная комбинация

```bash
printf '%s\n' 500 500 404 500 | sort | uniq
```

Результат:

```text
404
500
```

### Посчитать повторения

```bash
printf '%s\n' 500 500 404 500 | sort | uniq -c
```

Результат:

```text
      1 404
      3 500
```

### Краткий ответ

> sort сортирует строки, а uniq убирает соседние дубликаты или подсчитывает их. Для анализа всех повторяющихся значений обычно используют sort | uniq -c.

---

## 41. Посчитать HTTP-статусы в логах

Наши логи содержат значения:

```text
status=200
status=500
status=409
status=200
status=503
status=201
status=500
status=200
```

Извлечём их:

```bash
grep -oE 'status=[0-9]{3}' logs/app.log
```

Теперь удалим префикс:

```bash
grep -oE 'status=[0-9]{3}' logs/app.log |
  cut -d= -f2
```

Затем посчитаем:

```bash
grep -oE 'status=[0-9]{3}' logs/app.log |
  cut -d= -f2 |
  sort |
  uniq -c |
  sort -nr
```

Результат:

```text
      3 200
      2 500
      1 503
      1 409
      1 201
```

Порядок строк с одинаковым количеством может зависеть от параметров сортировки и локали.

### Что делает каждая команда?

1. `grep -oE` — извлекает значения вида status=NNN.
2. `cut` — оставляет число после знака `=`.
3. `sort` — группирует одинаковые значения.
4. `uniq -c` — считает количество.
5. `sort -nr` — сортирует результаты по убыванию количества.

### Практическое применение

Можно быстро определить, какие HTTP-статусы чаще всего встречаются в логах.

Но такой способ предполагает определённый формат текстового лога.

# Часть 11. cut — извлечение полей

## 42. Что делает cut?

**cut** извлекает определённые части строки.

Например:

```bash
echo 'userId=123' | cut -d= -f2
```

Результат:

```text
123
```

### Параметры

- `-d` — разделитель.
- `-f` — номер поля.

### Пример CSV

```bash
echo '100,Anna,Minsk' | cut -d, -f2
```

Результат:

```text
Anna
```

### Важный нюанс

cut не является полноценным CSV-парсером.

Если CSV содержит значения с кавычками и запятыми внутри поля, простое разделение по запятой может дать неправильный результат.

Для таких данных лучше использовать полноценный CSV-парсер.

# Часть 12. sed — преобразование текста

## 43. Что такое sed?

**sed (Stream Editor)** — утилита потоковой обработки текста.

Она позволяет:

- Выбирать строки.
- Заменять фрагменты текста.
- Удалять строки из выводимого потока.
- Выполнять простые преобразования.

### Краткий ответ для собеседования

> sed — потоковый редактор для обработки текста. С его помощью можно выбирать строки, выполнять замены и преобразовывать текстовые потоки, не открывая интерактивный редактор.

---

## 44. sed — замена текста

Пример:

```bash
echo 'status=500' | sed 's/status=/HTTP /'
```

Результат:

```text
HTTP 500
```

### Синтаксис

```text
s/old/new/
```

`s` означает substitution — замену.

### Глобальная замена

```bash
echo 'ERROR ERROR' | sed 's/ERROR/WARN/g'
```

Результат:

```text
WARN WARN
```

Без `g` обычно заменяется только первое совпадение в каждой обрабатываемой строке.

---

## 45. sed — вывести диапазон строк

```bash
sed -n '2,5p' logs/app.log
```

Выведет строки со второй по пятую.

### Как это работает?

- `-n` отключает автоматическую печать строк.
- `2,5` обозначает диапазон.
- `p` печатает выбранные строки.

### Для QA

Полезно, если grep показал номер строки, а нужно изучить определённый участок файла.

Например:

```bash
sed -n '100,130p' large-app.log
```

---

## 46. sed — маскирование данных

Допустим, при подготовке диагностического файла нужно скрыть Request ID:

```bash
sed -E 's/requestId=req-[0-9]+/requestId=REDACTED/g' \
  logs/app.log
```

Команда выведет изменённые строки в STDOUT.

Сам файл не изменится, если не использовать дополнительные механизмы записи.

### Важный нюанс

Такое простое выражение маскирует только идентификаторы заданного формата.

Оно не гарантирует удаления всех чувствительных данных.

Для передачи логов за пределы доверенной среды нужна полноценная политика редактирования и защиты данных.

---

## 47. Что делает sed -i?

Опция `-i` позволяет редактировать файл на месте в распространённых реализациях sed.

Но синтаксис GNU sed и BSD/macOS sed может отличаться.

Например, способы задания резервной копии не полностью одинаковы.

### Практическая рекомендация

Для диагностики сначала использовать sed без `-i`.

То есть выводить результат в терминал и убедиться, что преобразование работает правильно.

**Не следует изменять оригинальные логи на общем сервере ради удобства просмотра.**

# Часть 13. awk — анализ структурированных строк

## 48. Что такое awk?

**awk** — язык и утилита обработки текста, ориентированная на записи и поля.

Очень полезен для анализа логов, в которых данные разделены пробелами или другими символами.

### Пример

```bash
echo 'Anna 25 Minsk' | awk '{print $1}'
```

Результат:

```text
Anna
```

### Основные переменные

| Переменная | Значение |
|---|---|
| `$0` | Вся текущая строка |
| `$1` | Первое поле |
| `$2` | Второе поле |
| `$NF` | Последнее поле |
| `NF` | Количество полей текущей записи |
| `NR` | Номер записи в общем входном потоке |
| `FS` | Разделитель входных полей |

### Краткий ответ для собеседования

> awk — инструмент обработки текстовых данных, позволяющий разбивать строки на поля, фильтровать записи, выполнять условия, подсчёты и агрегации. Он особенно удобен для текстовых логов и табличных данных.

---

## 49. awk — извлечение отдельных полей

Наш лог:

```text
2026-10-09T10:00:01Z ERROR requestId=req-101 method=POST path=/api/bonuses/issue status=500 durationMs=840 message="database timeout"
```

При стандартном разделении по пробельным символам:

| Поле | Значение |
|---|---|
| `$1` | Timestamp |
| `$2` | ERROR |
| `$3` | requestId=req-101 |
| `$4` | method=POST |
| `$5` | path=/api/bonuses/issue |
| `$6` | status=500 |
| `$7` | durationMs=840 |

### Вывести уровень логирования

```bash
awk '{print $2}' logs/app.log
```

### Вывести Request ID

```bash
awk '{print $3}' logs/app.log
```

### Вывести путь и статус

```bash
awk '{print $5, $6}' logs/app.log
```

### Важный нюанс

Это работает благодаря известному формату учебного лога.

Если поля располагаются в другом порядке или внутри них присутствуют пробелы, номера полей могут измениться.

Для JSON лучше использовать специализированный JSON-парсер.

---

## 50. awk — фильтрация

Найти строки, где второй столбец равен ERROR:

```bash
awk '$2 == "ERROR"' logs/app.log
```

Это более структурированная проверка, чем простой поиск подстроки ERROR.

### Найти HTTP 500

```bash
awk '$6 == "status=500"' logs/app.log
```

### Найти длительные запросы

В нашем формате поле `$7` содержит `durationMs=...`.

Можно извлечь число:

```bash
awk '{
  split($7, parts, "=");
  if (parts[2] + 0 > 500) print
}' logs/app.log
```

Результат — запросы с durationMs больше 500:

- req-101.
- req-104.
- req-106.

### Почему +0?

Это распространённый способ явно использовать числовую интерпретацию значения в awk.

---

## 51. awk — подсчёт ошибок

```bash
awk '$2 == "ERROR" {count++} END {print count+0}' logs/app.log
```

Результат:

```text
3
```

### Как работает?

`$2 == "ERROR"` — условие.

`count++` — увеличить счётчик.

`END` — блок, выполняемый после обработки входных данных.

`print count+0` — вывести числовое значение, в том числе 0, если ошибок не было.

---

## 52. awk — среднее время ответа

Наши строки содержат durationMs.

Вычислим среднее:

```bash
awk '{
  split($7, parts, "=");
  total += parts[2];
  count++;
}
END {
  if (count > 0) {
    print "Average duration:", total / count, "ms";
  }
}' logs/app.log
```

### Для чего полезно?

Можно быстро оценить среднюю продолжительность запросов в небольшом наборе логов.

### Важный нюанс

Среднее значение не заменяет p95 или p99.

Кроме того, наш пример предполагает, что каждая строка содержит корректное числовое поле durationMs.

Для реального анализа производительности лучше использовать метрики и специализированные инструменты.

---

## 53. awk — количество запросов по HTTP-статусам

```bash
awk '{
  split($6, parts, "=");
  count[parts[2]]++;
}
END {
  for (status in count) {
    print status, count[status];
  }
}' logs/app.log
```

Результат содержит:

```text
200 3
201 1
409 1
500 2
503 1
```

Порядок строк может отличаться, поскольку обычный обход ассоциативного массива awk не гарантирует числовую сортировку ключей.

### Что здесь происходит?

`count[status]` — ассоциативный массив.

Ключ — HTTP-статус.

Значение — количество соответствующих запросов.

Это пример небольшой агрегации без отдельного скрипта на Python.

# Часть 14. jq — работа с JSON

## 54. Зачем нужен jq?

Современные Backend-приложения часто используют структурированные JSON-логи.

Пример:

```json
{
  "timestamp": "2026-10-09T10:00:00Z",
  "level": "ERROR",
  "requestId": "req-101",
  "status": 500,
  "durationMs": 840
}
```

**jq** — инструмент обработки JSON из командной строки.

Он умеет:

- Выбирать поля.
- Фильтровать объекты.
- Преобразовывать данные.
- Работать с массивами.
- Выполнять агрегации.

### Проверить наличие jq

```bash
command -v jq
```

Если jq отсутствует, его установка зависит от дистрибутива и разрешений на сервере.

---

## 55. Простой пример jq

```bash
echo '{"userId":"user-100","bonusId":777}' | jq '.userId'
```

Результат:

```json
"user-100"
```

### Вывести без JSON-кавычек

```bash
echo '{"userId":"user-100"}' | jq -r '.userId'
```

Результат:

```text
user-100
```

### Несколько полей

```bash
echo '{"userId":"user-100","bonusId":777}' |
  jq '{userId, bonusId}'
```

---

## 56. Фильтрация JSON Lines

Допустим, отдельный файл `structured.log` содержит по одному JSON-объекту на строку.

Например:

```json
{"level":"INFO","requestId":"req-100","status":200}
{"level":"ERROR","requestId":"req-101","status":500}
{"level":"ERROR","requestId":"req-104","status":503}
```

### Найти только ERROR

```bash
jq -c 'select(.level == "ERROR")' structured.log
```

### Найти все 5xx

```bash
jq -c 'select(.status >= 500 and .status < 600)' structured.log
```

### Вывести Request ID ошибок

```bash
jq -r 'select(.status >= 500 and .status < 600) | .requestId' \
  structured.log
```

Результат:

```text
req-101
req-104
```

### Почему это лучше grep для JSON?

Потому что jq понимает структуру JSON.

Он не зависит от того, в каком порядке расположены поля и сколько между ними пробелов.

### Важный нюанс

Это пример формата JSON Lines.

Если файл содержит один большой JSON-массив, команды будут отличаться.

# Часть 16. Практические задачи Backend QA

## 58. Найти запрос по Request ID

Предположим, API вернул:

```http
HTTP/1.1 500 Internal Server Error
X-Request-ID: req-101
```

Команда:

```bash
grep -F 'requestId=req-101' logs/app.log
```

Находим:

```text
2026-10-09T10:00:01Z ERROR requestId=req-101 method=POST path=/api/bonuses/issue status=500 durationMs=840 message="database timeout"
```

### Что удалось выяснить?

- Метод — POST.
- Endpoint — `/api/bonuses/issue`.
- Статус — 500.
- Время обработки — 840 мс.
- Сообщение — database timeout.

### Следующие шаги

Проверить:

- Логи базы данных.
- Доступность БД.
- Connection Pool.
- Медленные запросы.
- Таймауты.
- Состояние транзакции.
- Наличие частично выполненной бизнес-операции.

### Senior QA-подход

Не стоит автоматически делать вывод, что проблема именно в медленном SQL-запросе.

Database timeout может быть связан с:

- Недоступностью БД.
- Исчерпанием Connection Pool.
- Блокировками.
- Сетевыми проблемами.
- Долгой транзакцией.
- Медленным SQL.
- Некорректной конфигурацией таймаутов.

- Не пишут HTTP-статус в каждую строку.

## 61. Найти медленные запросы

### Что важно для QA?

Высокое время ответа не всегда является дефектом.

- SLO/SLA.
- Нагрузкой.
- Типом endpoint.
- Объёмом данных.

- Требованиями производительности.

## 62. Посчитать долю 5xx

В учебном логе:

- Всего запросов: 8.
- Запросов с 5xx: 3.

Ошибка составляет:

```text
3 / 8 * 100 = 37.5%
```

Можно посчитать awk:

```bash
awk '{
  total++;
  if ($6 ~ /^status=5[0-9][0-9]$/) {
    errors++;
  }
}
END {
  if (total > 0) {
    printf "5xx rate: %.2f%%\n", errors / total * 100;
  }
}' logs/app.log
```

Результат:

```text
5xx rate: 37.50%
```

### Важный нюанс

Это корректно только при допущении, что одна строка соответствует одному HTTP-запросу и поле `$6` содержит status.

В реальных логах один запрос может создавать десятки записей.

Для расчёта error rate нужно использовать записи запросов или специализированные метрики, а не все строки приложения подряд.

## 63. Сохранить ошибки в отдельный файл

```bash
grep 'ERROR' logs/app.log > errors.log
```

Теперь:

```bash
cat errors.log
```

покажет найденные ошибки.

### Не изменяется ли исходный лог?

Нет.

Здесь grep только читает logs/app.log, а результат записывает в отдельный errors.log.

### Где полезно?

Для анализа тестового прогона или сравнения результатов.

Но перед передачей файла другим людям необходимо удалить секреты и персональные данные согласно установленным правилам.

## 64. Поиск ошибки за конкретный период

Если timestamp находится в начале строки и имеет стабильный ISO 8601 UTC формат, можно искать по точному префиксу.

Например:

```bash
grep '^2026-10-09T10:00:0' logs/app.log
```

Найдёт строки за секунды 00–09 соответствующей минуты.

### Важный нюанс

Этот способ удобен для небольших логов, но не является универсальной обработкой временных диапазонов.

В реальных системах стоит учитывать:

- Часовые пояса.
- Разные форматы времени.
- Микросекунды.
- Многострочные сообщения.
- Отсутствие строгой сортировки.
- Разные источники логов.

Для сложных временных фильтров удобнее структурированные логи или системы вроде Loki, Elasticsearch/OpenSearch и других решений наблюдаемости.

# Часть 17. Частые ошибки при работе с командами

## 65. grep и grep -F — не одно и то же

Пример:

```bash
grep 'api.example.com' file.log
```

Точка в регулярном выражении может соответствовать любому символу.

Для буквального поиска:

```bash
grep -F 'api.example.com' file.log
```

Это особенно важно при поиске адресов и специальных значений.

---

## 66. grep -c и wc -l после grep

```bash
grep -c 'ERROR' logs/app.log
```

Считает строки с совпадениями.

```bash
grep -o 'ERROR' logs/app.log | wc -l
```

Считает выведенные вхождения.

Количество может отличаться.

---

## 67. uniq не удаляет все дубликаты без сортировки

Неправильное предположение:

```bash
uniq file.txt
```

автоматически оставит каждую строку только один раз.

Правильно:

```bash
sort file.txt | uniq
```

Или:

```bash
sort -u file.txt
```

Если требуется глобальная уникальность строк.

---

## 68. Нельзя всегда использовать awk '$9' для HTTP-статуса

Иногда встречается совет:

```bash
awk '{print $9}' access.log
```

Он работает лишь для определённых текстовых форматов access log.

Если формат логирования изменится, HTTP-статус может находиться в другом поле.

### Правильный подход

Сначала посмотреть реальные строки:

```bash
head -n 5 access.log
```

Затем выбрать подходящий способ разбора.

---

## 69. Не путать поиск файлов и поиск текста

### find

```bash
find . -name '*.log'
```

Ищет файлы по имени.

### grep

```bash
grep 'ERROR' app.log
```

Ищет совпадения в содержимом.

### Вместе

```bash
find . -type f -name '*.log' \
  -exec grep -nH 'ERROR' {} +
```

Ищет ERROR внутри найденных файлов.

---

## 70. Не подавлять все ошибки при диагностике

Команда:

```bash
command > /dev/null 2>&1
```

Скрывает и обычный вывод, и сообщения об ошибках.

Это может мешать диагностике.

Если цель — разобраться в сбое, лучше сохранять STDERR или выводить его отдельно.

find ищет файловые объекты по атрибутам, grep ищет совпадения внутри текста.

Механизм передачи STDOUT одной команды на STDIN другой.

`>` — записать вывод с перезаписью.

`>>` — добавить вывод в конец файла.

Направить STDERR туда же, куда в данный момент направлен STDOUT.

## 86. Что такое STDIN, STDOUT и STDERR?

Стандартные потоки ввода, вывода и ошибок с дескрипторами 0, 1 и 2.

## 87. Что делает tail -f?

Следит за добавлением новых данных в файл.

## 88. Чем head отличается от tail?

head показывает начало файла, tail — его конец.

## 89. Что делает wc -l?

Считает символы перевода строки во входных данных.

## 90. Зачем использовать sort | uniq -c?

Чтобы сгруппировать одинаковые строки и посчитать количество повторений.

## 91. Для чего используется sed?

Для потоковой обработки и преобразования текста.

## 92. Для чего используется awk?

Для обработки записей и полей текста, фильтрации, подсчётов и агрегации.

## 93. Что означает $1 в awk?

Первое поле текущей записи.

## 94. Что означает $0 в awk?

Вся текущая запись.

## 95. Как посчитать ERROR через awk?

```bash
awk '$2 == "ERROR" {count++} END {print count+0}' app.log
```

При условии, что уровень логирования находится во втором поле.

## 96. Для чего используется jq?

Для структурированной обработки JSON в командной строке.

## 97. Как найти ошибки в JSON Lines?

```bash
jq -c 'select(.level == "ERROR")' structured.log
```

## 98. Как искать по сжатым gzip-логам?

```bash
zgrep 'ERROR' app.log.gz
```

## 99. Что такое pipefail?

Настройка Bash, позволяющая учитывать ошибки промежуточных команд в exit status pipeline.

## 100. Как найти причину HTTP 500 на Backend?

Проверить Request ID, найти связанные логи, определить ошибку и проверить состояние зависимостей и бизнес-операции.
