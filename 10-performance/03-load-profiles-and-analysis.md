## 1. От DAU к профилю RPS

**DAU** — число уникальных активных пользователей за сутки. Нельзя получить RPS из одного DAU, не зная частоту действий.

**Пример — учебный сервис бонусов:**
- 400 000 зарегистрированных пользователей.
- DAU = 20% → 80 000 активных за сутки.
- Каждый активный пользователь в среднем запрашивает список бонусов **4 раза в сутки**.

Ожидаемые обращения к списку за сутки: 80 000 × 4 = **320 000**.

Среднее значение за полные сутки: 320 000 / 86 400 ≈ **3.70 RPS**.

Но трафик неравномерен! Пики, например ×5, дают около **18.5 RPS**, а краткие bursts ×2 от пикового — около **37 RPS**. Коэффициенты ×5 и ×2 — **допущения для примера**, их нужно подтвердить аналитикой или требованиями.

Важные дополнительные вопросы: сезонность, география, время активности, повторные запросы, retries и влияние кэширования.

## 2. Смесь запросов и think time

Если заявлено 80% запросов к списку, 18% на автовыдачу и 2% на выдачу по ID, это доли **запросов**, а не автоматически доли VU или итераций.

Например, при суммарном целевом 100 RPS можно планировать:
- список: 80 RPS;
- автовыдача: 18 RPS;
- выдача по ID: 2 RPS.

Если итерация выполняет несколько HTTP-вызовов, её arrival rate рассчитывается отдельно. Не забудь про историю бонусов, если она входит в тестируемый профиль.

Для операций изменения данных нужна подготовка уникальных пользователей и проверка состояния после теста. Иначе можно измерить только ошибки «бонус уже выдан», а не реальную выдачу.

## 3. Проверки окружения

**Перед запуском:**
1. Согласовать границы нагрузочного тестирования и расписание.
2. Зафиксировать версию Backend, конфигурацию, число реплик.
3. Указать размер и распределение БД (включая партиции/индексы).
4. Проверить кэш: cold vs warm, hit rate.
5. Подготовить достаточное число независимых пользователей.
6. Прогреть JIT/соединения, если требуется, и отдельно измерить steady state.
7. Проверить достаточную мощность load generator и сети.

**Нельзя сравнивать прогоны, если отличаются данные, профиль или инфраструктура, не зафиксировав эти отличия.**

## 4. Как анализировать результаты

Сначала проверить, что **заданная нагрузка реально достигнута**.

| Сигнал | Возможная интерпретация |
|---|---|
| Target 100 iter/s, achieved 70 | Возможно ограничение VU, генератора или длительность операций |
| dropped_iterations > 0 | Часть запланированных итераций не началась; реальная нагрузка меньше плановой |
| p95 вырос, ошибок пока мало | Деградация до отказов, проверка БД/кэша/CPU/локов |
| http_req_failed вырос | HTTP/сетевые ошибки по метрике k6 |
| Checks упали при HTTP 200 | Приложение вернуло формально успешный ответ, но не выполнило ожидаемое условие |
| Сильно выросло время ожидания | Возможна очередь, ограничение ресурсов или проблема зависимости |
| CPU генератора ~100% | Нельзя приписывать снижение RPS только Backend |

Разбирай **по сценариям и эндпоинтам**: общий p95 скрывает редкие дорогие операции.

**Bottleneck** — узкое место: CPU, память, GC, lock contention, connection pool, DB I/O, Kafka lag, сеть или лимиты gateway. Метрики указывают направление расследования, но сами по себе не доказывают причину.

## 5. Типичные ошибки

- Тестировать только 200 OK, не проверяя бизнес-результат.
- Считать iterations/s равными RPS при нескольких HTTP-вызовах.
- Использовать один bonusId/userId так, что после первого запроса все последующие измеряют 409.
- Настроить VU, но не оценить фактическую интенсивность.
- Не замечать dropped_iterations и объявлять целевую нагрузку достигнутой.
- Сравнивать cold-cache и warm-cache прогоны как одинаковые.
- Увеличить timeout до бесконечности и считать проблему решённой.
- Не мониторить сам генератор нагрузки.
- Делать вывод о производительности по короткому, непрогретому тесту.

## 6. Пример итогового отчёта

**Цель:** проверить выдачу бонусов при 50 RPS в течение 10 минут.

**Окружение:** test; 2 реплики Bonus Service; версия сборки, объём БД, число агентов и генераторов — обязательно зафиксировать.

**Ожидаемое:** p95 < 500 мс, error rate < 1%, без потери бизнес-операций (это учебные условия).

**Факт (демонстрация, не реальный замер):** 50 RPS достигнуты; p95 = 780 мс; HTTP error rate = 0.2%; CPU БД 95%; dropped_iterations = 0.

**Вывод:** SLO по p95 не выполнен, хотя формальных ошибок мало. Нужен анализ плана SQL и ресурсов БД; повтор после исправления при том же профиле.
