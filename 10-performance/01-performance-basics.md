## 1. Что мы измеряем

**Performance Testing** — оценка скорости, пропускной способности, стабильности и потребления ресурсов системы при заданных условиях.

Важно отличать **время ответа**, **количество запросов**, **число ошибок** и **потребление ресурсов**: это разные измерения.

Пример: API списка бонусов может успешно отвечать при 10 RPS, но при 200 RPS p95 растёт с 150 до 2500 мс, а CPU базы достигает 100%. Это признак деградации, даже если HTTP 500 нет.

## 2. RPS, VU, Latency, Throughput

| Метрика | Что означает | Нюанс |
|---|---|---|
| RPS | Requests per second — число HTTP-запросов в секунду | Один пользователь может делать много запросов |
| VU | Virtual User — виртуальный исполнитель сценария | 1 VU не равен 1 RPS |
| Throughput | Объём работы за время: запросы, операции, байты | Уточняй единицы |
| Latency | Задержка операции | Нужно определить границы измерения |
| Error Rate | Доля неуспешных запросов по принятому правилу | HTTP 200 может содержать бизнес-ошибку |
| Concurrency | Одновременно выполняемые операции/запросы | Не равна числу пользователей за день |

**Пример связи VU и RPS (закрытая модель):** один VU выполняет HTTP-запрос за 0.2 с и затем ждёт 0.8 с. В идеальном устойчивом случае это около 1 итерации/с на VU, но реальный RPS зависит от числа запросов на итерацию, сетевых задержек, think time и ограничений генератора.

**Приближённо** из Little's Law: одновременные выполняемые операции ≈ интенсивность поступления операций × среднее время выполнения. Это модель для устойчивого потока, не универсальная формула «VU = RPS».

## 3. Percentiles p90 p95 p99

**p95 = 400 мс** означает, что приблизительно 95% наблюдений не превышают 400 мс, а около 5% медленнее.

Пример длительностей (мс): 100, 120, 130, 140, 150, 160, 180, 200, 500, 1800.

- **Average** чувствителен к выбросам и может скрывать проблемный хвост.
- **Median p50** отражает центральную часть распределения.
- **p95/p99** помогают оценить опыт медленных запросов.
- **Max** описывает один самый медленный замер, а не типичную ситуацию.

Проверяй метрики **по отдельным эндпоинтам и сценариям**: общий p95 может выглядеть хорошо, хотя редкая ручка выдачи бонуса работает плохо.

## 4. Типы нагрузочных проверок

| Вид | Цель |
|---|---|
| **Load** | Проверить ожидаемую рабочую нагрузку |
| **Stress** | Найти область деградации и пределы |
| **Spike** | Проверить краткий резкий рост запросов |
| **Soak / Endurance** | Проверить длительную работу, утечки и накопление проблем |
| **Capacity** | Оценить, какой объём система выдерживает при заданных SLO |
| **Smoke Performance** | Быстро убедиться, что тестовый сценарий работает |

Терминология может немного отличаться по командам.

## 5. Критерии и результаты

До теста договорись:
- Окружение и версии сервиса/БД, объём данных, warm/cold cache.
- Профиль: какие операции, какой RPS, как долго, есть ли пики.
- SLO: p95, error rate, допустимые resource limits.
- Stop conditions: нагрузка не должна разрушать окружение и реальные данные.

**Пример учебного критерия:** при 50 RPS чтения списка бонусов p95 меньше 500 мс, error rate меньше 1% в течение 10 минут. Это лишь пример; реальные пороги задаёт продукт и инфраструктура.

**Интервью:** почему средний ответ 200 мс не означает хорошую производительность? Потому что хвостовые значения и отдельные сценарии могут быть значительно хуже.
