## 1. Клиент и сервер

**Клиент** инициирует обращение за ресурсом или операцией. **Сервер** принимает запрос, проверяет его и возвращает результат; это роли во взаимодействии, а не обязательно разные компьютеры.

```text
Web / Mobile WebView
       | HTTPS request
       v
API Gateway / Reverse Proxy
       |
       v
Bonus Service -----> PostgreSQL
       |
       +-----------> другой сервис / Kafka
```

**Пример:** мобильное приложение показывает список доступных бонусов. UI — клиент Backend API; Bonus Service сам становится клиентом сервиса профиля, когда узнаёт параметры пользователя.

**Для QA:** ответ 200 от Gateway не гарантирует правильность бизнес-данных; смотрим контракт, авторизацию, данные и зависимости.

## 2. Что происходит при открытии страницы

Упрощённый путь для страницы по HTTPS:
1. Браузер разбирает URL, проверяет применимый кэш и определяет, нужен ли сетевой запрос.
2. При необходимости узнаёт IP по DNS (или из другого механизма разрешения имени).
3. Устанавливает соединение: для HTTP/1.1 и HTTP/2 обычно TCP+TLS, для HTTP/3 — QUIC поверх UDP.
4. Отправляет HTTP-запрос, который может пройти через CDN, Proxy и Gateway.
5. Сервер возвращает HTML и другие ресурсы или API-ответ.
6. Браузер разбирает HTML в DOM, CSS в CSSOM, формирует дерево рендеринга, выполняет layout и paint. JavaScript может менять DOM и делать дополнительные API-запросы.

**CDN** хранит/доставляет контент ближе к потребителю; не каждый API-запрос обязательно обрабатывается CDN.

**Практика:** HTML открывается, но данные бонусов не показываются. Возможны ошибки API, CORS, JavaScript, авторизации или кэша; успешная загрузка страницы не означает успешную работу всех API.

Подробности протоколов и HTTP: [Сети](../06-networking/01-network-fundamentals.md), [HTTP](../02-http-api/01-http-basics.md).

## 3. Монолит и микросервисы

| | Монолит | Микросервисы |
|---|---|---|
| Организация | Модули в одном развёртываемом приложении | Несколько отдельно развёртываемых сервисов |
| Плюсы | Проще локальная разработка и отладка на старте | Независимые релизы и масштабирование отдельных компонентов |
| Сложности | Сильная связанность в плохо организованном коде; общие релизы | Сеть, согласованность, мониторинг, контракты, частичные отказы |
| Тестирование | Проверка границ модулей и общего состояния | Контракты, интеграции, повторы, таймауты, совместимость версий |

**Важно:** монолит не означает плохую архитектуру, а микросервисы не делают продукт автоматически надёжнее.

**Пример:** при выдаче бонуса Bonus Service обращается к Profile Service, сохраняет результат в БД и публикует событие. Даже если каждый сервис по отдельности работает, весь сценарий может завершиться частичным сбоем.

## 4. API Gateway, Reverse Proxy и балансировщик

- **Reverse Proxy** принимает запрос от клиента и перенаправляет Backend; может завершать TLS, ставить таймауты, ограничивать доступ.
- **API Gateway** — специализированная точка входа для API: маршрутизация, авторизация, rate limiting и другие политики.
- **Load Balancer** распределяет обращения между экземплярами сервиса.

Один программный компонент может выполнять несколько ролей.

```text
Client -> Gateway -> Load Balancer -> Bonus A
                                 -> Bonus B
```

**Пример QA:** только часть запросов возвращает 500. Проверяем, зависит ли ошибка от экземпляра сервиса, версии, конфигурации и конкретного набора данных.

**502** часто означает проблему ответа upstream для Gateway, **504** — ожидание upstream превысило допустимое время. Уточняем, **кто** сформировал статус, и проверяем логи.

## 5. Service Discovery и конфигурация

Сервис может обращаться к другому по имени (например, `profile-service`), которое разрешается в нужные адреса через инфраструктуру оркестрации или service discovery.

**Пример:** в тестовом окружении запросы идут в production-зависимость из-за неверного адреса конфигурации. Это риск утечки данных и побочных эффектов.

QA важно проверять **целевое окружение, конфигурацию, версии API и тестовые данные**, а не только HTTP-ответ.

## 6. Как QA проверять такую архитектуру

**Новая выдача бонуса:**
- Контракт API: метод, путь, обязательные поля, статусы, сообщения об ошибках.
- Авторизация: нельзя выдать чужому пользователю вне полномочий.
- Зависимости: что будет при недоступном Profile Service?
- Конкуренция: два запроса одновременно не нарушают лимит.
- Состояние: в БД ровно ожидаемое количество выдач.
- Асинхронность: событие публикуется и обрабатывается без дублирования эффекта.
- Наблюдаемость: есть Request ID/Trace ID и полезные логи.

**Тестировать всё только через UI не нужно:** unit и integration-тесты быстрее выявляют конкретный класс проблем.

## 7. Вопросы

**Чем монолит отличается от микросервисов?** Границей развёртывания и способом взаимодействия. Для микросервисов особенно важны сетевые сбои и согласованность.

**Что делает API Gateway?** Принимает и маршрутизирует API-запросы, применяет общие политики.

**Почему API может быть недоступен, если Backend жив?** DNS, TLS, Gateway, firewall, маршруты, зависимость или перегрузка.

**Что проверять после изменения версии одного микросервиса?** Совместимость API/событий, зависимые сервисы, состояние и критичные бизнес-сценарии.
