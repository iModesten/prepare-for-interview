## 1. Почему данные в разных сервисах могут отличаться

**Согласованность** — набор гарантий о том, какие данные и когда видят разные участники системы.

Если Backend обновляет БД, а другой сервис читает собственную проекцию, обновление не обязательно будет видно мгновенно.

\`\`\`text
POST /bonuses/issue
      |
      v
Bonus DB (данные уже записаны)
      |
      v
Kafka -> History Consumer -> History DB (обновится позднее)
\`\`\`

**Strong consistency** и **eventual consistency** — не просто названия режимов БД: нужно уточнять конкретный контракт системы. Даже сильные гарантии одного хранилища не распространяются автоматически на все сервисы.

**Пример QA:** POST вернул 201, но история ещё не показывает бонус. Это баг только если нарушен согласованный срок или свойство видимости данных.

## 2. Локальная транзакция, Outbox и Saga

Локальная SQL-транзакция атомарно объединяет изменения **в пределах одной БД** по её правилам. Она не делает публикацию в Kafka частью той же транзакции автоматически.

### Проблема Dual Write

\`\`\`text
1. COMMIT в PostgreSQL — успешно
2. Отправка Kafka-события — ошибка
\`\`\`

Данные сохранились, а подписчик об этом не узнал.

### Transactional Outbox

В одной транзакции сохраняются бизнес-данные и запись в таблице \`outbox\`.

\`\`\`text
BEGIN
  INSERT выдача бонуса
  INSERT outbox event
COMMIT
    |
    v
Отдельный Publisher публикует событие в Kafka
\`\`\`

**Почему работает:** если транзакция откатилась, не появятся ни выдача, ни outbox-запись. Если публикация временно недоступна, запись остаётся для следующей попытки.

**Не обещает:** потребитель не получит дубликаты. Publisher может повторно отправить событие после потери подтверждения, поэтому требуется идемпотентная обработка.

### Saga

**Saga** — последовательность локальных операций разных сервисов с предусмотренными компенсациями при сбоях.

Пример заказа: создать заказ → зарезервировать товар → провести платёж. Если платёж невозможен, можно отменить резерв. **Компенсация не всегда равна техническому откату** и иногда требует ручного вмешательства.

Подробнее: [Kafka и гарантии](../04-message-brokers/03-delivery-semantics.md) и [транзакции БД](../03-databases/03-transactions.md).

## 3. Что такое кэш и зачем он нужен

**Кэш** хранит копию или результат вычисления для более быстрого доступа и снижения нагрузки на основной источник.

Примеры:
- Браузер кэширует статические файлы и HTTP-ответы по правилам.
- CDN кэширует подходящий контент ближе к клиентам.
- Приложение хранит часто запрашиваемые данные в памяти.
- Redis может быть общим кэшем между экземплярами Backend.
- База использует собственные буферы страниц — это другой уровень кэширования.

**Не путать:** HTTP Cache-Control, Redis и кэш браузера — разные механизмы с разными правилами.

## 4. Cache-Aside, TTL и инвалидация

### Cache-Aside / Lazy Loading

\`\`\`text
GET /bonuses
    |
    v
Cache lookup
   | HIT  -> ответ из кэша
   |
   | MISS
   v
Получить из БД -> сохранить в кэш -> вернуть
\`\`\`

**Инвалидация** — удаление или обновление устаревшей записи. **TTL** — время до истечения записи; это не гарантия, что данные останутся актуальными весь TTL.

Способы обновления:
- Удалить ключ после успешного изменения основной БД.
- Записать обновлённое значение в кэш.
- Дождаться TTL, если допустима временная устарелость.
- Использовать версионирование или события инвалидации.

**Главная опасность:** между записью в БД и обновлением кэша возникает окно, когда другой запрос получает старые данные.

### Write-Through и Write-Behind

- **Write-Through:** запись через слой кэша синхронно обновляет источник по выбранной схеме.
- **Write-Behind / Write-Back:** запись в основной источник откладывается. Быстрее на критическом пути, но рискует потерять ещё не сброшенные изменения.

Эти названия обозначают паттерны, а не универсальные гарантии реализации.

## 5. Cache Stampede и Stale Data

**Stale Data** — кэш возвращает устаревшие данные.

**Cache Stampede** — многие запросы одновременно обнаруживают истёкший ключ и обращаются к БД, создавая пик нагрузки.

\`\`\`text
Популярный ключ истёк
     |
  1000 GET одновременно
     |
  1000 обращений к БД (если нет защиты)
\`\`\`

Способы снижения риска: запрос-одиночка (single flight), блокировка на обновление, разное время истечения ключей, предварительное прогревание кэша, stale-while-revalidate — в зависимости от допустимой устарелости.

**Важно для нагрузки:** быстрый ответ на прогретом кэше не характеризует производительность при массовых промахах.

## 6. Какие проверки нужны QA

| Сценарий | Ожидаемая идея |
|---|---|
| Первый GET при пустом кэше | Получить правильные данные из источника |
| Повторный GET | Не нарушить контракт и права доступа |
| Данные изменились в БД | Кэш обновляется/истекает согласно требованиям |
| Пользователь A, затем пользователь B | Нельзя отдать чужие персонализированные данные |
| Кэш недоступен | Ожидаемая деградация или отказ, без повреждения состояния |
| Срок TTL истёк | Обновлённые данные появляются в пределах согласованного окна |
| 1000 запросов после истечения ключа | Система выдерживает нагрузку или ограничивает всплеск |
| Outbox Publisher упал | Запись осталась и публикация восстанавливается |
| Consumer получил событие дважды | Бизнес-операция не повторилась недопустимым образом |

**Вопрос на интервью:** почему пользователь иногда видит старые данные после успешного обновления? Ответ: возможны кэши, реплики или асинхронные проекции; нужно проверить, откуда читает клиент и какие гарантии консистентности обещаны.
