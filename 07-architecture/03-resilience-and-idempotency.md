## 1. Виды отказов

В распределённой системе **частичный сбой** нормален: один компонент продолжает работать, другой недоступен. Ошибки бывают:
- Сеть не даёт установить соединение.
- Соединение установлено, но ответ слишком долгий.
- Сервер вернул отказ валидации или авторизации.
- Сервер выполнил действие, но ответ потерялся.
- Зависимость выполнила только часть работы.

**Главное правило QA:** HTTP-ошибка и фактический бизнес-результат — разные вещи.

## 2. Timeout

**Timeout** — ограничение времени ожидания определённого этапа: подключения, чтения ответа, полного запроса.

\`\`\`text
Client -> Bonus Service -> Database
         ждал 3 сек       запрос ещё выполняется?
         timeout
\`\`\`

Клиентский timeout не отменяет автоматически работу на сервере. Для финансовых и бонусных операций обязательно исследовать последствия повторных запросов.

**Пример:** POST выдал бонус, но клиент получил 504 от Gateway. Повтор может создать дубль, если не предусмотрена защита.

## 3. Retry и Backoff

**Retry** — повторная попытка операции. Полезна при временных сбоях, но опасна для операций с побочными эффектами.

**Backoff** — задержка между попытками. **Exponential Backoff** увеличивает её по мере повторов; **jitter** добавляет случайность, чтобы клиенты не повторяли запрос одновременно.

\`\`\`text
Попытка 1 -> ошибка 503
   wait ~200ms
Попытка 2 -> ошибка 503
   wait ~400ms
Попытка 3 -> успех / завершить с ошибкой
\`\`\`

Это иллюстрация, не универсальные интервалы.

**Когда НЕ надо слепо повторять:** ошибку валидации 400, постоянный 403, неизвестный результат неидемпотентного POST.

**Retry Storm:** если сотни клиентов одновременно повторяют запрос, перегруженный сервис может стать ещё менее доступным. Нужно учитывать предел числа попыток и общий deadline.

## 4. Идемпотентность

**Идемпотентная операция** при многократном выполнении имеет тот же предусмотренный эффект на состояние, что и при однократном выполнении. HTTP-код повторного ответа не обязан совпадать.

Пример API выдачи:
\`\`\`http
POST /bonuses/issue
Idempotency-Key: issue-user42-bonus7
Content-Type: application/json

{"userId":42,"bonusId":7}
\`\`\`

Возможный механизм:
1. Backend получает ключ и данные операции.
2. Атомарно резервирует/фиксирует ключ в хранилище.
3. Выполняет выдачу.
4. При повторе с тем же ключом не создаёт вторую выдачу, а возвращает предусмотренный контрактом результат.

**Нюансы для тестирования:**
- Повтор одинакового запроса с одинаковым ключом.
- Один ключ, но **другое тело** (обычно конфликт по контракту).
- Два параллельных запроса с одним ключом.
- Отказ между записью ключа и выдачей.
- Истечение срока хранения ключа.
- Разные пользователи и границы области действия ключа.

**Не путай:** идемпотентность HTTP-метода и идемпотентность бизнес-операции — связанные, но разные свойства. POST может быть спроектирован идемпотентным на бизнес-уровне.

Подробности: [HTTP API](../02-http-api/05-rest-api-testing.md).

## 5. Circuit Breaker, Bulkhead и Rate Limit

**Circuit Breaker** — после серии неудач временно перестаёт отправлять вызовы неисправной зависимости и быстро возвращает запасной результат/ошибку. Позже пробует восстановить обращения.

\`\`\`text
CLOSED (запросы проходят)
   -> слишком много сбоев
OPEN (быстрый отказ)
   -> пауза
HALF-OPEN (ограниченная проверка)
   -> CLOSED или обратно OPEN
\`\`\`

**Bulkhead** разделяет ресурсы, чтобы медленная зависимость не занимала все потоки/соединения и не блокировала остальные операции.

**Rate Limiting** ограничивает количество операций за период или по другим условиям. Это не то же самое, что Circuit Breaker. При превышении лимита HTTP API часто возвращает 429, иногда с Retry-After.

**Для QA:** после восстановления зависимости Circuit Breaker должен вернуться в рабочее состояние; лимиты разных клиентов должны не смешиваться, если это предусмотрено контрактом.

## 6. Частичный сбой и компенсация

Пример:
\`\`\`text
1. Выдача записана в PostgreSQL — успех
2. Отправка события в Kafka — ошибка
3. Уведомление пользователю — не получено
\`\`\`

**Нельзя просто откатить удалённую операцию общим SQL ROLLBACK:** локальная транзакция не охватывает все независимые системы.

Возможные решения — **Transactional Outbox**, Saga/компенсирующие действия и другие архитектурные механизмы. Эти механизмы различаются; компенсация не всегда возвращает мир точно в исходное состояние.

## 7. Тестовые сценарии

| Сбой | Что проверять |
|---|---|
| Ответ потерялся после успешного POST | Факт операции, повтор, отсутствие дубля |
| Один запрос выполняется дольше timeout | Поведение клиента и Gateway, результат в БД |
| 503 при временном сбое | Контролируемые retry/backoff, лимит попыток |
| 400/403 | Нет опасных автоматических повторов |
| Два одновременных одинаковых POST | Атомарность, идемпотентность, лимиты |
| Dependency недоступна 5 минут | Circuit Breaker / деградация / восстановление |
| Kafka недоступна после записи в БД | Outbox, восстановление публикации, отсутствие дубликатов |
| Поток запросов выше лимита | 429, корректность политики rate limiting |

**Интервью:** «Почему нельзя просто повторить любой POST после timeout?» — потому что сервер мог уже выполнить операцию, и повтор может создать второй эффект.
