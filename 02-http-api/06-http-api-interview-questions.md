# Часть 1. HTTP — основы и методы

## 1. Что такое HTTP?

**Middle**

HTTP — протокол прикладного уровня, используемый для обмена сообщениями между клиентом и сервером.

Клиент отправляет запрос с методом, адресом ресурса, заголовками и необязательным телом. Сервер возвращает ответ со статус-кодом, заголовками и необязательным телом.

HTTP по своей семантике stateless.

## 2. Что означает Stateless?

**Middle**

Каждый HTTP-запрос рассматривается самостоятельно. Сам протокол не требует хранить историю предыдущих запросов пользователя.

Для сохранения пользовательского состояния приложение использует дополнительные механизмы:

- Cookies.
- Сессии.
- Токены.
- Данные в БД или Redis.

**Уточнение:** stateless не означает, что сервер вообще не хранит состояние.

## 3. Чем HTTP отличается от HTTPS?

**Middle**

HTTPS — это HTTP, передаваемый через защищённое соединение TLS.

TLS обеспечивает конфиденциальность передаваемых данных, контроль целостности соединения и аутентификацию сервера при корректной проверке сертификата.

Стандартные порты:

- HTTP — 80.
- HTTPS — 443.

**Senior:** при HTTP/3 используется QUIC поверх UDP, включающий TLS 1.3.

## 4. Что происходит, когда пользователь открывает веб-страницу?

**Middle**

Упрощённо:

1. Браузер определяет адрес и проверяет доступные кэши.
2. При необходимости выполняет DNS-разрешение.
3. Устанавливает соединение.
4. Для HTTPS выполняет защищённое установление соединения.
5. Отправляет HTTP-запрос.
6. Получает ответ сервера или CDN.
7. Обрабатывает HTML.
8. Загружает CSS, JavaScript и другие ресурсы.
9. Формирует DOM и CSSOM, выполняет layout и rendering.

**Senior:** можно дополнительно рассказать о CDN, Reverse Proxy, Load Balancer, HTTP-кэшировании и последующих API-запросах.

## 5. Чем GET отличается от POST?

**Middle**

GET предназначен для получения представления ресурса и является безопасным и идемпотентным по стандартной семантике.

POST передаёт данные для обработки согласно правилам целевого ресурса. Он может создавать сущности или запускать бизнес-операции.

POST не является безопасным и не гарантирует идемпотентность.

## 6. Чем PUT отличается от PATCH?

**Middle**

PUT предназначен для создания или замены состояния целевого ресурса.

PATCH применяется для частичного изменения ресурса.

PUT имеет идемпотентную семантику.

PATCH не гарантированно идемпотентен: всё зависит от конкретной операции.

**Пример:** установить баланс в 100 и увеличить баланс на 100 — разные по идемпотентности действия.

## 7. Что такое Safe Method?

**Middle**

Безопасный метод — метод, который по своей семантике не предполагает запрошенного клиентом изменения состояния сервера.

Примеры:

- GET.
- HEAD.
- OPTIONS.

Технические побочные эффекты, например запись в лог, могут происходить.

**Важно:** GET, который списывает деньги или выдаёт бонус, нарушает семантику безопасного метода.

## 8. Что такое идемпотентность HTTP-метода?

**Middle**

Идемпотентность означает, что многократное выполнение одинакового запроса оказывает тот же предполагаемый эффект на сервер, что и однократное.

Идемпотентны по стандарту:

- GET.
- HEAD.
- OPTIONS.
- PUT.
- DELETE.

POST и PATCH не гарантированно идемпотентны.

**Senior:** идемпотентность не требует одинаковых HTTP-ответов при повторах.

## 9. Почему для логина обычно используют POST, а не GET?

**Middle**

Логин — это операция обработки учётных данных, часто создающая сессию или выдающая токен.

GET предназначен для чтения, а размещение логина и пароля в URL создаёт дополнительные риски их попадания в историю, логи и другие системы.

POST позволяет передавать учётные данные в теле запроса.

**Важно:** POST сам по себе не шифрует данные. Для защиты пароля необходим HTTPS.

### Готовый ответ

> POST лучше соответствует семантике логина, потому что операция обрабатывает учётные данные и может создавать сессию. Кроме того, при GET параметры обычно находятся в URL, который может сохраняться в истории браузера и логах. Поэтому данные передают в теле POST-запроса по HTTPS.

## 10. Может ли POST быть идемпотентным?

**Middle / Senior**

Да, конкретное API может реализовать идемпотентную бизнес-операцию поверх POST.

Например:

```http
POST /payments
Idempotency-Key: payment-123
```

Сервер распознаёт повторную попытку и не выполняет второй платёж.

Однако сам HTTP-метод POST не гарантирует такое поведение.

# Часть 2. HTTP Status Codes

## 11. Чем отличаются 200, 201, 202 и 204?

**Middle**

| Код | Значение |
|---|---|
| 200 OK | Успешное выполнение |
| 201 Created | Создан новый ресурс |
| 202 Accepted | Запрос принят, обработка не завершена |
| 204 No Content | Успех без содержимого ответа |

**Уточнение:** 202 не гарантирует успешного завершения асинхронной бизнес-операции.

## 12. Чем 400 отличается от 422?

**Middle**

400 Bad Request — проблема с запросом, например некорректный синтаксис.

422 Unprocessable Content — сервер понимает тип и синтаксис содержимого, но не может выполнить его инструкции из-за семантической ошибки.

Пример:

```json
{
  "startDate": "2026-10-20",
  "endDate": "2026-10-10"
}
```

Синтаксис корректный, но даты могут нарушать бизнес-правило.

**Важно:** некоторые API используют 400 и для ошибок валидации. Ожидаемое поведение определяется контрактом.

## 13. Чем 401 отличается от 403?

**Middle**

401 Unauthorized — требуется корректная аутентификация либо предоставленные учётные данные не приняты.

403 Forbidden — сервер отказывает в выполнении запроса, например из-за недостаточных прав.

**Пример:**

- Нет access token — обычно 401.
- Токен действителен, но нет прав ADMIN — обычно 403.

Сервер может возвращать 404 для сокрытия существования приватного ресурса, если это предусмотрено политикой.

## 14. Чем 409 отличается от 412?

**Middle / Senior**

409 Conflict — запрос конфликтует с текущим состоянием ресурса.

412 Precondition Failed — не выполнено условие запроса, переданное через условные заголовки, например `If-Match`.

**Пример:**

- Бонус уже выдан — возможен 409.
- Клиент пытается обновить ресурс со старым ETag — возможен 412.

## 15. Чем отличаются 500, 502, 503 и 504?

**Middle**

- 500 — внутренняя ошибка сервера.
- 502 — шлюз или прокси получил непригодный ответ от upstream.
- 503 — сервис временно не может обработать запрос.
- 504 — шлюз или прокси не дождался ответа upstream вовремя.

**Senior:** HTTP-статус помогает локализовать проблему, но для точной причины нужны логи, tracing и информация об инфраструктуре.

# Часть 3. HTTP Headers и CORS

## 16. Что такое HTTP Headers?

**Middle**

HTTP-заголовки передают метаданные и управляющую информацию о запросе и ответе.

Примеры:

- Authorization.
- Cookie.
- Content-Type.
- Accept.
- Cache-Control.
- Origin.
- ETag.

Имена заголовков регистронезависимы.

## 17. Чем Content-Type отличается от Accept?

**Middle**

Content-Type описывает формат содержимого текущего сообщения.

Accept указывает форматы ответа, которые клиент готов получить.

Например:

```http
Content-Type: application/json
Accept: application/xml
```

Клиент отправляет JSON, но предпочитает XML в ответе.

## 18. Что такое Origin?

**Middle**

Origin — источник браузерного запроса, определяемый комбинацией:

```text
scheme + host + port
```

Например:

```http
Origin: https://shop.example.com
```

Origin не содержит URL path и query parameters.

Используется в CORS и может применяться в дополнительных проверках безопасности, включая CSRF-защиту.

**Важно:** Origin не является способом аутентификации пользователя.

## 19. Чем Origin отличается от Host и Referer?

**Middle**

Предположим, страница:

```text
https://shop.example.com/catalog
```

Обращается к:

```text
https://api.example.com/orders
```

Запрос может содержать:

```http
Host: api.example.com
Origin: https://shop.example.com
Referer: https://shop.example.com/catalog
```

- Host — целевой хост.
- Origin — источник запроса: схема, хост, порт.
- Referer — сведения об исходной странице, которые могут включать путь.

Содержимое Referer зависит от Referrer-Policy.

## 20. Что такое Same-Origin Policy?

**Middle**

Same-Origin Policy — браузерная политика безопасности, ограничивающая определённые взаимодействия между разными origin.

В частности, она не позволяет произвольному JavaScript одного сайта свободно читать данные другого сайта.

**Важно:** SOP не запрещает абсолютно все cross-origin запросы.

## 21. Что такое CORS?

**Middle**

CORS — механизм, позволяющий серверу через HTTP-заголовки сообщить браузеру, каким origin разрешён доступ к cross-origin ответам.

Например:

```http
Access-Control-Allow-Origin: https://shop.example.com
```

**Senior:** CORS применяется браузером и не заменяет серверную аутентификацию, авторизацию или CSRF-защиту.

## 22. Что такое CORS Preflight?

**Middle**

Preflight — предварительный OPTIONS-запрос, который браузер отправляет перед определёнными cross-origin запросами.

Он может содержать:

```http
Origin: https://shop.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

Сервер отвечает соответствующими CORS-разрешениями.

Если preflight не проходит, основной запрос браузер обычно не отправляет.

**Уточнение:** не каждый cross-origin POST требует preflight.

## 23. Почему API работает в Postman, но не работает в браузере?

**Middle**

Потому что Postman не применяет браузерную Same-Origin Policy для доступа к ответам.

Браузер проверяет:

- Origin.
- Access-Control-Allow-Origin.
- Preflight.
- Разрешённые методы и заголовки.
- Credentials.

Если политика не позволяет доступ, JavaScript получит CORS-ошибку.

**Senior:** при некоторых CORS-ошибках запрос уже дошёл до Backend и мог изменить данные.

## 24. Что делают HttpOnly, Secure и SameSite?

**Middle**

Это атрибуты cookie.

- HttpOnly — ограничивает чтение cookie через JavaScript.
- Secure — ограничивает передачу cookie защищённым соединением.
- SameSite — регулирует отправку cookie в межсайтовых контекстах.

Основные значения SameSite:

- Strict.
- Lax.
- None.

Для SameSite=None обычно требуется Secure.

## 25. Чем SameSite отличается от Same-Origin?

**Middle / Senior**

Same-Origin требует совпадения схемы, хоста и порта.

SameSite использует понятие site, которое в современных браузерах учитывает схему и регистрируемый домен.

Например:

```text
https://shop.example.com
https://api.example.com
```

Это разные origin, но обычно один site.

Поэтому SameSite не следует считать эквивалентом Same-Origin Policy.

# Часть 4. Кэширование и безопасность браузера

## 26. Чем Cache-Control: no-cache отличается от no-store?

**Middle**

`no-cache` допускает хранение ответа, но требует проверки его актуальности перед повторным использованием.

`no-store` предписывает кэшу не сохранять сообщение.

Для чувствительных API-ответов может использоваться:

```http
Cache-Control: no-store
```

Но фактическая политика должна соответствовать требованиям приложения.

## 27. Что такое ETag и If-Match?

**Middle / Senior**

ETag — валидатор версии представления ресурса.

`If-None-Match` используется, например, для условного получения кэшированного представления.

`If-Match` позволяет выполнить операцию только при совпадении версии.

Пример:

```http
PUT /users/100
If-Match: "version-10"
```

Если версия изменилась, сервер может вернуть 412 Precondition Failed.

Это один из способов защиты от потерянных обновлений.

## 28. Чем CSRF отличается от XSS?

**Middle**

CSRF — атака, при которой браузер пользователя выполняет нежелательное действие с его полномочиями.

XSS — выполнение недоверенного JavaScript в контексте веб-приложения.

Для CSRF важны:

- CSRF-токены.
- SameSite.
- Проверка Origin/Referer.
- Fetch Metadata.

Для XSS важны:

- Безопасный вывод данных.
- Контекстное экранирование.
- Безопасные DOM API.
- HTML Sanitization.
- CSP.

**Важно:** CORS сам по себе не является полной CSRF-защитой.

# Часть 5. Authentication и Authorization

## 29. Чем Authentication отличается от Authorization?

**Middle**

Authentication — проверка того, кто обращается к системе.

Authorization — проверка того, какие действия этому субъекту разрешены.

Пользователь может успешно пройти аутентификацию, но не иметь доступа к чужому счёту или административному API.

## 30. Чем Session-based Authentication отличается от Token-based?

**Middle**

При типичной Session-based Authentication сервер хранит состояние сессии, а клиент передаёт её идентификатор.

При Token-based Authentication клиент предъявляет токен, который сервер проверяет.

Однако механизмы могут комбинироваться: например, токены тоже могут передаваться в cookies, а токенная авторизация может обращаться к серверному состоянию.

## 31. Что такое JWT?

**Middle**

JWT — формат передачи набора claims.

Типичный подписанный JWT в компактной форме имеет три части:

```text
HEADER.PAYLOAD.SIGNATURE
```

Подпись позволяет проверить целостность и подлинность токена.

Обычный подписанный JWT не зашифрован: payload можно декодировать без секретного ключа.

## 32. Какие JWT Claims важно проверять?

**Middle / Senior**

- `iss` — издатель токена.
- `sub` — субъект.
- `aud` — целевая аудитория.
- `exp` — срок окончания действия.
- `nbf` — время, раньше которого токен недействителен.
- `iat` — время выпуска.

Также проверяется подпись и допустимый алгоритм.

Нужный набор claims определяется типом токена и политикой приложения.

## 33. Чем Access Token отличается от Refresh Token?

**Middle**

Access Token используется для доступа к защищённым ресурсам.

Refresh Token применяется для получения нового Access Token.

Refresh Token требует строгой защиты, поскольку позволяет продлевать доступ.

**Senior:** стоит знать Refresh Token Rotation, отзыв токенов и повторное использование старого refresh token.

## 34. Чем OAuth 2.0 отличается от OpenID Connect?

**Middle**

OAuth 2.0 — framework делегированной авторизации.

OpenID Connect — протокол аутентификации поверх OAuth 2.0.

OIDC определяет ID Token, содержащий сведения об аутентификации пользователя.

**Важно:** Access Token и ID Token имеют разные назначения.

## 35. Что такое PKCE?

**Middle / Senior**

PKCE — механизм защиты Authorization Code Flow от определённых атак с перехватом или внедрением authorization code.

Клиент формирует:

- code_verifier.
- code_challenge.

При обмене authorization code сервер проверяет соответствие verifier и challenge.

PKCE используется не только в мобильных приложениях.

# Часть 6. REST и тестирование API

## 36. Что такое REST?

**Middle**

REST — архитектурный стиль построения распределённых систем.

Основные ограничения:

- Client–Server.
- Stateless.
- Cacheable.
- Uniform Interface.
- Layered System.
- Code on Demand — необязательное.

REST — не отдельный протокол и не просто HTTP с JSON.

## 37. Что такое API Contract?

**Middle**

API Contract — соглашение между клиентом и сервером.

Включает:

- Endpoints и методы.
- Параметры.
- Request/Response Schema.
- HTTP-статусы.
- Ошибки.
- Авторизацию.
- Бизнес-ограничения взаимодействия.

OpenAPI позволяет формализовать значительную часть HTTP API-контракта.

## 38. Чем Contract Testing отличается от Integration Testing?

**Middle**

Contract Testing проверяет соответствие API согласованному контракту.

Integration Testing проверяет взаимодействие компонентов и зависимостей.

Например:

- Проверка JSON Schema — контрактная проверка.
- Проверка записи в PostgreSQL и публикации события Kafka — интеграционная проверка.

Один интеграционный тест может также проверять часть контракта.

## 39. Какие техники тест-дизайна ты используешь для API?

**Middle**

Основные:

- Классы эквивалентности.
- Анализ граничных значений.
- Таблицы решений.
- Переходы состояний.
- Pairwise.
- Error Guessing.

**Senior:** важно выбирать технику в зависимости от структуры требований, а не применять все техники механически.

## 40. Что такое Pairwise Testing?

**Middle**

Pairwise — комбинаторная техника тестирования, обеспечивающая покрытие каждой пары значений параметров хотя бы в одной тестовой комбинации.

Она помогает сократить число проверок относительно полного перебора.

Однако не гарантирует выявление дефектов, зависящих от комбинаций трёх и более параметров.

# Часть 7. API Testing — уровень Senior

## 41. Как ты подходишь к тестированию нового Backend Endpoint?

**Senior**

Мой подход:

1. Изучить бизнес-требования.
2. Проанализировать API-контракт.
3. Определить зависимости.
4. Выявить наиболее существенные риски.
5. Спроектировать позитивные и негативные проверки.
6. Учесть авторизацию, идемпотентность и конкурентный доступ.
7. Проверить фактические бизнес-результаты.
8. Учесть существующее автоматизированное покрытие.

Главное — не просто проверить статус-коды, а убедиться в корректности операции в разных состояниях системы.

## 42. Что проверять в Response помимо Status Code?

**Middle / Senior**

- Response Headers.
- Content-Type.
- JSON Schema.
- Типы данных.
- Значения.
- Обязательные поля.
- Бизнес-согласованность.
- Отсутствие чувствительных данных.
- Фактические изменения в системе.
- Время ответа, если имеются требования.

HTTP 200 не доказывает, что бизнес-операция выполнена правильно.

## 43. Как тестировать Pagination?

**Middle / Senior**

Нужно проверить:

- Первую страницу.
- Последнюю страницу.
- Пустую страницу.
- Минимальный и максимальный размер.
- Некорректные параметры.
- Сортировку.
- Отсутствие неожиданных дублей и пропусков.
- Поведение при конкурентном изменении данных.

**Senior:** знать различия Offset и Cursor Pagination.

Offset Pagination может приводить к повторам или пропускам при изменении набора данных между запросами.

## 44. Как тестировать Filtering и Sorting?

**Middle**

Проверять фильтры отдельно и в комбинациях, допустимые и недопустимые значения, NULL, регистр символов и граничные даты.

Для сортировки:

- ASC и DESC.
- Числа.
- Строки.
- Даты.
- Одинаковые значения.
- NULL.

**Senior:** обязательно проверять совместную работу фильтрации, сортировки и пагинации.

## 45. Что означает Timeout при POST?

**Senior**

Timeout означает, что клиент не получил результат в установленное время.

Он не доказывает, что сервер не выполнил операцию.

Например, сервер мог зафиксировать платёж в БД, но ответ потерялся.

Поэтому нужно проверять фактическое состояние операции и безопасное повторение запроса.

## 46. Как тестировать Idempotency Key?

**Senior**

Основные сценарии:

1. Первый запрос.
2. Повтор идентичного запроса.
3. Повтор после таймаута.
4. Параллельные запросы с одним ключом.
5. Один ключ с разными параметрами.
6. Разные ключи.
7. Повтор после истечения срока хранения ключа.

Главная проверка — отсутствие нежелательного повторного бизнес-эффекта.

## 47. Как тестировать конкурентную выдачу последнего бонуса?

**Senior**

Предположим, осталось одно доступное начисление.

Параллельно отправляем несколько запросов.

Проверяем:

- Не превышен лимит.
- Не создано лишних выдач.
- Согласованы счётчики и история.
- Корректны ответы на конфликтующие операции.
- Нет частично сохранённых данных.
- Повторные запросы безопасны.

Важно обеспечить реальное пересечение операций, чтобы проверить race condition.

## 48. Что такое BOLA / IDOR и как это тестировать?

**Senior**

BOLA — ошибка объектной авторизации, позволяющая получить или изменить ресурс без необходимых прав.

Например, пользователь A меняет:

```http
GET /orders/100
```

На:

```http
GET /orders/101
```

Если заказ 101 принадлежит другому пользователю, Backend должен проверить право доступа.

**Важно:** валидный JWT и использование UUID сами по себе не защищают от BOLA.

## 49. Что проверять при ошибке внешней зависимости?

**Senior**

Например, Backend обращается к PostgreSQL или другому микросервису.

Нужно проверить:

- Какую ошибку получает клиент.
- Откатываются ли изменения при необходимости.
- Не возникает ли неконсистентное состояние.
- Есть ли корректные retry.
- Не дублируется ли бизнес-операция.
- Как система восстанавливается.
- Есть ли достаточные логи и метрики.

Для асинхронных операций также необходимо проверить публикацию и обработку событий.

## 50. Нужно ли вручную проверять Endpoint, если разработчик уже написал тесты?

**Senior**

Необязательно дублировать все сценарии.

Я бы сначала оценил:

- Какие требования покрыты.
- Насколько качественные тесты.
- Какие реальные зависимости используются.
- Есть ли непокрытые бизнес-риски.
- Проверены ли ошибки, конкурентность и авторизация.

После этого выбрал бы дополнительные проверки на подходящем уровне.

Главная цель — достаточная уверенность в качестве, а не максимальное количество тестов.

# Дополнительные практические сценарии

## Сценарий A. POST вернул 500, но запись появилась в БД

**Вопрос:** считать ли операцию неуспешной?

**Ответ:** нельзя делать вывод только по HTTP-статусу.

Возможно, DB COMMIT прошёл успешно, а ошибка произошла позже, например при формировании ответа или обращении к другой зависимости.

Нужно выяснить точку сбоя, фактическое состояние данных и ожидаемое контрактное поведение.

Повторный запрос может быть опасен без идемпотентности.

---

## Сценарий B. В браузере CORS Error, а в логах Backend успешный POST

**Вопрос:** как такое возможно?

**Ответ:** основной запрос мог успешно дойти до Backend, а браузер заблокировал JavaScript доступ к ответу из-за CORS-политики.

Нужно проверить Origin, CORS-заголовки ответа, наличие preflight и фактическое изменение данных.

---

## Сценарий C. Пользователь перелогинился, но видит данные предыдущего пользователя

**Вопрос:** что проверять?

**Ответ:**

- Cache-Control.
- Browser cache.
- CDN.
- Backend cache.
- Session/Cookie.
- Authorization.
- Корректность ключей кэша.
- Клиентское состояние после logout/login.

Это потенциальный дефект безопасности с высоким приоритетом.

---

## Сценарий D. Два клиента одновременно редактируют один ресурс

**Вопрос:** какая проблема возможна?

**Ответ:** Lost Update.

Клиент B может перезаписать изменения клиента A, если оба редактировали устаревшую версию.

Возможное решение — ETag и If-Match либо другой механизм контроля версии.

Тестируем конфликт и отсутствие потерянных обновлений.

---

## Сценарий E. API вернул 202 Accepted, но операция так и не выполнилась

**Вопрос:** всегда ли это дефект?

**Ответ:** 202 не гарантирует завершения операции.

Нужно проверить контракт: предусмотрены ли статус операции, таймаут, повторные попытки и переход в FAILED.

Дефект определяется тем, как фактическое поведение соответствует этим требованиям.

---

## Сценарий F. Endpoint корректно валидирует JWT, но позволяет изменять чужие заказы

**Вопрос:** какая ошибка?

**Ответ:** BOLA — Broken Object Level Authorization.

Backend проверяет подлинность токена, но недостаточно проверяет право пользователя на конкретный ресурс.

Нужно тестировать не только роли и scopes, но и принадлежность объектов.

---

## Сценарий G. Login API работает через POST, но пароль появляется в логах

**Вопрос:** решает ли POST проблему безопасности?

**Ответ:** нет.

POST не гарантирует безопасное логирование или шифрование само по себе.

Нужно использовать HTTPS, исключать секреты из логов, защищать доступ к журналам и корректно управлять учётными данными.

---

## Сценарий H. Клиент автоматически повторяет POST после 504

**Вопрос:** в чём риск?

**Ответ:** upstream мог выполнить бизнес-операцию, но не успеть вернуть ответ шлюзу.

Повтор без идемпотентности может привести к двойному списанию, созданию двух заказов или повторной выдаче бонуса.

Для критичных операций нужен способ безопасного повторения или проверки статуса.

# Частые ошибки на собеседовании

| Неправильное утверждение | Как правильно |
|---|---|
| POST всегда безопаснее GET | Безопасность передачи обеспечивает HTTPS; методы отличаются семантикой |
| Идемпотентный запрос всегда возвращает одинаковый ответ | Идемпотентность относится к предполагаемому эффекту |
| Origin — полный адрес страницы | Origin содержит схему, хост и порт |
| CORS запрещает все чужие запросы | CORS регулирует браузерный доступ к cross-origin ответам |
| CORS полностью защищает от CSRF | CSRF может не требовать чтения ответа |
| JWT всегда зашифрован | Подписанный JWT обычно можно декодировать |
| OAuth 2.0 — протокол аутентификации | OAuth 2.0 — framework авторизации; OIDC добавляет аутентификацию |
| Валидный JWT даёт доступ к любому ресурсу | Нужна объектная и функциональная авторизация |
| HTTP 500 гарантирует откат операции | Бизнес-операция могла завершиться до ошибки |
| Timeout означает, что сервер ничего не сделал | Результат операции может быть неизвестен |
| UUID защищает от чтения чужих объектов | UUID не заменяет проверку прав |
| Достаточно проверить JSON Schema | Нужны бизнес-ассерции и проверки фактического состояния |
