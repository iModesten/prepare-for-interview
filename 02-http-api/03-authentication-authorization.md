# Authentication & Authorization — сессии, JWT, OAuth 2.0 и безопасность API

**Уровень:** Middle / Senior QA Engineer  
**Темы:** Authentication, Authorization, Sessions, Cookies, JWT, Access Token, Refresh Token, OAuth 2.0, OpenID Connect, RBAC, API Security

---

## 1. Authentication vs Authorization

Это два связанных, но разных процесса.

**Authentication (аутентификация)** — проверка того, кто обращается к системе.

**Authorization (авторизация)** — проверка того, что этому пользователю или сервису разрешено делать.

### Пример

Пользователь открывает банковское приложение.

1. Вводит логин и пароль.
2. Система проверяет учётные данные.
3. Пользователь успешно аутентифицирован.
4. Пользователь пытается открыть чужой счёт.
5. Система проверяет его права.
6. Доступ запрещается.

Шаги 1–3 — Authentication.

Шаги 4–6 — Authorization.

### Краткий ответ для собеседования

> Authentication — это проверка личности пользователя или другого субъекта. Authorization — проверка его прав на конкретное действие или ресурс. Успешная аутентификация не означает, что пользователю разрешены все операции.

### Типичный вопрос

**Может ли пользователь быть аутентифицированным, но не авторизованным?**

Да.

Например, пользователь успешно вошёл в систему, но не имеет доступа к административному API или чужому заказу.

## 2. Основные способы аутентификации

В веб-приложениях и API используются разные механизмы.

| Механизм | Принцип |
|---|---|
| Login / Password | Проверка учётных данных |
| Session-based | Идентификатор серверной сессии |
| HTTP Basic Auth | Передача учётных данных через HTTP authentication |
| Bearer Token | Предъявление токена доступа |
| JWT | Использование структурированного токена, часто подписанного |
| API Key | Ключ для идентификации клиента или приложения |
| OAuth 2.0 | Делегированная авторизация и получение токенов |
| OpenID Connect | Аутентификация поверх OAuth 2.0 |
| mTLS | Аутентификация с использованием клиентских TLS-сертификатов |

Эти механизмы могут комбинироваться.

Например, пользователь входит по паролю и MFA, после чего приложение использует серверную сессию или токены.

## 3. Session-based Authentication

При **Session-based Authentication** сервер создаёт сессию пользователя и выдаёт клиенту её идентификатор.

### Как работает

```text
Browser                         Backend
   |                               |
   | POST /login                   |
   | username + password           |
   |------------------------------>|
   |                               |
   |                         Проверка данных
   |                         Создание сессии
   |                               |
   | Set-Cookie: sessionId=abc     |
   |<------------------------------|
   |                               |
   | GET /profile                  |
   | Cookie: sessionId=abc         |
   |------------------------------>|
   |                               |
   |                         Поиск сессии
   |                         Проверка пользователя
   |                               |
   | 200 OK                        |
   |<------------------------------|
```

### Где хранится сессия?

Например:

- В памяти сервера.
- В Redis.
- В базе данных.
- В специализированном session store.

Типичная запись:

```text
sessionId: abc123
userId: 100
expiresAt: 2026-10-10T12:00:00Z
```

Браузер получает идентификатор сессии, а не обязательно все данные о пользователе.

### Преимущества

- Возможность централизованно отзывать сессии.
- Удобный контроль времени жизни.
- Необязательно передавать данные пользователя в каждом токене.
- Сервер может быстро изменить права пользователя в сессионном состоянии.

### Недостатки

- Требуется хранение и управление сессиями.
- При масштабировании нескольких серверов нужен общий session store или другой согласованный механизм.
- Необходимо защищаться от кражи или фиксации идентификатора сессии.

### Что проверять QA?

- Создание сессии после логина.
- Изменение идентификатора сессии после успешной аутентификации.
- Срок жизни.
- Logout.
- Истечение сессии.
- Работа нескольких устройств.
- Отзыв сессии.
- Поведение после изменения пароля.
- Защита cookie.

## 4. Session ID и Cookie — не одно и то же

**Session ID** — идентификатор серверной сессии.

**Cookie** — браузерный механизм хранения и передачи небольших значений.

Session ID часто передают через Cookie:

```http
Cookie: sessionId=abc123
```

Но Cookie может содержать и другие данные:

```http
Cookie: theme=dark; language=ru
```

А идентификатор сессии технически может передаваться и другим способом.

### Set-Cookie

После успешного логина сервер может вернуть:

```http
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
```

### Атрибуты безопасности

**HttpOnly** — ограничивает доступ JavaScript к значению cookie.

**Secure** — ограничивает отправку cookie защищёнными соединениями.

**SameSite** — регулирует отправку cookie в cross-site запросах.

**Max-Age / Expires** — управляют временем жизни cookie.

**Path / Domain** — ограничивают область действия cookie.

### Важный нюанс

`HttpOnly` не означает, что XSS больше не опасен.

Даже если JavaScript не может прочитать session cookie, вредоносный скрипт может попытаться отправить действия от имени пользователя через браузер.

## 5. Session Hijacking и Session Fixation

### Session Hijacking

Атака, при которой злоумышленник получает действующий идентификатор сессии и использует его для доступа к системе.

Возможные причины:

- Кража cookie.
- Небезопасная передача данных.
- XSS.
- Утечка логов.
- Компрометация устройства пользователя.

### Session Fixation

Атака, при которой злоумышленник пытается заставить пользователя использовать заранее известный злоумышленнику идентификатор сессии.

### Защита

После успешного логина приложение должно обновлять идентификатор сессии, если используется соответствующая session-based архитектура.

Также применяются:

- HTTPS.
- Secure и HttpOnly.
- Сроки жизни сессий.
- Отзыв сессий.
- Дополнительная проверка критичных операций.

### Что проверять QA?

1. Получить анонимную сессию.
2. Выполнить логин.
3. Проверить изменение идентификатора сессии, если так устроен механизм.
4. Выполнить logout.
5. Проверить невозможность использования отозванной сессии.

## 6. Token-based Authentication

При токенной аутентификации клиент получает токен и предъявляет его в последующих запросах.

Например:

```http
GET /api/profile
Authorization: Bearer access-token
```

Backend проверяет токен и определяет, разрешён ли доступ.

### Основные понятия

**Access Token** — токен для доступа к защищённым ресурсам.

**Refresh Token** — токен, используемый для получения нового access token.

**ID Token** — токен OpenID Connect, содержащий сведения об аутентификации пользователя.

### Важный нюанс

Не каждый access token — JWT.

Access token может быть:

- JWT.
- Opaque token — непрозрачным значением.
- Другим форматом, предусмотренным инфраструктурой.

Поэтому нельзя ставить знак равенства между Bearer Token и JWT.

## 7. Что такое JWT?

**JWT (JSON Web Token)** — компактный формат передачи набора утверждений (claims) в виде JSON.

Наиболее распространённый в API вариант — подписанный JWT (JWS Compact Serialization).

Он состоит из трёх частей:

```text
HEADER.PAYLOAD.SIGNATURE
```

Например:

```text
eyJhbGciOiJIUzI1NiJ9
.
eyJzdWIiOiIxMjMiLCJleHAiOjE3OTAwMDAwMDB9
.
signature
```

### Header

Описывает параметры токена.

Например:

```json
{
  "alg": "RS256",
  "typ": "JWT"
}
```

### Payload

Содержит claims.

```json
{
  "sub": "user-123",
  "iss": "https://auth.example.com",
  "aud": "bonus-service",
  "exp": 1790000000,
  "iat": 1789996400,
  "scope": "bonuses:read"
}
```

### Signature

Позволяет проверять подлинность и целостность подписанного токена при корректной криптографической проверке.

### Важный момент

**Подписанный JWT не является автоматически зашифрованным.**

Header и Payload обычного JWS-токена закодированы в Base64URL и могут быть прочитаны без секретного ключа.

Поэтому нельзя хранить в payload пароли и другие секретные данные.

JWT также может использовать формат JWE для шифрования, но это отдельный механизм.

### Краткий ответ для собеседования

> JWT — формат токена, содержащий header, payload с claims и, для подписанного JWT, signature. Подпись позволяет проверить целостность и подлинность токена. JWT не обязательно зашифрован, поэтому его содержимое не следует считать секретным.

## 8. Основные JWT Claims

| Claim | Значение |
|---|---|
| `iss` | Issuer — издатель токена |
| `sub` | Subject — субъект, часто пользователь |
| `aud` | Audience — целевой получатель |
| `exp` | Expiration Time |
| `nbf` | Not Before |
| `iat` | Issued At |
| `jti` | JWT ID |

### exp

Момент окончания срока действия.

Сервер должен отклонять истёкший токен, если политика не предусматривает строго ограниченный допуск на расхождение часов.

### nbf

Токен не должен приниматься раньше указанного времени.

### iss

Позволяет проверить, что токен выдан ожидаемым сервисом.

### aud

Позволяет проверить, что токен предназначен именно для данного API.

### jti

Уникальный идентификатор JWT, если он используется.

Может применяться для механизмов отслеживания или отзыва токенов.

### Важно

Наличие claim в payload не означает, что сервер автоматически его проверяет.

Проверка должна быть реализована корректно.

## 9. Как сервер проверяет JWT?

Типичная последовательность:

1. Получить токен.
2. Определить допустимый алгоритм проверки.
3. Проверить криптографическую подпись.
4. Проверить `iss`.
5. Проверить `aud`.
6. Проверить `exp` и `nbf`.
7. Проверить необходимые claims и область действия.
8. Проверить дополнительные ограничения безопасности.
9. Выполнить авторизацию конкретного действия.

### Почему нельзя доверять alg из JWT без ограничений?

Потому что приложение должно заранее знать, какие алгоритмы и ключи допустимы для конкретного источника токенов.

Нельзя разрешать произвольный алгоритм только потому, что он указан в неподтверждённом заголовке токена.

### Что проверять QA?

- Изменение payload без пересоздания подписи.
- Неверная подпись.
- Неверный issuer.
- Неверный audience.
- Истёкший токен.
- Токен с будущим nbf.
- Отсутствующие обязательные claims.
- Токен другого пользователя.
- Токен с недостаточными scope.
- Неподдерживаемый алгоритм.

**Ожидаемый результат:** некорректный токен не принимается, а сервер не раскрывает лишние внутренние детали ошибки.

## 10. HS256 vs RS256

Оба алгоритма могут использоваться для подписи JWT, но отличаются моделью ключей.

### HS256

Использует симметричный секрет.

Один и тот же секрет применяется для создания и проверки подписи.

Плюсы:

- Относительно простая реализация.
- Не требует асимметричной пары ключей.

Минус:

- Сервис, имеющий секрет для проверки, технически способен создавать подписи.

### RS256

Использует асимметричную криптографию.

- Private Key — для подписи.
- Public Key — для проверки.

Плюсы:

- Можно распространять публичный ключ между сервисами.
- Проверяющий сервис не получает возможности подписывать произвольные токены.

### Что обычно удобнее в микросервисах?

Часто используются асимметричные алгоритмы, позволяющие центральному сервису авторизации выпускать токены, а другим сервисам проверять их по публичным ключам.

Но выбор зависит от архитектуры и требований безопасности.

## 11. Access Token vs Refresh Token

### Access Token

Предназначен для доступа к API.

Часто имеет относительно короткий срок жизни.

Пример:

```http
GET /api/bonuses
Authorization: Bearer access-token
```

### Refresh Token

Используется для получения нового access token.

Обычно имеет более длительный срок действия и требует более строгого контроля хранения и отзыва.

### Пример последовательности

```text
Client                      Auth Server
  |                              |
  | POST /login                  |
  |----------------------------->|
  |                              |
  | access + refresh tokens      |
  |<-----------------------------|
  |                              |
  | Access token expired         |
  |                              |
  | POST /token/refresh          |
  | refresh token                |
  |----------------------------->|
  |                              |
  | new access token             |
  | optional new refresh token   |
  |<-----------------------------|
```

### Почему не сделать Access Token бессрочным?

Потому что при компрометации злоумышленник сможет использовать его в течение всего срока действия, если нет дополнительных ограничений или механизмов отзыва.

Короткое время жизни ограничивает окно использования украденного токена.

## 12. Refresh Token Rotation

**Refresh Token Rotation** — механизм, при котором после успешного обновления токенов клиент получает новый refresh token, а предыдущий становится недействительным.

### Пример

```text
Refresh Token A
       |
       | Refresh
       v
Access Token B + Refresh Token B
       |
       v
Refresh Token A invalidated
```

### Зачем нужна Rotation?

Для обнаружения повторного использования ранее выданного refresh token и уменьшения последствий его утечки.

### Сценарий

1. Пользователь использовал Refresh Token A.
2. Получил Refresh Token B.
3. Злоумышленник пытается повторно использовать A.
4. Authorization Server обнаруживает reuse.
5. В соответствии с политикой может отозвать активную цепочку токенов.

### Что проверять QA?

- Успешный refresh.
- Недействительность использованного refresh token.
- Параллельные запросы refresh.
- Поведение после повторного использования старого токена.
- Истечение refresh token.
- Logout.
- Отзыв при смене пароля, если предусмотрено.

### Важный нюанс

Для public OAuth clients современные рекомендации требуют защищать refresh tokens от повторного использования через rotation или привязку токена к отправителю (sender-constraining).

## 13. Logout и отзыв токенов

В Session-based системе logout обычно может завершить или отозвать серверную сессию.

С JWT ситуация отличается.

Если API проверяет только подпись и срок жизни токена без обращения к серверному состоянию, уже выданный access token может продолжать работать после logout до своего истечения.

### Как решают эту проблему?

Возможные подходы:

- Короткоживущие access tokens.
- Отзыв refresh tokens.
- Token denylist.
- Проверка версии токена или пользователя.
- Token introspection.
- Централизованная проверка сессии.

### Что тестировать?

1. Получить access и refresh tokens.
2. Выполнить logout.
3. Проверить использование старого refresh token.
4. Проверить поведение старого access token.
5. Сравнить результат с требованиями безопасности.

**Важно:** нельзя автоматически считать, что после logout любой ранее выданный JWT должен сразу становиться недействительным. Это зависит от конкретной архитектуры и контракта.

## 14. Где хранить токены?

В браузерных приложениях встречаются разные варианты.

### In-memory storage

Токен хранится в памяти JavaScript-приложения.

Плюсы:

- Не сохраняется автоматически между перезапусками страницы.
- Уменьшается долговременное хранение чувствительных данных.

Минусы:

- Может быть доступен вредоносному JavaScript при XSS.
- После перезагрузки страницы может потребоваться восстановление авторизации.

### localStorage

Данные сохраняются между перезапусками страницы.

Проблема: JavaScript, выполняемый в origin приложения, может прочитать значения.

Поэтому хранение чувствительных долгоживущих токенов в localStorage связано с риском при XSS.

### HttpOnly Cookie

JavaScript не может прочитать значение cookie через `document.cookie`.

Но браузер может автоматически отправлять её в подходящих запросах.

Поэтому необходимо учитывать CSRF и правила SameSite.

### Что лучше?

Нет универсального варианта, подходящего для всех архитектур.

Для браузерных приложений часто используют защищённую серверную сессию или архитектуру Backend-for-Frontend с HttpOnly cookies.

Выбор должен учитывать XSS, CSRF, срок жизни токенов, требования приложения и особенности cross-origin взаимодействия.

## 15. OAuth 2.0 — что это?

**OAuth 2.0** — framework делегированной авторизации.

Он позволяет приложению получать ограниченный доступ к ресурсам без необходимости передавать этому приложению пароль пользователя.

### Пример

Приложение хочет получить разрешение на чтение календаря пользователя.

Вместо получения пароля от календаря приложение перенаправляет пользователя к Authorization Server.

Пользователь подтверждает доступ, а приложение получает подходящий токен.

### Основные роли

| Роль | Значение |
|---|---|
| Resource Owner | Владелец защищённых ресурсов, часто пользователь |
| Client | Приложение, запрашивающее доступ |
| Authorization Server | Выдаёт токены после соответствующей авторизации |
| Resource Server | API, предоставляющее защищённые ресурсы |

### Краткий ответ для собеседования

> OAuth 2.0 — framework делегированной авторизации. Он позволяет клиентскому приложению получить ограниченный доступ к ресурсам пользователя через токены, не раскрывая приложению пользовательский пароль. Сам по себе OAuth 2.0 не является полноценным протоколом аутентификации пользователя.

## 16. OAuth 2.0 vs OpenID Connect

Очень распространённый вопрос.

### OAuth 2.0

Отвечает на вопрос:

**Что клиентскому приложению разрешено делать?**

Например, читать определённые данные через API.

### OpenID Connect (OIDC)

Протокол аутентификации, построенный поверх OAuth 2.0.

Позволяет приложению получить проверяемую информацию о факте аутентификации пользователя.

В частности, OIDC определяет ID Token.

### Пример

Пользователь выбирает:

```text
Sign in with Google
```

Для реализации такой функции обычно используется OpenID Connect поверх OAuth 2.0.

### Готовый ответ

> OAuth 2.0 предназначен для делегированной авторизации, а OpenID Connect добавляет стандартизованную аутентификацию пользователя поверх OAuth 2.0. В OIDC используется ID Token, содержащий claims об аутентификации.

## 17. Authorization Code Flow

Один из основных OAuth 2.0 flows.

### Упрощённая схема

```text
User / Browser           Client App             Authorization Server
      |                      |                            |
      | Нажал Login          |                            |
      |--------------------->|                            |
      |                      |                            |
      | Redirect to Authorization Server                  |
      |<---------------------|                            |
      |-------------------------------------------------->|
      |                      |                            |
      |                 Login + Consent                    |
      |                      |                            |
      | Redirect with Authorization Code                  |
      |<--------------------------------------------------|
      |                      |                            |
      | Передача Code        |                            |
      |--------------------->|                            |
      |                      | Token Request              |
      |                      |--------------------------->|
      |                      |                            |
      |                      | Access Token               |
      |                      |<---------------------------|
```

В реальной системе также используются параметры безопасности и проверка соответствия redirect URI.

### Почему используется Authorization Code?

Потому что токены не нужно передавать непосредственно через фронтальный redirect в браузере.

Клиент получает краткоживущий authorization code и обменивает его на токены через подходящий защищённый процесс.

### Важно

Authorization Code является временным и одноразовым в соответствии с требованиями протокола.

---

## 18. PKCE — Proof Key for Code Exchange

**PKCE** — расширение OAuth 2.0, защищающее Authorization Code Flow от определённых атак с перехватом или внедрением authorization code.

### Как работает?

Клиент генерирует случайный:

```text
code_verifier
```

Из него вычисляет:

```text
code_challenge
```

Обычно с методом `S256`.

При первоначальном запросе авторизации отправляется code_challenge.

При обмене authorization code на токены клиент передаёт code_verifier.

Authorization Server проверяет соответствие.

### Упрощённо

```text
Client                              Authorization Server
  |                                           |
  | Authorization Request                    |
  | code_challenge                           |
  |------------------------------------------>|
  |                                           |
  | Authorization Code                       |
  |<------------------------------------------|
  |                                           |
  | Token Request                            |
  | code + code_verifier                      |
  |------------------------------------------>|
  |                                           |
  | Проверка соответствия                     |
  |                                           |
  | Access Token                              |
  |<------------------------------------------|
```

### Почему PKCE важен?

Даже если злоумышленник получит authorization code, ему недостаточно просто предъявить его для получения токенов без соответствующего code_verifier.

### Важный вопрос

**PKCE нужен только мобильным приложениям?**

Нет.

Современные рекомендации применяют PKCE для различных типов OAuth Clients. Для public clients он обязателен согласно OAuth 2.0 Security Best Current Practice, а для confidential clients рекомендован.

---

## 19. Что такое Scope?

**Scope** определяет запрашиваемый или предоставляемый объём доступа.

Примеры:

```text
profile:read
orders:read
orders:write
bonuses:issue
```

### Пример

Токен содержит:

```json
{
  "scope": "orders:read"
}
```

Клиент пытается вызвать:

```http
POST /orders
```

Если операция требует `orders:write`, сервер должен отклонить доступ.

### Scope vs Role

**Scope** часто описывает разрешённые операции для токена.

**Role** описывает назначенную субъекту роль в системе.

Например:

```text
Role: SUPPORT
Scope: orders:read
```

Важно, что наличие scope не должно автоматически позволять обращаться к объектам других пользователей.

Кроме scope сервер обязан применять объектные и бизнес-ограничения.

---

## 20. RBAC, ABAC и объектная авторизация

### RBAC — Role-Based Access Control

Доступ определяется ролями.

Пример:

| Роль | Разрешения |
|---|---|
| USER | Просмотр своих заказов |
| SUPPORT | Просмотр заказов клиентов |
| ADMIN | Управление пользователями |

### ABAC — Attribute-Based Access Control

Решение принимается с учётом атрибутов.

Например:

- Роль пользователя.
- Статус ресурса.
- Отдел сотрудника.
- Владелец объекта.
- Контекст запроса.

### Object-Level Authorization

Проверка доступа к конкретному объекту.

Например:

```http
GET /api/orders/100
```

Пользователь A не должен получать заказ пользователя B, если это не разрешено требованиями.

### BOLA / IDOR

**BOLA (Broken Object Level Authorization)** — уязвимость, при которой API не проверяет права пользователя на конкретный объект.

IDOR — распространённый вариант проблемы, при котором можно изменить идентификатор ресурса и получить несанкционированный доступ.

### Пример

Пользователь A запрашивает:

```http
GET /api/users/100/orders/501
```

Затем меняет идентификатор:

```http
GET /api/users/100/orders/502
```

Если заказ 502 принадлежит другому пользователю, сервер обязан выполнить независимую проверку доступа.

**Скрытие кнопок в интерфейсе не является авторизацией.**

## 21. HTTP 401 vs 403

### 401 Unauthorized

Несмотря на название, относится к аутентификации.

Часто используется, когда:

- Нет требуемых учётных данных.
- Токен недействителен.
- Токен истёк.
- Не пройдена требуемая HTTP-аутентификация.

### 403 Forbidden

Сервер понимает запрос, но отказывает в выполнении.

Например:

- Пользователь не имеет нужной роли.
- Операция запрещена политикой доступа.
- Объект недоступен этому пользователю.

### 404 вместо 403

Иногда сервер намеренно возвращает 404, чтобы не раскрывать существование приватного ресурса.

### Краткий ответ

> 401 связан с необходимостью корректной аутентификации, а 403 — с отказом выполнять запрос, например из-за недостаточных прав. При этом сервер может скрывать наличие чужого ресурса через 404, если это предусмотрено политикой безопасности.

## 22. Authentication vs Authorization vs Accounting

Иногда на собеседованиях спрашивают AAA:

**Authentication** — кто обращается?

**Authorization** — что разрешено?

**Accounting** — какие действия совершены, учёт и аудит активности.

Например:

1. Пользователь вошёл в банк.
2. Получил право на определённую операцию.
3. Система записала операцию в журнал аудита.

Это полезно знать, но для обычного QA-интервью достаточно уверенно понимать первые два понятия.

---

## 23. MFA — Multi-Factor Authentication

**MFA** — аутентификация с использованием двух или более независимых факторов.

Основные категории:

- Something you know — пароль, PIN.
- Something you have — аппаратный ключ, приложение-аутентификатор.
- Something you are — биометрический фактор.

### Пример

```text
Password
   ↓
TOTP / Security Key
   ↓
Successful Authentication
```

### Что проверять QA?

- Успешный вход.
- Неверный второй фактор.
- Истёкший одноразовый код.
- Повторное использование кода.
- Блокировку или замедление перебора.
- Восстановление доступа.
- Смену устройства.
- Поведение после logout.
- Дополнительную проверку для критичных операций.

### Важный нюанс

Два пароля не являются двумя независимыми факторами.

А SMS-код — фактор владения, но имеет известные риски, например SIM-swapping.

# Часть 2. Практическое тестирование аутентификации

## 24. Тестирование Login API

Допустим:

```http
POST /api/auth/login
Content-Type: application/json

{
  "username": "anna",
  "password": "secret"
}
```

### Позитивные сценарии

- Корректный логин и пароль.
- Успешная выдача сессии или токенов.
- Доступ к защищённому API после логина.
- Корректный пользовательский контекст.

### Негативные сценарии

- Несуществующий пользователь.
- Неверный пароль.
- Пустой логин.
- Пустой пароль.
- NULL вместо обязательного значения.
- Некорректный формат запроса.
- Заблокированная учётная запись.
- Неактивная учётная запись.
- Превышен лимит попыток.
- Ошибка сервиса аутентификации.

### Проверки безопасности

- Использование HTTPS.
- Отсутствие пароля в URL.
- Отсутствие пароля в обычных логах.
- Отсутствие секретов в ответе.
- Защита от перебора.
- Отсутствие нежелательного раскрытия существования пользователя.
- Безопасная обработка ошибок.

## 25. Тестирование Session-based Authentication

### Сценарий 1. Успешный логин

1. Выполнить POST /login.
2. Проверить Set-Cookie.
3. Проверить атрибуты cookie.
4. Вызвать защищённый endpoint.
5. Убедиться в корректной идентификации пользователя.

### Сценарий 2. Истечение сессии

1. Авторизоваться.
2. Дождаться или смоделировать истечение сессии.
3. Выполнить защищённый запрос.
4. Проверить отклонение доступа.
5. Проверить ожидаемое поведение повторного логина.

### Сценарий 3. Logout

1. Авторизоваться.
2. Выполнить logout.
3. Повторно отправить прежнюю session cookie.
4. Проверить отказ в доступе.

### Сценарий 4. Session Fixation

1. Получить анонимный идентификатор сессии.
2. Авторизоваться.
3. Проверить изменение сессионного идентификатора согласно требованиям безопасности.

### Сценарий 5. Несколько устройств

Проверить:

- Допускаются ли параллельные сессии.
- Можно ли завершить одну сессию.
- Можно ли завершить все сессии.
- Что происходит после смены пароля.

## 26. Тестирование JWT

### Позитивные проверки

- Валидная подпись.
- Корректный issuer.
- Корректный audience.
- Неистёкший токен.
- Необходимые claims.
- Достаточный scope.

### Негативные проверки

| Проверка | Ожидаемое поведение |
|---|---|
| Отсутствует токен | Доступ отклонён |
| Невалидный формат | Доступ отклонён |
| Изменён payload | Подпись не проходит проверку |
| Истёк exp | Доступ отклонён |
| nbf в будущем | Доступ отклонён |
| Неверный iss | Доступ отклонён |
| Неверный aud | Доступ отклонён |
| Недостаточный scope | Операция запрещена |
| Токен другого пользователя | Нет доступа к чужим ресурсам |
| Неподдерживаемый alg | Токен отклонён |

### Важный нюанс

Не все claims обязательны для каждого JWT по самому формату.

Конкретный набор проверок определяется типом токена, протоколом и политикой API.

## 27. Тестирование Refresh Token

### Сценарии

1. Получение нового access token по валидному refresh token.
2. Использование истёкшего refresh token.
3. Использование отозванного refresh token.
4. Повторное использование старого refresh token после rotation.
5. Два одновременных refresh-запроса.
6. Refresh после logout.
7. Refresh после смены пароля.
8. Проверка неправильного client binding.
9. Проверка неверного scope или audience.
10. Проверка устойчивости к повторным запросам после таймаута.

### Особенно важно: конкурентный Refresh

Представим, что два запроса почти одновременно пытаются обновить один refresh token.

При строгой rotation второй запрос может использовать уже недействительный токен.

Система должна иметь определённое поведение для такого случая.

Нельзя просто предполагать, что оба запроса всегда успешно выдадут новую пару токенов.

## 28. Тестирование авторизации API

Аутентификация — только первая часть.

Для каждого защищённого endpoint важно проверить права доступа.

### Role-Based Checks

Например:

```http
DELETE /api/users/100
```

Проверяем:

- ADMIN — доступ разрешён.
- USER — доступ запрещён.
- Неавторизованный клиент — доступ запрещён.

### Object-Level Checks

```http
GET /api/orders/501
```

Проверяем:

- Владелец получает свой заказ.
- Другой пользователь не получает этот заказ.
- Сотрудник поддержки получает доступ только в пределах своих полномочий.

### Field-Level Checks

Например:

```http
PATCH /api/users/100
Content-Type: application/json

{
  "name": "Anna",
  "role": "ADMIN"
}
```

Обычный пользователь не должен иметь возможность изменить себе роль через передачу дополнительного поля.

### Function-Level Checks

Например, пользователь не должен вызывать административную операцию только потому, что знает её URL.

**Для Senior QA:** важно упоминать проверки объекта, полей и конкретных действий, а не ограничиваться только наличием токена.

## 29. Матрица авторизации

Удобный способ тест-дизайна — матрица ролей и операций.

| Операция | Неавторизованный | USER | SUPPORT | ADMIN |
|---|---|---|---|---|
| Просмотр своего профиля | Нет | Да | Да | Да |
| Просмотр чужого профиля | Нет | Нет | По правилам | Да |
| Изменение своей анкеты | Нет | Да | По правилам | Да |
| Изменение чужой роли | Нет | Нет | Нет | Да |
| Удаление пользователя | Нет | Нет | Нет | Да |

Это иллюстративная матрица: фактические права должны быть определены требованиями.

### Дополнительные измерения

- Владелец / не владелец.
- Активный / заблокированный пользователь.
- Действующий / истёкший токен.
- Разрешённый / запрещённый ресурс.
- Разрешённое / запрещённое поле.
- Статус бизнес-операции.

Такой подход позволяет выявлять пропущенные проверки доступа.

## 30. Ошибка 200 вместо 403

Представим:

Пользователь USER вызывает:

```http
DELETE /api/users/100
```

Сервер возвращает:

```http
HTTP/1.1 200 OK
```

Но фактически ничего не удаляет.

Является ли это корректным поведением?

Зависит от контракта, однако для операции с отказом в правах обычно требуется явно сообщать об отказе.

Самое важное — убедиться, что неавторизованное действие не выполнилось.

При тестировании нужно проверять не только HTTP-статус, но и фактическое состояние данных.

## 31. Практический кейс: пользователь получил чужой бонус

Есть endpoint:

```http
POST /api/bonuses/issue
Authorization: Bearer user-a-token
Content-Type: application/json

{
  "userId": "user-b",
  "bonusId": 777
}
```

### Что проверять?

- Имеет ли пользователь A право выполнять операцию для B.
- Проверяется ли соответствие субъекта токена и целевого пользователя.
- Не доверяет ли Backend только userId из тела запроса.
- Можно ли изменить userId.
- Можно ли использовать токен другого клиента.
- Корректно ли обрабатываются недостаточные scopes.
- Нет ли нежелательных изменений в БД.

### Типичный дефект

Backend проверил валидность JWT, но не проверил разрешение на выдачу бонуса указанному пользователю.

Это ошибка авторизации, а не аутентификации.

## 32. Практический кейс: истёк Access Token

### Сценарий

1. Пользователь успешно авторизовался.
2. Access token истёк.
3. Клиент отправляет запрос.
4. API отклоняет токен.
5. Клиент выполняет предусмотренный refresh flow.
6. Повторяет исходный запрос.

### Что проверить?

- Корректное обнаружение истечения токена.
- Отсутствие бесконечного цикла refresh.
- Правильное обновление токенов.
- Защиту от повторного выполнения неидемпотентной бизнес-операции.
- Поведение при истечении refresh token.

### Важный нюанс

Если первый запрос завершился таймаутом, клиент не всегда знает, выполнилась ли бизнес-операция.

Повтор после обновления токена может создать дублирование.

Поэтому для критичных POST-операций важно учитывать идемпотентность.

## 33. OAuth 2.0 — что проверять QA?

### Authorization Code Flow

- Корректный redirect.
- Проверка redirect URI.
- Успешное получение authorization code.
- Одноразовое использование code.
- Истечение code.
- Привязка code к клиенту.
- Проверка state / PKCE согласно flow.
- Отказ при неверном code_verifier.
- Отказ при попытке использовать code повторно.

### Token Endpoint

- Корректный grant type.
- Правильная аутентификация клиента, когда требуется.
- Валидация client_id.
- Проверка scope.
- Выдача токенов только после успешной проверки.
- Корректная обработка неверного или истёкшего кода.

### OIDC

- Наличие ID Token, если предусмотрен flow.
- Проверка подписи ID Token.
- Проверка iss и aud.
- Проверка exp.
- Проверка nonce, если используется.
- Корректное сопоставление пользователя.

# Часть 3. Вопросы для собеседования

## 34. Чем аутентификация отличается от авторизации?

Аутентификация отвечает на вопрос «Кто ты?», авторизация — «Что тебе разрешено?».

## 35. Что такое Session-based Authentication?

Механизм, при котором сервер хранит пользовательскую сессию, а клиент передаёт её идентификатор, часто через cookie.

## 36. Что такое JWT?

Формат токена, который может содержать claims и быть криптографически подписан или зашифрован в соответствии с используемым представлением.

## 37. Состоит ли JWT всегда из трёх частей?

Компактное представление подписанного JWS обычно состоит из Header.Payload.Signature. Зашифрованный JWE в компактном представлении состоит из пяти частей.

## 38. Можно ли прочитать Payload JWT без секретного ключа?

У обычного подписанного JWT — да, поскольку Base64URL не является шифрованием.

## 39. Какие Claims JWT ты знаешь?

iss, sub, aud, exp, nbf, iat, jti.

## 40. В чём отличие HS256 от RS256?

HS256 использует симметричный секрет, RS256 — пару приватного и публичного ключей.

## 41. Чем Access Token отличается от Refresh Token?

Access Token используется для доступа к ресурсам, Refresh Token — для получения нового Access Token.

## 42. Что такое Refresh Token Rotation?

Выдача нового Refresh Token при обновлении токенов с инвалидированием предыдущего и возможностью обнаруживать его повторное использование.

## 43. Что происходит с JWT после Logout?

Это зависит от архитектуры. Stateless JWT может оставаться действительным до истечения срока, если не реализован дополнительный механизм отзыва.

## 44. Что такое OAuth 2.0?

Framework делегированной авторизации, позволяющий клиенту получить ограниченный доступ к ресурсам через токены.

## 45. Чем OAuth 2.0 отличается от OpenID Connect?

OAuth 2.0 предназначен для делегированной авторизации, а OpenID Connect добавляет стандартизованную аутентификацию пользователя.

## 46. Что такое Authorization Code Flow?

Flow, при котором клиент получает authorization code через Authorization Server и обменивает его на токены.

## 47. Что такое PKCE?

Механизм защиты Authorization Code Flow с использованием code_verifier и code_challenge.

## 48. Что такое Scope?

Область разрешений, предоставленных или запрошенных для токена.

## 49. Что такое RBAC?

Role-Based Access Control — управление доступом на основе ролей.

## 50. Что такое BOLA / IDOR?

Ошибка объектной авторизации, позволяющая получить или изменить ресурс, к которому у пользователя нет прав.

## 51. Чем 401 отличается от 403?

401 относится к необходимости корректной аутентификации, 403 — к отказу выполнить запрос, в том числе из-за недостаточных прав.

## 52. Что такое MFA?

Аутентификация с использованием нескольких независимых факторов.

## 53. Что такое Session Fixation?

Атака, при которой злоумышленник пытается заставить пользователя использовать заранее известный идентификатор сессии.

## 54. Почему нельзя просто доверять Role из тела запроса?

Потому что клиентские данные контролируются отправителем. Права должны определяться доверенным контекстом и проверяться на сервере.

## 55. Как протестировать авторизацию API?

Проверить доступ без учётных данных, с различными ролями, scopes, владельцами ресурсов, ограничениями полей и бизнес-состояниями. Подтверждать фактическое отсутствие неразрешённых изменений.

## Частые ошибки на собеседовании

**Ошибка:** «JWT всегда зашифрован».

Правильно: подписанный JWT обычно доступен для чтения, но защищён подписью от незаметного изменения.

**Ошибка:** «JWT и Access Token — одно и то же».

Правильно: JWT — формат, Access Token — назначение. Access Token может быть непрозрачным.

**Ошибка:** «OAuth 2.0 — протокол аутентификации».

Правильно: OAuth 2.0 предназначен для делегированной авторизации. Для стандартизованной аутентификации существует OIDC.

**Ошибка:** «Если JWT валидный, пользователю разрешены все операции».

Правильно: после проверки токена необходимо выполнить авторизацию конкретного действия и объекта.

**Ошибка:** «HttpOnly полностью защищает от XSS».

Правильно: HttpOnly защищает значение cookie от прямого чтения JavaScript, но не устраняет все последствия XSS.

**Ошибка:** «После Logout любой JWT мгновенно перестаёт работать».

Правильно: это зависит от механизма отзыва токенов.

**Ошибка:** «PKCE нужен только для мобильных приложений».

Правильно: он применим к различным типам OAuth Clients и обязателен для public clients согласно современным рекомендациям.

**Ошибка:** «Достаточно скрыть кнопку Admin в интерфейсе».

Правильно: авторизация должна проверяться на Backend.
