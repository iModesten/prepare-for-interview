## 1. Сначала разберёмся: что с чем сравниваем?

На собеседовании легко перепутать формат данных и способ построения API. Это не одно и то же.

| Что это | Примеры | Зачем нужно |
|---|---|---|
| Формат данных | JSON, XML, CSV | Описывает, как записаны данные |
| Способ построения API / технология взаимодействия | REST, SOAP, GraphQL, gRPC | Определяет, как клиент обращается к сервису и получает ответ |
| Транспорт | HTTP, TCP, WebSocket | Помогает передавать данные между участниками |
| Формат сериализации сообщений | JSON, Avro, Protobuf | Представляет данные для передачи или хранения |

**Сериализация** — превращение данных программы в формат, который можно передать или сохранить. **Десериализация** — обратное преобразование.

Примеры: REST API может передавать JSON или XML. GraphQL обычно возвращает JSON. SOAP 1.2 использует XML для сообщений. gRPC обычно использует Protocol Buffers, но способен работать и с другими кодировками.

# Часть 1. JSON

## 2. Что такое JSON?

**JSON (JavaScript Object Notation)** — текстовый формат записи данных. Он часто используется в HTTP API и событиях между сервисами.

```json
{
  "userId": "user-100",
  "bonusId": 777,
  "active": true
}
```

### Шесть типов данных JSON

| Тип | Пример | Что означает |
|---|---|---|
| String | `"hello"` | Строка |
| Number | `777`, `-5`, `12.5`, `1e3` | Число |
| Boolean | `true`, `false` | Логическое значение |
| Null | `null` | Явное отсутствие значения |
| Object | `{"id":1}` | Набор полей с именами |
| Array | `[1,2,3]` | Упорядоченный набор значений |

В одном документе могут встречаться все типы:

```json
{
  "name": "Anna",
  "amount": 50.5,
  "available": true,
  "finishedAt": null,
  "settings": {"notifications": false},
  "bonuses": [1001, 1002]
}
```

**Ответ для интервью:** «В JSON шесть типов: String, Number, Boolean, Null, Object и Array. Отдельных типов Integer, Float и Date в самом JSON нет».

### Частые уточнения

- **Integer и Float:** в JSON это один тип `Number`. В JSON Schema есть отдельные типы `number` и `integer` — это правила проверки данных, а не новые типы JSON.
- **Дата:** отдельного типа `Date` нет; обычно используется строка, например `"2026-10-13T10:00:00Z"`.
- **`undefined`:** не существует в JSON. Это значение есть в JavaScript.
- **`NaN` и `Infinity`:** не разрешены стандартным JSON.
- **Комментарии:** не поддерживаются стандартным JSON.
- **Ключи объекта:** записываются строками в двойных кавычках.
- **Корень документа:** может быть объектом, массивом, строкой, числом, boolean или null — не обязательно объектом.

### Что важно QA

Обрати внимание на различия:

```json
{"bonusId": 777}
```

```json
{"bonusId": "777"}
```

```json
{"bonusId": null}
```

```json
{}
```

Это четыре разных варианта: число, строка, явный `null` и отсутствие поля. API может обрабатывать их по-разному.

Также не путай `[]` (пустой массив) и `{}` (пустой объект).

### Невалидный JSON

Примеры **некорректного** JSON:

```javascript
{ userId: "user-100" }            // ключ без двойных кавычек
{"userId": "user-100",}          // лишняя запятая
{'userId': 'user-100'}            // одинарные кавычки
{"amount": NaN}                 // недопустимое число
```

Этот блок намеренно помечен как JavaScript, **не как валидный JSON**.

### Что тестировать

1. Правильный тип каждого поля.
2. Обязательное поле, отсутствующее поле и `null`.
3. Пустые массивы, объекты и строки.
4. Граничные значения чисел и строк.
5. Неожиданные поля и вложенные объекты.
6. Некорректный синтаксис JSON.
7. Отсутствие случайного преобразования `"777"` в `777`, если контракт требует число.
8. Очень большие числа: JavaScript-клиенты могут потерять точность для целых значений за пределами диапазона безопасных целых чисел.

**Важно:** конкретный HTTP-статус на неверный JSON или тип зависит от контракта и реализации. Часто применяются 400 или 422. Главное — согласованная обработка без неожиданных изменений данных и без необработанного 500.

# Часть 2. XML

## 3. Что такое XML?

**XML (Extensible Markup Language)** — текстовый формат с тегами. Используется, например, в SOAP, интеграциях со старыми системами и документах.

```xml
<bonus>
  <id>777</id>
  <userId>user-100</userId>
  <active>true</active>
</bonus>
```

### Чем XML отличается от JSON?

| JSON | XML |
|---|---|
| Поля, объекты и массивы | Элементы и атрибуты |
| Есть стандартные значения number, boolean, null | Содержимое элемента — текст; типы задаются правилами схемы или приложения |
| Обычно компактнее для простых данных | Часто более многословный |
| JSON Schema применяется для проверки JSON | XSD применяется для проверки структуры и типов XML |
| Нет XML namespaces | Есть namespaces для различения имён |

### Элемент и атрибут

```xml
<bonus id="777" active="true">
  <userId>user-100</userId>
</bonus>
```

Здесь `bonus` и `userId` — элементы, а `id` и `active` — атрибуты.

### Что такое XSD?

**XSD (XML Schema Definition)** — описание ожидаемой структуры XML: какие элементы допустимы, какие обязательны, какие типы и ограничения у значений.

### Что такое Namespace?

Namespace помогает различать одинаковые имена элементов из разных наборов правил.

```xml
<b:bonus xmlns:b="https://example.com/bonus">
  <b:id>777</b:id>
</b:bonus>
```

Префикс `b` связан с указанным пространством имён. Сам URI в этом примере используется как идентификатор пространства имён, а не обязательно как доступная веб-страница.

### Что проверять QA?

- XML корректно сформирован: все теги закрыты, есть один корневой элемент, атрибуты корректны.
- XML соответствует XSD, если он используется.
- Обязательные элементы присутствуют.
- Верно обрабатываются namespaces, атрибуты, пустые элементы и специальные символы.
- Сервис безопасно обрабатывает XML: в частности, не раскрывает файлы или внутренние ресурсы через внешние сущности (XXE), если парсер и формат позволяют такую опасную конфигурацию.

**Вопрос:** «Чем XML отличается от JSON?»  
**Ответ:** «JSON — формат со значениями, объектами и массивами; XML — формат с элементами и атрибутами. XML часто применяется в SOAP, а JSON — в современных HTTP API. Для XML могут использовать XSD, а для JSON — JSON Schema».

# Часть 3. REST, SOAP, GraphQL и gRPC

## 4. REST

**REST** — архитектурный стиль, часто используемый при построении HTTP API. Обычно клиент обращается к ресурсам по URL и использует HTTP-методы.

Получить бонус:

```http
GET /api/bonuses/777 HTTP/1.1
Host: api.example.com
Accept: application/json
```

Ответ:

```json
{
  "id": 777,
  "status": "AVAILABLE"
}
```

Выдать бонус:

```http
POST /api/bonuses/777/issue HTTP/1.1
Content-Type: application/json

{"userId":"user-100"}
```

Это пример дизайна HTTP API, а не единственно правильный REST-путь.

**Плюсы:** широко используется, знакомые HTTP-методы и статусы, много инструментов тестирования.  
**Что проверять:** методы, статусы, заголовки, контракт, валидацию, авторизацию, бизнес-результат, идемпотентность.

## 5. SOAP

**SOAP** — протокол обмена структурированными сообщениями. Использует XML-сообщения с определённой оболочкой (Envelope). Часто встречается в корпоративных и старых интеграциях.

Пример SOAP-запроса:

```xml
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope"
               xmlns:b="https://example.com/bonus">
  <soap:Body>
    <b:GetBonusRequest>
      <b:bonusId>777</b:bonusId>
    </b:GetBonusRequest>
  </soap:Body>
</soap:Envelope>
```

Здесь:

- **Envelope** — внешняя оболочка сообщения.
- **Header** — необязательная часть для дополнительных сведений.
- **Body** — содержимое операции.
- **Fault** — стандартный способ описать ошибку SOAP.

### WSDL — что это?

**WSDL (Web Services Description Language)** — документ, описывающий операции веб-сервиса, сообщения, адреса и правила взаимодействия. В SOAP-интеграциях WSDL часто используется как контракт.

### Что проверять QA?

1. Корректность XML и обязательных элементов.
2. Соответствие WSDL/XSD.
3. Правильность операции и namespace.
4. SOAP Fault при ошибках.
5. Заголовки, аутентификацию и бизнес-результат.

**Вопрос:** «Чем SOAP отличается от REST?»  
**Ответ:** «SOAP — протокол с определённым форматом XML-сообщений; REST — архитектурный стиль. REST API часто используют HTTP-методы и JSON, а SOAP-интеграции — XML и WSDL. При тестировании SOAP дополнительно проверяют Envelope, Fault, XSD и WSDL».

## 6. GraphQL

**GraphQL** — язык запросов к API и среда выполнения таких запросов. Главная идея: клиент сам перечисляет нужные ему поля.

Запрос:

```graphql
query {
  bonus(id: "777") {
    id
    status
  }
}
```

Пример ответа:

```json
{
  "data": {
    "bonus": {
      "id": "777",
      "status": "AVAILABLE"
    }
  }
}
```

### Основные понятия

- **Schema** — какие типы, поля и операции доступны.
- **Query** — обычно получение данных.
- **Mutation** — изменение данных.
- **Subscription** — получение обновлений, если сервер это поддерживает.
- **Resolver** — код, который получает данные для конкретного поля или операции.

Пример Mutation:

```graphql
mutation {
  issueBonus(userId: "user-100", bonusId: "777") {
    issueId
    status
  }
}
```

### В чём отличие от REST?

При REST обычно вызывают endpoint, который возвращает заранее определённую структуру. В GraphQL клиент может выбрать поля, определённые схемой.

### Важная ловушка для собеседования

GraphQL-ответ с ошибкой выполнения **может иметь HTTP 200**, а сведения об ошибке — находиться в поле `errors`.

```json
{
  "data": {"bonus": null},
  "errors": [{"message":"Bonus service unavailable"}]
}
```

Это не означает, что любые ошибки GraphQL всегда возвращают 200: HTTP-статус зависит от этапа и правил обработки запроса и используемого GraphQL-over-HTTP поведения.

### Что проверять QA?

1. Query и Mutation с корректными параметрами.
2. Выбор только запрошенных полей.
3. Обязательные и необязательные аргументы; типы по GraphQL Schema.
4. Ошибки в `errors`, даже если HTTP-статус успешный.
5. Авторизацию **каждого доступного поля и объекта**, а не только endpoint.
6. Глубоко вложенные и дорогие запросы: ограничения сложности, глубины и нагрузки.
7. Пагинацию, сортировку, фильтрацию, если реализованы.

**Вопрос:** «Что такое GraphQL?»  
**Ответ:** «Это способ обращения к API, при котором клиент указывает нужные поля в запросе. Обычно есть Query для чтения, Mutation для изменения и Subscription для обновлений. QA должен проверять схему, данные, авторизацию и поле `errors`».

## 7. gRPC и Protocol Buffers

**gRPC** — технология удалённого вызова методов. Клиент вызывает метод сервиса, как будто это функцию, но фактически запрос уходит по сети. Обычно gRPC использует HTTP/2 и Protocol Buffers.

Контракт в файле `.proto`:

```proto
syntax = "proto3";

service BonusService {
  rpc GetBonus(GetBonusRequest) returns (GetBonusResponse);
}

message GetBonusRequest {
  int64 bonus_id = 1;
}

message GetBonusResponse {
  int64 bonus_id = 1;
  string status = 2;
}
```

Здесь описаны метод, типы запросов и ответов. В стандартной gRPC-конфигурации сообщения обычно кодируются бинарным форматом Protobuf.

### Четыре вида вызовов gRPC

1. **Unary** — один запрос, один ответ.
2. **Server streaming** — один запрос, поток ответов.
3. **Client streaming** — поток запросов, один ответ.
4. **Bidirectional streaming** — обе стороны обмениваются потоками сообщений.

### Статусы gRPC

gRPC использует свои статусы, например:

- `OK` — успешно.
- `INVALID_ARGUMENT` — некорректный аргумент.
- `NOT_FOUND` — объект не найден.
- `UNAUTHENTICATED` — проблема аутентификации.
- `PERMISSION_DENIED` — нет прав.
- `DEADLINE_EXCEEDED` — не успели завершить вызов вовремя.
- `UNAVAILABLE` — сервис недоступен.

**Важно:** статус gRPC нельзя автоматически приравнивать к HTTP-статусу. Например, RPC может закончиться ошибкой gRPC при корректно выполненном обмене на транспортном уровне.

### Что проверять QA?

- Контракт `.proto`, обязательные бизнес-ограничения и значения по умолчанию.
- Правильный gRPC-статус и error details.
- Metadata (похожи по роли на служебные заголовки).
- Авторизацию и аутентификацию.
- Deadlines, отмену вызова, недоступность сервиса.
- Порядок и завершение streaming.
- Совместимость новых и старых версий схем.

**Вопрос:** «Чем gRPC отличается от REST?»  
**Ответ:** «В REST API обычно обращаются к ресурсам через HTTP-методы. В gRPC вызывают описанные в контракте методы сервиса; обычно используются HTTP/2 и бинарные сообщения Protobuf. Для тестирования важны `.proto`, gRPC-статусы, deadlines и streaming».

# Часть 4. Другие форматы

## 8. CSV

**CSV** — простой текстовый формат таблиц: строки содержат поля, разделённые запятыми или другим разделителем.

```csv
bonusId,userId,status
777,user-100,AVAILABLE
778,user-200,ISSUED
```

Часто встречается при импорте, экспорте и подготовке тестовых данных.

**Что проверять:** кодировку, заголовки, разделители, кавычки, пустые значения, переносы строк, дубликаты, граничные объёмы и ошибки импорта. Простое разделение строки по запятой не заменяет полноценный CSV-парсер.

## 9. multipart/form-data

Используется, например, для загрузки файлов через HTTP-формы. Состоит из нескольких частей, каждая может содержать собственные заголовки и данные.

**Что проверять:** тип и размер файла, имя, содержимое, границы частей, сочетание файла с текстовыми полями, ошибки и ограничения безопасности.

## 10. Avro и Protobuf в брокерах сообщений

JSON удобен тем, что его можно прочитать как текст. Но не все сообщения между сервисами хранятся как JSON.

**Avro** — формат сериализации, часто применяемый вместе со схемами для передачи событий.  
**Protobuf** — формат сериализации с описанием сообщений в `.proto`, часто используется с gRPC и в событиях.

Для Kafka это может выглядеть так:

```text
Producer → Serialize event → Kafka topic → Deserialize event → Consumer
```

### Что такое Schema Registry?

Сервис для хранения и управления схемами сообщений и проверки их совместимости в поддерживаемых форматах.

### Что проверять QA?

- Consumer способен прочитать событие Producer.
- Обязательные бизнес-поля присутствуют.
- Допустимы ли старые сообщения после изменения схемы.
- Не ломается ли старый Consumer после выпуска нового Producer.
- Корректно обрабатываются неизвестные поля, значения по умолчанию и ошибки десериализации.

**Важный нюанс:** совместимость схем зависит от формата и правил эволюции; нельзя считать, что «любое добавление поля всегда безопасно».

# Часть 5. Сравнение технологий

## 11. Сводная таблица

| Технология | Как выглядит взаимодействие | Чем чаще передают данные | На что смотреть QA |
|---|---|---|---|
| REST API | HTTP-метод + ресурс | Часто JSON | HTTP-статусы, схема, бизнес-логика |
| SOAP | Операция в SOAP Envelope | XML | WSDL, XSD, Fault, namespace |
| GraphQL | Query / Mutation / Subscription | Обычно JSON для HTTP-запросов и ответов | Schema, `data`, `errors`, поля, права |
| gRPC | Вызов метода сервиса | Обычно Protobuf | `.proto`, статусы gRPC, streaming, deadlines |

Нет технологии, которая всегда лучше остальных. Выбор зависит от требований системы, имеющихся клиентов, производительности, контрактов и ограничений интеграции.

### Как запомнить

- **JSON/XML** — в каком виде записаны данные.
- **REST** — работа с ресурсами через набор архитектурных правил.
- **SOAP** — обмен строго оформленными XML-сообщениями.
- **GraphQL** — клиент запрашивает конкретные поля.
- **gRPC** — клиент вызывает удалённые методы по контракту.

# Часть 6. Вопросы для собеседования

## 12. Короткие ответы

**1. Какие типы данных есть в JSON?**  
String, Number, Boolean, Null, Object, Array — всего шесть.

**2. Есть ли в JSON Integer, Float и Date?**  
Отдельных таких типов нет. Есть Number, а дату обычно записывают строкой.

**3. Чем `null` отличается от отсутствующего поля?**  
`null` — поле присутствует с явным значением. Отсутствующее поле вообще не передано.

**4. Что такое сериализация?**  
Преобразование данных программы в формат для хранения или передачи.

**5. JSON и XML — это протоколы?**  
Нет, это форматы представления данных.

**6. Что такое XSD?**  
Схема, описывающая правила структуры и типов XML-документа.

**7. Что такое SOAP?**  
Протокол обмена XML-сообщениями с Envelope, Body и механизмом Fault.

**8. Что такое WSDL?**  
Описание возможностей веб-сервиса и способов обращения к его операциям.

**9. Чем REST отличается от SOAP?**  
REST — архитектурный стиль, SOAP — протокол обмена сообщениями.

**10. Что такое GraphQL?**  
Язык запросов к API, позволяющий клиенту выбирать нужные поля из схемы.

**11. Чем Query отличается от Mutation?**  
Query обычно читает данные, Mutation используется для изменения данных.

**12. Может ли GraphQL вернуть HTTP 200 с ошибкой?**  
Да. При ошибках выполнения GraphQL ответ может содержать поле `errors` и частичные `data`.

**13. Что такое gRPC?**  
Технология удалённых вызовов методов, обычно поверх HTTP/2 с Protocol Buffers.

**14. Что такое `.proto`?**  
Файл, описывающий сообщения и методы сервиса для Protocol Buffers/gRPC.

**15. Какие бывают RPC в gRPC?**  
Unary, Server Streaming, Client Streaming, Bidirectional Streaming.

**16. Что такое Avro?**  
Формат сериализации данных, поддерживающий работу со схемами.

**17. Зачем нужен Schema Registry?**  
Хранить и проверять схемы сообщений и совместимость их версий.

**18. Почему важно проверять обратную совместимость схем сообщений?**  
Чтобы новый Producer не сломал старых Consumer и наоборот, в зависимости от правил совместимости.

# Часть 7. Практические задания для QA

## Задание 1. Типы JSON

Контракт требует `bonusId: integer` и необязательное `comment: string`.

Какие случаи проверить?

- `bonusId=777`.
- `bonusId="777"`.
- `bonusId=777.5`.
- `bonusId=true`.
- `bonusId=null`.
- `bonusId=[]`.
- Поле `bonusId` отсутствует.
- `comment` отсутствует, `null`, пустая строка, длинная строка.

Для каждого случая сверять ожидания с контрактом, а также проверять, что при ошибке не произошло нежелательного изменения данных.

## Задание 2. XML

Проверить SOAP-запрос с правильным Envelope, но отсутствующим обязательным `bonusId`.

Ожидается корректная обработка ошибки в рамках SOAP-контракта, без нежелательного бизнес-эффекта.

## Задание 3. GraphQL

Запросить доступный бонус с полями `id` и `status`, затем запросить несуществующее поле.

Проверить валидность схемы, структуру ответа и ошибки GraphQL. Отдельно проверить доступ к чужому бонусу: выбор полей не должен обходить авторизацию.

## Задание 4. gRPC

Вызвать `GetBonus` с допустимым и несуществующим ID, затем с некорректным значением по правилам контракта.

Проверить gRPC-статус, ответ, метаданные и deadline. Помнить, что в `proto3` у некоторых полей значение по умолчанию и отсутствие поля могут требовать отдельного проектного решения.

## Задание 5. Kafka и совместимость схем

Producer начал отправлять новую версию сообщения с дополнительным полем. Проверить, может ли прежний Consumer прочитать новое событие при выбранной схеме и правилах совместимости. Затем проверить обработку сообщений, созданных старой версией Producer.
