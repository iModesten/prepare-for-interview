## 1. Основные понятия

В браузерной безопасности важно различать четыре механизма.

| Понятие | Назначение |
|---|---|
| Same-Origin Policy (SOP) | Ограничивает определённые взаимодействия между разными origin |
| CORS | Позволяет серверу разрешить браузерному JavaScript доступ к cross-origin ответам |
| CSRF | Атака, заставляющая браузер пользователя отправить нежелательный запрос с его полномочиями |
| XSS | Уязвимость, позволяющая выполнять недоверенный JavaScript в контексте приложения |

### Краткий ответ для собеседования

> Same-Origin Policy — браузерная политика безопасности, ограничивающая доступ к данным другого origin. CORS — механизм, позволяющий серверу ослабить некоторые из этих ограничений для разрешённых origin. CSRF — атака, при которой браузер авторизованного пользователя отправляет нежелательный запрос. XSS — внедрение и выполнение недоверенного JavaScript в контексте сайта.

**Главное:** CORS, CSRF и XSS — не три названия одной проблемы. Они работают на разных уровнях.

# Часть 1. Same-Origin Policy

## 2. Что такое Origin?

**Origin** — комбинация:

```text
scheme + host + port
```

Например:

```text
https://shop.example.com:443
```

В стандартной записи порт 443 для HTTPS обычно опускается.

Origin не включает:

- Path.
- Query parameters.
- Fragment.

### Пример

Текущая страница:

```text
https://shop.example.com/products/100
```

Её origin:

```text
https://shop.example.com
```

Сравним адреса:

| URL | Same-Origin? |
|---|---|
| https://shop.example.com/api | Да |
| https://shop.example.com/profile | Да |
| http://shop.example.com/api | Нет |
| https://api.example.com | Нет |
| https://shop.example.com:8443 | Нет |

Даже изменение схемы HTTP на HTTPS означает другой origin.

---

## 3. Что такое Same-Origin Policy?

**Same-Origin Policy** — браузерная модель безопасности, ограничивающая доступ одного origin к данным и возможностям другого origin.

Например, пользователь одновременно открыл:

```text
https://bank.example
https://other.example
```

JavaScript сайта `other.example` не должен автоматически получать возможность читать содержимое банковского приложения.

### Зачем нужна SOP?

Чтобы изолировать сайты друг от друга.

Без такой изоляции произвольная веб-страница могла бы читать конфиденциальную информацию из других открытых пользователем сайтов.

### Важный нюанс

SOP не означает, что браузер блокирует все запросы между origin.

Например, браузер может:

- Загружать изображения с другого сайта.
- Выполнять навигацию.
- Отправлять HTML-формы.
- Выполнять некоторые cross-origin запросы.

Но возможности чтения ответов и взаимодействия между origin ограничены.

### Типичный вопрос

**Может ли браузер отправить запрос на другой origin?**

> Да. Same-Origin Policy не запрещает все cross-origin запросы. Она ограничивает определённые виды доступа к данным. Для чтения cross-origin ответа через JavaScript обычно необходима корректная политика CORS.

# Часть 2. CORS

## 4. Что такое CORS?

**CORS (Cross-Origin Resource Sharing)** — механизм HTTP-заголовков, позволяющий серверу сообщить браузеру, каким origin разрешено получать доступ к cross-origin ответам.

### Пример

Frontend:

```text
https://shop.example.com
```

Backend:

```text
https://api.example.com
```

JavaScript выполняет:

```javascript
fetch("https://api.example.com/products");
```

Это cross-origin запрос, поскольку хосты различаются.

Браузер может отправить:

```http
GET /products HTTP/1.1
Host: api.example.com
Origin: https://shop.example.com
```

Backend возвращает:

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://shop.example.com
Content-Type: application/json

{
  "products": []
}
```

Браузер проверяет CORS-заголовки и разрешает JavaScript прочитать ответ.

### Кто контролирует CORS?

**Браузер.**

Сервер объявляет политику, а браузер её применяет.

Обычные небраузерные клиенты, например curl и Postman, не ограничивают доступ к ответу браузерной CORS-политикой.

---

## 5. Что делает Origin?

Заголовок `Origin` указывает источник запроса.

Пример:

```http
Origin: https://shop.example.com
```

Он содержит только схему, хост и порт.

### Origin vs Host

```http
Host: api.example.com
Origin: https://shop.example.com
```

- Host — куда отправлен запрос.
- Origin — из какого origin запрос инициирован.

### Всегда ли браузер отправляет Origin?

Нет.

Это зависит от контекста запроса, метода и режима Fetch.

Например, обычный same-origin GET может не содержать Origin.

### Можно ли доверять Origin?

Как сигналу браузерного контекста — при корректной модели угроз.

Но Origin не заменяет аутентификацию и авторизацию.

Небраузерный клиент может самостоятельно установить произвольный Origin.

---

## 6. Основные CORS-заголовки

| Заголовок | Назначение |
|---|---|
| Origin | Источник запроса |
| Access-Control-Allow-Origin | Разрешённый origin |
| Access-Control-Allow-Methods | Разрешённые HTTP-методы для preflight |
| Access-Control-Allow-Headers | Разрешённые заголовки запроса |
| Access-Control-Allow-Credentials | Разрешение браузеру предоставить ответ credentialed-запроса |
| Access-Control-Max-Age | Кэширование результата preflight |
| Access-Control-Expose-Headers | Какие дополнительные заголовки ответа может читать JS |
| Access-Control-Request-Method | Метод предполагаемого запроса |
| Access-Control-Request-Headers | Заголовки предполагаемого запроса |

### Access-Control-Allow-Origin

```http
Access-Control-Allow-Origin: https://shop.example.com
```

Разрешает указанному origin доступ к ответу при выполнении остальных условий CORS.

### Wildcard

```http
Access-Control-Allow-Origin: *
```

Разрешает доступ произвольным origin в сценариях, где wildcard допустим.

Но wildcard нельзя использовать для credentialed CORS-ответов, доступ к которым разрешается через `Access-Control-Allow-Credentials: true`.

---

## 7. Что такое CORS Preflight?

**Preflight** — предварительный OPTIONS-запрос браузера, который проверяет, разрешён ли предполагаемый cross-origin запрос.

Он нужен не для каждого cross-origin запроса.

### Пример

Frontend выполняет:

```javascript
fetch("https://api.example.com/orders", {
  method: "POST",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify({
    productId: 10
  })
});
```

Такой запрос обычно требует preflight, поскольку `application/json` не относится к CORS-safelisted типам содержимого.

### Шаг 1. Preflight Request

```http
OPTIONS /orders HTTP/1.1
Host: api.example.com
Origin: https://shop.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

### Шаг 2. Preflight Response

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://shop.example.com
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: content-type
Access-Control-Max-Age: 600
```

### Шаг 3. Основной запрос

Если браузер считает preflight успешным, он может отправить основной POST.

### Вопрос на собеседовании

**Почему OPTIONS проходит перед POST?**

> Браузер проверяет CORS-политику сервера перед выполнением определённых cross-origin запросов. Через OPTIONS он сообщает предполагаемый метод и заголовки, после чего сервер возвращает разрешённые параметры.

---

## 8. Когда Preflight обычно не нужен?

Пример простого cross-origin GET без дополнительных несоответствующих safelist-заголовков:

```javascript
fetch("https://api.example.com/products");
```

Такой запрос обычно выполняется без предварительного OPTIONS.

Также существуют условия, при которых POST может быть отправлен без preflight.

Например, использование определённых CORS-safelisted значений Content-Type:

- application/x-www-form-urlencoded.
- multipart/form-data.
- text/plain.

Но должны выполняться и другие требования CORS-safelisted request.

### Важный вывод

**Отсутствие preflight не означает, что запрос безопасен.**

Это лишь означает, что он соответствует условиям, при которых браузер не обязан предварительно согласовывать запрос.

---

## 9. CORS и Credentials

Credentials могут включать:

- Cookies.
- HTTP authentication.
- Клиентские TLS-сертификаты.

Пример браузерного запроса:

```javascript
fetch("https://api.example.com/profile", {
  credentials: "include"
});
```

Если запрос использует credentials и сервер должен разрешить JavaScript прочитать ответ, требуется подходящая CORS-конфигурация.

Например:

```http
Access-Control-Allow-Origin: https://shop.example.com
Access-Control-Allow-Credentials: true
```

### Неправильная конфигурация

```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

Браузер не разрешит credentialed CORS response с такой комбинацией.

### Дополнительный нюанс

Даже при правильном CORS cookies могут не передаваться из-за:

- SameSite.
- Domain.
- Path.
- Secure.
- Политик блокировки сторонних cookies.
- Настроек браузерного запроса.

CORS и правила cookies работают совместно, но это разные механизмы.

---

## 10. Почему в Postman работает, а в браузере CORS Error?

Это один из самых частых практических вопросов.

### Ситуация

API:

```text
https://api.example.com/orders
```

В Postman:

```text
200 OK
```

В браузере:

```text
CORS error
```

### Причина

Postman не применяет браузерную Same-Origin Policy.

Браузер проверяет Origin, CORS-разрешения, preflight и наличие необходимых заголовков ответа.

### Что проверять QA?

1. Какой Origin отправляет браузер.
2. Какой Access-Control-Allow-Origin возвращает сервер.
3. Нужен ли preflight.
4. Как отвечает OPTIONS.
5. Разрешён ли требуемый метод.
6. Разрешены ли требуемые заголовки.
7. Используются ли credentials.
8. Не изменяет ли ответ CDN или Reverse Proxy.

### Важный нюанс

При некоторых CORS-ошибках основной запрос уже мог дойти до сервера и изменить данные.

Браузер может заблокировать именно **доступ JavaScript к ответу**.

При неуспешном preflight основной запрос, напротив, обычно вообще не отправляется.

---

# Часть 3. CSRF

## 11. Что такое CSRF?

**CSRF (Cross-Site Request Forgery)** — атака, при которой злоумышленник заставляет браузер пользователя выполнить нежелательное действие на сайте, где пользователь уже имеет действующую аутентификацию.

### Пример

Пользователь авторизован на:

```text
https://bank.example
```

Его браузер хранит действующую session cookie.

Пользователь открывает вредоносную страницу.

Страница пытается отправить запрос на банковский сайт:

```http
POST /transfer
Cookie: session=valid-session
```

Если браузер приложит действующие credentials, а сервер не проверит подлинность происхождения операции, запрос может выполниться от имени пользователя.

### Упрощённая схема

```text
Пользователь авторизован в Bank
                |
                v
Браузер хранит session cookie
                |
                v
Пользователь открывает другой сайт
                |
                v
Вредоносная страница инициирует запрос
                |
                v
Браузер может приложить credentials
                |
                v
Bank выполняет операцию без проверки CSRF
```

### Краткий ответ для собеседования

> CSRF — атака, при которой браузер авторизованного пользователя отправляет нежелательный запрос на доверенный сайт. Она особенно актуальна, когда аутентификация основана на cookies, автоматически прикладываемых браузером. Для защиты используют CSRF-токены, SameSite, проверку Origin/Referer и Fetch Metadata.

---

## 12. Почему CSRF вообще возможен?

Потому что браузер может автоматически прикладывать учётные данные к запросам.

Например, session cookie.

При этом запрос может быть инициирован не самим банковским приложением, а другой страницей.

Если Backend проверяет только наличие действующей сессии, он может не отличить легитимное действие пользователя от поддельного.

### Важный нюанс

CSRF не обязательно требует, чтобы атакующая страница могла прочитать HTTP-ответ.

Ей может быть достаточно заставить браузер **отправить запрос с побочным эффектом**.

Именно поэтому CORS сам по себе не является универсальной защитой от CSRF.

---

## 13. CSRF и CORS — в чём разница?

Это вопрос уровня уверенного Backend QA.

| Характеристика | CORS | CSRF |
|---|---|---|
| Что это? | Механизм браузерного доступа | Тип атаки |
| Основной вопрос | Можно ли JS прочитать cross-origin ответ? | Можно ли выполнить нежелательное действие с полномочиями пользователя? |
| Связан с браузером? | Да | Обычно да |
| Связан с cookies? | Не обязательно | Часто |
| Защита | Корректная CORS-политика | CSRF-токены, SameSite, Origin/Referer, Fetch Metadata |

### Пример

Вредоносный сайт отправляет HTML-форму на другой origin.

Браузер может выполнить отправку, даже если атакующий JavaScript не получит доступа к ответу из-за SOP.

Поэтому нельзя просто сказать:

> У нас настроен CORS, значит CSRF невозможен.

Это неверно.

### Но помогает ли CORS защищаться от CSRF?

Иногда косвенно.

Например, если API требует нестандартный заголовок, браузер обычно выполняет preflight, а строгая CORS-политика может не позволить отправить такой cross-origin запрос.

Однако этот механизм зависит от архитектуры и не должен подменять комплексную серверную CSRF-защиту.

---

## 14. CSRF Token

Один из основных способов защиты — **CSRF Token**.

Это непредсказуемое значение, которое сервер связывает с пользовательской сессией или другим проверяемым контекстом.

### Пример

Сервер предоставляет клиенту CSRF-токен.

При изменяющем запросе приложение отправляет его отдельно от автоматически прикладываемой cookie:

```http
POST /profile/update
Cookie: session=abc123
X-CSRF-Token: random-token-value
Content-Type: application/json

{
  "name": "Anna"
}
```

Backend проверяет:

- Наличие токена.
- Корректность значения.
- Связь с сессией или защищаемым контекстом.
- Другие предусмотренные условия.

### Почему это работает?

Атакующая страница обычно не может получить корректный секретный CSRF-токен защищённого приложения из-за браузерных ограничений и правильной реализации защиты.

Поэтому ей недостаточно просто инициировать запрос с автоматически прикладываемой cookie.

### Основные требования

CSRF-токен должен быть:

- Непредсказуемым.
- Связанным с защищаемым контекстом.
- Проверяемым сервером.
- Защищённым от утечек.

### Что проверять QA?

- Отсутствующий токен.
- Неверный токен.
- Токен другого пользователя.
- Токен другой сессии.
- Повторный токен, если предусмотрена одноразовость.
- Истёкший токен, если предусмотрен срок жизни.
- Подмена Cookie при сохранении прежнего токена.

---

## 15. Synchronizer Token Pattern

В этом подходе сервер генерирует CSRF-токен и связывает его с пользовательской сессией.

Клиент получает токен через доверенный канал приложения.

Затем передаёт его в защищённых изменяющих запросах.

### Схема

```text
User login
    |
    v
Server creates session
    |
    v
Server generates CSRF token
    |
    v
Client receives token
    |
    v
POST with session cookie + CSRF token
    |
    v
Server validates token
```

### Преимущества

- Сервер контролирует связь токена с сессией.
- Можно централизованно управлять его действительностью.
- Защита не зависит только от политики SameSite.

### Недостатки

- Необходимо управлять токенами.
- Нужна корректная работа при нескольких вкладках и изменении сессии.
- Одноразовые токены могут усложнять пользовательские сценарии.

---

## 16. Double Submit Cookie

Другой подход к CSRF-защите.

В упрощённом варианте:

1. Сервер выдаёт cookie с CSRF-значением.
2. Клиент передаёт соответствующее значение ещё и в отдельном параметре или заголовке.
3. Backend проверяет соответствие.

Однако простой Double Submit без криптографической привязки имеет ограничения безопасности.

Для современных систем предпочтительнее использовать **Signed Double Submit Cookie**, привязанный к пользовательской сессии или другому доверенному контексту.

### Важно

Не следует воспринимать совпадение двух произвольных клиентских значений как достаточную защиту.

Нужно учитывать возможность подделки или внедрения cookie, в том числе через подконтрольные поддомены.

---

## 17. SameSite Cookie

Атрибут `SameSite` регулирует отправку cookie в межсайтовых контекстах.

### SameSite=Strict

```http
Set-Cookie: session=abc; Secure; HttpOnly; SameSite=Strict
```

Наиболее строгий из основных режимов.

Cookie не отправляется в обычных cross-site контекстах.

### SameSite=Lax

```http
Set-Cookie: session=abc; Secure; HttpOnly; SameSite=Lax
```

Ограничивает отправку cookie в ряде cross-site запросов, но допускает некоторые верхнеуровневые навигации с безопасными методами.

### SameSite=None

```http
Set-Cookie: session=abc; Secure; HttpOnly; SameSite=None
```

Позволяет использовать cookie в cross-site контекстах при соблюдении браузерных правил.

Для SameSite=None обычно требуется Secure.

### Важный нюанс

**SameSite и Same-Origin — разные понятия.**

Например:

```text
https://shop.example.com
https://api.example.com
```

Это разные origin, но обычно один site.

### Достаточно ли SameSite для защиты от CSRF?

Не всегда.

SameSite — важный механизм, но его достаточность зависит от архитектуры, поддерживаемых браузеров, доверия к поддоменам и отсутствия опасных изменяющих GET-операций.

Для критичных систем обычно рассматривают дополнительные защиты.

---

## 18. Origin и Referer при CSRF-защите

Backend может проверять, откуда был инициирован запрос.

Пример:

```http
Origin: https://bank.example
```

Сервер сравнивает его с ожидаемым доверенным origin.

Если Origin отсутствует, определённые системы используют Referer как дополнительный источник информации.

### Что важно проверять?

- Корректный Origin.
- Origin другого сайта.
- Origin: null.
- Отсутствие Origin.
- Отсутствие Referer.
- Некорректные домены, похожие на доверенные.
- Работа через Reverse Proxy.
- Корректность определения целевого origin.

### Пример ошибки

Система доверяет любому значению, содержащему строку:

```text
bank.example
```

Тогда ошибочно может быть принят адрес:

```text
https://bank.example.attacker.test
```

Нужно сравнивать корректно разобранные origin, а не использовать небезопасный поиск подстроки.

---

## 19. Fetch Metadata

Современные браузеры могут отправлять заголовки:

```http
Sec-Fetch-Site: cross-site
Sec-Fetch-Mode: cors
Sec-Fetch-Dest: empty
```

### Sec-Fetch-Site

Показывает отношение инициатора к целевому ресурсу.

Основные значения:

- same-origin.
- same-site.
- cross-site.
- none.

### Зачем это нужно?

Backend может использовать Fetch Metadata для дополнительной защиты от нежелательных cross-site запросов.

Например, отклонять часть cross-site POST-запросов, которые не должны поступать извне.

### Важно

Fetch Metadata не заменяет аутентификацию, авторизацию и всю CSRF-защиту.

Также нужно учитывать клиентов, которые не отправляют эти заголовки.

---

# Часть 4. XSS

## 20. Что такое XSS?

**XSS (Cross-Site Scripting)** — уязвимость, позволяющая внедрить недоверенное содержимое таким образом, что браузер выполнит его как JavaScript в контексте веб-приложения.

### Пример

Приложение выводит комментарий пользователя как HTML без безопасной обработки.

Вместо обычного текста может быть интерпретирован HTML с обработчиком события.

Пример небезопасного ввода:

```html
<img src=x onerror=alert(1)>
```

Если приложение вставит его как исполняемый HTML, может выполниться JavaScript.

Это демонстрационный пример для тестовой среды. В реальном тестировании достаточно подтвердить выполнение безвредного действия, не затрагивая данные других пользователей.

### Краткий ответ для собеседования

> XSS — уязвимость, при которой недоверенный ввод попадает в исполняемый контекст страницы. Злоумышленник может выполнить JavaScript с полномочиями origin приложения. Защита строится на контекстном экранировании вывода, безопасных DOM API, проверенной HTML-санации и дополнительных механизмах вроде CSP.

---

## 21. Основные типы XSS

### Reflected XSS

Вредоносное содержимое приходит в запросе и сразу отражается в ответе.

Например:

```text
/search?q=some-input
```

Если значение `q` небезопасно вставляется в HTML, возникает риск выполнения JavaScript.

### Stored XSS

Вредоносное содержимое сохраняется на сервере.

Например:

1. Пользователь создаёт комментарий.
2. Комментарий сохраняется в БД.
3. Другой пользователь открывает страницу.
4. Браузер выполняет небезопасно вставленный код.

Stored XSS особенно опасен, поскольку может затрагивать множество пользователей.

### DOM-based XSS

Уязвимость возникает при небезопасной обработке данных непосредственно в браузерном JavaScript.

Например, когда приложение передаёт недоверенный текст в `innerHTML`.

---

## 22. Пример DOM-based XSS

### Небезопасный вариант

```javascript
const value = new URLSearchParams(location.search).get("name");

document.querySelector("#result").innerHTML = value;
```

Если пользователь управляет `name`, приложение может интерпретировать его как HTML.

### Более безопасный вариант

```javascript
const value = new URLSearchParams(location.search).get("name");

document.querySelector("#result").textContent = value;
```

`textContent` вставляет значение как текст, а не как HTML-разметку.

### Важный нюанс

Не существует универсальной функции «экранировать всё», которая правильно работает во всех контекстах.

Защита зависит от того, куда вставляется значение:

- HTML-текст.
- HTML-атрибут.
- URL.
- JavaScript.
- CSS.
- DOM API.

---

## 23. Почему XSS опасен?

Вредоносный JavaScript может выполнять действия в контексте origin приложения.

Возможные последствия:

- Выполнение запросов от имени пользователя.
- Чтение доступных JavaScript данных.
- Изменение интерфейса.
- Перехват пользовательского ввода.
- Подмена содержимого страницы.
- Обход части клиентских ограничений.
- Доступ к токенам, доступным JavaScript.

### Может ли XSS украсть HttpOnly Cookie?

Напрямую через `document.cookie` — нет.

Но XSS всё равно может быть опасен, поскольку браузер способен автоматически отправлять HttpOnly cookie в запросах к соответствующему сайту.

### Важный вывод

**HttpOnly снижает отдельные риски XSS, но не устраняет XSS.**

---

## 24. Как защищаются от XSS?

Основные механизмы:

### Контекстное экранирование вывода

Недоверенные данные должны вставляться в страницу с учётом конкретного контекста.

### Безопасные DOM API

Например, `textContent` вместо `innerHTML`, когда нужно вывести обычный текст.

### HTML Sanitization

Если приложение действительно должно принимать пользовательскую HTML-разметку, необходима проверенная санация с разрешённым набором элементов и атрибутов.

### Content Security Policy

Ограничивает источники исполняемых ресурсов и некоторые опасные действия браузера.

### Безопасная работа с шаблонами

Современные frontend-фреймворки часто автоматически экранируют обычные текстовые значения, но небезопасные API могут обходить эту защиту.

### Дополнительные меры

- HttpOnly для session cookies.
- Минимизация хранения секретов в доступном JS пространстве.
- Ограничение полномочий пользователя.
- Серверная авторизация каждой операции.

---

## 25. Что такое Content Security Policy?

**CSP (Content Security Policy)** — механизм браузерной безопасности, позволяющий задавать ограничения на загрузку и выполнение ресурсов.

Пример:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

Это может ограничивать выполнение скриптов из недоверенных источников.

### Может ли CSP полностью заменить защиту от XSS?

Нет.

CSP полезна как дополнительный слой защиты, но основные механизмы — безопасная обработка недоверенных данных и корректное использование DOM API.

### CSP Report-Only

Существует режим:

```http
Content-Security-Policy-Report-Only: ...
```

Он позволяет наблюдать нарушения политики без полного применения соответствующих ограничений.

Это полезно при внедрении CSP.

---

# Часть 5. CSRF vs XSS

## 26. Чем CSRF отличается от XSS?

| Характеристика | CSRF | XSS |
|---|---|---|
| Суть | Поддельное действие через браузер жертвы | Выполнение недоверенного JavaScript |
| Где выполняется вредоносный код | Обычно на стороннем сайте или в другом контексте | В контексте уязвимого приложения |
| Требуется действующая сессия? | Часто да | Не обязательно |
| Главный риск | Нежелательная бизнес-операция | Компрометация возможностей origin приложения |
| Типичная защита | CSRF-токены, SameSite, Origin | Экранирование, санация, безопасный DOM, CSP |

### Почему XSS может обходить CSRF-защиту?

Если злоумышленник уже выполняет JavaScript внутри origin уязвимого приложения, скрипт может получить доступ к доступным странице CSRF-токенам и отправить запросы в допустимом контексте.

Поэтому XSS способен подорвать некоторые CSRF-механизмы.

### Краткий ответ

> CSRF использует существующую авторизацию пользователя, заставляя его браузер выполнить нежелательное действие. XSS позволяет выполнять недоверенный JavaScript в контексте приложения. XSS обычно предоставляет злоумышленнику более широкие возможности и может обходить часть CSRF-защит.

---

# Часть 6. Практика QA

## 27. Как тестировать CORS?

### Подготовка

Есть Backend:

```text
https://api.example.com
```

Разрешённый frontend:

```text
https://app.example.com
```

### Основные проверки

- [ ] Запрос с разрешённого Origin.
- [ ] Запрос с запрещённого Origin.
- [ ] Отсутствующий Origin.
- [ ] Origin: null.
- [ ] Корректность Access-Control-Allow-Origin.
- [ ] Разрешённые и запрещённые методы.
- [ ] Разрешённые и запрещённые заголовки.
- [ ] Preflight OPTIONS.
- [ ] Credentialed requests.
- [ ] Отсутствие wildcard при credentialed CORS.
- [ ] Корректность Vary: Origin при динамической политике.

### Важный нюанс

Для проверки реального CORS-поведения лучше использовать браузер, поскольку curl или Postman не обеспечивают браузерный контроль доступа к ответу.

---

## 28. Как тестировать CSRF?

Предположим, приложение использует cookie-based authentication.

### Основные проверки

1. Изменяющий запрос без CSRF-токена.
2. Запрос с неправильным токеном.
3. Запрос с токеном другого пользователя.
4. Запрос с токеном другой сессии.
5. Запрос с запрещённого Origin.
6. Запрос с Origin: null.
7. Запрос без Origin и Referer.
8. Проверка SameSite.
9. Попытка изменения состояния через GET.
10. Проверка корректной авторизации самой операции.

### Ожидаемый результат

Нежелательное изменение состояния не выполняется, если запрос не соответствует установленным правилам защиты.

### Нужно ли всегда требовать CSRF-токен?

Не обязательно в любой архитектуре.

Например, API, которое принимает только Bearer Token, явно устанавливаемый клиентом в Authorization, может иметь другую модель CSRF-риска, чем cookie-based приложение.

Однако необходимо учитывать все способы передачи credentials и реальные браузерные сценарии.

## 29. Как тестировать XSS?

### Основные точки ввода

- Поля профиля.
- Комментарии.
- Поисковые запросы.
- Названия объектов.
- Сообщения.
- Параметры URL.
- Данные, полученные из API.
- Ошибки, выводимые интерфейсом.

### Что проверять?

- [ ] Ввод отображается как текст, а не исполняемый код.
- [ ] HTML не интерпретируется там, где он не предусмотрен.
- [ ] Пользовательская HTML-разметка проходит безопасную санацию.
- [ ] Нет небезопасной вставки через innerHTML.
- [ ] Ввод корректно обрабатывается в атрибутах.
- [ ] Содержимое из URL не создаёт DOM XSS.
- [ ] Сохранённый ввод безопасно отображается другим пользователям.
- [ ] CSP соответствует требованиям.
- [ ] Нет утечки чувствительных данных через клиентские ошибки.

### Важно для QA

Проверки нужно проводить в разрешённой тестовой среде с безопасными демонстрационными значениями.

Нельзя тестировать выполнение вредоносного кода на данных реальных пользователей без соответствующего разрешения.

## 30. Практический кейс: CORS Error после логина

### Ситуация

Frontend:

```text
https://app.example.com
```

Backend:

```text
https://api.example.com
```

Пользователь выполняет логин, но следующий запрос `/profile` не работает.

В DevTools:

```text
CORS policy error
```

### Возможные причины

- Неверный Access-Control-Allow-Origin.
- Отсутствует Access-Control-Allow-Credentials.
- Используется wildcard с credentials.
- Не проходит preflight.
- Cookie не отправляется из-за SameSite или Domain.
- Backend возвращает ошибку без CORS-заголовков.
- Reverse Proxy некорректно обрабатывает OPTIONS.

### Как диагностировать?

1. Найти запрос во вкладке Network.
2. Проверить Origin.
3. Посмотреть, был ли OPTIONS.
4. Проверить статус OPTIONS.
5. Проверить CORS-заголовки.
6. Проверить Set-Cookie и Cookie.
7. Проверить атрибуты cookie.
8. Установить, был ли реально отправлен основной запрос.
9. Проверить серверные логи по Request ID.

## 31. Практический кейс: списание выполняется через GET

### Ситуация

Разработчик создал endpoint:

```http
GET /api/withdraw?amount=100
```

Вызов списывает деньги.

### Что здесь не так?

GET по стандартной семантике является безопасным методом.

Он не должен использоваться для запроса нежелательных изменений состояния.

Браузер может выполнять GET через:

- Навигацию.
- Ссылки.
- Предварительную загрузку.
- Другие автоматические механизмы.

Кроме того, при некоторых SameSite=Lax сценариях cookies могут отправляться при верхнеуровневой навигации GET.

### Как исправить?

Использовать соответствующий изменяющий метод, например POST, и добавить полноценные проверки:

- Аутентификация.
- Авторизация.
- Защита от CSRF при соответствующей модели.
- Идемпотентность для повторных запросов.
- Проверка бизнес-ограничений.

# Часть 7. Вопросы для собеседования

## 32. Что такое Same-Origin Policy?

Браузерная политика, ограничивающая определённый доступ между origin.

## 33. Что такое Origin?

Сочетание схемы, хоста и порта.

## 34. Что такое CORS?

Механизм, позволяющий серверу через HTTP-заголовки разрешить браузеру предоставлять JavaScript доступ к cross-origin ответам.

## 35. Кто обеспечивает CORS?

Браузер применяет политику на основании заголовков ответа сервера.

## 36. Почему Postman не показывает CORS Error?

Потому что Postman не реализует браузерную Same-Origin Policy для чтения ответов.

## 37. Что такое Preflight?

Предварительный OPTIONS-запрос для проверки разрешений на определённый cross-origin запрос.

## 38. Когда используется Access-Control-Allow-Origin: *?

Когда сервер разрешает доступ произвольным origin и конкретный сценарий допускает wildcard, например без credentialed CORS-доступа.

## 39. Что такое CSRF?

Атака, вызывающая нежелательное действие через браузер пользователя, часто с автоматически прикладываемыми credentials.

## 40. Почему Cookie-based Authentication связана с CSRF?

Потому что браузер автоматически отправляет подходящие cookies с запросами, а значит сторонняя страница может попытаться инициировать действие от имени пользователя.

## 41. Как защищаться от CSRF?

CSRF-токены, SameSite, проверка Origin/Referer, Fetch Metadata и дополнительные проверки для чувствительных операций.

## 42. Может ли CORS полностью защитить от CSRF?

Нет. Некоторые cross-origin запросы могут быть отправлены без возможности прочитать ответ.

## 43. Что такое SameSite?

Атрибут cookie, регулирующий её отправку в межсайтовых контекстах.

## 44. Чем SameSite отличается от Same-Origin?

Same-Origin сравнивает схему, хост и порт. SameSite использует понятие site, основанное на схеме и регистрируемом домене в современных браузерах.

## 45. Что такое XSS?

Уязвимость, позволяющая выполнять недоверенный JavaScript в контексте веб-приложения.

## 46. Какие типы XSS существуют?

Reflected, Stored и DOM-based.

## 47. Чем CSRF отличается от XSS?

CSRF заставляет браузер выполнить нежелательный запрос. XSS позволяет выполнять JavaScript внутри доверенного origin.

## 48. Защищает ли HttpOnly от XSS полностью?

Нет. Он препятствует прямому чтению cookie через JavaScript, но не устраняет остальные последствия XSS.

## 49. Что такое CSP?

Content Security Policy — механизм ограничения загрузки и выполнения ресурсов в браузере.

## 50. Что такое Sec-Fetch-Site?

Браузерный заголовок, описывающий отношение origin инициатора запроса к целевому ресурсу.

## Частые ошибки на собеседовании

**Ошибка:** «CORS запрещает отправлять запросы на чужие сайты».

Правильно: CORS прежде всего управляет разрешением браузеру предоставить JavaScript доступ к ответу. Некоторые запросы могут быть отправлены даже без разрешения на чтение ответа.

**Ошибка:** «Если CORS настроен, CSRF невозможен».

Правильно: CSRF связан с нежелательным выполнением действия, которому не обязательно требуется чтение ответа.

**Ошибка:** «Origin содержит полный URL страницы».

Правильно: Origin содержит схему, хост и порт, но не path и query.

**Ошибка:** «CSRF и XSS — одно и то же».

Правильно: это разные классы атак.

**Ошибка:** «HttpOnly полностью решает проблему XSS».

Правильно: HttpOnly защищает чтение cookie, но не предотвращает выполнение вредоносного JavaScript.

**Ошибка:** «SameSite=Lax защищает от любого CSRF».

Правильно: защита зависит от контекста, методов, поддоменов и архитектуры. Изменяющие GET-запросы особенно опасны.

**Ошибка:** «Любой POST автоматически требует Preflight».

Правильно: необходимость preflight зависит от характеристик запроса, включая метод, заголовки и тип содержимого.

**Ошибка:** «CSP позволяет не экранировать пользовательские данные».

Правильно: CSP — дополнительный слой, а не замена безопасного вывода.
