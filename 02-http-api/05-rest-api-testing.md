# REST API Testing — теория, тест-дизайн и практические проверки

**Уровень:** Middle / Senior QA Engineer  
**Темы:** REST, API Contracts, Test Design, CRUD, Validation, Pagination, Filtering, Sorting, Idempotency, Concurrency, Integration Testing

---

## 1. Что такое API?

**API (Application Programming Interface)** — интерфейс взаимодействия между программными компонентами.

API определяет, какие операции доступны, какие данные необходимо передавать и какой результат ожидается.

Например, сервис бонусов предоставляет:

```http
GET /api/bonuses
POST /api/bonuses/issue
GET /api/users/123/bonuses
```

Другие системы используют эти операции, не зная внутренних деталей реализации.

### API не обязательно использует HTTP

Возможные варианты:

- REST API поверх HTTP.
- SOAP.
- GraphQL.
- gRPC.
- WebSocket API.
- Внутренние программные API.

### Краткий ответ для собеседования

> API — это контракт взаимодействия между программными компонентами. В HTTP API контракт обычно описывает доступные endpoints, методы, параметры, форматы данных, статус-коды, ошибки и требования к авторизации.

---

## 2. Что такое REST?

**REST (Representational State Transfer)** — архитектурный стиль построения распределённых систем, предложенный Роем Филдингом.

REST описывает ограничения, при соблюдении которых система получает определённые архитектурные свойства.

### Основные ограничения REST

**Client–Server**

Разделение ответственности клиента и сервера.

**Stateless**

Каждый запрос содержит информацию, необходимую для его обработки.

**Cacheable**

Ответы должны обозначать возможность их кэширования.

**Uniform Interface**

Единый интерфейс взаимодействия с ресурсами.

**Layered System**

Клиент не обязан знать, взаимодействует ли он напрямую с конечным сервером или с промежуточным компонентом.

**Code on Demand**

Необязательное ограничение, позволяющее серверу передавать клиенту исполняемый код.

### Важный нюанс

REST — не синоним JSON поверх HTTP.

Также REST не является отдельным сетевым протоколом.

Система, использующая HTTP и JSON, не обязательно полностью соответствует REST.

### Краткий ответ для собеседования

> REST — архитектурный стиль, основанный на ресурсах и наборе ограничений, включая client-server, stateless, cacheable, uniform interface и layered system. В HTTP API ресурсы обычно идентифицируются через URI, а операции над ними выражаются HTTP-методами.

---

## 3. Что такое Resource?

**Resource** — сущность или концепция, доступная через интерфейс API.

Например:

```text
/users
/users/123
/orders
/orders/100
```

### Ресурс и его представление

Ресурс — не обязательно строка в базе данных.

Например, ресурс `/users/123` может иметь JSON-представление:

```json
{
  "id": 123,
  "name": "Anna"
}
```

Это представление ресурса, а не обязательно его физическая структура хранения.

### Примеры проектирования

```http
GET /orders
GET /orders/100
POST /orders
PUT /orders/100
PATCH /orders/100
DELETE /orders/100
```

Такая структура хорошо соответствует распространённому REST-подходу.

Но наличие URL с существительными само по себе не делает систему RESTful.

---

## 4. URI, Endpoint и HTTP Method

**URI** — идентификатор ресурса.

**Endpoint** — точка взаимодействия с API, обычно конкретная комбинация метода и пути.

Например:

```http
GET /api/orders/100
```

И:

```http
DELETE /api/orders/100
```

Это разные операции над одним целевым ресурсом.

### Path Parameters

```http
GET /api/users/123
```

`123` — идентификатор пользователя.

### Query Parameters

```http
GET /api/orders?status=PAID&page=2
```

Здесь параметры используются для фильтрации и пагинации.

### Request Body

```http
POST /api/orders
Content-Type: application/json

{
  "productId": 10,
  "quantity": 2
}
```

Тело содержит данные создаваемого заказа.

---

## 5. CRUD и HTTP-методы

**CRUD** — Create, Read, Update, Delete.

| CRUD | Типичный HTTP-метод |
|---|---|
| Create | POST или PUT |
| Read | GET |
| Update | PUT или PATCH |
| Delete | DELETE |

### GET

Получение представления ресурса.

### POST

Передача данных ресурсу для обработки, часто создание новой сущности.

### PUT

Создание или замена состояния ресурса по известному URI.

### PATCH

Частичное изменение ресурса.

### DELETE

Удаление ресурса или связи с его текущим представлением.

### Важный нюанс

REST API не обязан быть простым отображением CRUD на таблицы БД.

Например:

```http
POST /payments/100/refund
```

Это бизнес-операция возврата платежа, а не обычное изменение одной записи.

Такие endpoints встречаются на практике. Их корректность оценивается по архитектурной модели и контракту.

## 6. API Contract

**API Contract** — соглашение между клиентом и сервером о правилах взаимодействия.

Он может включать:

- URL и HTTP-метод.
- Path и query parameters.
- Request headers.
- Request body.
- Типы данных.
- Обязательные и необязательные поля.
- Ограничения значений.
- Response status.
- Response headers.
- Response schema.
- Коды бизнес-ошибок.
- Правила авторизации.
- Идемпотентность.
- Ограничения частоты вызовов.

### Пример контракта

```http
POST /api/bonuses/issue
Content-Type: application/json
Authorization: Bearer token
```

Request:

```json
{
  "userId": "user-100",
  "bonusId": 777
}
```

Успешный ответ:

```http
HTTP/1.1 201 Created
Content-Type: application/json
```

```json
{
  "issueId": "issue-500",
  "status": "ISSUED"
}
```

Возможные ошибки по условному контракту:

| Ситуация | Статус |
|---|---|
| Некорректные данные | 400 |
| Нет аутентификации | 401 |
| Нет прав | 403 |
| Бонус не найден | 404 |
| Бонус уже выдан | 409 |
| Внутренняя ошибка | 500 |

Это пример, а не универсальное требование ко всем API.

**Основной принцип QA:** проверять поведение относительно согласованного контракта, а не только относительно собственных ожиданий.

## 7. Что такое OpenAPI?

**OpenAPI Specification** — стандарт машиночитаемого описания HTTP API.

Обычно спецификация записывается в YAML или JSON.

Она может содержать:

- Paths.
- HTTP Methods.
- Parameters.
- Request Bodies.
- Responses.
- Schemas.
- Security Schemes.
- Examples.

### Пример OpenAPI

```yaml
openapi: 3.1.0
info:
  title: Bonus API
  version: 1.0.0

paths:
  /bonuses/{bonusId}:
    get:
      parameters:
        - name: bonusId
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: Bonus found
          content:
            application/json:
              schema:
                type: object
                required:
                  - id
                  - name
                properties:
                  id:
                    type: integer
                  name:
                    type: string
        '404':
          description: Bonus not found
```

### Что даёт QA?

Можно использовать спецификацию как основу для:

- Анализа требований.
- Разработки проверок.
- Автоматической валидации схем.
- Контрактных тестов.
- Выявления несоответствий документации и реализации.

### Но достаточно ли OpenAPI для полноценного тестирования?

Нет.

OpenAPI может описывать структуру запросов и ответов, но не обязательно содержит всю бизнес-логику.

Например, правило:

> Один пользователь может получить определённый бонус только один раз.

Может отсутствовать в формальных JSON-схемах.

Поэтому контрактные проверки необходимо дополнять функциональным и интеграционным тестированием.

# Часть 2. Тест-дизайн HTTP API

## 8. С чего начать тестирование нового Endpoint?

Допустим, разработали:

```http
POST /api/bonuses/issue
```

### Мой порядок работы

**Шаг 1. Понять бизнес-операцию**

- Для чего существует endpoint?
- Кто его вызывает?
- Какой результат должен быть?
- Какие бизнес-ограничения существуют?

**Шаг 2. Изучить контракт**

- Какие параметры обязательны?
- Какие типы данных?
- Какие статусы?
- Какие ошибки?
- Как устроена авторизация?

**Шаг 3. Определить зависимости**

- База данных.
- Внешние сервисы.
- Kafka или RabbitMQ.
- Кэш.
- Система авторизации.

**Шаг 4. Определить риски**

- Двойная выдача.
- Выдача чужому пользователю.
- Нарушение лимита.
- Некорректное состояние после ошибки.
- Повтор после таймаута.

**Шаг 5. Спроектировать проверки**

Позитивные, негативные, граничные, конкурентные и интеграционные.

**Шаг 6. Выбрать уровни тестирования**

Часть сценариев может быть покрыта тестами разработчика, часть — интеграционными или E2E-тестами QA.

### Готовый ответ для собеседования

> Сначала я анализирую бизнес-требования и API-контракт, затем определяю зависимости и основные риски. После этого выделяю классы эквивалентности, границы, бизнес-состояния, негативные сценарии и проверки авторизации. Для операций с изменением данных отдельно рассматриваю транзакционность, идемпотентность, конкурентный доступ и ошибки зависимостей. При этом учитываю существующее покрытие, чтобы не дублировать проверки без необходимости.

## 9. Позитивные и негативные сценарии

### Позитивные проверки

Проверяют корректную работу при допустимых данных.

Например:

```http
POST /api/bonuses/issue
```

Request:

```json
{
  "userId": "user-100",
  "bonusId": 777
}
```

Ожидается успешная выдача бонуса.

### Негативные проверки

Проверяют обработку некорректных данных, состояний и отсутствия прав.

Примеры:

- Отсутствует userId.
- Не существует bonusId.
- Пользователь заблокирован.
- Бонус уже выдан.
- Истёк срок действия бонуса.
- Недостаточно прав.
- Недоступна база данных.

### Важный нюанс

Негативный тест — не только проверка 400 или 404.

Для изменяющих операций необходимо проверить, что после ошибки не произошло нежелательных изменений данных.

## 10. Классы эквивалентности

**Equivalence Partitioning** — техника тест-дизайна, разделяющая входные данные на классы, для которых ожидается одинаковое поведение.

Допустим:

```text
quantity: integer, 1..100
```

Классы:

| Класс | Пример |
|---|---|
| Допустимые значения | 50 |
| Меньше минимума | 0 |
| Больше максимума | 101 |
| Неверный тип | "abc" |
| Отсутствует значение | Поле отсутствует |
| NULL | null |

### Зачем это нужно?

Позволяет выбрать небольшое количество представительных проверок вместо перебора всех возможных значений.

### Типичный вопрос

**Достаточно ли одной проверки на класс?**

Не всегда.

Это допущение тест-дизайна, а не доказательство одинакового поведения всей системы.

При высоком риске нужны дополнительные проверки.

---

## 11. Анализ граничных значений

**Boundary Value Analysis (BVA)** — тестирование значений на границах допустимых диапазонов.

Пример:

```text
quantity: 1..100
```

Проверяем:

```text
0
1
2

99
100
101
```

Если параметр имеет ограничения:

```text
length: 5..20
```

Проверяем длины:

```text
4
5
6

19
20
21
```

### Почему границы важны?

Ошибки часто возникают при использовании неправильных сравнений:

```text
< вместо <=
> вместо >=
```

### Что ещё учитывать?

- Минимальные и максимальные даты.
- Пустые коллекции.
- Переполнение числовых типов.
- Ограничения размера запросов.
- Сроки действия.
- Переходы через полночь и часовые пояса.

## 12. Decision Table

**Decision Table** — техника тест-дизайна для проверки комбинаций условий и ожидаемых решений.

Предположим, бонус можно выдать, если:

1. Пользователь активен.
2. Бонус доступен.
3. Бонус ещё не выдавался.

| User active | Bonus available | Already issued | Результат |
|---|---|---|---|
| Да | Да | Нет | Успех |
| Нет | Да | Нет | Отказ |
| Да | Нет | Нет | Отказ |
| Да | Да | Да | Отказ |
| Нет | Нет | Да | Отказ |

Полная таблица трёх независимых бинарных условий содержит восемь комбинаций. Здесь приведены только несколько репрезентативных вариантов.

### Когда полезна?

Когда результат зависит от комбинации нескольких условий.

Например:

- Выдача бонуса.
- Расчёт комиссии.
- Авторизация.
- Проверка лимитов.
- Правила скидок.

### Senior-нюанс

При построении Decision Table важно определить:

- Возможны ли все комбинации.
- Приоритет условий.
- Какие действия выполняются.
- Какие состояния считаются недопустимыми.
- Не противоречат ли правила друг другу.

## 13. Pairwise Testing

**Pairwise Testing** — комбинаторная техника, обеспечивающая покрытие всех пар значений параметров хотя бы в одном тесте.

Допустим, API зависит от:

- User Type: Regular / Premium.
- Currency: BYN / USD / EUR.
- Payment Method: Card / Account.
- Platform: Web / Mobile.

Полный перебор:

```text
2 × 3 × 2 × 2 = 24 комбинации
```

Pairwise может позволить проверить меньше комбинаций, сохранив покрытие всех пар значений.

### Почему Pairwise полезен?

Многие дефекты возникают из-за взаимодействия небольшого количества параметров.

### Но что он не гарантирует?

Не гарантирует обнаружение дефектов, зависящих от комбинации трёх и более параметров.

Также Pairwise не заменяет анализ бизнес-правил.

### Готовый ответ

> Pairwise — техника комбинаторного тестирования, при которой каждый возможный набор значений любой пары параметров встречается хотя бы в одном тесте. Она позволяет сократить количество проверок по сравнению с полным перебором, но не гарантирует покрытие сложных зависимостей между тремя и более факторами.

---

## 14. State Transition Testing

**State Transition Testing** — проверка переходов между состояниями системы.

Предположим, заказ имеет состояния:

```text
CREATED
PAID
CANCELLED
REFUNDED
```

Допустимые переходы:

```text
CREATED → PAID
CREATED → CANCELLED
PAID → REFUNDED
```

Недопустимые переходы:

```text
CANCELLED → PAID
REFUNDED → CREATED
```

### Что проверять?

- Каждый разрешённый переход.
- Запрещённые переходы.
- Повтор одного перехода.
- Конкурентные переходы.
- Переход при ошибке зависимости.
- Сохранение истории состояний.

### Пример

```http
POST /api/orders/100/pay
```

Если заказ уже отменён, операция оплаты должна быть отклонена согласно бизнес-правилам.

# Часть 3. Проверки входных данных

## 15. Обязательные и необязательные поля

Допустим:

```json
{
  "userId": "user-100",
  "bonusId": 777,
  "comment": "optional"
}
```

Обязательные:

- userId.
- bonusId.

Необязательное:

- comment.

### Проверяем

- Полное корректное тело.
- Отсутствует userId.
- Отсутствует bonusId.
- Отсутствует comment.
- userId = null.
- bonusId = null.
- comment = null.
- comment = "".

### Важный нюанс

Отсутствующее поле, NULL и пустая строка — разные значения.

API может обрабатывать их по-разному.

Например, при PATCH:

- Отсутствующее поле — не изменять.
- Поле со значением null — очистить.
- Пустая строка — установить пустое значение.

Но конкретная семантика зависит от формата PATCH и контракта.

---

## 16. Проверка типов данных

Предположим:

```json
{
  "bonusId": 777
}
```

Проверяем:

```json
{
  "bonusId": "777"
}
```

```json
{
  "bonusId": true
}
```

```json
{
  "bonusId": 777.5
}
```

```json
{
  "bonusId": null
}
```

```json
{
  "bonusId": []
}
```

```json
{
  "bonusId": {}
}
```

### Что важно?

Проверять не только HTTP-ответ, но и то, не приводит ли невалидное значение к:

- Исключению 500.
- Неожиданному преобразованию типов.
- Неверному поиску сущности.
- Изменению данных.
- Нарушению ограничения БД.

### Senior-нюанс

Разные языки и JSON-библиотеки могут по-разному обрабатывать числовые значения, большие целые числа и неявные преобразования типов.

---

## 17. Проверка строк

Для строкового поля стоит учитывать:

- Пустую строку.
- Строку из пробелов.
- Unicode.
- Эмодзи.
- Кириллицу.
- Специальные символы.
- Переводы строк.
- Очень длинную строку.
- Символы управления.
- Нормализацию Unicode.

### Пример

```json
{
  "name": "Анна"
}
```

И:

```json
{
  "name": "  Анна  "
}
```

Могут вести себя по-разному в зависимости от требований.

### Возможные проблемы

- Некорректное сохранение.
- Неожиданное удаление пробелов.
- Неверная длина.
- Ошибки кодировки.
- Несовпадение данных после чтения.
- Ошибки фильтрации.

---

## 18. Проверка дат и времени

Пример:

```json
{
  "usageStartAt": "2026-10-09T10:00:00Z",
  "usageEndAt": "2026-10-16T10:00:00Z"
}
```

### Проверяем

- Корректные даты.
- Некорректный формат.
- Отсутствие timezone, если он обязателен.
- Разные временные зоны.
- Дата начала равна дате окончания.
- Дата начала позже окончания.
- Дата в прошлом.
- Дата в будущем.
- Границы срока действия.
- Переход суток.
- Летнее/зимнее время в применимых временных зонах.

### Особенно важно для API бонусов

Нужно явно определить семантику границ:

```text
usageStartAt <= now < usageEndAt
```

Или:

```text
usageStartAt <= now <= usageEndAt
```

Это разные правила.

### Практический пример

Бонус заканчивается в:

```text
2026-10-16T10:00:00Z
```

Проверяем:

- За миллисекунду до окончания.
- Ровно в момент окончания.
- Сразу после окончания.

---

# Часть 4. Response Testing

## 19. Что проверять в HTTP Response?

Нужно анализировать не только статус-код.

### Основные проверки

1. HTTP status.
2. Content-Type.
3. Response body.
4. Типы полей.
5. Обязательные поля.
6. Значения.
7. Отсутствие лишних чувствительных данных.
8. Response headers.
9. Побочные эффекты.
10. Время ответа при наличии требований.

### Пример

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/bonuses/issued/500
```

```json
{
  "id": 500,
  "userId": "user-100",
  "bonusId": 777,
  "status": "ISSUED"
}
```

Нужно проверить:

- Создана корректная выдача.
- userId соответствует запросу.
- bonusId соответствует запросу.
- status правильный.
- id уникален.
- Данные действительно сохранены.

---

## 20. Проверка JSON Schema

**JSON Schema** позволяет описывать и валидировать структуру JSON-документа.

Пример:

```json
{
  "type": "object",
  "required": [
    "id",
    "status"
  ],
  "properties": {
    "id": {
      "type": "integer"
    },
    "status": {
      "type": "string",
      "enum": ["ISSUED", "FAILED"]
    }
  },
  "additionalProperties": false
}
```

### Что проверяет схема?

- Тип данных.
- Обязательность полей.
- Допустимые значения.
- Структуру объектов.
- Структуру массивов.
- Ограничения строк и чисел.

### Чего схема не гарантирует?

Не доказывает бизнес-корректность данных.

Например:

```json
{
  "id": 500,
  "status": "ISSUED"
}
```

Может соответствовать схеме, даже если бонус был выдан не тому пользователю.

### Контрактные проверки должны дополняться бизнес-ассерциями.

---

## 21. Проверка ошибок API

Хороший API должен возвращать ошибки в согласованном формате.

Пример:

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
```

```json
{
  "type": "https://example.com/problems/bonus-already-issued",
  "title": "Bonus already issued",
  "status": 409,
  "detail": "The bonus has already been issued to this user"
}
```

Формат `application/problem+json` описан в RFC 9457.

### Что проверять?

- Корректный HTTP-статус.
- Машинно-читаемый код ошибки.
- Понятное описание.
- Отсутствие stack trace.
- Отсутствие секретов.
- Согласованность ошибки с контрактом.
- Стабильность формата между endpoints.

### Важный нюанс

Не все API обязаны использовать RFC 9457.

Это один из стандартных способов описания ошибок.

---

## 22. Проверка статус-кодов

| Статус | Что обычно проверять |
|---|---|
| 200 | Успешное выполнение и корректный результат |
| 201 | Создание ресурса |
| 202 | Принятие асинхронной операции |
| 204 | Успех без тела |
| 400 | Некорректный запрос |
| 401 | Отсутствие или недействительность аутентификации |
| 403 | Запрещённое действие |
| 404 | Ресурс не найден |
| 405 | Метод не разрешён |
| 409 | Конфликт состояния |
| 412 | Не выполнено условие запроса |
| 415 | Неподдерживаемый формат |
| 422 | Семантическая ошибка содержимого |
| 429 | Ограничение частоты |
| 500 | Внутренняя ошибка |
| 502 | Некорректный ответ upstream |
| 503 | Сервис временно недоступен |
| 504 | Таймаут upstream |

### Senior-нюанс

Статус — только одна часть контракта.

Для критичных операций важно дополнительно проверить фактический бизнес-результат.

Например, 500 после POST не гарантирует, что операция не была выполнена.

Сервер мог успешно зафиксировать транзакцию, но столкнуться с ошибкой при формировании ответа.

# Часть 5. Pagination, Filtering и Sorting

## 23. Pagination — постраничная выдача

**Pagination** — разбиение результатов на отдельные страницы или порции.

Основные варианты:

- Offset-based.
- Cursor-based.
- Keyset pagination.

---

## 24. Offset-based Pagination

Пример:

```http
GET /api/orders?limit=20&offset=40
```

Это запрос третьей порции при нумерации с нулевого смещения.

### Пример SQL

```sql
SELECT *
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 40;
```

### Что проверять QA?

- Первая страница.
- Последняя страница.
- Пустая страница.
- limit = 1.
- Максимальный limit.
- limit = 0.
- Отрицательный limit.
- Отрицательный offset.
- Очень большой offset.
- Отсутствие повторов при стабильном наборе данных.
- Детерминированный порядок.

### Важная проблема

Если сортировать только по `created_at`, несколько записей могут иметь одинаковую дату.

Тогда порядок может быть нестабильным.

Поэтому часто добавляют уникальный tie-breaker:

```sql
ORDER BY created_at DESC, id DESC
```

---

## 25. Проблемы Offset Pagination

Offset Pagination может вести себя неожиданно при конкурентных изменениях данных.

### Пример

Первая страница:

```text
A B C
```

Между запросами в начало списка добавили новую запись X.

Вторая страница с OFFSET может вернуть:

```text
C D E
```

Запись C повторилась.

Или при удалении записи некоторые элементы могут быть пропущены.

### Вывод

Offset Pagination удобна, но при изменяющихся данных не всегда обеспечивает стабильную постраничную навигацию.

Это важно для лент, истории транзакций и больших списков.

---

## 26. Cursor-based Pagination

Вместо числового смещения клиент получает курсор.

Пример ответа:

```json
{
  "items": [
    {
      "id": 100,
      "createdAt": "2026-10-09T10:00:00Z"
    }
  ],
  "nextCursor": "opaque-cursor-value"
}
```

Следующий запрос:

```http
GET /api/orders?cursor=opaque-cursor-value&limit=20
```

### Преимущества

- Может быть эффективнее на больших наборах данных.
- Позволяет избежать ряда проблем с OFFSET.
- Подходит для последовательного чтения потоков записей.

### Что проверять QA?

- Получение первой страницы.
- Переход по nextCursor.
- Завершение списка.
- Невалидный курсор.
- Устаревший курсор.
- Изменение фильтров.
- Изменение сортировки.
- Повторное использование курсора.
- Поведение при вставке новых записей.

### Важный нюанс

Cursor Pagination сама по себе не гарантирует полностью стабильный snapshot списка.

Конкретные гарантии определяются реализацией.

---

## 27. Filtering

Фильтрация позволяет получить подмножество данных.

Пример:

```http
GET /api/orders?status=PAID&currency=BYN
```

### Что проверять?

- Один фильтр.
- Несколько фильтров.
- Неизвестное значение.
- Пустое значение.
- NULL-семантику.
- Регистр символов.
- Специальные символы.
- Граничные даты.
- Несуществующие комбинации.
- Корректное пересечение условий.

### Пример бизнес-ошибки

Пользователь запрашивает:

```http
GET /api/orders?status=PAID
```

API возвращает оплаченные заказы и один отменённый.

Схема JSON может быть корректной, статус 200 тоже, но фильтрация нарушена.

---

## 28. Sorting

Пример:

```http
GET /api/orders?sort=createdAt&direction=desc
```

### Что проверять?

- По возрастанию.
- По убыванию.
- Стабильность при одинаковых значениях.
- NULL-значения.
- Сортировку строк.
- Сортировку чисел.
- Сортировку дат.
- Неподдерживаемое поле.
- Неподдерживаемое направление.
- Совместную работу с пагинацией.

### Пример

Числа:

```text
2
10
100
```

Лексикографическая сортировка строк может дать:

```text
10
100
2
```

Поэтому важно убедиться, что API сортирует по правильному типу данных.

---

## 29. Filtering + Sorting + Pagination

Это один из наиболее важных комбинированных сценариев.

Пример:

```http
GET /api/orders?status=PAID&sort=createdAt&direction=desc&limit=20&offset=20
```

### Логическая последовательность

1. Отобрать подходящие данные.
2. Отсортировать результат.
3. Вернуть запрошенную порцию.

Реальный план выполнения SQL может отличаться, но результирующая семантика должна соответствовать контракту.

### Проверки

- Фильтрация применяется ко всему набору.
- Сортировка применяется ко всем подходящим записям.
- Пагинация возвращает нужную часть отсортированного результата.
- Нет неожиданных дубликатов.
- totalCount соответствует контракту.
- При изменении фильтров корректно работает cursor или offset.

### Типичный дефект

Приложение сначала выбирает первые 20 записей, а потом фильтрует их.

В результате пользователь получает 3 записи, хотя в базе существует гораздо больше подходящих.

# Часть 6. Идемпотентность, Retry и Concurrency

## 30. Идемпотентность API

Операция идемпотентна, если повтор одинакового запроса приводит к тому же предполагаемому состоянию сервера, что и один запрос.

По стандартной семантике HTTP:

- GET — идемпотентен.
- PUT — идемпотентен.
- DELETE — идемпотентен.
- POST — не гарантированно идемпотентен.
- PATCH — не гарантированно идемпотентен.

### Важный нюанс

Одинаковое состояние не означает одинаковый HTTP-ответ.

Например:

```http
DELETE /api/orders/100
```

Первый запрос может вернуть 204.

Повторный — 404.

Это не нарушает идемпотентность, если предполагаемый эффект остаётся тем же.

---

## 31. Idempotency Key

Для критичных POST-операций часто используется механизм идемпотентности.

Пример:

```http
POST /api/payments
Idempotency-Key: payment-123
Content-Type: application/json
```

```json
{
  "amount": 100,
  "currency": "BYN"
}
```

### Сценарий

1. Клиент отправил POST.
2. Сервер выполнил платёж.
3. Ответ потерялся из-за сетевой ошибки.
4. Клиент повторил POST с тем же ключом.
5. Сервер распознал повтор и не создал второй платёж.

### Что проверять QA?

- Первый запрос.
- Повтор того же запроса.
- Повтор после таймаута.
- Два параллельных запроса с одинаковым ключом.
- Один ключ с разными параметрами.
- Разные ключи.
- Истечение срока хранения ключа.
- Повтор после сбоя сервера.

### Важный нюанс

Конкретное поведение зависит от API-контракта.

Например, повтор может вернуть сохранённый ответ либо информацию о существующей операции.

Однако нельзя допускать нежелательного повторного бизнес-эффекта в пределах заявленной гарантии.

---

## 32. Почему Timeout не означает, что операция не выполнилась?

Предположим:

```text
Client                     Server
  |                           |
  |------ POST /pay --------->|
  |                           |
  |                      DB COMMIT
  |                           |
  |<----- response lost -------|
  |                           |
  |       Client timeout      |
```

Клиент не получил ответ.

Но платёж мог быть успешно зафиксирован.

### Опасный вариант

Клиент немедленно повторяет POST без механизма идемпотентности.

В результате могут появиться два платежа.

### Как правильно тестировать?

- Искусственно задержать ответ.
- Проверить фактическое состояние операции.
- Повторить запрос.
- Убедиться, что не создаётся второй бизнес-эффект.
- Проверить предусмотренный API способ получения статуса операции.

### Готовый ответ для собеседования

> Timeout означает, что клиент не получил результат в установленное время. Он не доказывает, что сервер не выполнил операцию. Поэтому для изменяющих запросов нужно учитывать идемпотентность и возможность проверки фактического статуса бизнес-операции.

---

## 33. Concurrency Testing

**Concurrency Testing** — проверка корректности системы при одновременном выполнении операций.

Пример:

```http
POST /api/bonuses/issue
```

Одновременно отправляются два запроса на выдачу одного бонуса одному пользователю.

### Что проверять?

- Не возникает ли двойная выдача.
- Не нарушаются ли лимиты.
- Корректно ли работают уникальные ограничения.
- Согласованы ли связанные записи.
- Правильны ли ответы обоих запросов.
- Не остаётся ли система в промежуточном состоянии.

### Важный нюанс

Параллельная отправка запросов не гарантирует, что критические участки действительно выполнялись одновременно.

Для надёжного воспроизведения race condition полезно управлять точкой пересечения операций или использовать подходящую тестовую синхронизацию.

---

## 34. Lost Update через API

Предположим, два клиента читают ресурс:

```json
{
  "id": 100,
  "name": "Anna",
  "city": "Minsk"
}
```

Клиент A меняет имя.

Клиент B меняет город, используя старое представление объекта.

Если оба отправляют полный PUT без контроля версии, изменение A может потеряться.

### Возможное решение

Оптимистическая конкурентность через ETag:

```http
PUT /api/users/100
If-Match: "version-10"
```

Если другой клиент уже изменил ресурс, сервер возвращает:

```http
412 Precondition Failed
```

### Что проверять QA?

- Успешное изменение с актуальной версией.
- Конфликт при устаревшей версии.
- Отсутствие потерянного изменения.
- Повтор после получения новой версии.

# Часть 7. Интеграции и надёжность

## 35. Тестирование API с базой данных

Допустим, endpoint выдаёт бонус.

```http
POST /api/bonuses/issue
```

### Что проверять?

- Корректный HTTP-ответ.
- Создание записи о выдаче.
- Изменение счётчиков.
- Связь с пользователем.
- Корректность временных полей.
- Отсутствие дубликатов.
- Атомарность связанных изменений.

### Ошибка

Если один INSERT успешен, а второй завершился ошибкой, не должно остаться некорректного частичного состояния, если обе операции должны быть атомарными.

### Важный принцип

HTTP 200 или 201 не всегда является достаточным доказательством корректной бизнес-операции.

Для наиболее важных сценариев нужно проверять фактическое состояние системы.

---

## 36. Тестирование API с Kafka

Предположим:

```http
POST /api/orders
```

После создания заказа сервис публикует:

```text
OrderCreated
```

### Проверки

- Заказ создан.
- Событие опубликовано.
- Содержимое события корректно.
- eventId уникален согласно контракту.
- Событие связано с правильным заказом.
- Повтор запроса не создаёт нежелательных дублей.
- Ошибка Kafka обрабатывается корректно.
- После восстановления системы событие не теряется в пределах архитектурных гарантий.

### Что ещё учитывать?

Если используется Transactional Outbox, необходимо проверять согласованность бизнес-записи и outbox-записи.

---

## 37. Асинхронный API и 202 Accepted

Пример:

```http
POST /api/reports
```

Response:

```http
HTTP/1.1 202 Accepted
```

```json
{
  "operationId": "operation-100",
  "status": "PENDING"
}
```

Позже клиент проверяет:

```http
GET /api/operations/operation-100
```

### Что проверять?

- Создание операции.
- Наличие идентификатора.
- Переход PENDING → RUNNING → COMPLETED.
- Переход в FAILED.
- Таймауты.
- Повторные запросы.
- Сохранение статуса после рестарта.
- Отсутствие потери задачи.
- Корректность конечного результата.

### Важно

`202 Accepted` означает принятие запроса к обработке, а не успешное завершение бизнес-операции.

## 38. Тестирование ошибок зависимостей

API может зависеть от:

- PostgreSQL.
- Redis.
- Kafka.
- Другого микросервиса.
- Внешнего платёжного провайдера.

### Типовые сценарии

**Dependency unavailable**

Внешний сервис недоступен.

**Timeout**

Зависимость отвечает слишком долго.

**Invalid response**

Зависимость вернула некорректные данные.

**Partial failure**

Часть операций выполнена, часть — нет.

**Connection reset**

Соединение оборвалось во время выполнения операции.

### Что проверять QA?

- Корректный HTTP-статус.
- Понятную ошибку.
- Отсутствие утечки stack trace.
- Отсутствие нежелательного частичного состояния.
- Поведение retry.
- Идемпотентность.
- Восстановление после возвращения зависимости.
- Логи и метрики.

---

## 39. Retry и Circuit Breaker

### Retry

Повторная попытка при временной ошибке.

Например:

```text
Request
   ↓
Timeout
   ↓
Retry
   ↓
Success
```

### Основные риски

- Повтор неидемпотентной операции.
- Дополнительная нагрузка на уже перегруженную систему.
- Долгие задержки.
- Повторные списания.
- Шторм повторных запросов.

### Circuit Breaker

Механизм, временно ограничивающий обращения к проблемной зависимости.

Типичные состояния:

- Closed.
- Open.
- Half-Open.

### Для QA

Проверять:

- Когда открывается Circuit Breaker.
- Какие ошибки учитываются.
- Когда выполняется пробное восстановление.
- Какой ответ получает клиент.
- Нет ли неконтролируемых повторов.
- Не нарушаются ли бизнес-инварианты.

---

# Часть 8. Безопасность API

## 40. Authentication и Authorization

**Authentication** — проверка личности субъекта.

**Authorization** — проверка его прав.

Для каждого защищённого endpoint нужно проверить:

- Запрос без токена.
- Невалидный токен.
- Истёкший токен.
- Недостаточные права.
- Доступ к чужому ресурсу.
- Недопустимые действия.
- Недопустимые поля.

### Важно

Сервер не должен доверять userId из request body без проверки прав субъекта.

---

## 41. BOLA / IDOR

**Broken Object Level Authorization** — уязвимость, при которой API позволяет получить доступ к чужому объекту из-за отсутствующей или неправильной проверки прав.

### Пример

Пользователь A вызывает:

```http
GET /api/orders/100
```

Затем меняет идентификатор:

```http
GET /api/orders/101
```

Если заказ 101 принадлежит другому пользователю, API должен проверить право доступа.

### Что проверять?

- Чтение чужого объекта.
- Изменение чужого объекта.
- Удаление чужого объекта.
- Обращение по UUID.
- Массовые операции со списком ID.
- Скрытые и неактивные объекты.

**UUID не заменяет проверку авторизации.**

---

## 42. Mass Assignment и Field-Level Authorization

Допустим, API принимает:

```http
PATCH /api/users/100
```

Ожидаемое тело:

```json
{
  "name": "Anna"
}
```

Пользователь добавляет:

```json
{
  "name": "Anna",
  "role": "ADMIN"
}
```

Если backend автоматически копирует поля запроса в модель без проверки, пользователь может изменить запрещённое поле.

### Что проверять?

- Дополнительные поля.
- Поля, доступные только администраторам.
- Поля, управляемые сервером.
- Поля владельца ресурса.
- Статусы операций.
- Финансовые значения.

### Ожидаемый результат

Неавторизованный пользователь не может изменять защищённые атрибуты независимо от того, как сформирован запрос.

---

## 43. Rate Limiting

**Rate Limiting** — ограничение частоты запросов.

Например:

```text
100 requests / minute / client
```

При превышении лимита API может вернуть:

```http
429 Too Many Requests
Retry-After: 60
```

### Что проверять?

- Достижение лимита.
- Запрос сверх лимита.
- Сброс лимита.
- Поведение разных пользователей.
- Поведение разных IP.
- Конкурентные запросы.
- Корректность Retry-After.
- Отсутствие обхода ограничения через доступные параметры.

### Важный нюанс

Лимит не обязательно считается по IP.

Он может быть связан с:

- Пользователем.
- API Key.
- Токеном.
- Endpoint.
- Организацией.
- Комбинацией параметров.

# Часть 9. Автоматизация и уровни тестирования

## 44. Какие уровни тестирования применяются к API?

### Unit Tests

Проверяют отдельные функции и компоненты.

### Component Tests

Проверяют компонент в контролируемом окружении.

### Integration Tests

Проверяют взаимодействие с реальными или подходящими заменёнными зависимостями.

### Contract Tests

Проверяют соблюдение соглашения между поставщиком и потребителем API.

### E2E Tests

Проверяют полный бизнес-сценарий через несколько компонентов.

### Performance Tests

Проверяют производительность под нагрузкой.

### Security Tests

Проверяют различные требования безопасности.

### Важный принцип

Не нужно проверять все сценарии на каждом уровне.

Лучше распределять проверки по рискам, стоимости выполнения и способности теста обнаружить конкретную проблему.

---

## 45. Contract Testing vs Integration Testing

### Contract Testing

Проверяет, соответствует ли взаимодействие согласованному контракту.

Например:

- Endpoint существует.
- Статус соответствует контракту.
- Схема JSON корректна.
- Требуемые поля присутствуют.
- Формат данных не нарушен.

### Integration Testing

Проверяет взаимодействие компонентов и зависимостей.

Например:

- API сохраняет данные в PostgreSQL.
- После операции публикуется событие Kafka.
- Сервис корректно использует внешний API.

### Могут ли эти проверки пересекаться?

Да.

Интеграционный тест может одновременно проверять часть контракта.

Но один тип тестирования не заменяет автоматически другой.

---

## 46. Нужно ли вручную проверять Endpoint, если разработчик уже написал тесты?

**Не всегда.**

Если разработчик реализовал endpoint и покрыл все бизнес-кейсы качественными тестами, QA не обязан дублировать каждый сценарий вручную.

### Что я бы сделал?

1. Изучил требования и риски.
2. Проверил покрытие разработчика.
3. Оценил качество и реалистичность тестового окружения.
4. Выявил непокрытые интеграционные и негативные сценарии.
5. При необходимости выполнил исследовательскую проверку.
6. Добавил проверки на том уровне, где они наиболее полезны.

### Когда дополнительная ручная проверка полезна?

- Изменения затрагивают несколько сервисов.
- Тесты используют моки вместо реальных интеграций.
- Есть сложная конфигурация окружения.
- Не проверены ошибки зависимостей.
- Есть риски конкурентного доступа.
- Не покрыта реальная авторизация.
- Есть подозрения на расхождение спецификации и реализации.

### Краткий ответ для собеседования

> Я не считаю обязательным вручную дублировать все сценарии, уже покрытые качественными тестами. Сначала оцениваю требования, риски и существующее покрытие. Затем добавляю проверки, которые дают дополнительную уверенность: интеграции, конфигурацию, негативные и конкурентные сценарии или исследовательское тестирование.

---

## 47. Что автоматизировать в первую очередь?

Обычно приоритет имеют:

- Критичные бизнес-сценарии.
- Часто выполняемый регресс.
- Стабильные API-контракты.
- Детерминированные проверки.
- Ошибки, способные привести к потере денег или данных.
- Сценарии, которые дорого проверять вручную.

### Что может быть менее приоритетным?

- Редкие малорисковые сценарии.
- Нестабильные требования.
- Проверки с высокой стоимостью поддержки.
- Тесты, полностью дублирующие существующее покрытие без дополнительной ценности.

### Senior-подход

Приоритизация должна учитывать:

```text
Risk × Impact × Likelihood
```

А также:

- Стоимость автоматизации.
- Стоимость поддержки.
- Скорость обратной связи.
- Вероятность обнаружения дефекта.

Это эвристика, а не универсальная математическая формула.

# Часть 10. Практический кейс Senior QA

## 48. Полный план тестирования Endpoint выдачи бонуса

### Условие

Есть API:

```http
POST /api/bonuses/issue
```

Request:

```json
{
  "userId": "user-100",
  "bonusId": 777
}
```

Бизнес-правила:

- Пользователь должен существовать.
- Пользователь должен быть активен.
- Бонус должен существовать.
- Бонус должен быть доступен.
- Один и тот же бонус можно выдать пользователю только один раз.
- Общий лимит выдач бонуса — 1000.
- После выдачи необходимо сохранить запись в БД и опубликовать событие.

### 1. Позитивные сценарии

- Активный пользователь.
- Доступный бонус.
- Бонус ещё не выдавался.
- Лимит не исчерпан.

Проверяем:

- Успешный статус.
- Корректный response.
- Запись в БД.
- Изменение счётчика.
- Публикацию события.

### 2. Валидация

- Отсутствует userId.
- Отсутствует bonusId.
- NULL.
- Неверные типы.
- Некорректный JSON.
- Неизвестные поля.
- Слишком длинные значения.

### 3. Бизнес-ограничения

- Пользователь не существует.
- Пользователь заблокирован.
- Бонус не существует.
- Бонус неактивен.
- Бонус уже выдавался.
- Лимит исчерпан.
- Последняя допустимая выдача.

### 4. Авторизация

- Без токена.
- Невалидный токен.
- Токен другого пользователя.
- Недостаточные права.
- Подмена userId в request body.

### 5. Идемпотентность

- Повтор после успеха.
- Повтор после таймаута.
- Параллельные повторы.
- Повтор с тем же ключом и другими параметрами.
- Проверка количества фактических выдач.

### 6. Конкурентность

- Два одновременных запроса одному пользователю.
- Несколько одновременных запросов на последний бонус.
- Конкурентное изменение лимита.
- Проверка атомарности счётчика.

### 7. Ошибки зависимостей

- PostgreSQL недоступна.
- Kafka недоступна.
- Ошибка после частичного выполнения.
- Сбой между DB COMMIT и публикацией.
- Повтор после восстановления.

### 8. Проверка данных

После каждого критичного сценария проверяем:

- Количество выдач.
- Состояние счётчика.
- Отсутствие дубликатов.
- Корректность связей.
- Наличие события или записи outbox.
- Отсутствие неконсистентного состояния.

### 9. Нагрузочные проверки

- Ожидаемая интенсивность.
- Пиковая интенсивность.
- Конкурентные запросы.
- Время ответа p95/p99.
- Доля ошибок.
- Поведение БД.
- Отставание Consumer при асинхронной обработке.

### 10. Критерии завершения тестирования

- Критичные бизнес-правила покрыты.
- Согласованы ожидаемые ошибки.
- Нет нарушений бизнес-инвариантов.
- Проверена авторизация.
- Проверены ключевые аварийные сценарии.
- Понятны оставшиеся риски.
- Результаты отражены в тестовой документации.

# Часть 11. Вопросы для собеседования

## 49. Что такое REST?

Архитектурный стиль для распределённых систем, основанный на наборе ограничений, включая stateless, uniform interface и cacheable.

## 50. Что такое API Contract?

Соглашение между клиентом и сервером о запросах, ответах, форматах, ошибках и правилах взаимодействия.

## 51. Чем REST отличается от HTTP?

HTTP — протокол, REST — архитектурный стиль. REST часто используют поверх HTTP.

## 52. Что такое CRUD?

Create, Read, Update, Delete — базовые операции с данными.

## 53. Какие основные техники тест-дизайна применяются к API?

Классы эквивалентности, граничные значения, таблицы решений, переходы состояний, pairwise и другие.

## 54. Чем Positive Testing отличается от Negative Testing?

Позитивное проверяет работу с допустимыми данными, негативное — корректность реакции на ошибки, ограничения и недопустимые состояния.

## 55. Что такое Contract Testing?

Проверка соответствия API согласованному контракту.

## 56. Что такое JSON Schema?

Формальное описание допустимой структуры и ограничений JSON-документа.

## 57. Чем Offset Pagination отличается от Cursor Pagination?

Offset использует числовое смещение, cursor — специальную позицию продолжения. Cursor часто удобнее для больших и активно меняющихся наборов данных.

## 58. Что такое Idempotency Key?

Идентификатор логической операции, позволяющий серверу распознавать повторы и предотвращать нежелательное повторное выполнение.

## 59. Почему Timeout не означает ошибку бизнес-операции?

Потому что клиент мог не получить ответ после успешного выполнения операции сервером.

## 60. Что такое BOLA?

Ошибка объектной авторизации, позволяющая получить доступ к чужому ресурсу.

## 61. Как тестировать конкурентные запросы?

Отправлять операции с реальным пересечением выполнения и проверять бизнес-инварианты, состояние БД, ошибки и отсутствие дубликатов.

## 62. Что проверять при 202 Accepted?

Не только сам ответ, но и жизненный цикл асинхронной операции, её конечный статус и результат.

## 63. Нужно ли дублировать тесты разработчика вручную?

Не обязательно. Нужно оценивать риски, качество покрытия и необходимость дополнительных проверок.

# Частые ошибки на собеседовании

**Ошибка:** «REST — это HTTP + JSON».

Правильно: REST — архитектурный стиль. HTTP API с JSON не обязательно полностью соответствует REST.

**Ошибка:** «Если API вернул 200, значит бизнес-операция точно корректна».

Правильно: необходимо проверить фактический результат и связанные данные.

**Ошибка:** «Schema Validation гарантирует отсутствие ошибок в API».

Правильно: схема проверяет структуру, но не всю бизнес-логику.

**Ошибка:** «Негативный тест — это просто проверка 400».

Правильно: нужно проверить отсутствие нежелательных побочных эффектов.

**Ошибка:** «После Timeout сервер ничего не сделал».

Правильно: операция могла успешно завершиться, но ответ не дошёл до клиента.

**Ошибка:** «Повторный POST всегда безопасен».

Правильно: POST не гарантирует идемпотентность.

**Ошибка:** «UUID защищает от доступа к чужим ресурсам».

Правильно: UUID не заменяет объектную авторизацию.

**Ошибка:** «Cursor Pagination всегда гарантирует отсутствие пропусков и дубликатов».

Правильно: гарантии зависят от реализации курсора, сортировки и согласованности данных.

**Ошибка:** «Для Senior QA достаточно проверить статус и JSON».

Правильно: нужны анализ рисков, бизнес-инвариантов, конкурентности, интеграций и отказов.
