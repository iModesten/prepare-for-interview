# HTTP — основы протокола, методы и статус-коды

**Уровень:** Middle / Senior QA Engineer  
**Темы:** HTTP, HTTPS, HTTP Methods, Status Codes, Safe Methods, Idempotency, Request/Response, HTTP Versions

---

## 1. Что такое HTTP?

**HTTP (Hypertext Transfer Protocol)** — протокол прикладного уровня, предназначенный для обмена сообщениями между клиентом и сервером.

HTTP используется для передачи:

- HTML-страниц.
- JSON и XML.
- Изображений.
- Файлов.
- Данных API.
- Других представлений ресурсов.

HTTP работает по модели запрос–ответ (Request–Response).

### Упрощённая схема

```text
Client                       Server
  |                            |
  |-------- HTTP Request ----->|
  |                            |
  |<------- HTTP Response -----|
  |                            |
```

Клиент отправляет запрос, сервер обрабатывает его и возвращает ответ.

### Краткий ответ для собеседования

> HTTP — протокол прикладного уровня для взаимодействия клиента и сервера. Клиент отправляет HTTP-запрос, содержащий метод, адрес ресурса, заголовки и при необходимости тело. Сервер возвращает ответ со статус-кодом, заголовками и необязательным телом. HTTP по своей природе stateless, а сохранение пользовательского состояния реализуется дополнительными механизмами, например сессиями и cookies.

---

## 2. Что означает Stateless?

**Stateless** означает, что каждый HTTP-запрос имеет самостоятельную семантику и для его понимания сервер не обязан полагаться на историю предыдущих запросов на уровне самого протокола.

Например:

```text
GET /profile
GET /orders
GET /bonuses
```

HTTP сам по себе не определяет, что эти запросы принадлежат одному авторизованному пользователю.

Для идентификации пользователя применяют дополнительные механизмы:

- Cookies.
- Session ID.
- Authorization header.
- Access Token.
- JWT.

### Важный нюанс

Stateless не означает, что сервер не может хранить состояние.

Сервер может сохранять:

- Сессии.
- Корзины пользователей.
- Данные авторизации.
- Историю запросов.
- Состояние бизнес-операций.

Просто эти механизмы находятся поверх HTTP.

### Типичный вопрос

**Как HTTP может быть stateless, если сайт запоминает авторизацию пользователя?**

> HTTP сам по себе не хранит пользовательскую сессию. Приложение использует cookies, токены или идентификаторы сессий, передаваемые в запросах, чтобы связать их с состоянием пользователя.

## 3. Структура HTTP Request

HTTP-запрос состоит из:

1. Request Line — в HTTP/1.1.
2. Headers.
3. Необязательного тела (Body).

Пример HTTP/1.1:

```http
POST /api/bonuses/issue HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJ...
Content-Type: application/json
Accept: application/json

{
  "userId": "user-123",
  "bonusId": 777
}
```

### Request Line

```http
POST /api/bonuses/issue HTTP/1.1
```

Содержит:

- HTTP Method — `POST`.
- Request Target — `/api/bonuses/issue`.
- Protocol Version — `HTTP/1.1`.

### Headers

Передают метаданные запроса.

Например:

```http
Content-Type: application/json
Accept: application/json
Authorization: Bearer token
```

### Body

Необязательное тело запроса.

Может содержать:

- JSON.
- XML.
- Form Data.
- Файл.
- Двоичные данные.

**Важно:** приведённая текстовая структура относится к HTTP/1.1. В HTTP/2 и HTTP/3 сообщения кодируются иначе, хотя общая семантика методов, заголовков и статус-кодов сохраняется.

---

## 4. Структура HTTP Response

HTTP-ответ содержит:

1. Status Line — в HTTP/1.1.
2. Headers.
3. Необязательное тело.

Пример:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/bonuses/issued/1001
Cache-Control: no-store

{
  "id": 1001,
  "status": "ISSUED"
}
```

### Status Line

```http
HTTP/1.1 201 Created
```

Содержит:

- Версию протокола.
- Статус-код.
- Текстовое описание — в HTTP/1.1.

### Response Headers

Например:

- Content-Type.
- Content-Length.
- Cache-Control.
- Location.
- Set-Cookie.
- ETag.

### Response Body

Содержит данные, ошибку или другое представление результата.

Не каждый HTTP-ответ должен иметь тело. Например, `204 No Content` запрещает содержимое ответа.

## 5. HTTP и HTTPS

### HTTP

Обычный HTTP не обеспечивает шифрование передаваемых данных на уровне протокола.

Если соединение не защищено другими средствами, данные могут быть доступны для перехвата или изменения на сетевом пути.

### HTTPS

**HTTPS — HTTP поверх TLS.**

TLS обеспечивает:

- Шифрование передаваемых данных.
- Контроль целостности соединения.
- Аутентификацию сервера через сертификат при корректной проверке.

### Типичные порты

| Протокол | Порт по умолчанию |
|---|---|
| HTTP | 80 |
| HTTPS | 443 |

Порты могут быть изменены настройками.

### Что происходит при HTTPS-соединении?

Упрощённо:

1. Клиент определяет адрес сервера.
2. Устанавливается транспортное соединение.
3. Выполняется TLS handshake.
4. Проверяется сертификат сервера.
5. Согласовываются криптографические параметры.
6. Передаются зашифрованные HTTP-сообщения.

Для HTTP/3 используется QUIC, который включает механизмы TLS 1.3 и работает поверх UDP.

### Важный вопрос

**Защищает ли HTTPS URL полностью?**

HTTPS шифрует HTTP-путь, query-параметры, заголовки и тело при передаче между TLS-участниками.

Однако доменное имя может быть доступно наблюдателю через DNS, SNI или сетевые метаданные в зависимости от используемых механизмов защиты.

Кроме того, URL может сохраняться:

- В истории браузера.
- В логах приложения.
- В логах прокси после TLS-терминации.
- В аналитических системах.

Поэтому пароли и токены не следует помещать в URL.

## 6. Основные HTTP-методы

HTTP Method описывает предполагаемую семантику операции над ресурсом.

### GET

Получение представления ресурса.

```http
GET /api/users/123
```

Обычно используется для чтения данных.

По стандарту GET является безопасным методом: клиент не запрашивает изменения состояния.

### POST

Передача данных для обработки согласно логике ресурса.

```http
POST /api/orders
Content-Type: application/json

{
  "productId": 10,
  "quantity": 2
}
```

Часто используется для создания сущностей или запуска бизнес-операций.

### PUT

Создание или полная замена состояния ресурса по известному URI.

```http
PUT /api/users/123
Content-Type: application/json

{
  "name": "Anna",
  "city": "Minsk"
}
```

В типичной REST-модели PUT предназначен для замены представления ресурса.

### PATCH

Частичное изменение ресурса.

```http
PATCH /api/users/123
Content-Type: application/merge-patch+json

{
  "city": "Warsaw"
}
```

Семантика изменений зависит от формата PATCH и API-контракта.

### DELETE

Удаление связи ресурса с его текущим представлением согласно семантике сервера.

```http
DELETE /api/users/123
```

Удаление может быть физическим или логическим — это определяется реализацией.

### HEAD

Похож на GET, но сервер не отправляет содержимое ответа.

Используется для получения метаданных ресурса.

### OPTIONS

Позволяет получить информацию о возможностях взаимодействия с ресурсом.

В браузерах особенно важен для CORS preflight.

### Сравнительная таблица

| Метод | Типичное назначение | Safe | Idempotent |
|---|---|---|---|
| GET | Получение ресурса | Да | Да |
| HEAD | Получение заголовков | Да | Да |
| OPTIONS | Возможности взаимодействия | Да | Да |
| POST | Обработка или создание | Нет | Не гарантировано |
| PUT | Создание или замена | Нет | Да |
| PATCH | Частичное изменение | Нет | Не гарантировано |
| DELETE | Удаление | Нет | Да |

Это свойства стандартной семантики методов, а не гарантия того, что конкретное приложение реализовано правильно.

## 7. Safe Methods

**Safe Method** — метод, семантика которого не предполагает запрошенного клиентом изменения состояния сервера.

Основные безопасные методы:

- GET.
- HEAD.
- OPTIONS.
- TRACE.

### Пример

```http
GET /api/orders/101
```

Ожидается получение заказа, а не его изменение.

### Важный нюанс

Safe не означает полное отсутствие побочных эффектов.

Сервер может:

- Записать запрос в лог.
- Обновить метрики.
- Изменить технический счётчик.

Но клиент не запрашивает бизнес-изменение ресурса.

### Ошибка проектирования

```http
GET /api/accounts/1/withdraw?amount=100
```

Если такой GET действительно списывает деньги, API нарушает семантику безопасного метода.

Браузеры, поисковые роботы и прокси могут выполнять автоматические GET-запросы, поэтому опасно использовать GET для операций с изменением бизнес-состояния.

## 8. Идемпотентность HTTP-методов

**Idempotency** — свойство операции, при котором многократное выполнение одного и того же запроса оказывает такой же предполагаемый эффект на состояние сервера, как однократное выполнение.

Математически:

```text
f(f(x)) = f(x)
```

### GET

Повторный запрос не должен сам по себе менять бизнес-состояние.

```http
GET /api/users/123
```

Ответ может измениться, если данные изменил другой процесс, но метод остаётся идемпотентным по своей семантике.

### PUT

```http
PUT /api/users/123

{
  "name": "Anna"
}
```

Повторение одного и того же PUT должно приводить к одинаковому предполагаемому состоянию ресурса.

### DELETE

```http
DELETE /api/users/123
```

Первый запрос удалил ресурс.

Второй запрос может вернуть `404 Not Found`.

Однако метод остаётся идемпотентным, поскольку ресурс уже отсутствует.

**Важно:** идемпотентность не означает одинаковый HTTP-статус при каждом повторе.

### POST

```http
POST /api/orders

{
  "productId": 10
}
```

Первый запрос может создать заказ 101.

Повторный — заказ 102.

Поэтому POST не является идемпотентным по стандартной семантике.

### Может ли POST быть идемпотентным?

Да, на уровне конкретной бизнес-операции.

Например:

```http
POST /api/payments
Idempotency-Key: payment-123
```

Сервер может сохранять результат операции и предотвращать повторное списание.

### PATCH

PATCH не гарантированно идемпотентен.

Например:

```json
{
  "operation": "increment",
  "value": 1
}
```

Повторное применение увеличит значение ещё раз.

Но PATCH, который устанавливает фиксированное значение, может быть идемпотентным по своей конкретной семантике.

## 9. Почему для логина обычно используют POST, а не GET?

Это вопрос, который уже встретился на скрининге.

Рассмотрим два варианта.

### Нежелательный вариант: GET

```http
GET /login?username=anna&password=secret
```

Проблемы:

1. Логин и пароль оказываются в URL.
2. URL может попасть в историю браузера.
3. URL может записываться в access logs и аналитические системы.
4. URL может случайно копироваться или передаваться.
5. GET предназначен для получения ресурса, а логин обычно создаёт авторизованную сессию или выдаёт токен.
6. GET-запросы могут автоматически повторяться, кэшироваться или выполняться механизмами предварительной загрузки.

### Предпочтительный вариант: POST

```http
POST /login
Content-Type: application/json

{
  "username": "anna",
  "password": "secret"
}
```

Здесь учётные данные находятся в теле запроса, а не в URL.

POST соответствует семантике обработки данных для создания сессии или выдачи токена.

### Но является ли POST безопасным сам по себе?

Нет.

Тело POST не шифруется только потому, что используется POST.

Для защиты передаваемых учётных данных нужен HTTPS.

Также необходимо учитывать:

- Защиту от перебора паролей.
- Безопасное логирование.
- Защиту токенов и cookies.
- CSRF при cookie-based аутентификации.
- Защиту от перехвата и повторного использования учётных данных.

### Готовый ответ для собеседования

> Для логина обычно используют POST, потому что операция обрабатывает учётные данные и часто создаёт сессию или токен, то есть не является обычным чтением ресурса. Кроме того, при GET параметры обычно передаются в URL и могут попасть в историю браузера, логи и другие системы. POST позволяет передавать данные в теле запроса. Но это не замена HTTPS: для защиты логина и пароля необходимо шифрованное соединение.

## 10. Основные группы HTTP Status Codes

HTTP-статусы разделены на пять классов.

| Диапазон | Значение |
|---|---|
| 1xx | Информационные |
| 2xx | Успешное выполнение |
| 3xx | Перенаправление и работа с представлениями |
| 4xx | Ошибка, связанная с клиентским запросом |
| 5xx | Ошибка сервера при выполнении запроса |

### 1xx — Informational

**100 Continue**

Сервер сообщает, что клиент может продолжить отправку содержимого запроса.

**101 Switching Protocols**

Согласованный переход на другой протокол, например при WebSocket Upgrade через HTTP/1.1.

**103 Early Hints**

Позволяет отправить предварительные подсказки, например для загрузки ресурсов.

## 11. Статусы 2xx — Success

### 200 OK

Запрос успешно выполнен.

Пример:

```http
GET /api/users/123

HTTP/1.1 200 OK
```

Часто используется для успешного GET, PUT, PATCH или POST, когда возвращается представление результата.

### 201 Created

Новый ресурс успешно создан.

```http
POST /api/orders

HTTP/1.1 201 Created
Location: /api/orders/101
```

### 202 Accepted

Запрос принят к обработке, но работа ещё не завершена.

Например:

```http
POST /api/reports

HTTP/1.1 202 Accepted
```

Полезно для асинхронных операций.

**Важно:** 202 не означает, что операция обязательно завершится успешно.

### 204 No Content

Запрос успешно выполнен, но содержимое ответа отсутствует.

Часто используется для DELETE или UPDATE без возвращаемого тела.

---

## 12. Статусы 3xx — Redirection

### 301 Moved Permanently

Постоянное перенаправление ресурса.

### 302 Found

Временное перенаправление. Исторически некоторые клиенты могут менять POST на GET при следовании такому redirect.

### 303 See Other

Указывает клиенту перейти к другому ресурсу с GET (или HEAD).

Часто используется после обработки POST.

### 304 Not Modified

Сообщает, что клиент может использовать подходящее кэшированное представление ресурса.

### 307 Temporary Redirect

Временное перенаправление с сохранением метода запроса.

### 308 Permanent Redirect

Постоянное перенаправление с сохранением метода запроса.

### Важное отличие

- 301/302 имеют исторические особенности изменения POST на GET.
- 307/308 требуют сохранения исходного метода при перенаправлении.

---

## 13. Статусы 4xx — Client Errors

### 400 Bad Request

Сервер не может или не хочет обрабатывать запрос из-за проблемы с самим запросом.

Например, некорректный синтаксис.

### 401 Unauthorized

Для доступа требуется корректная аутентификация.

Несмотря на название, статус относится прежде всего к отсутствию или недействительности учётных данных.

Для HTTP authentication challenge используется заголовок `WWW-Authenticate`.

### 403 Forbidden

Сервер понимает запрос, но отказывается его выполнять.

Например, пользователь аутентифицирован, но не имеет необходимых прав.

### 404 Not Found

Ресурс не найден или сервер не хочет раскрывать его существование.

### 405 Method Not Allowed

Метод известен серверу, но не разрешён для указанного ресурса.

Сервер должен передать заголовок `Allow` с допустимыми методами.

### 408 Request Timeout

Сервер не получил полный запрос за отведённое время.

### 409 Conflict

Запрос конфликтует с текущим состоянием ресурса.

Примеры:

- Конфликт версий.
- Попытка создать сущность с уже существующим уникальным бизнес-идентификатором.
- Конфликт состояния операции.

Точный выбор между 409 и другими 4xx определяется контрактом.

### 412 Precondition Failed

Условия предварительной проверки не выполнены.

Например, значение `If-Match` не совпало с текущим ETag.

### 413 Content Too Large

Размер содержимого запроса превышает допустимый лимит.

### 415 Unsupported Media Type

Сервер не поддерживает формат содержимого запроса.

Например, API ожидает JSON, а клиент отправляет неподдерживаемый тип данных.

### 422 Unprocessable Content

Сервер понимает тип и синтаксис содержимого, но не может выполнить инструкции из-за семантической ошибки.

Например, дата начала позже даты окончания.

### 429 Too Many Requests

Клиент отправил слишком много запросов за определённый период.

Часто применяется при rate limiting.

Может сопровождаться заголовком `Retry-After`.

---

## 14. Статусы 5xx — Server Errors

### 500 Internal Server Error

Общая внутренняя ошибка сервера.

### 501 Not Implemented

Сервер не поддерживает функциональность, необходимую для выполнения запроса.

Например, не распознаёт или не реализует HTTP-метод.

### 502 Bad Gateway

Сервер, действующий как шлюз или прокси, получил некорректный ответ от upstream-сервера.

### 503 Service Unavailable

Сервис временно не может обработать запрос.

Например, из-за перегрузки или технического обслуживания.

Может сопровождаться `Retry-After`.

### 504 Gateway Timeout

Шлюз или прокси не получил своевременный ответ от upstream-сервера.

### Частый вопрос: 502 vs 504

**502:** промежуточный сервер получил непригодный ответ от зависимости.

**504:** промежуточный сервер не дождался ответа в установленный срок.

## 15. Частые сравнения HTTP-статусов

### 200 vs 201 vs 202 vs 204

| Статус | Когда применяется |
|---|---|
| 200 | Операция выполнена, возвращается подходящий результат |
| 201 | Создан новый ресурс |
| 202 | Запрос принят, обработка ещё не завершена |
| 204 | Успех без тела ответа |

### 400 vs 422

400 — проблема с запросом, например синтаксическая.

422 — корректно сформированное содержимое имеет семантическую ошибку.

На практике многие API используют 400 для различных ошибок валидации. Важны согласованность и контракт API.

### 401 vs 403

401 — требуется аутентификация или предоставленные учётные данные не приняты.

403 — сервер отказывает в выполнении запроса, например из-за недостаточных прав.

### 404 vs 403

Иногда приложение намеренно возвращает 404 вместо 403, чтобы не раскрывать существование ресурса.

Например, для чужих приватных объектов.

### 409 vs 422

409 чаще используется для конфликта с текущим состоянием ресурса.

422 — для семантической ошибки содержимого запроса.

В конкретном API границы могут зависеть от принятых соглашений.

## 16. Content-Type и Accept

### Content-Type

Описывает формат содержимого сообщения.

Пример:

```http
Content-Type: application/json
```

Означает, что тело содержит JSON.

### Accept

Описывает форматы представления, которые клиент готов принять.

```http
Accept: application/json
```

### Пример

```http
POST /api/orders
Content-Type: application/json
Accept: application/json

{
  "productId": 100
}
```

Клиент сообщает:

- Отправляю JSON.
- Хочу получить JSON.

### Возможные ошибки

**415 Unsupported Media Type**

Неподдерживаемый формат входного содержимого.

**406 Not Acceptable**

Сервер не может предоставить подходящее представление согласно условиям Accept и выбранной стратегии согласования содержимого.

---

## 17. Query Parameters, Path Parameters и Request Body

### Path Parameters

Идентифицируют ресурс или его часть.

```http
GET /api/users/123
```

Здесь `123` — идентификатор пользователя.

### Query Parameters

Передают параметры запроса, часто используемые для фильтрации, сортировки и пагинации.

```http
GET /api/orders?status=PAID&page=2&limit=20
```

### Request Body

Содержит представление или параметры операции.

```http
POST /api/orders
Content-Type: application/json

{
  "productId": 10,
  "quantity": 2
}
```

### Важный нюанс

Размещение значения в path, query или body определяется семантикой и контрактом API.

Например, фильтрация через POST тоже встречается, когда критерии сложные или API имеет специальный контракт. Однако следует учитывать семантику метода и последствия для кэширования и повторов.

## 18. Кэширование HTTP

HTTP поддерживает механизмы кэширования ответов.

Основные цели:

- Уменьшить количество запросов к серверу.
- Уменьшить задержку.
- Снизить нагрузку.
- Повторно использовать ранее полученные представления.

### Cache-Control

Примеры:

```http
Cache-Control: max-age=300
```

Представление можно считать свежим в течение 300 секунд в соответствующем кэше.

```http
Cache-Control: no-cache
```

Не означает «запрещено хранить». Обычно требует валидации перед повторным использованием.

```http
Cache-Control: no-store
```

Предписывает не сохранять ответ в кэше.

```http
Cache-Control: private
```

Ограничивает использование ответа частными кэшами, например браузерным, но не общими кэшами.

### ETag

ETag — идентификатор версии представления ресурса.

Пример:

```http
ETag: "version-10"
```

Клиент может отправить:

```http
If-None-Match: "version-10"
```

Если представление не изменилось, сервер может вернуть:

```http
304 Not Modified
```

### Для QA

Проверяем:

- Обновление данных после изменения.
- Корректную валидацию кэша.
- Отсутствие кэширования чувствительных данных там, где оно запрещено.
- Поведение после смены пользователя.
- Работу ETag и условных запросов.

## 19. HTTP/1.1, HTTP/2 и HTTP/3

### HTTP/1.1

Использует текстовое представление HTTP-сообщений на уровне соединения.

Особенности:

- Persistent connections.
- Последовательность запросов и ответов в рамках соединений.
- Поддержка chunked transfer encoding.
- Ограничения параллельной передачи в рамках одного соединения.

### HTTP/2

Использует бинарное фреймирование.

Основные преимущества:

- Multiplexing нескольких потоков через одно соединение.
- Сжатие заголовков HPACK.
- Более эффективное использование соединения во многих сценариях.

HTTP/2 обычно работает поверх TCP, часто с TLS.

### HTTP/3

Использует QUIC поверх UDP.

Основные особенности:

- Мультиплексирование потоков QUIC.
- TLS 1.3.
- Уменьшение влияния потери пакетов одного потока на другие потоки на транспортном уровне.
- Поддержка миграции соединений в рамках возможностей QUIC.

### Важно для интервью

Различия HTTP/1.1, HTTP/2 и HTTP/3 в основном относятся к способу передачи сообщений и работе соединений.

Семантика GET, POST, PUT, DELETE и основных статус-кодов сохраняется.

## 20. Что происходит, когда пользователь открывает страницу?

Это один из классических вопросов о клиент-серверной архитектуре.

Упрощённая последовательность:

1. Пользователь вводит URL.
2. Браузер определяет схему и адрес.
3. Проверяет доступные кэши и другие механизмы оптимизации.
4. При необходимости выполняет DNS-разрешение.
5. Устанавливает соединение с сервером.
6. Для HTTPS выполняет TLS-handshake или соответствующее защищённое установление соединения QUIC.
7. Отправляет HTTP-запрос.
8. Сервер или промежуточная инфраструктура обрабатывает запрос.
9. Браузер получает HTTP-ответ.
10. Начинает разбор HTML.
11. Загружает необходимые CSS, JavaScript, изображения и другие ресурсы.
12. Формирует DOM и CSSOM.
13. Вычисляет стили, layout и выполняет rendering.
14. Выполняет JavaScript и последующие API-запросы по необходимости.

### Что может находиться между клиентом и приложением?

```text
Browser
   |
   v
DNS
   |
   v
CDN / Reverse Proxy / Load Balancer
   |
   v
Backend
   |
   v
Database / Cache / Other Services
```

Это упрощённая схема: реальные маршруты могут быть другими, а CDN может отдать ответ без обращения к Backend.

### Что важно QA?

Понимать, где могла возникнуть проблема:

- DNS.
- TLS.
- Прокси.
- CDN.
- Авторизация.
- Backend.
- БД.
- Кэш.
- Клиентский JavaScript.
- CORS.

## 21. Как тестировать HTTP API?

### Проверки методов

- [ ] GET не изменяет запрошенное бизнес-состояние.
- [ ] POST создаёт или обрабатывает операцию согласно контракту.
- [ ] PUT выполняет предусмотренную замену ресурса.
- [ ] PATCH корректно применяет частичные изменения.
- [ ] DELETE правильно удаляет или деактивирует ресурс.
- [ ] Недопустимый метод возвращает ожидаемую ошибку.

### Проверки ответов

- [ ] Корректный статус-код.
- [ ] Правильное тело ответа.
- [ ] Корректный Content-Type.
- [ ] Правильная схема JSON.
- [ ] Корректное сообщение об ошибке.
- [ ] Нет утечки чувствительных данных.

### Проверки безопасности

- [ ] HTTPS используется для чувствительных операций.
- [ ] Неавторизованный доступ запрещён.
- [ ] Не раскрываются чужие данные.
- [ ] Токены и пароли не передаются в URL.
- [ ] Нет небезопасного кэширования чувствительных ответов.

### Проверки идемпотентности

- [ ] Повторный PUT приводит к ожидаемому состоянию.
- [ ] Повторный DELETE не создаёт нежелательных побочных эффектов.
- [ ] Повторный POST корректно обрабатывается согласно контракту.
- [ ] Таймаут не приводит к неконтролируемому повторению бизнес-операции.

### Проверки ошибок

- [ ] Некорректный JSON.
- [ ] Отсутствующие обязательные поля.
- [ ] Неподдерживаемый Content-Type.
- [ ] Несуществующий ресурс.
- [ ] Конфликт бизнес-состояния.
- [ ] Ошибка зависимости.
- [ ] Таймаут.
- [ ] Rate limiting.

## 22. Типичные вопросы на собеседовании

### 1. Что такое HTTP?

Протокол прикладного уровня для обмена запросами и ответами между клиентом и сервером.

### 2. Что означает Stateless?

HTTP сам по себе не управляет пользовательской сессией между запросами. Состояние можно реализовать дополнительными механизмами.

### 3. Чем HTTP отличается от HTTPS?

HTTPS использует TLS для защиты соединения, обеспечивая шифрование, целостность и проверку сервера.

### 4. Что входит в HTTP-запрос?

Метод, адрес ресурса, заголовки и необязательное тело.

### 5. Что входит в HTTP-ответ?

Статус-код, заголовки и необязательное тело.

### 6. Чем GET отличается от POST?

GET предназначен для получения представления ресурса и является безопасным методом. POST передаёт данные для обработки и не является безопасным или гарантированно идемпотентным.

### 7. Чем PUT отличается от PATCH?

PUT предназначен для полной замены состояния ресурса, PATCH — для частичного изменения.

### 8. Чем PUT отличается от POST?

PUT работает с известным целевым URI и обладает идемпотентной семантикой. POST передаёт данные ресурсу для обработки по его правилам и не гарантирует идемпотентность.

### 9. Что такое идемпотентность?

Свойство, при котором повторение одинакового запроса оказывает тот же предполагаемый эффект, что и один запрос.

### 10. Какие HTTP-методы идемпотентны?

GET, HEAD, OPTIONS, TRACE, PUT и DELETE по стандартной семантике.

POST и PATCH не гарантированно идемпотентны.

### 11. Почему DELETE идемпотентен?

Повторное удаление оставляет ресурс в том же предполагаемом состоянии — удалённым.

HTTP-статусы первого и повторного запросов при этом могут различаться.

### 12. Почему для логина используют POST?

Поскольку логин обрабатывает учётные данные и обычно создаёт сессию или токен. POST позволяет передавать данные в теле, а не в URL. Для защиты данных всё равно необходим HTTPS.

### 13. Чем 401 отличается от 403?

401 связан с отсутствием или недействительностью аутентификации. 403 означает отказ сервера выполнять запрос, например из-за недостаточных прав.

### 14. Чем 400 отличается от 422?

400 — некорректный запрос. 422 — синтаксически корректное содержимое с семантической ошибкой.

### 15. Чем 502 отличается от 504?

502 — шлюз получил непригодный ответ от upstream. 504 — шлюз не дождался ответа вовремя.

### 16. Чем 200 отличается от 201?

200 — успешное выполнение, 201 — успешное создание нового ресурса.

### 17. Что означает 202?

Запрос принят к обработке, но выполнение ещё не завершено.

### 18. Что означает 304?

Представление не изменилось для рассматриваемого условного запроса, поэтому можно использовать подходящее кэшированное представление.

### 19. Что такое Content-Type?

Заголовок, описывающий формат содержимого сообщения.

### 20. Что такое Accept?

Заголовок, описывающий форматы представления, которые клиент готов принять.

### 21. Что такое ETag?

Идентификатор версии представления, используемый в условных запросах и кэшировании.

### 22. Что такое CORS?

Механизм, позволяющий серверу через HTTP-заголовки сообщать браузеру, каким другим origin разрешён доступ к ответу.

### 23. Что такое Origin?

Комбинация схемы, хоста и порта, определяющая источник веб-контекста.

### 24. Чем HTTP/2 отличается от HTTP/1.1?

HTTP/2 использует бинарное фреймирование и multiplexing нескольких потоков на одном соединении.

### 25. Чем HTTP/3 отличается от HTTP/2?

HTTP/3 использует QUIC поверх UDP, а HTTP/2 обычно использует TCP.

## 23. Частые ошибки на собеседовании

**Ошибка:** «GET вообще ничего не меняет на сервере».

Правильно: безопасная семантика GET запрещает запрашиваемое клиентом изменение состояния, но технические побочные эффекты, например логи, возможны.

**Ошибка:** «POST безопаснее GET, потому что тело всегда зашифровано».

Правильно: шифрование обеспечивает HTTPS, а не HTTP-метод.

**Ошибка:** «Идемпотентный запрос всегда возвращает одинаковый ответ».

Правильно: идемпотентность относится к предполагаемому эффекту на сервер, а не к идентичности ответа.

**Ошибка:** «DELETE не может вернуть 404, иначе он не идемпотентен».

Правильно: повторный DELETE может вернуть 404, оставаясь идемпотентным.

**Ошибка:** «401 означает отсутствие прав, а 403 — отсутствие авторизации».

Правильно: 401 относится к аутентификации, 403 — к отказу выполнять запрос.

**Ошибка:** «202 означает успешное завершение операции».

Правильно: 202 означает принятие к обработке, которая ещё может завершиться ошибкой.

**Ошибка:** «HTTP/2 — это просто HTTP/1.1 с более быстрыми серверами».

Правильно: HTTP/2 меняет способ передачи сообщений, включая мультиплексирование и бинарные фреймы.
