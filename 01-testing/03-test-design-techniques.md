## 1. Классы эквивалентности

**Equivalence Partitioning** — делим множество входов на группы, для которых ожидаем одинаковое поведение. Из группы выбираем представителей.

**Требование:** `count` в API выдачи бонусов должен быть **целым числом от 1 до 10 включительно**.

| Класс | Примеры | Ожидание |
|---|---|---|
| Валидный | 1, 5, 10 | Успешная обработка, если остальные условия выполнены |
| Меньше минимума | 0, -1 | Ошибка валидации |
| Больше максимума | 11, 100 | Ошибка валидации |
| Нецелый тип | 1.5 | Ошибка валидации |
| Строка вместо числа | `"5"` | По контракту: отказ или явно разрешённое преобразование |
| `null` / отсутствует | `null`, нет поля | Зависит от обязательности поля в контракте |

**Нюанс:** классы нужно выбирать исходя из требований. Если число 0 означает «не выдавать бонусы», это отдельный **валидный** класс — пока команда не уточнит контракт, нельзя объявлять его багом.

## 2. Граничные значения

**Boundary Value Analysis** — ошибки часто возникают около границы диапазона.

При правиле `1 <= count <= 10`:

```text
... -1, 0 | 1, 2, ... 9, 10 | 11, 12 ...
            min            max
```

Проверяем: **0, 1, 2, 9, 10, 11** (для трёхточечной проверки каждой границы); можно начать с 0, 1, 10, 11 при ограниченном времени.

**Что обнаружим:** ошибочное сравнение `< 10` вместо `<= 10`, неверную валидацию минимума и обработку отсутствующего значения.

**Ещё пример:** бонус доступен с `2026-10-14T10:00:00Z` до `2026-10-15T10:00:00Z`. Проверяем секунду до начала, точное начало, секунду до конца, точный конец и момент после. Обязательно уточняем, включена ли граница конца, часовой пояс и точность времени.

## 3. Таблица решений

**Decision Table** полезна, когда результат зависит от сочетания нескольких условий.

**Требование:** бонус выдаётся, если пользователь активен, бонус доступен и не достигнут лимит.

| Пользователь активен? | Бонус доступен? | Лимит не исчерпан? | Результат |
|---|---|---|---|
| Да | Да | Да | Выдать |
| Нет | Да | Да | Отказать |
| Да | Нет | Да | Отказать |
| Да | Да | Нет | Отказать |
| Нет | Нет | Нет | Отказать |

Полная таблица из трёх бинарных условий содержит **8 сочетаний**. Здесь показаны характерные правила, но для полного покрытия всех комбинаций следует дополнить остальные три строки. Если разные причины отказа возвращают разные коды — их нужно зафиксировать отдельно.

**Что уточнить:** если одновременно недоступен бонус и исчерпан лимит, какой статус и текст ошибки ожидаются? Приоритет ошибок — часть контракта.

## 4. Переходы состояний

**State Transition Testing** применяется, когда действие допустимо только в определённом состоянии.

Например, бонус может быть:

```text
AVAILABLE --issue--> ISSUED --use--> USED
    |                  |
    | expire           | expire
    v                  v
  EXPIRED            EXPIRED
```

Это **учебная модель**: в реальном продукте нужно согласовать, что означает истечение уже выданного бонуса и допустим ли такой переход.

Проверяем не только разрешённые переходы:
- Из `AVAILABLE` в `ISSUED` после выдачи.
- Из `ISSUED` в `USED` после применения.
- Попытка повторной выдачи из `ISSUED` — не создавать дубль.
- Попытка использования из `EXPIRED` — отказ.
- Одновременные запросы на выдачу — соблюдается правило единственности.

**Сила техники:** легко найти баги в запрещённых переходах, которые не видны при проверке только успешного сценария.

## 5. Pairwise

**Pairwise / All-pairs** — выбираем небольшой набор комбинаций, чтобы каждую **пару** значений параметров проверить хотя бы один раз.

Пример параметров WebView:
- iOS / Android.
- Авторизован / не авторизован.
- Русский / английский язык.
- Wi-Fi / мобильная сеть.

Полный перебор: `2 × 2 × 2 × 2 = 16` сочетаний. Pairwise позволяет выбрать меньше случаев, но точное число зависит от ограничений и выбранного алгоритма.

**Когда не подходит:** если ошибка зависит от сочетания трёх или четырёх факторов, попарное покрытие её может не обнаружить. Критичные сценарии нужно добавить отдельно.

## 6. Error Guessing и исследование рисков

**Error Guessing** — опытная гипотеза о местах ошибок. Не подмена требованиям и другим техникам.

Примеры:
- Два POST одновременно приводят к двойной выдаче.
- Повторный запрос после timeout создаёт дубль.
- Истёк JWT между шагами сценария.
- Время истечения бонуса неверно трактуется из-за часового пояса.
- В запросе `bonusId` из другого проекта.
- Сервис Kafka временно недоступен после коммита в БД.

**Exploratory Testing** — одновременное изучение продукта, проектирование проверок и их выполнение. Подробнее: [исследовательское тестирование](06-exploratory-and-risk-based-testing.md).

## 7. Как выбрать технику

| Ситуация | Подход |
|---|---|
| Ограничение диапазона или длины | Классы + границы |
| Много бизнес-условий | Таблица решений |
| Жизненный цикл статуса | Переходы состояний |
| Много комбинаций окружения | Pairwise + рисковые сочетания |
| Неясные требования / сложные интеграции | Исследование, уточнение правил, Error Guessing |
| Возможны повторы и параллелизм | Сценарии конкуренции, повторов, идемпотентности |

**Задача на собеседовании:** поле принимает целое число от 1 до 10. Назови техники и кейсы.  
**Ответ:** классы эквивалентности и граничные значения; 0,1,2,9,10,11, а также дробь, строка, null/отсутствие и отрицательные значения согласно контракту.

**Не делай:** десятки почти одинаковых тестов без понимания того, какой риск каждый из них покрывает.
