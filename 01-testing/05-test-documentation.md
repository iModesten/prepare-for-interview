## 1. Test Plan и Test Strategy

**Test Strategy** определяет общий подход: какие риски важны, какие уровни тестов используем, что автоматизируем, как работаем с данными, окружениями и качеством.

**Test Plan** конкретизирует проверку задачи или релиза: объём, сроки, зависимости, критерии начала и завершения. В небольшой задаче план может быть кратким разделом тикета, а не отдельным документом.

**Пример плана для API бонусов:** успешная выдача, ограничения и лимиты, авторизация, повторные запросы, интеграции PostgreSQL/Kafka. Критичный риск — двойная выдача.

## 2. Checklist и Test Case

**Checklist** — перечень проверок без обязательных подробных шагов. Удобен для знакомого функционала и smoke.

- [ ] Валидный бонус выдаётся.
- [ ] Просроченный бонус не выдаётся.
- [ ] Чужому пользователю нельзя выдать бонус без прав.
- [ ] Повтор не создаёт дубль.
- [ ] После выдачи есть запись в истории.

**Test Case** — условия, шаги и ожидаемые результаты. Полезен для сложного сценария, повторяемости и передачи знаний.

**Пример:**
- **Название:** повтор POST не приводит к дублированию выдачи.
- **Предусловие:** активный бонус, допустимый пользователь, известное исходное состояние.
- **Шаги:** вызвать POST, затем повторить тот же запрос по правилам контракта.
- **Ожидание:** выдача не дублируется; повторный HTTP-ответ соответствует согласованному контракту (не угадываем код).

**Главное:** не всегда нужны подробные кейсы. Формализация зависит от цены ошибки и необходимости повторить проверку другим человеком.

## 3. Bug Report

Хороший дефект позволяет воспроизвести проблему и оценить её влияние.

**Пример:**

**Заголовок:** при двух параллельных POST создаются две выдачи одного бонуса.

**Окружение:** тестовый стенд, версия приложения, время в UTC.

**Предусловия:** бонус доступен, у пользователя ещё нет выдачи.

**Шаги:** одновременно отправить два запроса `POST /bonuses/issue`.

**Ожидание:** лимит выдачи соблюдён, дубля нет.

**Факт:** в БД две записи выдачи.

**Приложения:** обезличенные Request ID, ответы, SQL-результат, ссылка на логи.

**Безопасность:** токены, секреты и персональные данные из отчёта убираем.

## 4. Severity vs Priority

- **Severity** — насколько серьёзно дефект влияет на систему и пользователя.
- **Priority** — насколько срочно его исправить.

Пример: двойная выдача имеет высокую Severity и обычно высокий Priority. Опечатка на экране крупной рекламной кампании может иметь низкую Severity, но высокий Priority перед запуском.

Точные шкалы зависят от команды.

## 5. Traceability и Coverage

**Traceability** — связь требований, проверок, дефектов и результатов.

| Правило | Проверка | Результат |
|---|---|---|
| Бонус выдаётся один раз | Повторный POST и параллельные запросы | Failed |
| Недоступный бонус не выдаётся | Запрос после срока действия | Passed |
| История защищена | Запрос другого пользователя | Not Run |

**Coverage** всегда имеет конкретную базу: требования, сценарии, условия, ветви кода. Утверждение «покрытие 90%» без определения метрики малоинформативно.

## 6. Test Summary

Краткий итог тестирования включает: что проверено, окружение, результаты, дефекты, непроверенные области, остаточные риски и вывод.

**Пример:** «Основные проверки API завершены, обнаружена критичная двойная выдача при параллельных запросах. Нагрузочные проверки не проводились. Риск релиза высокий, рекомендовано исправление».

## 7. Вопросы

**Когда checklist лучше test case?** Когда сценарий знаком, а стоимость подробной поддержки кейсов выше пользы.

**Что важно в баг-репорте?** Факт, ожидание, воспроизведение, окружение, доказательства и влияние.

**Test Strategy vs Test Plan?** Общий подход vs план конкретных работ.

**Severity vs Priority?** Тяжесть последствий vs срочность исправления.

**Что QA сообщает перед релизом?** Проверенный объём, результаты, важные дефекты и остаточные риски.
