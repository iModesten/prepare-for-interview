## 1. Уровни тестирования

**Уровень** отвечает на вопрос «какую часть системы проверяем?», а не «кто именно пишет тесты».

| Уровень | Что проверяем | Пример с бонусами |
|---|---|---|
| Component / Unit | Небольшую единицу логики изолированно | Функция определяет, разрешено ли выдать бонус |
| Integration | Взаимодействие компонентов | Backend сохраняет выдачу в PostgreSQL и публикует событие |
| System | Систему в целом | Вся цепочка от API до истории бонусов |
| Acceptance | Соответствие критериям приёмки и задачам бизнеса | Пользователь получает именно положенный ему бонус |

**Нюанс:** слова «интеграционный тест» разные команды используют по-разному. Уточняем, какие компоненты реально включены, а какие замоканы.

**Пример:** запрос к реальному Backend с тестовой БД — это не unit-тест только потому, что вызвана одна ручка. Если участвуют несколько компонентов, это уже интеграционная проверка.

### Component Integration vs System Integration

- Взаимодействие модуля с БД — интеграция внутри системы.
- Взаимодействие с отдельным сервисом профиля или Kafka — интеграция между системами (точные названия зависят от подхода команды).

## 2. Функциональное и нефункциональное

**Функциональное:** *что* должна делать система — выдавать бонус, запрещать повторную выдачу, возвращать историю.

**Нефункциональное:** *как* она работает — производительность, безопасность, надёжность, доступность, совместимость и удобство.

Примеры:
- **Performance:** p95 ответа выдачи бонуса не превышает согласованный порог при заданной нагрузке.
- **Security:** пользователь А не может получить историю пользователя Б.
- **Reliability:** повторная доставка события не создаёт вторую выдачу.
- **Compatibility:** WebView корректно работает на поддерживаемых устройствах.

**Regression** и **Smoke** — не альтернативы функциональному/нефункциональному тестированию. Это классификация по цели и моменту применения, а не по свойству продукта.

## 3. Smoke, Sanity, Regression и Retest

| Название | Когда и зачем | Пример |
|---|---|---|
| Smoke | Быстрая проверка, что сборка пригодна для дальнейшего тестирования | Health endpoint, авторизация, основные API работают |
| Sanity | Узкая проверка конкретной области после небольших изменений | После исправления лимита перепроверить выдачу бонусов и близкие сценарии |
| Regression | Поиск побочных дефектов после изменений | Изменили выдачу — проверяем список, историю и другие связанные процессы |
| Retest / Confirmation | Повторная проверка конкретного исправленного дефекта | Ошибка «выдаётся 11 бонусов вместо 10» больше не воспроизводится |

**Smoke vs Sanity:** определения могут отличаться между командами. Важно объяснять *объём* и *цель*. Не нужно спорить, что слово «sanity» имеет единственно правильное значение.

**Retest vs Regression:** первое проверяет исправление известной проблемы, второе — что изменение не сломало другое поведение.

## 4. Чёрный, белый и серый ящик

- **Black-box:** проектируем тесты по внешнему поведению, не опираясь на внутреннюю реализацию.
- **White-box:** учитываем структуру кода, ветви и пути.
- **Gray-box:** используем часть знаний об устройстве, например схему БД и обработку Kafka, при проверке API.

**Пример gray-box:** после POST проверяем ответ 200 и отдельно убеждаемся, что в БД одна запись, а в Kafka отправлено ожидаемое событие.

**Важно:** доступ к базе не означает, что тест автоматически полезен. Нужно понимать, какое требование подтверждает проверка и не слишком ли она привязана к реализации.

## 5. Где автоматизировать проверки

Практическая схема:

```text
Много быстрых проверок логики (unit)
             ↓
Целевые интеграционные тесты API/БД/Kafka
             ↓
Немного критичных E2E цепочек через UI
```

Это иллюстрация **пирамиды тестирования**, а не жёсткое требование количества тестов на каждом уровне.

**Пример:** проверку «недоступный бонус нельзя выдать» удобно покрыть на уровне бизнес-логики. Контракт ошибки 409 — интеграционным/API-тестом. Полный сценарий «выбрать бонус в приложении и увидеть его в истории» — одним E2E.

## 6. Практика и вопросы

**Вопрос:** у разработчика покрыты unit-тестами все условия выдачи бонуса. Нужно ли дополнительно вручную тестировать API?

**Ответ:** не обязательно повторять все unit-кейсы. Нужно оценить риски *непокрытых границ*: HTTP-контракт, сериализацию, авторизацию, транзакции, настройки окружения, интеграции, реальные данные и достоверность самих unit-тестов. Если это уже качественно закрыто автоматизированными тестами, ручная проверка может быть короткой исследовательской, а не дублирующей регрессией.

**Вопросы на интервью:**
- Unit vs Integration? — Изоляция компонента vs взаимодействие компонентов.
- Smoke vs Regression? — Узкая проверка пригодности сборки vs проверка побочных последствий изменений.
- Retest vs Regression? — Проверка конкретного исправления vs поиск новых поломок.
- Нефункциональное тестирование? — Оценка характеристик качества, например производительности и безопасности.
