## 1. Как устроен Git

**Git** — распределённая система контроля версий, которая хранит историю снимков проекта. **Working tree** — рабочие файлы, **staging/index** — выбранные изменения для коммита, **repository** — сохранённая история.

~~~text
Изменил файл → git add → staging → git commit → локальная история → git push → remote
~~~

**Branch** — указатель на цепочку коммитов. **HEAD** указывает на текущий checkout, обычно на ветку. **origin** — распространённое имя удалённого репозитория.

## 2. Основные команды

| Цель | Команда |
|---|---|
| Состояние изменений | `git status` |
| Рабочие изменения | `git diff` |
| Staged-изменения | `git diff --staged` |
| История | `git log --oneline --graph -10` |
| Создать ветку | `git switch -c test/bonus-api` |
| Добавить изменения | `git add path/to/test.spec.ts` |
| Коммит | `git commit -m "test: add bonus cases"` |
| Отправить ветку | `git push -u origin test/bonus-api` |
| Обновить remote-tracking ветки | `git fetch origin` |
| Получить и интегрировать изменения | `git pull` |
| Посмотреть коммит | `git show <sha>` |
| Кто менял строки | `git blame path/to/file` |

**Fetch vs Pull:** fetch загружает сведения и объекты, не внедряя изменения в текущую ветку; pull обычно делает fetch + merge/rebase согласно настройкам.

## 3. Merge, Rebase и Cherry-pick

~~~text
main:    A---B-------M
              \     /
feature:       C---D
~~~

**Merge** объединяет истории и может создать merge-коммит (при fast-forward отдельного коммита нет).

**Rebase** повторно применяет коммиты на другой базе и **меняет их SHA**. Не переписывай общую историю без согласования.

~~~bash
git fetch origin
git switch test/bonus-api
git rebase origin/main
~~~

Если личная ветка опубликована и был rebase, иногда нужен `git push --force-with-lease`, а не опасный обычный `--force`.

**Cherry-pick** переносит эффект выбранного коммита в текущую ветку:

~~~bash
git cherry-pick <sha>
~~~

Пример: перенести фикс API-теста в release-ветку, не забирая всю разработку.

## 4. Конфликты и откат

Конфликт возникает, если Git не смог автоматически объединить изменения.

Порядок: `git status` → открыть конфликтные файлы → решить по смыслу, а не автоматически выбрать чужой/свой вариант → удалить маркеры → `git add` → `git merge --continue` / `git rebase --continue`.

Отказаться от операции: `git merge --abort` / `git rebase --abort`.

| Действие | Команда | Осторожность |
|---|---|---|
| Убрать файл из staging | `git restore --staged file` | Рабочие изменения остаются |
| Отменить рабочие изменения | `git restore file` | Незакоммиченные данные могут потеряться |
| Отменить опубликованный коммит | `git revert <sha>` | Новый отменяющий коммит |
| Передвинуть историю и сбросить файлы | `git reset --hard <sha>` | Опасно для незакоммиченных данных |

## 5. Практический QA-сценарий

Разработчик изменил POST /bonuses/issue. QA создаёт ветку, добавляет интеграционные проверки, запускает их локально, делает commit/push и открывает PR/MR. Pipeline запускает тесты; QA смотрит изменения контракта, результаты CI, покрытие повторов и отсутствие чувствительных данных в логах.

**Для интервью:** объясни разницу между fetch/pull, merge/rebase, revert/reset и способ расследовать конфликт.
