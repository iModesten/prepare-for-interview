## 1. Git

### 1. Чем git fetch отличается от git pull?

<details>
<summary>Показать ответ</summary>

Fetch получает обновления удалённых ссылок и объектов, но не внедряет их в текущую ветку. Pull затем интегрирует их через merge/rebase согласно конфигурации.

</details>

### 2. Merge vs Rebase?

<details>
<summary>Показать ответ</summary>

Merge соединяет ветки, сохраняя их историю. Rebase применяет коммиты на новой базе с новыми SHA. Rebase общей ветки без согласования опасен.

</details>

### 3. Revert vs Reset?

<details>
<summary>Показать ответ</summary>

Revert создаёт отменяющий коммит и обычно подходит для общей истории. Reset перемещает HEAD и, в зависимости от режима, меняет index/working tree; hard может уничтожить несохранённые изменения.

</details>

### 4. Что делать при merge conflict?

<details>
<summary>Показать ответ</summary>

Узнать конфликтные файлы через status, сравнить оба изменения, разрешить вручную по смыслу, убрать маркеры, сделать add и продолжить операцию.

</details>

## 2. CI/CD

### 5. CI, Continuous Delivery и Continuous Deployment?

<details>
<summary>Показать ответ</summary>

CI — регулярное объединение и автоматическая проверка. Delivery — готовность к выпуску, который может быть одобрен вручную. Deployment — автоматическая поставка каждого прошедшего проверки изменения.

</details>

### 6. Job, Stage, Runner?

<details>
<summary>Показать ответ</summary>

Job — выполняемая работа; Stage — группа jobs; Runner — исполнитель. Стадии не обязательно полностью последовательны, это зависит от системы CI.

</details>

### 7. Artifacts vs Cache?

<details>
<summary>Показать ответ</summary>

Artifact хранит результат выполнения (например, test report), Cache хранит повторно используемые данные для ускорения работы, например зависимости.

</details>

### 8. Почему зелёный pipeline не означает отсутствие дефектов?

<details>
<summary>Показать ответ</summary>

Проверены только реализованные тесты и условия quality gate в определённом окружении. Непокрытые требования, неверные тесты и инциденты вне условий проверки остаются возможными.

</details>

## 3. Docker

### 9. Image vs Container?

<details>
<summary>Показать ответ</summary>

Image — упакованный шаблон, Container — экземпляр, созданный из image и имеющий жизненный цикл и процесс.

</details>

### 10. RUN vs CMD в Dockerfile?

<details>
<summary>Показать ответ</summary>

RUN выполняется при сборке образа. CMD задаёт команду по умолчанию при запуске контейнера.

</details>

### 11. EXPOSE публикует порт?

<details>
<summary>Показать ответ</summary>

Нет. EXPOSE документирует предполагаемый порт. Для доступа с хоста требуется публикация порта, например docker run -p 8080:3000, и слушающий нужный адрес процесс.

</details>

### 12. Почему API из контейнера не видит БД по localhost?

<details>
<summary>Показать ответ</summary>

localhost — текущий контейнер. В пользовательской Docker-сети/Compose обычно обращаются по имени сервиса, например postgres:5432.

</details>

### 13. Для чего нужны volumes?

<details>
<summary>Показать ответ</summary>

Хранят данные отдельно от изменяемого слоя контейнера, позволяя сохранять состояние при пересоздании экземпляров.

</details>

## 4. Kubernetes

### 14. Pod vs Container?

<details>
<summary>Показать ответ</summary>

Pod — минимальный объект запуска Kubernetes, может содержать один или несколько контейнеров с общей сетью; контейнер — отдельный исполняемый экземпляр образа.

</details>

### 15. Deployment vs Service?

<details>
<summary>Показать ответ</summary>

Deployment управляет желаемым состоянием и обновлением Pod. Service предоставляет устойчивую сетевую точку доступа и выбирает Pod по меткам.

</details>

### 16. Readiness vs Liveness?

<details>
<summary>Показать ответ</summary>

Readiness показывает готовность принимать трафик. Liveness проверяет, следует ли перезапустить контейнер. Непрохождение readiness само по себе не требует рестарта.

</details>

### 17. Что такое CrashLoopBackOff?

<details>
<summary>Показать ответ</summary>

Контейнер неоднократно завершался и Kubernetes увеличивает паузу перед очередным стартом. Проверяются события, логи текущего и предыдущего запуска, exit code и конфигурация.

</details>

## 5. Практические ситуации

### 18. Pipeline падает только на CI, локально тест проходит

<details>
<summary>Показать ответ</summary>

Сравнить версии зависимостей, переменные, окружение, параллельность, тестовые данные, таймзоны и network access. Посмотреть artifacts/trace; проверить, не flaky ли тест. Не сводить автоматически к «проблеме CI».

</details>

### 19. После деплоя API отдаёт 503

<details>
<summary>Показать ответ</summary>

Проверить rollout, количество Ready Pod, endpoints Service, probes, логи контейнеров, зависимости, конфигурацию и Ingress/Gateway. Уточнить источник 503.

</details>

### 20. Контейнер постоянно перезапускается

<details>
<summary>Показать ответ</summary>

Проверить exit code, логи, лимиты памяти, probes и конфигурацию. OOMKilled — возможный вариант, но exit code 137 сам по себе не доказывает нехватку памяти.

</details>

### 21. После rollback старого приложения SQL-запросы перестали работать

<details>
<summary>Показать ответ</summary>

Rollback версии контейнера не возвращает автоматически старую схему БД. Нужно проверить миграции и их backward compatibility, данные и контракт старой версии.

</details>

### 22. Как организовать API-тесты в CI?

<details>
<summary>Показать ответ</summary>

Поднять нужные зависимости/стенд с известными версиями, подготовить изолированные данные, выполнить API-тесты, сохранить отчёты и trace/logs, обеспечить понятные критерии падения и очистку окружения.

</details>

### 23. Как уменьшить flaky-тесты в pipeline?

<details>
<summary>Показать ответ</summary>

Исключить общие изменяемые данные, заменить фиксированные sleep на ожидания условий, стабилизировать окружение и сеть, исследовать ошибки, запускать тесты в параллели для воспроизведения race. Retry — не лечение.

</details>

### 24. Что проверять QA при Canary Release?

<details>
<summary>Показать ответ</summary>

Доли и маршрутизацию трафика, совместимость разных версий API/событий, критичные сценарии, метрики и ошибки новой версии, критерии остановки/rollback.

</details>
