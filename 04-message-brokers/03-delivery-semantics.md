# Kafka — гарантии доставки и обработки сообщений (Delivery Semantics)

## 1. Что такое Delivery Semantics?

**Delivery Semantics** — гарантии, определяющие, сколько раз сообщение может быть доставлено или обработано при нормальной работе и сбоях системы.

В распределённых системах могут происходить:

- Потеря сетевого соединения.
- Недоступность брокера.
- Падение Producer.
- Падение Consumer.
- Ошибки базы данных.
- Таймауты.
- Повторные попытки отправки и обработки.

Поэтому важно понимать, какие гарантии предоставляет система и что происходит при отказах.

### Три основные модели

| Модель | Основная гарантия | Возможная проблема |
|---|---|---|
| At-most-once | Не более одной попытки обработки | Потеря обработки |
| At-least-once | Как минимум одна успешная обработка при соблюдении предпосылок восстановления | Повторная обработка |
| Exactly-once | Однократный результат обработки в определённых границах системы | Сложность реализации |

### Краткий ответ для собеседования

> Есть три основные семантики: at-most-once, at-least-once и exactly-once. At-most-once допускает потерю сообщений, но исключает повторную доставку в рамках выбранной модели. At-least-once предполагает повторные попытки до успешной обработки, поэтому возможны дубликаты. Exactly-once означает однократный результат обработки, но гарантии всегда имеют определённые границы. Например, Kafka поддерживает exactly-once для определённых Kafka-to-Kafka сценариев, однако для внешних БД требуется дополнительная координация или идемпотентность.

## 2. Разница между доставкой и обработкой

Это принципиально важное различие.

Представим событие:

```json
{
  "eventId": "payment-123",
  "userId": "user-10",
  "amount": 100
}
```

Kafka может успешно сохранить событие.

Consumer может успешно его прочитать.

Но это ещё не означает, что деньги зачислены пользователю.

Разделим процесс:

```text
Producer
   |
   | 1. Публикация
   v
Kafka
   |
   | 2. Получение
   v
Consumer
   |
   | 3. Бизнес-обработка
   v
Database
   |
   | 4. Фиксация результата
   v
COMMIT
```

Здесь есть несколько независимых этапов:

1. Запись сообщения в Kafka.
2. Чтение сообщения Consumer.
3. Выполнение бизнес-логики.
4. Сохранение результата в БД.
5. Фиксация Kafka offset.

Сбой может произойти между любыми этапами.

**Важно:** успешный commit offset не доказывает, что внешняя бизнес-операция выполнилась. И наоборот, успешный commit БД не означает, что Kafka offset уже зафиксирован.

## 3. At-most-once — не более одного раза

**At-most-once** — модель, при которой повторная доставка или попытка обработки сообщения не выполняется в рамках рассматриваемого механизма.

Сообщение может быть потеряно для бизнес-обработки.

### Как это может работать?

Consumer сначала фиксирует offset, а затем выполняет бизнес-операцию.

```text
1. Consumer получил сообщение
              ↓
2. Commit offset
              ↓
3. Начало обработки
              ↓
4. Сбой Consumer
```

После восстановления группа продолжает чтение с уже сохранённой позиции.

Сообщение не будет автоматически прочитано повторно этой группой, хотя его бизнес-обработка не завершилась.

### Пример

Сообщение имеет offset 10.

```text
Получен offset 10
        ↓
Committed offset = 11
        ↓
Consumer упал
        ↓
Начисление бонуса не выполнено
        ↓
После перезапуска чтение с offset 11
```

**Результат:** бонус не начислен, хотя позиция группы уже продвинута.

### Преимущества

- Нет повторных попыток обработки в выбранной модели.
- Может быть проще управление прогрессом.
- Подходит, когда отдельную потерю события допустимо пережить.

### Недостатки

- Возможна потеря обработки.
- Не подходит для критичных операций без дополнительной защиты.

### Где может использоваться?

Например:

- Некритичная телеметрия.
- Некоторые виды статистики.
- События, отдельную потерю которых допускают требования.

Для списания денег или выдачи бонусов обычно нужны более сильные гарантии.

---

## 4. At-least-once — как минимум один раз

**At-least-once** — модель, при которой система предусматривает повторную доставку или обработку до успешного завершения при соблюдении условий доступности, хранения и восстановления.

При этом сообщение может обрабатываться несколько раз.

### Типичная реализация

Consumer сначала выполняет бизнес-операцию, затем фиксирует offset.

```text
1. Consumer получил сообщение
              ↓
2. Бизнес-обработка
              ↓
3. DB COMMIT
              ↓
4. Kafka offset COMMIT
```

### Сценарий без ошибок

```text
Offset 10 получен
        ↓
Бонус начислен
        ↓
DB COMMIT
        ↓
Committed offset = 11
```

Всё прошло успешно.

### Сценарий со сбоем

```text
Offset 10 получен
        ↓
Бонус начислен
        ↓
DB COMMIT
        ↓
Consumer упал
        ↓
Kafka offset не зафиксирован
        ↓
Consumer перезапустился
        ↓
Offset 10 получен повторно
```

Бонус уже был начислен, но Kafka не знает об этом.

Если приложение просто повторит начисление, получится двойная выдача.

### Преимущества

- Снижается риск потери необходимой обработки.
- Возможна повторная попытка после временного сбоя.
- Подходит для большинства критичных асинхронных операций при наличии идемпотентности.

### Недостатки

- Возможны дубликаты.
- Consumer должен корректно обрабатывать повторы.
- Необходима стратегия для постоянно неуспешных сообщений.

### Ограничения гарантии

At-least-once не означает, что сообщение будет успешно обработано при любых обстоятельствах.

Например:

- Сообщение может быть удалено по retention до восстановления.
- Сообщение может постоянно завершаться ошибкой.
- Данные могут быть потеряны при недостаточных гарантиях записи и репликации.
- Обработка может быть прекращена из-за истечения лимита попыток.

Поэтому необходимо определять условия и границы гарантии.

## 5. Exactly-once — ровно один раз

**Exactly-once** — семантика, при которой результат обработки каждого сообщения учитывается ровно один раз в пределах определённой системы и её гарантий.

Самое важное — не путать:

- Однократную физическую доставку.
- Однократный вызов обработчика.
- Однократный бизнес-эффект.

В распределённых системах сообщение может быть доставлено повторно, но итоговый эффект останется однократным.

### Пример

Consumer дважды получил событие:

```json
{
  "eventId": "bonus-500",
  "userId": "user-100",
  "bonusId": 777
}
```

Первое получение:

```text
Бонус выдан
```

Второе получение:

```text
Событие распознано как уже обработанное
Новая выдача не выполняется
```

Итог:

```text
Сообщение получено: 2 раза
Бизнес-выдача: 1 раз
```

Это пример однократного бизнес-эффекта, достигнутого с помощью идемпотентной обработки.

Но такой механизм сам по себе не означает, что все этапы всей распределённой системы обладают exactly-once гарантиями.

### Вопрос на собеседовании

**Может ли Kafka гарантировать Exactly-once?**

Да, для определённых сценариев.

Например, Kafka Transactions позволяют атомарно зафиксировать результаты записи в Kafka и соответствующие offsets исходных сообщений.

Но если Consumer записывает результат в PostgreSQL или MySQL, Kafka Transactions сами по себе не делают коммит внешней БД частью Kafka-транзакции.

## 6. Сравнение трёх гарантий на одном примере

Представим Consumer, который начисляет пользователю 100 бонусных баллов.

| Сценарий | At-most-once | At-least-once | Exactly-once effect |
|---|---|---|---|
| Успешная обработка | +100 | +100 | +100 |
| Сбой до обработки | Возможен пропуск | Повторная попытка | Повторная попытка |
| Сбой после DB COMMIT | Повтор обычно не предусмотрен | Возможен повтор | Повтор без второго начисления |
| Итог при корректной реализации гарантий | Возможна потеря эффекта | Возможен двойной эффект без идемпотентности | Один бизнес-эффект |

### Главное отличие

At-most-once допускает потерю.

At-least-once допускает повтор.

Exactly-once effect требует механизмов, предотвращающих и потерю требуемого результата, и его нежелательное дублирование в заданных границах.

## 7. Почему возникают дубликаты сообщений?

### Сценарий 1. Сбой Consumer до commit offset

Consumer обработал событие, но не успел зафиксировать позицию.

После восстановления событие снова поступает в обработку.

### Сценарий 2. Повторная отправка Producer

Producer отправляет сообщение.

Kafka записывает сообщение, но подтверждение теряется в сети.

Producer не знает, была ли запись успешной, и повторяет запрос.

Без подходящих механизмов защиты может появиться вторая запись.

### Сценарий 3. Повтор на уровне приложения

API получает запрос:

```http
POST /payments
```

Клиент не получил ответ и повторяет запрос.

Приложение может создать две самостоятельные бизнес-операции, даже если Kafka Producer настроен на идемпотентную отправку.

### Сценарий 4. Повторная публикация через Outbox

Message Relay опубликовал событие, но упал до отметки о публикации в БД.

После восстановления событие публикуется снова.

### Важный вывод

Дубликаты могут возникать на разных уровнях.

Идемпотентный Kafka Producer решает не все проблемы повторной бизнес-операции.

## 8. Idempotent Producer

**Idempotent Producer** — режим Kafka Producer, предотвращающий дублирование записей вследствие поддерживаемых повторных попыток отправки.

Пример конфигурации:

```properties
enable.idempotence=true
acks=all
retries=2147483647
```

Это иллюстрация настроек; фактические значения по умолчанию и допустимые комбинации зависят от клиента и версии Kafka.

### Как это работает?

В упрощённой модели Kafka использует:

- Producer ID.
- Идентификаторы эпохи Producer.
- Sequence numbers для записей в партициях.

Они позволяют брокеру распознавать определённые повторные отправки от Producer.

### Чего Idempotent Producer не гарантирует?

Он не предотвращает автоматически:

- Два разных бизнес-запроса с одинаковым смыслом.
- Два сообщения, которые приложение намеренно отправило отдельно.
- Повторное начисление в базе данных Consumer.
- Дубликаты, возникающие при повторной работе Message Relay.

### Краткий ответ для собеседования

> Idempotent Producer защищает от определённых дубликатов записи при повторных отправках в Kafka. Но он не обеспечивает идемпотентность бизнес-операции и не гарантирует отсутствие повторной обработки Consumer.

## 9. Kafka Transactions

Kafka поддерживает транзакционную запись сообщений.

Это позволяет Producer атомарно публиковать записи в несколько партиций или топиков.

При использовании подходящей конфигурации также можно включить фиксацию offsets исходных сообщений в одну Kafka-транзакцию с публикацией результатов.

### Пример

Сервис читает событие:

```text
payments.completed
```

После обработки публикует:

```text
bonuses.issued
analytics.updated
```

Желательно, чтобы либо оба выходных события стали видимыми как подтверждённый результат обработки, либо ни одно из них.

Kafka Transactions позволяют организовать такую атомарность в пределах Kafka.

### Типичная последовательность

```text
1. poll() исходного сообщения
              ↓
2. beginTransaction()
              ↓
3. send() выходного события A
              ↓
4. send() выходного события B
              ↓
5. sendOffsetsToTransaction()
              ↓
6. commitTransaction()
```

После commit выходные записи и позиции чтения фиксируются согласованно в Kafka.

### Основные механизмы

**transactional.id**

Стабильный идентификатор транзакционного Producer, используемый в том числе для fencing прежних экземпляров.

**beginTransaction()**

Начало транзакции Kafka.

**sendOffsetsToTransaction()**

Добавление offsets обработанных исходных сообщений в транзакцию Producer.

**commitTransaction()**

Фиксация Kafka-транзакции.

**abortTransaction()**

Отмена Kafka-транзакции.

### Важный нюанс

Если приложение одновременно записывает данные во внешнюю БД, её COMMIT не становится автоматически частью Kafka Transactions.

Поэтому нельзя говорить:

> Мы включили Kafka Transactions, значит денежная операция в MySQL всегда будет выполнена ровно один раз.

Это некорректно без дополнительных гарантий.

## 10. read_committed и read_uncommitted в Kafka Consumer

У Kafka Consumer есть настройка `isolation.level`.

### read_uncommitted

Consumer может читать записи из завершённых, незавершённых и впоследствии отменённых транзакций, если они уже доступны для чтения согласно правилам Kafka.

### read_committed

Consumer читает нетранзакционные записи и записи подтверждённых Kafka-транзакций.

Записи отменённых транзакций не выдаются приложению.

```properties
isolation.level=read_committed
```

### Пример

Producer начал транзакцию:

```text
beginTransaction()
send(A)
send(B)
abortTransaction()
```

Consumer с `read_committed` не получит A и B как подтверждённые записи.

Consumer с `read_uncommitted` может их увидеть.

### Важно

`read_committed` в Kafka не следует путать с одноимённым уровнем изоляции транзакций реляционной БД.

Названия похожи, но применяются к разным механизмам.

## 11. Идемпотентность Consumer

**Idempotent Consumer** — обработчик, который может безопасно получать одно логическое сообщение несколько раз без нежелательного повторного бизнес-эффекта.

### Пример без идемпотентности

Получено событие:

```json
{
  "eventId": "evt-100",
  "userId": "user-1",
  "amount": 100
}
```

Consumer выполняет:

```sql
UPDATE accounts
SET balance = balance + 100
WHERE user_id = 'user-1';
```

При повторном получении события операция выполняется повторно.

Результат:

```text
Начальный баланс: 500
Первое событие: 600
Повтор события: 700
```

Бизнес-ошибка — двойное начисление.

### Как можно реализовать идемпотентность?

Один из способов — хранить идентификаторы обработанных сообщений.

```sql
CREATE TABLE processed_events (
    consumer_name VARCHAR(100) NOT NULL,
    event_id VARCHAR(100) NOT NULL,
    processed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (consumer_name, event_id)
);
```

В одной транзакции:

1. Пытаемся зарегистрировать eventId.
2. Если событие новое — выполняем бизнес-изменение.
3. Коммитим транзакцию.
4. После этого фиксируем Kafka offset.
5. Если eventId уже существует — не повторяем бизнес-операцию.

### Пример для PostgreSQL

```sql
BEGIN;

INSERT INTO processed_events (consumer_name, event_id)
VALUES ('bonus-service', 'evt-100')
ON CONFLICT DO NOTHING;
```

Далее приложение должно проверить количество вставленных строк.

Если вставлена одна строка:

```sql
UPDATE accounts
SET balance = balance + 100
WHERE user_id = 'user-1';

COMMIT;
```

Если вставлено ноль строк:

```sql
ROLLBACK;
```

В этом случае бизнес-обновление не выполняется.

После успешного распознавания дубликата Kafka offset можно безопасно продвинуть, если остальные требования обработки выполнены.

### Почему всё должно быть в одной транзакции?

Если сначала начислить бонус, а потом сохранить eventId, сбой между этими действиями приведёт к повторному начислению.

Если eventId и начисление фиксируются атомарно, такая проблема устраняется для изменений внутри той же БД.

**Важно:** этот механизм не делает автоматически идемпотентными внешние HTTP-запросы, отправку email или вызовы платёжных систем.

## 12. Inbox Pattern

**Inbox Pattern** — подход к надёжной обработке входящих событий с сохранением информации о них в базе данных получателя.

Одна из распространённых реализаций:

```text
Kafka
  |
  v
Consumer
  |
  v
Database Transaction
  |
  +--> processed_events
  |
  +--> business tables
  |
  v
COMMIT
```

Сохранение идентификатора события и бизнес-изменения происходит в одной транзакции.

### Преимущества

- Защита от повторных бизнес-эффектов.
- Устойчивость к сбоям после DB COMMIT.
- Возможность отслеживать обработанные события.
- Поддержка at-least-once доставки с однократным эффектом в БД.

### Недостатки

- Дополнительное хранение идентификаторов.
- Необходимость управления сроками хранения.
- Дополнительные операции с БД.
- Нужно правильно обрабатывать конкурентную обработку одного eventId.

### Что проверять QA?

- Первую обработку события.
- Повторную обработку того же eventId.
- Параллельную обработку дублей.
- Сбой до DB COMMIT.
- Сбой после DB COMMIT.
- Повтор после перезапуска.
- События с одинаковым eventId, но разным содержимым.

## 13. Transactional Outbox Pattern

**Transactional Outbox** — паттерн надёжной публикации событий при изменении данных в БД.

Он решает проблему атомарности между сохранением бизнес-данных и намерением отправить событие.

### Проблема без Outbox

Представим:

```text
1. Создали заказ в БД
2. DB COMMIT
3. Отправили OrderCreated в Kafka
```

Если приложение упадёт между шагами 2 и 3:

- Заказ существует.
- Событие не опубликовано.
- Другие сервисы не узнают о заказе.

Если сначала отправить сообщение, а потом выполнить DB COMMIT, возникает обратный риск:

- Событие опубликовано.
- DB COMMIT завершился ошибкой.
- Другие сервисы обрабатывают событие о несуществующем заказе.

### Решение через Outbox

В одной транзакции записываем:

1. Бизнес-данные.
2. Событие в таблицу outbox.

Пример:

```sql
BEGIN;

INSERT INTO orders (id, status)
VALUES (101, 'CREATED');

INSERT INTO outbox_events (
    event_id,
    event_type,
    payload
)
VALUES (
    'evt-101',
    'OrderCreated',
    '{"orderId":101}'
);

COMMIT;
```

Отдельный компонент публикует события из outbox в Kafka.

### Архитектура

```text
              Order Service
                    |
                    v
             DB Transaction
               /         \
              v           v
          orders      outbox_events
               \         /
                    |
                  COMMIT
                    |
                    v
              Message Relay
                    |
                    v
                  Kafka
                    |
                    v
             Other Services
```

### Почему это работает?

Бизнес-изменение и запись события в outbox находятся внутри одной транзакции БД.

Если транзакция откатится, не сохранятся ни заказ, ни событие.

Если транзакция успешно зафиксируется, событие останется в outbox для последующей публикации.

### Но есть нюанс

Outbox не исключает повторную публикацию.

Например:

1. Relay опубликовал событие в Kafka.
2. Kafka подтвердила запись.
3. Relay упал до отметки события как опубликованного.
4. После перезапуска событие будет опубликовано снова.

Поэтому получатель должен корректно обрабатывать дубликаты.

**Outbox обеспечивает надёжность намерения публикации, а Inbox помогает обеспечить идемпотентность обработки.**

---

## 14. Outbox vs Inbox

| Характеристика | Outbox | Inbox |
|---|---|---|
| Сторона | Producer / Publisher | Consumer |
| Основная задача | Надёжно публиковать событие | Надёжно обрабатывать повторы |
| Хранилище | Таблица исходящих событий | Таблица входящих/обработанных событий |
| Основная проблема | DB COMMIT без публикации события | Повторный бизнес-эффект |
| Типичный результат | At-least-once публикация | Идемпотентная обработка |

### Как они работают вместе?

```text
Service A
  |
  v
DB + Outbox
  |
  v
Message Relay
  |
  v
Kafka
  |
  v
Service B
  |
  v
Inbox + Business Transaction
```

Такая архитектура часто используется в микросервисных системах, особенно там, где нежелательны потери событий и повторные финансовые операции.

## 15. Что такое Dual Write Problem?

**Dual Write Problem** — необходимость изменить состояние сразу в двух независимых системах, например в БД и Kafka, без единой атомарной транзакции.

Пример:

```text
Write to DB
Write to Kafka
```

Возможные проблемы:

- БД обновилась, Kafka — нет.
- Kafka получила событие, БД не обновилась.
- Один из шагов завершился таймаутом, и результат неизвестен.
- Повтор операции создал дубликаты.

### Способы решения

- Transactional Outbox.
- CDC.
- Inbox / Idempotent Consumer.
- Координация транзакций в поддерживаемых системах.
- Saga для многошаговых распределённых бизнес-процессов.

**Важно:** Kafka Transactions решают атомарность в пределах Kafka, но не автоматически произвольную Dual Write Problem с внешней БД.

## 16. CDC — Change Data Capture

**CDC** — механизм получения изменений данных из БД и их передачи другим системам.

Один из примеров — Debezium.

В архитектуре с Outbox CDC может читать изменения журнала транзакций БД и публиковать записи Outbox в Kafka.

### Пример

```text
Order Service
      |
      v
Database + Outbox
      |
      v
Transaction Log
      |
      v
CDC Connector
      |
      v
Kafka
```

### Преимущества

- Не требуется постоянно опрашивать таблицу outbox обычными SELECT.
- Можно эффективно обнаруживать новые изменения.
- События связаны с зафиксированными изменениями БД.

### Недостатки

- Дополнительная инфраструктура.
- Необходимость мониторинга CDC.
- Возможность повторных публикаций.
- Зависимость от журналов транзакций и их хранения.

## 17. Retry и обработка ошибок

При ошибке обработки сообщения часто применяется retry.

### Retry — повторная попытка

Например:

1. Consumer получил событие.
2. База данных недоступна.
3. Consumer ожидает.
4. Повторяет обработку.

### Retry с задержкой

Для уменьшения нагрузки применяют:

- Fixed Delay.
- Exponential Backoff.
- Ограничение количества попыток.
- Jitter.

### Проблема бесконечного Retry

Одно некорректное сообщение может блокировать обработку следующих сообщений партиции, если Consumer всегда пытается обработать только его.

Такое сообщение часто называют Poison Message.

### Dead Letter Topic

После определённого числа неудачных попыток сообщение может быть направлено в специальный топик ошибок:

```text
payments.completed.DLT
```

Важно, чтобы публикация в DLT и продвижение исходного offset были организованы согласованно.

Иначе сообщение может потеряться между ними.

### Что проверять QA?

- Временная ошибка зависимости.
- Постоянная ошибка валидации.
- Исчерпание попыток.
- Правильность задержек.
- Отправка в DLT.
- Отсутствие потери события при сбое во время переноса.
- Повторная обработка после исправления причины.

## 18. Практический пример: начисление бонуса по событию платежа

Представим банковскую систему.

После оплаты картой создаётся событие:

```json
{
  "eventId": "payment-event-1001",
  "paymentId": "payment-777",
  "userId": "user-123",
  "amount": 250,
  "currency": "BYN"
}
```

Consumer начисляет 25 бонусных баллов.

### Сценарий 1. Успешная обработка

1. Consumer получает событие.
2. Проверяет, что событие не обрабатывалось.
3. Рассчитывает бонус.
4. Записывает начисление и eventId в БД.
5. Фиксирует транзакцию.
6. Фиксирует Kafka offset.

**Ожидаемый результат:** 25 бонусных баллов начислены один раз.

### Сценарий 2. Consumer падает до DB COMMIT

Бизнес-изменения не зафиксированы.

После восстановления событие должно быть доступно для повторной обработки.

**Ожидаемый результат:** в конечном счёте одна корректная выдача при успешном восстановлении.

### Сценарий 3. Consumer падает после DB COMMIT

Начисление сохранено, но Kafka offset не зафиксирован.

После перезапуска сообщение может прийти повторно.

**Ожидаемый результат:** Consumer распознаёт eventId и не начисляет бонус второй раз.

### Сценарий 4. Два Consumer параллельно обрабатывают одно логическое событие

В обычной группе одна партиция назначается одному Consumer, но дубликаты могут оказаться в разных партициях, прийти через разные каналы или возникнуть при некорректном управлении обработкой.

**Ожидаемый результат:** уникальное ограничение и транзакционная обработка предотвращают повторное начисление.

### Сценарий 5. Ошибка после изменения баланса, но до регистрации eventId

При корректной реализации обе операции находятся в одной транзакции.

Если транзакция откатывается, не должно остаться ни начисления, ни отметки об обработке.

### Сценарий 6. Истёк срок хранения idempotency key

Если идентификаторы обработанных событий удаляются, необходимо понимать, допускается ли повторная доставка старого события.

Для финансовых операций недостаточно бездумно очищать ключи без учёта срока жизни бизнес-операций.

## 19. Как тестировать гарантии обработки?

### At-most-once

- [ ] Проверить успешную обработку.
- [ ] Создать сбой после продвижения offset, но до бизнес-операции.
- [ ] Убедиться, что сообщение не повторяется автоматически в выбранной модели.
- [ ] Проверить, соответствует ли такая потеря бизнес-требованиям.

### At-least-once

- [ ] Проверить успешную обработку.
- [ ] Создать сбой до фиксации offset.
- [ ] Проверить повторное получение.
- [ ] Проверить сохранение необходимого бизнес-результата.
- [ ] Проверить обработку дубликатов.

### Exactly-once Effect

- [ ] Повторно отправить одно событие.
- [ ] Параллельно отправить логические дубликаты.
- [ ] Создать сбой до DB COMMIT.
- [ ] Создать сбой после DB COMMIT.
- [ ] Проверить уникальность результата.
- [ ] Проверить атомарность eventId и бизнес-изменения.
- [ ] Проверить поведение после истечения срока хранения ключей.

### Kafka Transactions

- [ ] Успешная транзакционная публикация.
- [ ] Abort транзакции.
- [ ] Чтение с read_committed.
- [ ] Чтение с read_uncommitted.
- [ ] Сбой Producer во время транзакции.
- [ ] Восстановление после перезапуска.
- [ ] Проверка фиксации offsets вместе с выходными событиями.

### Transactional Outbox

- [ ] Бизнес-транзакция завершилась успешно — событие появилось в outbox.
- [ ] Бизнес-транзакция откатилась — событие отсутствует.
- [ ] Kafka недоступна — событие остаётся доступным для публикации.
- [ ] Relay упал после публикации — повтор не нарушает бизнес-логику Consumer.
- [ ] Проверить порядок событий, если он является требованием.

## 20. Вопросы на собеседовании

### 1. Какие существуют гарантии доставки сообщений?

At-most-once, at-least-once, exactly-once.

### 2. Что означает At-most-once?

Сообщение не обрабатывается повторно в рамках рассматриваемой модели, но необходимая обработка может потеряться при сбое.

### 3. Что означает At-least-once?

Система предусматривает повторную обработку до успешного завершения при соответствующих условиях. Поэтому возможны дубликаты.

### 4. Что означает Exactly-once?

Однократный результат обработки в определённых границах системы, даже при сбоях и повторных попытках.

### 5. Почему при At-least-once возможны дубликаты?

Потому что Consumer может завершить бизнес-операцию, но упасть до фиксации offset.

### 6. Почему при At-most-once возможна потеря?

Потому что позиция может быть зафиксирована раньше завершения обработки сообщения.

### 7. Гарантирует ли Kafka Exactly-once?

Для определённых Kafka-to-Kafka сценариев — да, при правильной транзакционной конфигурации. Для внешней БД нужны дополнительные механизмы.

### 8. Что такое Idempotent Producer?

Producer, который предотвращает определённые дубликаты записи при повторной отправке в Kafka.

### 9. Что такое Idempotent Consumer?

Consumer, который может повторно получить одно событие без нежелательного повторного бизнес-эффекта.

### 10. Чем Idempotent Producer отличается от Idempotent Consumer?

Producer защищает публикацию в Kafka. Consumer защищает бизнес-обработку сообщения.

### 11. Что такое Transactional Outbox?

Паттерн, при котором бизнес-изменение и исходящее событие сохраняются в одной транзакции БД, а публикация выполняется отдельным компонентом.

### 12. Что такое Inbox Pattern?

Подход к обработке входящих сообщений с атомарной регистрацией события и его бизнес-результата.

### 13. Что такое Dual Write Problem?

Проблема согласованной записи в две независимые системы без единой транзакции.

### 14. Что такое CDC?

Change Data Capture — получение изменений БД и передача их другим системам, часто через журнал транзакций.

### 15. Почему Kafka Transactions не гарантируют Exactly-once в MySQL?

Потому что локальная транзакция MySQL и Kafka-транзакция не становятся автоматически единой атомарной транзакцией.

### 16. Зачем нужен read_committed в Kafka?

Чтобы Consumer не получал отменённые транзакционные записи как доступный подтверждённый результат.

### 17. Зачем сохранять eventId при обработке?

Чтобы распознавать повторные сообщения и предотвращать нежелательные повторные бизнес-операции.

### 18. Почему недостаточно сначала выполнить SELECT для проверки eventId?

Потому что два конкурентных обработчика могут одновременно увидеть отсутствие записи. Нужны атомарная регистрация и уникальное ограничение.

### 19. Для чего нужен Dead Letter Topic?

Для изоляции и дальнейшего анализа сообщений, которые не удалось обработать согласно принятой retry-политике.

### 20. Как протестировать Exactly-once бизнес-эффект?

Повторять события, создавать конкурентные дубликаты и контролируемые сбои до и после коммитов, затем проверять, что итоговый бизнес-результат появляется ровно один раз.

## 21. Типичные ошибки на собеседовании

**Ошибка:** «At-least-once означает, что сообщение всегда приходит ровно один раз».

Правильно: возможна повторная доставка или обработка.

**Ошибка:** «Exactly-once означает, что Consumer физически получает сообщение только один раз».

Правильно: важен однократный результат в границах гарантии. Повторное выполнение отдельных попыток возможно.

**Ошибка:** «Idempotent Producer предотвращает двойное начисление денег».

Правильно: он защищает определённые повторные публикации в Kafka, но не бизнес-эффекты во внешней БД.

**Ошибка:** «Manual Commit гарантирует Exactly-once».

Правильно: между DB COMMIT и offset commit существует окно сбоя.

**Ошибка:** «Outbox полностью исключает дубликаты событий».

Правильно: Message Relay может публиковать одно событие несколько раз.

**Ошибка:** «Достаточно проверить наличие eventId через SELECT, чтобы избежать дубликатов».

Правильно: при конкурентной обработке нужен атомарный механизм дедупликации, обычно через UNIQUE/PRIMARY KEY и транзакцию.

**Ошибка:** «Kafka Transactions включают MySQL в ту же транзакцию».

Правильно: Kafka Transactions атомарно координируют поддерживаемые операции внутри Kafka. Внешняя БД требует отдельного решения.
