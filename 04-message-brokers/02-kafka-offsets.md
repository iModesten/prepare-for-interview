# Kafka — Offset, Commit и управление чтением сообщений

## 1. Что такое Offset?

**Offset** — числовая позиция записи внутри конкретной партиции Kafka.

Каждая запись, добавленная в партицию, получает offset, позволяющий определить её положение в журнале.

Пример:

```text
Topic: payments
Partition: 0

Offset:    0     1     2     3     4
          [A]   [B]   [C]   [D]   [E]
```

Основные свойства:

- Offset уникален в пределах конкретной партиции.
- Разные партиции могут содержать одинаковые offset.
- Offset назначается Kafka при записи сообщения.
- Offset не является глобальным идентификатором события.
- Offset не означает, что сообщение успешно обработано.
- Offset не обязан совпадать с количеством доступных или обработанных сообщений.

### Краткий ответ для собеседования

> Offset — позиция записи внутри партиции Kafka. Consumer использует offset для отслеживания чтения, а Consumer Group сохраняет committed offset для возобновления обработки после перезапуска или перераспределения партиций. Важно различать позицию чтения, зафиксированную позицию и фактическую бизнес-обработку сообщения.

---

## 2. Разница между Message Offset, Consumer Position и Committed Offset

Это три разных понятия.

### Message Offset

Позиция конкретной записи в партиции.

Например:

```text
Message A → offset 5
Message B → offset 6
Message C → offset 7
```

### Consumer Position

Позиция, с которой Consumer планирует продолжить выдачу записей приложению.

При вызове `poll()` Consumer может получить сразу несколько сообщений, после чего позиция чтения переместится вперёд.

### Committed Offset

Сохранённая позиция группы, которую Kafka использует при восстановлении чтения после перезапуска или rebalance.

Пример:

```text
Partition 0:

Offset:           5      6      7      8      9
                 [A]    [B]    [C]    [D]    [E]

Получены poll(): ✓      ✓      ✓
Обработаны:      ✓      ✓
Ожидает обработки:             C

Consumer Position: 8
Committed Offset: 7
```

Consumer получил сообщения 5, 6 и 7.

Сообщения 5 и 6 обработаны.

Committed offset равен 7, то есть следующая запись для восстановления — сообщение с offset 7.

После перезапуска сообщение C может быть получено повторно.

**Главное:** Consumer Position не равен автоматически последней успешно обработанной записи.

---

## 3. Почему коммитится Offset + 1?

Предположим, Consumer обработал сообщение с offset 10.

Какую позицию нужно сохранить?

```text
Последняя обработанная запись: 10
Следующая запись:             11
Committed Offset:             11
```

Kafka сохраняет позицию следующей записи, с которой следует продолжить чтение.

Поэтому при ручной фиксации после последовательной обработки записей обычно используют:

```text
lastProcessedOffset + 1
```

Если последняя успешно обработанная запись имеет offset 25, нужно зафиксировать 26.

**Ошибка:** коммитить 25 после обработки сообщения 25.

Это приведёт к тому, что при восстановлении сообщение с offset 25 может быть прочитано повторно.

При этом не следует вручную предполагать непрерывность всех offset в сложных сценариях с транзакционными записями и фильтрацией. Современный Kafka Consumer API предоставляет информацию о следующей позиции, подходящей для фиксации.

## 4. Где хранятся Committed Offsets?

В стандартной модели Consumer Groups offset хранятся внутри Kafka в служебном топике:

```text
__consumer_offsets
```

Consumer Group имеет собственные сохранённые позиции для назначаемых ей партиций.

Например:

```text
Topic: payments
Partition: 0

Group: bonuses-service
Committed Offset: 150

Group: analytics-service
Committed Offset: 100

Group: notifications-service
Committed Offset: 145
```

Это три независимые группы.

Сервис аналитики может отставать от сервиса бонусов, поскольку каждая группа самостоятельно управляет чтением.

### Важный нюанс

Offset не является свойством самого Consumer-приложения навсегда.

Позиция обычно связана с Consumer Group и конкретной партицией.

Consumer может завершиться, а новый участник той же группы продолжит чтение с сохранённой позиции.

## 5. Как Consumer получает и обрабатывает сообщения?

Обычно работа Consumer выглядит так:

```text
1. Subscribe to topic
          ↓
2. Partition assignment
          ↓
3. poll()
          ↓
4. Получение сообщений
          ↓
5. Валидация
          ↓
6. Бизнес-обработка
          ↓
7. Сохранение результата
          ↓
8. Commit offset
          ↓
9. Следующий poll()
```

В реальной реализации `poll()` может вернуть целый пакет сообщений.

Кроме того, Consumer может продолжать вызовы `poll()` для поддержания работы группы, пока обработка выполняется отдельно.

Поэтому нужно понимать, какая часть сообщений уже получена, какая действительно обработана и до какой позиции безопасно выполнять commit.

### Пример

Consumer получил:

```text
Offset 100 → PaymentCompleted A
Offset 101 → PaymentCompleted B
Offset 102 → PaymentCompleted C
```

Если все три сообщения успешно обработаны последовательно, можно зафиксировать следующую позицию 103.

Но если обработка B завершилась ошибкой, а C ещё не обработано, фиксировать 103 нельзя без специальной логики, поскольку это может привести к пропуску необходимых операций после восстановления.

## 6. Auto Commit — автоматическая фиксация Offset

Kafka Consumer может периодически фиксировать позицию автоматически.

Пример конфигурации:

```properties
enable.auto.commit=true
auto.commit.interval.ms=5000
```

Это означает, что клиент будет периодически пытаться фиксировать текущую позицию чтения.

**Важно:** Auto Commit не проверяет, успешно ли завершилась бизнес-обработка каждого сообщения.

### Пример потенциальной проблемы

```text
1. Consumer получил сообщения A, B, C
2. Consumer Position переместилась вперёд
3. Приложение ещё обрабатывает сообщения
4. Срабатывает Auto Commit
5. Позиция фиксируется
6. Приложение падает до завершения обработки
```

После восстановления Consumer может продолжить чтение после уже зафиксированной позиции.

Некоторые бизнес-операции могут остаться невыполненными.

### Нюанс

Автоматическая фиксация выполняется механизмами Kafka Consumer при его работе, а не независимым процессом, который всегда коммитит offset строго каждые пять секунд.

Если приложение синхронно обрабатывает весь пакет до следующего `poll()`, риск преждевременного commit отличается от ситуации с асинхронной обработкой.

### Когда может использоваться Auto Commit?

Когда приложение допускает соответствующие риски и организация обработки корректно согласована с автоматической фиксацией.

Для критичных операций часто выбирают более явное управление прогрессом обработки.

---

## 7. Manual Commit — ручная фиксация Offset

При Manual Commit приложение самостоятельно контролирует, когда фиксировать позицию.

Конфигурация:

```properties
enable.auto.commit=false
```

Типичный процесс:

```text
poll()
  ↓
Получить событие
  ↓
Обработать бизнес-логику
  ↓
Сохранить результат в БД
  ↓
COMMIT транзакции БД
  ↓
COMMIT Kafka offset
```

Это позволяет избежать фиксации позиции до завершения бизнес-операции.

Однако остаётся важная проблема: фиксация результата в БД и фиксация offset в Kafka — две разные операции.

Между ними приложение может завершиться.

Следовательно, **Manual Commit сам по себе не обеспечивает Exactly-Once бизнес-обработку**.

## 8. CommitSync и CommitAsync

В Java Kafka Consumer API существуют два основных способа ручной фиксации.

### commitSync()

Синхронный commit.

Приложение ожидает результат операции фиксации offset.

Преимущества:

- Удобнее контролировать результат.
- Ошибки можно обработать непосредственно.
- Полезен при завершении работы и контролируемом сохранении позиции.

Недостаток:

- Может блокировать выполнение на время подтверждения.

### commitAsync()

Асинхронный commit.

Приложение отправляет запрос фиксации и продолжает выполнение, получая результат через callback.

Преимущества:

- Не нужно ожидать завершения каждого commit.
- Может снижать задержки, связанные с управлением offset.

Недостатки:

- Нужно отдельно обрабатывать ошибки.
- Сложнее организовывать безопасные повторные попытки и завершение приложения.

### Важная особенность

Если асинхронный commit завершился ошибкой, нельзя бездумно повторять фиксацию старой позиции, когда приложение уже продвинулось дальше.

Иначе можно ошибочно откатить сохранённый прогресс.

Точная организация callbacks и порядок завершения commits зависят от версии и используемого consumer group protocol.

## 9. Падение Consumer до обработки сообщения

Рассмотрим сценарий:

```text
Offset 10 → Получен Consumer
             ↓
         Consumer упал
             ↓
       Бизнес-обработка
         не выполнена
             ↓
      Offset 11 не зафиксирован
```

Если сохранённая позиция группы равна 10, новый Consumer может повторно прочитать сообщение с offset 10.

### Ожидаемый результат

При сохранности сообщения в Kafka и корректном восстановлении группа получает возможность повторной обработки.

Это типичный сценарий для At-Least-Once при commit после обработки.

**Для QA:** проверить, что приложение восстанавливается и не пропускает событие.

## 10. Падение Consumer после обработки, но до Commit Offset

Это один из самых важных сценариев для интервью.

```text
1. Consumer получает сообщение offset 10
2. Выполняет бизнес-операцию
3. Сохраняет результат в БД
4. COMMIT транзакции БД успешен
5. Consumer падает
6. Kafka offset 11 ещё не зафиксирован
```

После перезапуска Consumer может повторно получить offset 10.

Но бизнес-операция уже была выполнена.

### Какие проблемы возможны?

- Повторная выдача бонуса.
- Двойное начисление.
- Повторная отправка уведомления.
- Создание дубликата заказа.
- Повторная запись события в историю.

### Как решить проблему?

Использовать идемпотентную обработку.

Например, у события есть идентификатор:

```json
{
  "eventId": "evt-1001",
  "userId": "user-123",
  "bonusId": 500
}
```

В одной транзакции с бизнес-изменениями приложение сохраняет факт обработки `eventId`.

При повторном получении события проверяет, было ли оно уже обработано.

Если да — не выполняет бизнес-действие повторно, но может безопасно продвинуть offset.

### Главный вывод

**Коммит после обработки снижает риск пропуска операции, но допускает дубликаты обработки.**

## 11. Commit Offset до бизнес-обработки

Другой порядок:

```text
1. Consumer получает сообщение offset 10
2. Коммитит offset 11
3. Начинает бизнес-обработку
4. Consumer падает
```

После восстановления группа обычно продолжит чтение с offset 11.

Сообщение с offset 10 уже считается пройденным с точки зрения сохранённой позиции.

Однако бизнес-операция не завершилась.

### Результат

Возможен пропуск необходимой обработки.

Это характерный риск модели At-Most-Once.

### Вывод

| Порядок | Основной риск |
|---|---|
| Commit до обработки | Потеря обработки |
| Commit после обработки | Повторная обработка |
| Атомарная координация результата и позиции | Может обеспечить более сильные гарантии в пределах определённой системы |

## 12. Сравнение сценариев падения Consumer

| Момент падения | Бизнес-результат | Committed Offset | Возможный результат после восстановления |
|---|---|---|---|
| До обработки | Не сохранён | Старый | Повторное получение |
| Во время обработки до DB commit | Обычно откат | Старый | Повторное получение |
| После DB commit, до offset commit | Сохранён | Старый | Дубликат обработки |
| После offset commit, до обработки | Не сохранён | Новый | Пропуск обработки |
| После обработки и offset commit | Сохранён | Новый | Продолжение со следующей записи |

Таблица описывает типовые сценарии при корректной работе Kafka и доступности записей в пределах retention.

Она не учитывает все дополнительные механизмы вроде Kafka Transactions, Inbox, Outbox или внешнего хранения позиций.

## 13. Что происходит при Rebalance?

Rebalance — перераспределение партиций между Consumer одной группы.

Например:

```text
До:

Partition 0 → Consumer A
Partition 1 → Consumer A
Partition 2 → Consumer B
```

Consumer A завершился.

После перераспределения:

```text
Partition 0 → Consumer B
Partition 1 → Consumer B
Partition 2 → Consumer B
```

Теперь Consumer B продолжит обработку назначенных партиций.

### С какой позиции он продолжит?

Обычно с committed offset соответствующей Consumer Group.

Например:

```text
Partition 0

Последняя обработанная запись: 150
Committed Offset: 148
```

Новый Consumer может начать с 148.

Следовательно, уже обработанные записи с offset 148–150 могут поступить повторно.

### Почему это важно?

При rebalance необходимо корректно:

- Завершать обработку отзываемых партиций.
- Фиксировать безопасную позицию.
- Не допускать неконтролируемой параллельной обработки после потери назначения.
- Учитывать повторное получение сообщений.

### ConsumerRebalanceListener

В Java API предусмотрен механизм callbacks для событий назначения и отзыва партиций.

Например:

- `onPartitionsRevoked`
- `onPartitionsAssigned`

При этом порядок и характер callbacks зависят от протокола и вида перераспределения.

## 14. Что такое max.poll.interval.ms?

Это настройка, ограничивающая максимальный интервал между вызовами `poll()` при участии Consumer в управляемой группе.

Она помогает обнаруживать Consumer, который слишком долго не возвращается к чтению, например из-за зависшей бизнес-обработки.

Пример:

```properties
max.poll.interval.ms=300000
```

Это пять минут.

### Сценарий

1. Consumer получает пакет из 500 сообщений.
2. Начинает обрабатывать их последовательно.
3. Обработка занимает слишком много времени.
4. Интервал между poll превышает допустимый.
5. Consumer может потерять право на назначенные партиции.
6. Происходит перераспределение.
7. Часть сообщений может потребовать повторной обработки.

### Как уменьшить риск?

- Уменьшить `max.poll.records`.
- Сократить время обработки одного пакета.
- Использовать отдельные обработчики с корректным учётом завершённых сообщений.
- Настроить `max.poll.interval.ms` под реальные задержки.
- Корректно обрабатывать потерю назначения партиций.

**Нюанс:** при использовании static membership с `group.instance.id` поведение исключения из группы может отличаться. Также детали зависят от версии и consumer group protocol.

## 15. Heartbeat и Session Timeout

Kafka должна понимать, что Consumer остаётся активным.

### Heartbeat

Сигнал, позволяющий координатору группы контролировать присутствие Consumer.

### Session Timeout

Период, по истечении которого Consumer может считаться недоступным при отсутствии необходимых сигналов активности.

### Отличие от max.poll.interval.ms

- Session timeout связан с определением доступности участника группы.
- max.poll.interval.ms связан с тем, продолжает ли приложение вызывать poll достаточно регулярно.

Это разные механизмы, хотя оба могут повлиять на участие Consumer в группе.

**Важно:** конкретные настройки heartbeat зависят от того, используется классический или новый consumer group protocol.

## 16. auto.offset.reset

Настройка определяет поведение, когда Consumer не имеет корректной сохранённой позиции для чтения.

Основные значения:

### earliest

Начать с самой ранней доступной позиции.

### latest

Начать с конца доступного потока.

### none

Сообщить об ошибке при отсутствии подходящей позиции.

Пример:

```properties
auto.offset.reset=earliest
```

### Типичный вопрос

**Если поставить earliest, Consumer будет после каждого перезапуска читать топик с самого начала?**

Нет.

Если у Consumer Group есть корректный committed offset, он обычно используется для восстановления.

`auto.offset.reset` применяется в ситуациях отсутствия корректной позиции, например для новой группы или после удаления старых записей.

## 17. Что такое Seek?

`seek()` — операция, позволяющая Consumer явно изменить позицию чтения определённой партиции.

Например, для диагностики или повторной обработки можно перейти к конкретному offset.

В Java API:

```java
consumer.seek(
    new TopicPartition("payments", 0),
    100
);
```

После изменения позиции Consumer будет пытаться читать начиная с указанного offset.

### Зачем может понадобиться Seek?

- Повторное чтение сообщений.
- Диагностика инцидентов.
- Восстановление после ошибок.
- Специальная логика повторной обработки.
- Чтение с определённой позиции.

**Важно:** seek изменяет локальную позицию чтения, но сам по себе не выполняет commit offset группы.

## 18. Что такое Consumer Lag?

Consumer Lag отражает отставание группы от конца потока.

Упрощённая формула:

```text
Lag = Log End Offset - Committed Offset
```

Например:

```text
Log End Offset:   5000
Committed Offset: 4200

Lag = 800
```

### Почему Lag растёт?

- События публикуются быстрее, чем обрабатываются.
- Consumer недостаточно.
- Мало партиций для параллельной обработки.
- База данных медленно отвечает.
- Внешние сервисы недоступны.
- Consumer падает или часто проходит rebalance.
- Не удаётся зафиксировать прогресс обработки.

### Почему Lag не всегда равен количеству необработанных бизнес-событий?

Offset отражает позицию в журнале.

На разницу между позициями могут влиять транзакционные записи, compaction, пропуски offset и другие особенности.

Кроме того, приложение может успешно обработать сообщения, но ещё не зафиксировать offset.

Поэтому Lag следует анализировать совместно с:

- Скоростью публикации.
- Скоростью обработки.
- Временем обработки.
- Ошибками.
- Частотой rebalance.
- Фактическим состоянием бизнес-операций.

### Посмотреть группу

```bash
bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --group bonuses-service
```

Условный результат:

```text
GROUP           TOPIC       PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG
bonuses-service payments    0         150            200            50
bonuses-service payments    1         100            120            20
```

### Как читать результат?

Для Partition 0:

- Committed Offset: 150.
- Log End Offset: 200.
- Lag: 50.

Для Partition 1:

- Committed Offset: 100.
- Log End Offset: 120.
- Lag: 20.

Суммарный Lag по двум партициям — 70 offset-позиций.

### Что проверять QA?

- Есть ли участники у группы.
- Все ли партиции назначены.
- Продвигаются ли committed offsets.
- Увеличивается или уменьшается lag.
- Возникают ли частые смены участников.
- Успевает ли обработка за потоком сообщений.

## 20. Сброс Offset Consumer Group

Иногда при тестировании требуется повторно обработать сообщения.

Kafka CLI поддерживает операции изменения сохранённых позиций группы.

**Опасно:** изменение committed offsets может вызвать повторную обработку событий или пропуск части данных.

Такие действия выполняют только на разрешённых тестовых стендах.

### Посмотреть план изменения

Пример для тестовой группы:

```bash
bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --group test-group \
  --topic payments \
  --reset-offsets \
  --to-earliest \
  --dry-run
```

### Применить изменение

```bash
bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --group test-group \
  --topic payments \
  --reset-offsets \
  --to-earliest \
  --execute
```

Обычно для такой операции группа должна быть неактивна. Конкретные ограничения зависят от версии Kafka.

После сброса важно убедиться, что новые позиции применились.

## 21. Практический сценарий: выдача бонуса

Предположим, Consumer обрабатывает событие:

```json
{
  "eventId": "evt-500",
  "userId": "user-100",
  "bonusId": 777
}
```

Сообщение находится:

```text
Topic: bonuses.issue
Partition: 2
Offset: 450
```

### Позитивный сценарий

1. Consumer читает offset 450.
2. Проверяет бизнес-условия.
3. Сохраняет выдачу в БД.
4. Фиксирует транзакцию.
5. Коммитит Kafka offset 451.

Ожидаемый результат: бонус выдан, сохранён прогресс чтения.

### Ошибка до фиксации БД

1. Consumer читает offset 450.
2. Начинает выдачу.
3. БД возвращает ошибку.
4. Изменения откатываются.
5. Offset не должен быть продвинут так, чтобы необходимая обработка потерялась.

Ожидаемый результат: доступна повторная обработка либо предусмотренная процедура обработки ошибки.

### Ошибка после фиксации БД

1. Бонус успешно выдан.
2. DB COMMIT завершился.
3. Consumer падает до фиксации offset 451.
4. Новый Consumer снова получает offset 450.

Ожидаемый результат: повторная доставка не приводит к нежелательной повторной выдаче.

### Как обеспечить идемпотентность?

Один из подходов — таблица обработанных событий:

```sql
CREATE TABLE processed_events (
    event_id VARCHAR(100) PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

В одной транзакции с выдачей бонуса:

1. Регистрируем идентификатор события.
2. Выполняем бизнес-изменение.
3. Фиксируем транзакцию.

При повторной обработке уникальное ограничение помогает распознать повтор.

**Важно:** проверка существования eventId и вставка должны быть организованы без race condition. Недостаточно просто выполнить SELECT перед INSERT без атомарного контроля уникальности.

Также следует продумать срок хранения идентификаторов, допустимость повторного использования eventId и обработку нескольких версий события.

## 22. Что делать, если обработка одного сообщения завершилась ошибкой?

Предположим, Consumer получил:

```text
Offset 100 → успешно
Offset 101 → ошибка
Offset 102 → успешно
```

Можно ли просто зафиксировать offset 103?

**Не всегда.**

Если сообщение 101 обязательно должно быть обработано и не перенесено в предусмотренный надёжный механизм обработки ошибок, commit 103 может привести к его пропуску после перезапуска.

### Возможные подходы

**Retry**

Повторная обработка сообщения.

**Pause Partition**

Временно приостановить получение новых записей из конкретной партиции до разрешения проблемы.

**DLQ / DLT**

Перенести проблемное сообщение в специальный топик ошибок согласно принятой архитектуре.

**Пропуск по бизнес-правилу**

Если сообщение не требует дальнейшей обработки, зафиксировать такое решение и безопасно продвинуть позицию.

### Важный нюанс

При параллельной обработке сообщений нельзя считать завершение более поздней записи достаточным основанием для commit более поздней позиции.

Прогресс должен учитывать непрерывный диапазон сообщений, которые успешно обработаны или надёжно переданы в предусмотренный механизм обработки.

## 23. Как тестировать Offset Management?

### Тест 1. Успешная обработка

Публикуем сообщение.

Проверяем:

- Consumer выполнил бизнес-операцию.
- Committed offset продвинулся.
- После перезапуска не возникает нежелательных повторных действий.

### Тест 2. Ошибка до DB COMMIT

Создаём контролируемую ошибку в БД.

Проверяем:

- Нет частичного бизнес-результата.
- Позиция не продвинута небезопасно.
- Сообщение может быть обработано после восстановления.

### Тест 3. Падение после DB COMMIT

Имитируем сбой после успешной транзакции, но до offset commit.

Проверяем:

- Возможно повторное получение сообщения.
- Бизнес-операция не дублируется.
- Consumer корректно восстанавливает прогресс.

### Тест 4. Rebalance

Запускаем несколько Consumer в одной группе.

Останавливаем один Consumer во время обработки.

Проверяем:

- Партиции переназначены.
- Не потеряна необходимая обработка.
- Дубликаты обрабатываются корректно.
- Lag постепенно уменьшается.

### Тест 5. Новая Consumer Group

Создаём группу без committed offsets.

Проверяем её поведение при `auto.offset.reset=earliest` и `latest`.

### Тест 6. Отставание Consumer

Создаём поток событий быстрее скорости обработки.

Проверяем:

- Рост Lag.
- Восстановление после снижения нагрузки.
- Отсутствие нарушения бизнес-инвариантов.
- Метрики ошибок и времени обработки.

### Тест 7. Ошибка внутри пакета

Consumer получает несколько сообщений, одно из которых завершается ошибкой.

Проверяем, что последующий commit не приводит к непредусмотренному пропуску неудачного сообщения.

## 24. Типичные вопросы на собеседовании

### 1. Что такое Offset?

Позиция сообщения внутри конкретной партиции Kafka.

### 2. Offset уникален в рамках Kafka?

Нет. Только в пределах партиции.

### 3. Чем Consumer Position отличается от Committed Offset?

Consumer Position определяет следующую позицию чтения текущего Consumer, а Committed Offset — сохранённую позицию группы для восстановления.

### 4. Почему после обработки offset 10 коммитится 11?

Потому что сохраняется позиция следующей записи.

### 5. Где Kafka хранит committed offsets?

Обычно во внутреннем топике `__consumer_offsets`.

### 6. Что произойдёт при падении Consumer до commit?

После восстановления сообщение может быть прочитано повторно с сохранённой позиции.

### 7. Что произойдёт, если DB COMMIT успешен, а Kafka commit не выполнен?

Сообщение может поступить повторно, хотя бизнес-операция уже выполнена.

### 8. Можно ли потерять обработку сообщения при Auto Commit?

Да, если позиция зафиксирована до завершения необходимой бизнес-обработки.

### 9. Гарантирует ли Manual Commit отсутствие дубликатов?

Нет. Между сохранением бизнес-результата и фиксацией offset возможен сбой.

### 10. Чем commitSync отличается от commitAsync?

Первый ожидает завершения фиксации, второй работает асинхронно.

### 11. Что такое Rebalance?

Перераспределение партиций между Consumer одной группы.

### 12. Откуда новый Consumer продолжит чтение после Rebalance?

Обычно с committed offset соответствующей группы и партиции.

### 13. Что такое Consumer Lag?

Отставание зафиксированной позиции группы от конца потока.

### 14. Что делает auto.offset.reset?

Определяет начальную позицию при отсутствии корректного сохранённого offset.

### 15. Что такое seek?

Операция явного изменения локальной позиции чтения Consumer.

### 16. Что такое max.poll.interval.ms?

Максимально допустимый интервал между вызовами poll для управляемого Consumer.

### 17. Как избежать пропуска сообщения при ошибке в середине пакета?

Не фиксировать позицию дальше необработанного обязательного сообщения, пока оно не обработано либо не передано надёжно в предусмотренный механизм обработки ошибок.

### 18. Может ли Consumer обрабатывать одно сообщение несколько раз?

Да, особенно при повторной доставке после сбоя до фиксации offset.

### 19. Как обеспечить идемпотентность Consumer?

Например, сохранять уникальный идентификатор обработанного события в одной транзакции с бизнес-изменениями и корректно обрабатывать дубликаты.

### 20. Как проверить корректность управления offset?

Создавать контролируемые сбои до и после бизнес-фиксации, проверять состояние БД, committed offset, восстановление обработки и отсутствие нежелательных повторных эффектов.

## 25. Типичные ошибки на собеседовании

**Ошибка:** «Commit Offset означает, что сообщение успешно обработано».

Правильно: commit означает сохранение позиции чтения. Kafka сама не проверяет успешность внешней бизнес-операции.

**Ошибка:** «Если Consumer вызвал poll, все сообщения уже обработаны».

Правильно: poll только предоставляет записи приложению. Обработка происходит отдельно.

**Ошибка:** «При Manual Commit сообщения не дублируются».

Правильно: сбой между бизнес-операцией и commit offset способен привести к повторной обработке.

**Ошибка:** «При Rebalance новый Consumer продолжает со следующего после последнего обработанного сообщения».

Правильно: обычно он продолжает с сохранённого committed offset, который может отставать от фактической бизнес-обработки.

**Ошибка:** «Auto Commit фиксирует offset каждые пять секунд независимо от работы Consumer».

Правильно: фиксация связана с работой клиентского Consumer и его вызовами poll.

**Ошибка:** «Lag всегда равен точному количеству необработанных событий».

Правильно: Lag отражает разницу позиций и не обязательно точно показывает число незавершённых бизнес-операций.

**Ошибка:** «earliest означает чтение всех сообщений с начала после каждого запуска».

Правильно: при наличии корректного committed offset группа использует его.
