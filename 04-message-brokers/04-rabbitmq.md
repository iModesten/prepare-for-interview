# RabbitMQ — архитектура, очереди, маршрутизация и обработка сообщений

## 1. Что такое RabbitMQ?

**RabbitMQ** — брокер сообщений, позволяющий приложениям обмениваться данными асинхронно.

Отправитель (Producer/Publisher) публикует сообщение, RabbitMQ маршрутизирует его в подходящие очереди, а получатели (Consumers) обрабатывают сообщения из этих очередей.

RabbitMQ часто используется для:

- Асинхронного выполнения задач.
- Интеграции микросервисов.
- Обработки заказов и платежей.
- Отправки уведомлений.
- Фоновых операций.
- Распределения задач между обработчиками.

### Краткий ответ для собеседования

> RabbitMQ — брокер сообщений, позволяющий организовать асинхронное взаимодействие приложений. Producer публикует сообщения в Exchange, который по правилам маршрутизации направляет их в одну или несколько очередей. Consumer получает сообщения из очереди и подтверждает их обработку через acknowledgement. RabbitMQ поддерживает разные типы Exchange, повторную доставку, маршрутизацию ошибок и отказоустойчивые очереди.

---

## 2. Основные компоненты RabbitMQ

| Компонент | Назначение |
|---|---|
| Producer / Publisher | Отправляет сообщения |
| Exchange | Маршрутизирует сообщения |
| Queue | Хранит сообщения до доставки и подтверждения обработки |
| Binding | Связь Exchange с очередью |
| Routing Key | Ключ маршрутизации сообщения |
| Consumer | Получает сообщения |
| Connection | Сетевое соединение клиента с брокером |
| Channel | Логический канал внутри соединения |
| ACK | Подтверждение доставки/обработки со стороны Consumer |
| NACK / Reject | Отрицательное подтверждение |
| DLX | Exchange для dead-letter сообщений |
| DLQ | Очередь проблемных сообщений |

### Общая архитектура

```text
       Producer
           |
           | Publish message
           v
        Exchange
           |
           | Routing rules
           |
      +----+----+
      |         |
      v         v
    Queue A   Queue B
      |         |
      v         v
  Consumer A Consumer B
```

**Главное отличие от Kafka:** в традиционной модели RabbitMQ Producer обычно публикует в Exchange, который маршрутизирует сообщения в очереди. В Kafka Producer публикует в Topic, разделённый на Partition.

---

## 3. Exchange — точка маршрутизации

**Exchange** — компонент RabbitMQ, который принимает сообщения от Producer и решает, в какие очереди их направить.

Exchange сам по себе обычно не является хранилищем сообщений, ожидающих обработки. Хранение обеспечивают очереди и другие соответствующие типы ресурсов.

Маршрутизация зависит от:

- Типа Exchange.
- Routing Key сообщения.
- Bindings между Exchange и очередями.
- Дополнительных правил и аргументов.

Основные типы Exchange:

1. Direct.
2. Fanout.
3. Topic.
4. Headers.

### Важный вопрос

**Может ли одно сообщение попасть в несколько очередей?**

Да. Exchange может маршрутизировать публикацию в несколько очередей, если их bindings соответствуют правилам маршрутизации.

Это позволяет нескольким сервисам независимо обрабатывать одно событие.

---

## 4. Direct Exchange

**Direct Exchange** направляет сообщение в очереди, binding key которых точно совпадает с routing key сообщения.

### Пример

```text
                    Direct Exchange
                       payments
                           |
             +-------------+-------------+
             |                           |
       key: completed               key: failed
             |                           |
             v                           v
      completed.queue               failed.queue
```

Producer публикует:

```text
Exchange: payments
Routing Key: completed
Message: PaymentCompleted
```

Сообщение попадает в `completed.queue`.

Если Producer публикует с routing key `failed`, сообщение направляется в `failed.queue`.

### Когда используется?

Когда сообщения нужно маршрутизировать по конкретным типам событий или задач.

### Важный нюанс

Direct Exchange не означает, что сообщение всегда попадает строго в одну очередь.

Если несколько очередей имеют подходящий binding key, каждая из них может получить копию сообщения.

---

## 5. Fanout Exchange

**Fanout Exchange** направляет копию каждого сообщения во все связанные с ним очереди, игнорируя routing key.

### Пример

```text
                  Fanout Exchange
                    user.events
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
      analytics       emails         audit
       .queue         .queue         .queue
```

Producer публикует событие:

```json
{
  "eventType": "UserRegistered",
  "userId": "123"
}
```

Все три очереди получают свою копию.

### Где используется?

- Уведомление нескольких сервисов.
- Рассылка событий.
- Аудит.
- Аналитика.
- Pub/Sub сценарии.

### Важный вопрос

**Если три Consumer читают одну очередь, каждый получит одно и то же сообщение?**

Обычно нет.

Если три Consumer подключены к одной классической очереди, сообщения распределяются между ними.

Но если три очереди связаны с Fanout Exchange, в каждую очередь поступает собственная копия.

---

## 6. Topic Exchange

**Topic Exchange** маршрутизирует сообщения по шаблону routing key.

Routing key обычно состоит из сегментов, разделённых точками.

Примеры:

```text
payment.created
payment.completed
payment.failed
order.created
order.cancelled
```

Используются wildcard-символы:

| Символ | Значение |
|---|---|
| `*` | Ровно один сегмент |
| `#` | Ноль или больше сегментов |

### Пример

Binding:

```text
payment.*
```

Подходят:

```text
payment.created
payment.failed
payment.completed
```

Не подходит:

```text
payment.refund.completed
```

Другой binding:

```text
payment.#
```

Подходят:

```text
payment
payment.created
payment.refund.completed
```

### Пример маршрутизации

```text
                  Topic Exchange
                       events
                         |
        +----------------+----------------+
        |                |                |
    payment.*        order.*           *.failed
        |                |                |
        v                v                v
  payment.queue     order.queue       errors.queue
```

Событие `payment.failed` попадёт в две очереди:

- `payment.queue`.
- `errors.queue`.

### Когда используется?

Когда необходимо гибко маршрутизировать события по категориям.

---

## 7. Headers Exchange

**Headers Exchange** маршрутизирует сообщения по заголовкам вместо обычного routing key.

Например, сообщение содержит:

```text
type = payment
region = eu
```

Правила binding могут учитывать значения этих заголовков.

Часто используются условия:

- `x-match = all` — должны совпасть все указанные условия.
- `x-match = any` — достаточно одного совпадения.

### Когда полезен?

Когда маршрутизация зависит от нескольких независимых атрибутов сообщения.

На собеседовании обычно достаточно знать принцип работы.

---

## 8. Default Exchange

RabbitMQ имеет встроенный Default Exchange.

Это Direct Exchange с пустым именем:

```text
""
```

При создании очереди RabbitMQ автоматически связывает её с Default Exchange по имени очереди.

Поэтому можно публиковать сообщение практически напрямую в очередь.

Например:

```text
Exchange: ""
Routing Key: notifications.queue
```

Сообщение будет направлено в очередь `notifications.queue`, если она существует.

**Важно:** технически сообщение всё равно проходит через Exchange.

---

## 9. Queue — очередь

**Queue** — ресурс RabbitMQ, в котором сообщения ожидают доставки и подтверждения обработки.

В традиционной модели очередей:

1. Producer публикует сообщение.
2. Exchange направляет его в очередь.
3. RabbitMQ доставляет его Consumer.
4. Consumer обрабатывает сообщение.
5. Consumer отправляет ACK.
6. RabbitMQ удаляет подтверждённую запись из очереди.

### Ready и Unacked

В интерфейсе RabbitMQ можно увидеть:

**Ready**

Сообщения, ожидающие доставки Consumer.

**Unacked**

Сообщения, которые уже доставлены, но ещё не подтверждены.

### Пример

```text
Queue: payments.queue

Ready:   100
Unacked:  20
Total:   120
```

Это означает, что 100 сообщений ожидают доставки, а 20 уже переданы Consumer и ожидают acknowledgement.

### Вопрос на собеседовании

**Что означает большое количество Unacked?**

Возможные причины:

- Медленная обработка.
- Зависшие Consumer.
- Слишком высокий prefetch.
- Недоступность БД или другого сервиса.
- Ошибки в логике ACK.

---

## 10. Несколько Consumer одной очереди

Это одна из наиболее важных особенностей RabbitMQ.

Предположим:

```text
                   Queue
              payments.queue
                    |
          +---------+---------+
          |         |         |
          v         v         v
      Consumer A Consumer B Consumer C
```

Все три Consumer читают **одну очередь**.

В обычной модели competing consumers RabbitMQ распределяет доставки между ними.

Например:

```text
Message 1 → Consumer A
Message 2 → Consumer B
Message 3 → Consumer C
Message 4 → Consumer A
```

Это иллюстрация. Реальное распределение зависит от доступности Consumer, prefetch, скорости обработки и других факторов.

### Получит ли каждый Consumer все сообщения?

Нет. В обычной модели каждая доставка назначается одному Consumer.

Однако при отсутствии ACK и повторной доставке одно сообщение может позднее получить другой Consumer.

### Как сделать, чтобы каждый сервис получил событие?

Нужно создать отдельные очереди для независимых подписчиков и связать их с подходящим Exchange.

Например:

```text
                   Exchange
                       |
        +--------------+--------------+
        |              |              |
        v              v              v
    bonus.queue    email.queue   analytics.queue
        |              |              |
        v              v              v
    Bonus Service   Email Service   Analytics
```

Каждый сервис получает собственную копию маршрутизированного события.

## 11. Acknowledgement — подтверждение обработки

**Acknowledgement (ACK)** — механизм, позволяющий Consumer сообщить RabbitMQ, что доставленное сообщение можно считать успешно принятым и больше не нужно удерживать для повторной доставки в этой очереди.

### Auto ACK

При автоматическом подтверждении RabbitMQ считает доставку подтверждённой без ожидания завершения бизнес-обработки.

Если Consumer упадёт после доставки, но до завершения операции, сообщение может быть потеряно для обработки.

### Manual ACK

Consumer явно подтверждает сообщение после выполнения необходимой работы.

Типичная последовательность:

```text
1. RabbitMQ доставляет сообщение
2. Consumer выполняет бизнес-логику
3. Consumer сохраняет результат
4. Consumer отправляет ACK
5. RabbitMQ удаляет подтверждённую запись
```

### Пример

```text
Получено PaymentCompleted
          ↓
Проверка сообщения
          ↓
Обновление заказа в БД
          ↓
DB COMMIT
          ↓
basic.ack
```

### Что произойдёт, если Consumer упадёт до ACK?

При потере канала или соединения неподтверждённое сообщение обычно возвращается для повторной доставки, если очередь и сообщение доступны.

Это создаёт риск дубликатов обработки.

### Краткий ответ для собеседования

> ACK — подтверждение доставки со стороны Consumer. При Manual ACK приложение отправляет подтверждение после необходимой обработки. Если Consumer завершится до ACK, RabbitMQ может доставить сообщение повторно. Поэтому для критичных операций обычно применяют Manual ACK вместе с идемпотентной бизнес-логикой.

## 12. ACK, NACK и Reject

В AMQP 0-9-1 используются:

### basic.ack

Положительное подтверждение.

Сообщение считается подтверждённым и может быть удалено из очереди.

### basic.nack

Отрицательное подтверждение.

Позволяет отклонить одно или несколько доставленных сообщений и указать, следует ли возвращать их в очередь.

### basic.reject

Отклонение одного сообщения.

Поддерживает признак `requeue`.

### Requeue = true

Сообщение возвращается для повторной доставки.

```text
Consumer получил сообщение
          ↓
Ошибка обработки
          ↓
basic.nack(requeue=true)
          ↓
Сообщение снова доступно для доставки
```

### Requeue = false

Сообщение не возвращается в исходную очередь.

В зависимости от конфигурации оно может быть направлено через Dead Letter Exchange или удалено.

### Важный нюанс

ACK и NACK используют delivery tag, который имеет значение в пределах конкретного Channel.

Нельзя корректно подтвердить доставку через произвольный другой Channel.

## 13. Что такое Prefetch?

**Prefetch** — ограничение количества сообщений, доставленных Consumer, но ещё не подтверждённых.

Например:

```text
prefetch = 10
```

Consumer может иметь до 10 неподтверждённых доставок в рамках соответствующих правил QoS.

Когда лимит достигнут, RabbitMQ не будет отправлять ему новые сообщения, пока часть предыдущих не будет подтверждена.

### Пример

```text
Consumer A
├── Message 1 — Unacked
├── Message 2 — Unacked
├── Message 3 — Unacked
├── Message 4 — Unacked
└── Message 5 — Unacked
```

При prefetch = 5 дальнейшая доставка приостанавливается до освобождения места.

### Зачем нужен Prefetch?

- Ограничивать нагрузку на Consumer.
- Избегать чрезмерного накопления сообщений в памяти приложения.
- Регулировать число сообщений в обработке.
- Улучшать распределение работы между обработчиками.

### Слишком маленький Prefetch

Может ограничивать производительность, если Consumer часто ожидает сеть или БД.

### Слишком большой Prefetch

Может приводить к:

- Большому количеству Unacked.
- Повышенному потреблению памяти.
- Неравномерному распределению.
- Большому количеству повторных доставок при падении Consumer.

**Нюанс RabbitMQ:** для AMQP 0-9-1 RabbitMQ обычно применяет prefetch count отдельно к каждому Consumer, если используется соответствующий режим basic.qos. Это отличается от некоторых трактовок лимита на Channel в других реализациях AMQP.

## 14. Redelivery — повторная доставка

RabbitMQ может повторно доставить сообщение, если предыдущая доставка не была успешно подтверждена.

Например:

```text
1. Consumer A получил Message 100
2. Выполнил запись в БД
3. DB COMMIT успешен
4. Consumer A упал до ACK
5. RabbitMQ повторно доставил Message 100
6. Consumer B получил сообщение
```

### Что произойдёт без идемпотентности?

Бизнес-операция может выполниться дважды.

Например:

- Два начисления бонуса.
- Два платежа.
- Два уведомления.
- Два заказа.

### Как защищаться?

- Уникальный eventId.
- Таблица обработанных событий.
- Уникальные ограничения БД.
- Идемпотентные бизнес-операции.
- Атомарная фиксация eventId и результата.

### Redelivered Flag

AMQP-доставка может содержать флаг `redelivered`.

Он сообщает, что сообщение потенциально уже доставлялось раньше.

**Важно:** этот флаг не является надёжным идентификатором дубликата бизнес-события. Нельзя строить полноценную идемпотентность только на нём.

## 15. Retry — повторная обработка

Если Consumer не смог обработать сообщение, система может попытаться повторить операцию.

### Пример

```text
Message
   ↓
Consumer
   ↓
Database unavailable
   ↓
Retry
   ↓
Database available
   ↓
Success + ACK
```

### Основные подходы

**Immediate Requeue**

Вернуть сообщение в очередь для быстрой повторной доставки.

Недостаток: возможно бесконечное быстрое повторение при постоянной ошибке.

**Delayed Retry**

Повторить обработку через определённое время.

**Exponential Backoff**

Увеличивать задержку между попытками.

**Limited Attempts**

Ограничить количество попыток.

### Почему нельзя бесконечно делать NACK с requeue=true?

Может возникнуть цикл:

```text
Получение
   ↓
Ошибка
   ↓
NACK requeue=true
   ↓
Получение
   ↓
Ошибка
   ↓
...
```

Это создаёт нагрузку на RabbitMQ, приложение и зависимости.

Для постоянных ошибок лучше предусмотреть ограничение попыток, задержку и обработку проблемных сообщений.

## 16. Dead Letter Exchange и Dead Letter Queue

**Dead Letter Exchange (DLX)** — Exchange, через который RabbitMQ может перенаправлять сообщения, исключённые из исходной очереди по определённым причинам.

**Dead Letter Queue (DLQ)** — обычная очередь, используемая для хранения таких сообщений.

### Когда сообщение может попасть в DLX?

Например:

- Consumer отклонил сообщение с `requeue=false`.
- Истёк TTL сообщения.
- Превышен лимит длины очереди при определённой политике.
- Для Quorum Queue превышен delivery limit.

### Пример

```text
                  Main Exchange
                       |
                       v
                   Main Queue
                       |
                       v
                    Consumer
                       |
                    Failure
                       |
               NACK requeue=false
                       |
                       v
                Dead Letter Exchange
                       |
                       v
                     DLQ
```

### Зачем нужна DLQ?

- Изоляция проблемных сообщений.
- Анализ причин ошибок.
- Возможность повторной обработки после исправления.
- Предотвращение бесконечных циклов retry.

### Важный нюанс

DLQ — не отдельный особый тип очереди. Обычно это стандартная очередь, назначенная для получения сообщений через DLX.

Также перенос в DLQ не гарантирует абсолютной сохранности. Надёжность зависит от типа очереди и конфигурации dead-lettering.

Quorum Queues поддерживают специальные механизмы at-least-once dead-lettering.

---

## 17. TTL — Time To Live

**TTL** — время жизни сообщения или срок, применяемый к сообщениям в очереди.

Например:

```text
message TTL = 60000 ms
```

Это одна минута.

После истечения TTL сообщение может быть удалено из очереди либо направлено через DLX, если он настроен.

### Для чего используют TTL?

- Удаление устаревших задач.
- Ограничение срока хранения сообщений.
- Реализация некоторых схем отложенного retry.
- Контроль накопления сообщений.

### Retry через TTL и DLX

Пример:

```text
Main Queue
    |
    v
Consumer
    |
  Error
    |
    v
Retry Queue (TTL)
    |
  TTL expired
    |
    v
Main Exchange
    |
    v
Main Queue
```

Это один из вариантов отложенной повторной обработки.

### Важный нюанс

TTL не следует воспринимать как точный таймер запуска задачи.

Фактический момент удаления или dead-lettering может зависеть от реализации очереди и её состояния.

## 18. Durable Queue и Persistent Message

Эти понятия часто путают.

### Durable Queue

Очередь объявлена как durable, то есть её определение должно сохраняться при перезапуске брокера в рамках гарантий используемого типа очереди.

### Persistent Message

Сообщение публикуется с режимом, предполагающим сохранение на диск согласно возможностям RabbitMQ и очереди.

### Почему нужны оба механизма?

Durable Queue сама по себе не означает, что все опубликованные в неё сообщения обязательно переживут сбой.

И persistent message без подходящей надёжной очереди и подтверждения публикации также не даёт полной гарантии.

Для критичных сообщений обычно рассматривают:

- Durable Queue.
- Persistent Messages.
- Publisher Confirms.
- Репликацию и подходящий тип очереди.
- Manual Consumer ACK.

### Вопрос на собеседовании

**Если очередь Durable, сообщения гарантированно не потеряются?**

Нет. Надёжность зависит от всех этапов: публикации, маршрутизации, хранения, отказоустойчивости и подтверждения обработки.

---

## 19. Publisher Confirms

**Publisher Confirms** позволяют Publisher получать подтверждение от RabbitMQ о принятии сообщения в рамках гарантий брокера и используемого типа очереди.

### Зачем нужны?

Представим:

1. Producer отправил сообщение.
2. Соединение оборвалось.
3. Producer не знает, сохранил ли RabbitMQ сообщение.

Publisher Confirms помогают контролировать результат публикации.

### Важный нюанс

Подтверждение Publisher означает, что RabbitMQ принял ответственность за публикацию в соответствии со своими гарантиями.

Оно **не означает**, что Consumer обработал сообщение.

### Что делать при потере подтверждения?

Publisher может повторить отправку.

Но если первая публикация была успешной, а ответ потерялся, повтор может привести к дубликату.

Поэтому при критичных бизнес-операциях также важна идемпотентность получателей.

---

## 20. Classic Queue и Quorum Queue

RabbitMQ поддерживает разные типы очередей.

### Classic Queue

Традиционный тип очереди RabbitMQ.

Подходит для различных рабочих нагрузок, где не требуется модель репликации Quorum Queue.

### Quorum Queue

Реплицируемая очередь, основанная на консенсусном механизме Raft.

Разработана для сценариев, где важны отказоустойчивость и сохранность данных.

### Основные отличия

| Характеристика | Classic Queue | Quorum Queue |
|---|---|---|
| Основное назначение | Общие задачи очередей | Критичные и отказоустойчивые задачи |
| Репликация через Raft | Нет | Да |
| Требования к ресурсам | Обычно ниже | Обычно выше |
| Majority / Quorum | Нет аналогичной модели | Используется |
| Delivery limit | Зависит от прикладной реализации | Поддерживается встроенный механизм |

### Пример

Quorum Queue имеет три реплики.

Если один узел становится недоступным, оставшиеся две реплики могут сохранить кворум и продолжить обслуживание.

Если большинство реплик потеряно, очередь может стать недоступной.

**Важно:** Quorum Queue сама по себе не обеспечивает exactly-once бизнес-обработку.

---

## 21. Порядок сообщений в RabbitMQ

Очередь имеет порядок постановки сообщений, однако фактический порядок завершения обработки зависит от конфигурации.

Например:

```text
Queue: A → B → C
```

При одном Consumer с последовательной обработкой и подходящим prefetch проще сохранить порядок бизнес-операций.

Но при нескольких Consumer:

```text
Message A → Consumer 1 (обрабатывает 5 секунд)
Message B → Consumer 2 (обрабатывает 1 секунду)
```

B может завершиться раньше A.

### Что может нарушить ожидаемый порядок обработки?

- Несколько Consumer.
- Параллельная обработка.
- Повторная доставка.
- Requeue.
- Разная продолжительность операций.

### Single Active Consumer

RabbitMQ поддерживает режим Single Active Consumer, при котором в каждый момент доставку сообщений выполняет один активный Consumer очереди.

Это может быть полезно для сценариев, где нужна последовательная обработка и управляемое переключение между Consumer.

Но приложение всё равно должно учитывать повторные доставки и корректность бизнес-операций.

## 22. Kafka vs RabbitMQ

Важно сравнивать классические RabbitMQ Queues и Kafka Topics.

| Критерий | RabbitMQ Queues | Apache Kafka |
|---|---|---|
| Основная модель | Очереди и маршрутизация | Распределённый журнал событий |
| Публикация | Через Exchange | В Topic |
| Распределение | Exchange → Queue | Topic → Partition |
| Consumer | Получает доставки из очереди | Читает записи партиций |
| Подтверждение | ACK / NACK | Commit Offset |
| После обработки | ACK позволяет удалить сообщение из очереди | Запись остаётся согласно retention |
| Повторное чтение истории | Не является обычной моделью очереди | Поддерживается через offset |
| Параллелизм | Несколько Consumer одной очереди | Партиции распределяются в Consumer Group |
| Маршрутизация | Direct, Topic, Fanout, Headers | Ключи, партиции, отдельные топики |
| Повторная доставка | При отсутствии ACK и других условиях | При восстановлении со старого offset |
| Типичные сценарии | Задачи, команды, маршрутизация | Потоки событий, интеграция, аналитика |

### Главное архитектурное отличие

**RabbitMQ Queue** обычно ориентирована на передачу работы получателю с подтверждением обработки.

**Kafka Topic** представляет сохраняемый поток записей, который разные группы могут читать независимо со своих позиций.

Но это не абсолютное различие между всеми возможностями продуктов: RabbitMQ также поддерживает Streams, а Kafka можно использовать для распределённой обработки задач.

## 23. Отличие Consumer Kafka от Consumer RabbitMQ

Это один из наиболее вероятных вопросов технического интервью.

### RabbitMQ

```text
Queue
  |
  v
Consumer получает доставку
  |
  v
Обрабатывает сообщение
  |
  v
ACK
  |
  v
Сообщение удаляется из очереди
```

Consumer работает с доставками и подтверждает их через ACK.

RabbitMQ контролирует, какие сообщения находятся в состоянии Ready и Unacked.

### Kafka

```text
Topic / Partition
       |
       v
Consumer poll()
       |
       v
Бизнес-обработка
       |
       v
Commit Offset
       |
       v
Позиция чтения сохраняется
```

Consumer отслеживает позицию чтения в партиции.

Kafka хранит записи независимо от того, прочитала ли их группа.

### Почему Kafka Consumer иногда называют «умным», а RabbitMQ Consumer — «более простым»?

Это неофициальное упрощение.

В Kafka клиенту доступна явная модель управления позицией, чтением и повторным проигрыванием журнала.

В RabbitMQ классическая очередь управляет состояниями сообщений Ready/Unacked, а Consumer подтверждает либо отклоняет конкретные доставки.

Но это **не означает**, что RabbitMQ Consumer не может содержать сложную бизнес-логику или что Kafka Consumer всегда самостоятельно управляет всем без участия брокера.

### Краткий ответ для собеседования

> В RabbitMQ классический Consumer получает сообщения из очереди и подтверждает их через ACK, после чего брокер может удалить сообщение из очереди. В Kafka Consumer читает записи из партиций и управляет позицией через offset; прочитанные сообщения остаются в Kafka согласно retention. Внутри Consumer Group Kafka партиции распределяются между участниками, а в RabbitMQ несколько Consumer одной очереди конкурируют за доставки сообщений.

## 24. Практический пример: несколько очередей и Consumer

Предположим, имеется сервис заказов.

При создании заказа публикуется:

```json
{
  "eventId": "evt-500",
  "orderId": 100,
  "userId": 200
}
```

Exchange:

```text
orders.events
```

Тип:

```text
topic
```

Настроены очереди:

```text
notifications.queue
analytics.queue
bonus.queue
```

Binding:

```text
notifications.queue → order.created
analytics.queue     → order.#
bonus.queue         → order.created
```

При публикации с routing key:

```text
order.created
```

Сообщение будет направлено во все три очереди.

### Consumer

```text
notifications.queue
    ├── Consumer N1
    └── Consumer N2

analytics.queue
    └── Consumer A1

bonus.queue
    ├── Consumer B1
    ├── Consumer B2
    └── Consumer B3
```

### Как будет работать обработка?

**Notifications**

N1 и N2 распределяют между собой доставки из одной очереди.

**Analytics**

A1 самостоятельно обрабатывает сообщения из своей очереди.

**Bonus**

B1, B2 и B3 конкурируют за доставки из bonus.queue.

Таким образом, одно логическое событие попадёт в каждую из трёх очередей, но внутри конкретной очереди его обычная доставка назначается одному Consumer.

При ошибках и повторной доставке сообщение может попасть другому Consumer той же очереди.

## 25. Как тестировать RabbitMQ-интеграции?

### Маршрутизация

- [ ] Сообщение попадает в нужную очередь.
- [ ] Direct Exchange правильно сопоставляет Routing Key.
- [ ] Topic Exchange правильно обрабатывает `*` и `#`.
- [ ] Fanout рассылает сообщения во все связанные очереди.
- [ ] Неподходящие сообщения не попадают в лишние очереди.
- [ ] Корректно обрабатываются unroutable messages.

### Consumer

- [ ] Успешно обрабатывает сообщение.
- [ ] Отправляет ACK после необходимой обработки.
- [ ] Корректно обрабатывает ошибки.
- [ ] Повторная доставка не создаёт нежелательных дубликатов.
- [ ] Несколько Consumer правильно распределяют работу.
- [ ] Остановка Consumer не приводит к потере неподтверждённых сообщений при предусмотренных гарантиях.

### Retry и DLQ

- [ ] Работает заданное количество повторов.
- [ ] Соблюдаются задержки между попытками.
- [ ] Постоянно ошибочные сообщения попадают в DLQ.
- [ ] Нет бесконечного быстрого цикла retry.
- [ ] После исправления причины возможна повторная обработка.
- [ ] Не теряются сообщения при dead-lettering в пределах выбранных гарантий.

### Отказоустойчивость

- [ ] Durable Queue сохраняется после перезапуска.
- [ ] Persistent Messages сохраняются согласно требованиям.
- [ ] Publisher Confirms правильно обрабатываются.
- [ ] При потере Consumer неподтверждённые сообщения повторно доставляются.
- [ ] Quorum Queue корректно ведёт себя при отказе узла.
- [ ] Система восстанавливает обработку после временной недоступности RabbitMQ.

### Производительность

- [ ] Контролируется количество Ready.
- [ ] Контролируется количество Unacked.
- [ ] Prefetch соответствует требованиям.
- [ ] Обработчики успевают за входящим потоком.
- [ ] Нет неограниченного накопления сообщений.
- [ ] Нет чрезмерного потребления памяти Consumer.

## 26. RabbitMQ Management UI

RabbitMQ предоставляет Management UI при включённом соответствующем плагине.

В нём можно анализировать:

- Exchanges.
- Queues.
- Bindings.
- Connections.
- Channels.
- Consumers.
- Ready / Unacked.
- Скорость публикации и доставки.
- Состояние очередей.

### Что полезно QA?

При проблеме с сообщением последовательно проверить:

1. Успешно ли Producer опубликовал сообщение.
2. Существует ли нужный Exchange.
3. Совпадает ли Routing Key с Bindings.
4. Попало ли сообщение в Queue.
5. Есть ли активные Consumer.
6. Растёт ли Ready.
7. Растёт ли Unacked.
8. Возникают ли повторные доставки.
9. Появляется ли сообщение в DLQ.

### Важный нюанс

Ручное получение сообщений через UI может изменять их состояние в зависимости от выбранного режима подтверждения.

На общих стендах следует избегать действий, которые могут удалить или подтвердить чужие сообщения.

## 27. Типичные вопросы на собеседовании

### 1. Что такое RabbitMQ?

Брокер сообщений для асинхронного обмена между приложениями.

### 2. Что такое Exchange?

Компонент, который маршрутизирует опубликованные сообщения в связанные очереди по установленным правилам.

### 3. Какие типы Exchange ты знаешь?

Direct, Fanout, Topic, Headers.

### 4. Чем Direct отличается от Topic?

Direct использует точное совпадение Routing Key, а Topic — сопоставление с шаблоном.

### 5. Чем Fanout отличается от Direct?

Fanout направляет копию сообщения во все связанные очереди, игнорируя Routing Key.

### 6. Что такое Binding?

Связь Exchange с очередью или другим поддерживаемым назначением, определяющая правила маршрутизации.

### 7. Что такое Routing Key?

Ключ, передаваемый Publisher и используемый Exchange для выбора маршрута сообщения.

### 8. Получат ли два Consumer одной очереди каждое сообщение?

В обычной модели competing consumers — нет. Сообщения распределяются между ними.

### 9. Как отправить одно событие нескольким сервисам?

Создать отдельные очереди сервисов и связать их с подходящим Exchange.

### 10. Что такое ACK?

Подтверждение доставки Consumer, после которого RabbitMQ может удалить подтверждённую запись из очереди.

### 11. Что произойдёт, если Consumer упадёт до ACK?

При обычном Manual ACK неподтверждённое сообщение после потери соединения или канала может быть повторно доставлено.

### 12. Чем ACK отличается от NACK?

ACK подтверждает доставку, NACK позволяет отклонить сообщение и при необходимости запросить повторную доставку.

### 13. Что такое Prefetch?

Ограничение числа неподтверждённых сообщений, которые RabbitMQ может доставить Consumer согласно настройкам QoS.

### 14. Что означают Ready и Unacked?

Ready — сообщения в ожидании доставки. Unacked — доставленные, но ещё не подтверждённые.

### 15. Что такое DLQ?

Очередь для сообщений, которые не удалось обработать в обычном потоке.

### 16. Что такое DLX?

Exchange, через который RabbitMQ маршрутизирует dead-letter сообщения.

### 17. Что такое TTL?

Время жизни сообщения или правило срока его хранения в очереди.

### 18. Что такое Publisher Confirms?

Подтверждения от брокера о принятии публикации в рамках выбранных гарантий.

### 19. Гарантирует ли Publisher Confirm успешную обработку Consumer?

Нет. Это разные механизмы подтверждения.

### 20. Чем Durable Queue отличается от Persistent Message?

Durable относится к сохранению определения очереди, persistent — к режиму хранения сообщения.

### 21. Что такое Quorum Queue?

Реплицируемая очередь RabbitMQ, основанная на консенсусе Raft.

### 22. Может ли RabbitMQ доставить сообщение дважды?

Да. Например, если Consumer выполнил бизнес-операцию, но не отправил ACK до потери соединения.

### 23. Как избежать двойной обработки?

Использовать идемпотентную бизнес-логику, eventId, уникальные ограничения и транзакционную регистрацию обработанных событий.

### 24. Чем Consumer RabbitMQ отличается от Consumer Kafka?

RabbitMQ Consumer подтверждает доставки через ACK. Kafka Consumer читает партиции и фиксирует позиции через offset.

### 25. Когда использовать Kafka, а когда RabbitMQ?

RabbitMQ удобен для очередей задач и гибкой маршрутизации через Exchanges. Kafka особенно подходит для сохраняемых потоков событий, независимых групп потребителей и повторного чтения истории. Выбор зависит от требований к обработке, масштабированию и хранению данных.

## 28. Частые ошибки на собеседовании

**Ошибка:** «Producer RabbitMQ всегда отправляет сообщения напрямую в Queue».

Правильно: в AMQP 0-9-1 публикация проходит через Exchange, включая встроенный Default Exchange.

**Ошибка:** «Direct Exchange может направлять сообщение только в одну очередь».

Правильно: несколько очередей с подходящими Bindings могут получить копии.

**Ошибка:** «Если подключены три Consumer, каждое сообщение получат все трое».

Правильно: если они читают одну обычную очередь, доставки распределяются между ними.

**Ошибка:** «После получения сообщения Consumer RabbitMQ сразу удаляет его».

Правильно: при Manual ACK сообщение сохраняет состояние неподтверждённой доставки до ACK или другого разрешения.

**Ошибка:** «ACK гарантирует успешное сохранение в БД».

Правильно: RabbitMQ доверяет подтверждению Consumer и сам не проверяет результат внешней БД.

**Ошибка:** «NACK всегда направляет сообщение в DLQ».

Правильно: это зависит от requeue и настроек DLX.

**Ошибка:** «Durable Queue гарантирует полное отсутствие потери сообщений».

Правильно: нужны дополнительные механизмы и подходящие гарантии публикации и хранения.

**Ошибка:** «RabbitMQ гарантирует exactly-once бизнес-обработку».

Правильно: повторная доставка возможна; однократный бизнес-эффект требует дополнительной защиты.

**Ошибка:** «Kafka и RabbitMQ отличаются только скоростью».

Правильно: у них различаются модели хранения, распределения обработки, подтверждения и маршрутизации.
