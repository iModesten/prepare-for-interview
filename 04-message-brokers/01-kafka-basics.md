# Apache Kafka — основы и архитектура

## 1. Что такое Kafka?

**Apache Kafka** — распределённая платформа потоковой передачи событий (Distributed Event Streaming Platform).

Kafka позволяет приложениям публиковать, хранить и читать потоки событий. Её часто используют для асинхронного взаимодействия микросервисов, интеграции систем и обработки больших потоков данных.

Пример использования:

1. Пользователь совершает платёж.
2. Сервис платежей публикует событие `PaymentCompleted`.
3. Сервис бонусов получает событие и начисляет бонусы.
4. Сервис уведомлений отправляет уведомление.
5. Сервис аналитики обновляет статистику.

Все сервисы могут обрабатывать одно событие независимо.

### Краткий ответ для собеседования

> Kafka — распределённая платформа для обмена и обработки потоков событий. Producer публикует сообщения в топики, а Consumer читает их из партиций. Kafka хранит сообщения независимо от факта их прочтения, поддерживает масштабирование через партиции, репликацию для отказоустойчивости и Consumer Groups для распределения обработки.

### Где используется Kafka?

- Асинхронное взаимодействие микросервисов.
- Event-driven архитектура.
- Обработка финансовых событий.
- Передача данных между системами.
- Сбор логов и событий.
- Аналитика в реальном времени.
- CDC (Change Data Capture).
- Потоковая обработка данных.

## 2. Основные компоненты Kafka

| Компонент | Назначение |
|---|---|
| Broker | Сервер Kafka, хранящий сообщения и обслуживающий запросы |
| Cluster | Группа брокеров Kafka |
| Topic | Именованный поток сообщений |
| Partition | Упорядоченная часть топика |
| Producer | Приложение, отправляющее сообщения |
| Consumer | Приложение, читающее сообщения |
| Consumer Group | Группа потребителей, распределяющая чтение партиций |
| Offset | Позиция сообщения внутри партиции |
| Replication Factor | Количество копий партиции |
| Leader | Реплика партиции, обслуживающая основные операции чтения и записи |
| Follower | Реплика, копирующая данные лидера |

### Упрощённая архитектура

```text
                    PRODUCERS
                 /      |      \
                v       v       v

                KAFKA CLUSTER
        +-----------------------------+
        |        Topic: payments      |
        |                             |
        | Partition 0: [0][1][2][3]  |
        | Partition 1: [0][1][2][3]  |
        | Partition 2: [0][1][2][3]  |
        +-----------------------------+
                   |           |
                   v           v
             Consumer      Consumer
                 A             B
                    GROUP 1

                   |
                   v
            Consumer Group 2
              (Analytics)
```

Один топик может одновременно использоваться несколькими независимыми Consumer Groups.

## 3. Broker и Kafka Cluster

**Broker** — отдельный сервер Kafka, который хранит данные партиций и обслуживает клиентские запросы.

**Kafka Cluster** — набор брокеров, работающих совместно.

Например:

```text
Kafka Cluster
├── Broker 1
├── Broker 2
└── Broker 3
```

Партиции и их реплики распределяются между брокерами.

Это позволяет:

- Распределять нагрузку.
- Увеличивать ёмкость хранения.
- Обеспечивать отказоустойчивость.
- Масштабировать обработку данных.

### Что произойдёт при падении брокера?

Если у партиции есть синхронизированные реплики на других брокерах, одна из них может стать новым лидером.

Если подходящей реплики нет, партиция может временно стать недоступной.

**Важно:** наличие нескольких брокеров не гарантирует отсутствие потери данных. Гарантии зависят от репликации, подтверждений записи и настроек кластера.

---

## 4. Topic — топик

**Topic** — именованный поток сообщений определённого назначения.

Примеры:

```text
payments.completed
orders.created
bonuses.issued
users.updated
```

Producer отправляет сообщения в топик, а Consumer подписывается на него.

### Важная особенность Kafka

Kafka не удаляет сообщение сразу после того, как Consumer его прочитал.

Сообщения сохраняются согласно политикам хранения — например, по времени, размеру лога или правилам compaction.

Это позволяет:

- Повторно прочитать события.
- Восстановить состояние системы.
- Подключить новую группу потребителей.
- Повторно обработать историю событий, если данные ещё сохранены.

**Отличие от классической очереди:** чтение сообщения само по себе не удаляет его из топика.

---

## 5. Partition — партиция

**Partition** — упорядоченная последовательность сообщений внутри топика.

Топик может состоять из одной или нескольких партиций.

Пример:

```text
Topic: payments

Partition 0:
Offset:  0    1    2    3
        [A]  [B]  [C]  [D]

Partition 1:
Offset:  0    1    2
        [E]  [F]  [G]

Partition 2:
Offset:  0    1    2
        [H]  [I]  [J]
```

Каждая партиция имеет собственную последовательность offset.

### Для чего нужны партиции?

**Масштабирование**

Несколько Consumer могут параллельно обрабатывать разные партиции.

**Распределение данных**

Партиции можно размещать на разных брокерах.

**Сохранение порядка**

Kafka поддерживает порядок записей внутри одной партиции.

### Гарантии порядка

Kafka не гарантирует общий порядок сообщений между разными партициями.

Например:

```text
Partition 0: A → B → C
Partition 1: D → E → F
```

Порядок A, B, C сохраняется внутри первой партиции.

Но Kafka не гарантирует, что сообщение B будет обработано раньше E.

Также порядок записи в партицию не гарантирует завершение бизнес-обработки в том же порядке, если приложение само обрабатывает записи асинхронно и параллельно.

### Вопрос на собеседовании

**Почему Kafka использует партиции?**

> Партиции позволяют распределять данные и нагрузку между брокерами, а также параллельно обрабатывать сообщения разными Consumer. При этом порядок сообщений обеспечивается в пределах отдельной партиции, а не всего топика.

## 6. Message Key — ключ сообщения

Kafka-сообщение может содержать:

- Key.
- Value.
- Headers.
- Timestamp.
- Topic.
- Partition.
- Offset.

Пример логического события:

```json
{
  "eventId": "event-123",
  "paymentId": "payment-456",
  "userId": "user-789",
  "amount": 100,
  "status": "COMPLETED"
}
```

Producer может отправить его с ключом:

```text
key = user-789
```

### Зачем нужен Key?

Ключ часто используется для определения партиции.

При стандартном key-based partitioning одинаковый сериализованный ключ обычно направляется в одну и ту же партицию, пока количество партиций и алгоритм распределения остаются неизменными.

Это полезно для сохранения порядка событий одной сущности.

Например:

```text
Key = user-1

Event 1: BonusIssued
Event 2: BonusUsed
Event 3: BonusExpired
```

Если все события пользователя попадают в одну партицию, их порядок записи сохраняется.

### Что будет без Key?

Producer может выбирать партицию автоматически, распределяя сообщения в зависимости от стратегии partitioner.

Не стоит рассчитывать, что события одной сущности окажутся в одной партиции без соответствующей настройки.

### Важный нюанс

Увеличение количества партиций может изменить распределение ключей. Поэтому одинаковый ключ не обязательно навсегда закреплён за одним номером партиции.

## 7. Offset — смещение сообщения

**Offset** — числовая позиция записи внутри конкретной партиции.

Например:

```text
Topic: payments
Partition: 0

Offset 0 → PaymentCreated
Offset 1 → PaymentConfirmed
Offset 2 → PaymentCompleted
Offset 3 → PaymentRefunded
```

Offset уникален в пределах партиции, но не всего Kafka-кластера.

Два сообщения в разных партициях могут иметь одинаковый offset.

### Что важно понимать?

Offset позволяет Consumer определять свою позицию чтения.

Например, если Consumer зафиксировал offset 5 как позицию следующей записи, это обычно означает, что сообщения до этой позиции считаются обработанными с точки зрения управления offset.

### Current Position и Committed Offset

Это разные понятия.

**Current Position** — позиция, с которой Consumer собирается продолжить чтение.

**Committed Offset** — сохранённая позиция группы, используемая для возобновления чтения, например после перезапуска или перераспределения партиций.

Consumer может прочитать несколько сообщений, но ещё не зафиксировать новую позицию.

### Пример

```text
Partition 0:

Offset:       0   1   2   3   4   5
Message:     [A] [B] [C] [D] [E] [F]

Read:         ✓   ✓   ✓   ✓
Processed:    ✓   ✓   ✓
Committed next offset: 3
Current position: 4
```

В этом примере сообщения 0–2 обработаны, сообщение 3 прочитано, но ещё не обработано.

После восстановления с committed offset 3 Consumer может повторно получить сообщение 3.

### Где Kafka хранит committed offsets?

При обычной работе Consumer Groups зафиксированные offset хранятся в служебном топике:

```text
__consumer_offsets
```

В нём Kafka хранит сведения о позициях потребительских групп и связанные метаданные.

**Важно:** в пользовательском приложении также возможны другие способы хранения позиции, но стандартный механизм Consumer Groups использует Kafka.

### Краткий ответ для собеседования

> Offset — числовая позиция записи внутри партиции Kafka. Consumer использует offset для отслеживания чтения сообщений. При commit offset группа сохраняет позицию, с которой можно продолжить потребление после перезапуска или rebalance. Offset сам по себе не доказывает, что бизнес-операция успешно завершена.

## 8. Producer — отправитель сообщений

**Producer** — приложение, которое публикует сообщения в Kafka.

Пример:

```text
Payment Service
       |
       | PaymentCompleted
       v
Topic: payments.completed
```

Producer отвечает за:

- Формирование сообщения.
- Выбор топика.
- Сериализацию key и value.
- Определение партиции.
- Отправку в Kafka.
- Обработку результата публикации.
- Повторные попытки при ошибках.

### Основные настройки Producer

**acks**

Определяет, какие подтверждения записи ожидает Producer.

| Значение | Смысл |
|---|---|
| 0 | Не ждать подтверждения от брокера |
| 1 | Ждать подтверждения лидера |
| all / -1 | Ждать подтверждения согласно требованиям к синхронизированным репликам |

`acks=all` обычно даёт более сильные гарантии, но зависит также от `min.insync.replicas` и других настроек.

**retries**

Позволяет повторять отправку при определённых ошибках.

**enable.idempotence**

Включает идемпотентный режим Producer, который помогает предотвращать дубликаты записи, возникающие при повторных попытках отправки в рамках поддерживаемых гарантий.

**delivery.timeout.ms**

Ограничивает время, в течение которого Producer пытается доставить запись.

### Важный нюанс

Успешная запись сообщения в Kafka ещё не означает, что какой-либо Consumer его обработал.

Это отдельные этапы системы.

---

## 9. Consumer — получатель сообщений

**Consumer** — приложение, которое читает записи из Kafka.

Обычно Consumer:

1. Подписывается на топик.
2. Получает назначенные партиции.
3. Вызывает `poll()` для получения записей.
4. Обрабатывает сообщения.
5. При необходимости фиксирует offset.
6. Продолжает чтение.

Упрощённая последовательность:

```text
poll()
   |
   v
Read message
   |
   v
Validate
   |
   v
Business logic
   |
   v
Database update
   |
   v
Commit offset
```

Порядок обработки и фиксации offset непосредственно влияет на семантику доставки и риск дублирования либо потери обработки.

### Может ли Consumer читать одно сообщение несколько раз?

Да.

Например:

1. Consumer получил сообщение.
2. Успешно изменил БД.
3. Упал до фиксации offset.
4. После восстановления сообщение прочитывается снова.

Поэтому обработчик должен учитывать повторную доставку.

---

## 10. Consumer Group — группа потребителей

**Consumer Group** — набор Consumer, которые совместно обрабатывают партиции подписанных топиков.

Consumer с одинаковым `group.id` входят в одну группу.

В классической модели Consumer Groups одна партиция в каждый момент назначена одному Consumer внутри группы.

### Пример: 3 партиции и 3 Consumer

```text
Topic: payments
  Partition 0 ── Consumer A
  Partition 1 ── Consumer B
  Partition 2 ── Consumer C

          Group: payments-service
```

Каждый Consumer обрабатывает свою партицию.

### 3 партиции и 2 Consumer

```text
Partition 0 ── Consumer A
Partition 1 ── Consumer A
Partition 2 ── Consumer B
```

Один Consumer может обрабатывать несколько партиций.

### 3 партиции и 5 Consumer

```text
Partition 0 ── Consumer A
Partition 1 ── Consumer B
Partition 2 ── Consumer C

Consumer D ── No partition
Consumer E ── No partition
```

Если группа подписана только на этот топик, двум Consumer не достанется партиций.

### Что это означает для масштабирования?

В классической модели Consumer Groups число одновременно активных владельцев партиций одного топика не может превышать число его партиций.

Добавление Consumer сверх количества партиций не увеличит параллелизм обработки этого топика.

### Важное уточнение

В новых версиях Kafka существуют также share groups с другой моделью распределения записей. Но для стандартного собеседования обычно обсуждают классическую модель Consumer Groups, описанную выше.

## 11. Несколько Consumer Groups

Предположим, один топик `payments.completed` читают три сервиса:

```text
                  payments.completed
                         |
             +-----------+-----------+
             |           |           |
             v           v           v
          Group A      Group B      Group C
          Bonuses      Analytics    Notifications
```

Каждая Consumer Group независимо отслеживает свои позиции чтения.

Поэтому одно событие может быть обработано:

- Сервисом бонусов.
- Сервисом аналитики.
- Сервисом уведомлений.

При этом данные в топике не нужно копировать для каждой группы.

### Вопрос на собеседовании

**Чем отличаются два Consumer в одной группе от двух Consumer в разных группах?**

> Consumer внутри одной группы распределяют между собой партиции и совместно обрабатывают поток. Consumer в разных группах независимо читают сообщения согласно собственным позициям. Поэтому одно событие может быть обработано каждой группой.

## 12. Rebalance — перераспределение партиций

**Rebalance** — процесс изменения назначения партиций между Consumer одной группы.

Он может происходить, когда:

- Consumer присоединяется к группе.
- Consumer выходит из группы.
- Consumer перестаёт отвечать.
- Изменяется количество партиций.
- Изменяется подписка группы.

### Пример

Изначально:

```text
Partition 0 → Consumer A
Partition 1 → Consumer A
Partition 2 → Consumer B
```

Consumer A перестаёт работать.

После перераспределения:

```text
Partition 0 → Consumer B
Partition 1 → Consumer B
Partition 2 → Consumer B
```

Теперь Consumer B продолжает чтение всех трёх партиций.

### Почему Rebalance важен?

Во время перераспределения:

- Часть обработки может временно задерживаться.
- Могут меняться владельцы партиций.
- Необработанные или незафиксированные записи могут поступить повторно.
- Приложение должно корректно завершать работу с отзываемыми партициями.

### Eager и Cooperative Rebalance

В классических протоколах встречаются две стратегии:

**Eager**

При перераспределении прежние назначения партиций могут массово отзываться перед новым распределением.

**Cooperative**

Предполагает более постепенное перераспределение, позволяющее уменьшить остановки обработки.

В Kafka 4.0 появился новый consumer group protocol, поддерживающий более инкрементальное перераспределение с координацией на стороне брокера.

Поэтому подробности rebalance зависят от версии Kafka, протокола и assignor.

### Практический вопрос

**Что произойдёт, если Consumer упадёт во время обработки сообщения?**

Ответ зависит от момента падения и фиксации offset.

Если бизнес-операция завершилась, но offset ещё не был зафиксирован, после перераспределения сообщение может быть обработано повторно.

Если offset зафиксирован раньше завершения бизнес-операции, есть риск пропуска необходимой обработки.

## 13. Commit Offset — фиксация позиции

Consumer должен управлять позицией, с которой группа продолжит чтение после восстановления.

### Auto Commit

При включённом автоматическом commit клиент периодически фиксирует текущую позицию в соответствии с настройками Consumer.

Пример настройки:

```properties
enable.auto.commit=true
auto.commit.interval.ms=5000
```

**Риск:** автоматическая фиксация позиции не знает, действительно ли бизнес-логика приложения успешно завершилась, особенно если обработка выполняется асинхронно после poll.

### Manual Commit

Приложение самостоятельно решает, когда фиксировать offset.

Типичная последовательность:

```text
Read
  ↓
Process
  ↓
Commit DB transaction
  ↓
Commit Kafka offset
```

В этом случае повторная обработка возможна, но риск пропуска бизнес-операции ниже при правильной реализации.

### Что именно коммитится?

Обычно фиксируется **offset следующей записи, которую необходимо прочитать**.

Например, после успешной обработки записи с offset 10 фиксируют позицию 11.

**Не следует путать:**

- Offset конкретного сообщения.
- Текущую позицию чтения Consumer.
- Committed offset группы.
- Log End Offset партиции.

## 14. Consumer Lag

**Consumer Lag** — отставание Consumer Group от конца потока сообщений.

Упрощённо:

```text
Lag = Log End Offset - Committed Offset
```

Например:

```text
Log End Offset:   1000
Committed Offset: 750

Lag: 250
```

Это означает, что согласно зафиксированной позиции группа отстаёт на 250 offset-позиций.

### Причины роста Lag

- Consumer медленно обрабатывает сообщения.
- Недостаточно Consumer или партиций.
- Ошибки при обработке.
- Частые rebalance.
- Медленная база данных.
- Недоступность внешнего сервиса.
- Высокая скорость публикации событий.

### Почему Lag важен для QA?

При нагрузочном тестировании можно проверить:

1. Как быстро растёт Lag.
2. Успевают ли Consumer обрабатывать сообщения.
3. Восстанавливается ли система после всплеска нагрузки.
4. Не появляются ли ошибки или дубликаты.
5. Как долго событие ожидает обработки.

**Важно:** Lag по offset не всегда равен точному количеству необработанных бизнес-событий. Например, отдельные offset могут отсутствовать из-за особенностей хранения, compaction и транзакционных записей.

## 15. Replication Factor, Leader и Follower

Kafka поддерживает репликацию партиций между брокерами.

Например:

```text
Partition 0
├── Broker 1 — Leader
├── Broker 2 — Follower
└── Broker 3 — Follower
```

**Replication Factor = 3**

Это означает, что для партиции предусмотрены три реплики.

### Leader

Основная реплика, обрабатывающая операции записи и обычные операции чтения.

### Follower

Копирует данные лидера.

### ISR — In-Sync Replicas

ISR — набор реплик, которые Kafka считает достаточно синхронизированными согласно правилам кластера.

### Что будет при падении Leader?

Kafka может выбрать нового лидера из подходящих реплик.

Если актуальных подходящих реплик нет, партиция может стать недоступной.

### min.insync.replicas

Определяет минимальное количество синхронизированных реплик, необходимое для успешной записи при соответствующем режиме подтверждения (`acks=all`).

Например:

```properties
replication.factor=3
min.insync.replicas=2
```

При `acks=all` успешная запись требует выполнения условия о минимальном количестве ISR.

Это помогает снизить риск потери подтверждённых сообщений при отказах.

Однако абсолютную гарантию сохранности независимо от любых сбоев такая конфигурация не даёт.

---

## 16. Retention — хранение сообщений

В Kafka сообщения обычно хранятся независимо от того, прочитали ли их Consumer.

Срок хранения определяется конфигурацией топика.

### Time-based Retention

Данные хранятся ограниченное время.

Например:

```properties
retention.ms=604800000
```

Это соответствует семи дням.

### Size-based Retention

Kafka может удалять старые сегменты лога при превышении настроенного объёма.

### Log Compaction

При compaction Kafka сохраняет актуальные значения для ключей согласно правилам очистки лога.

Это полезно, например, для восстановления последнего известного состояния сущностей.

**Нюанс:** compacted topic не означает, что в каждый момент физически хранится строго одна запись на каждый ключ. Очистка происходит асинхронно.

### Что произойдёт, если Consumer долго не работает?

Если сообщения успеют выйти за пределы retention, Consumer может потерять возможность прочитать старые события из Kafka.

Поведение при отсутствии сохранённого offset или выходе позиции за допустимый диапазон зависит от настроек, в частности `auto.offset.reset`.

---

## 17. auto.offset.reset — откуда начинать чтение?

Настройка определяет поведение Consumer при отсутствии корректной начальной позиции, например если для группы нет сохранённого offset.

Основные значения:

| Значение | Поведение |
|---|---|
| earliest | Начинать с самой ранней доступной позиции |
| latest | Начинать с конца доступного потока |
| none | Сообщать об ошибке при отсутствии позиции |

Например, существует топик с 1000 сообщениями.

Создаём новую Consumer Group.

При `earliest` группа начнёт с самых ранних ещё доступных сообщений.

При `latest` — с конца потока, ожидая новые сообщения.

**Важно:** настройка `auto.offset.reset` не означает, что Consumer каждый раз при перезапуске начинает с начала или конца. Если существует корректный committed offset, обычно используется он.

## 18. Гарантии доставки и обработки сообщений

На собеседовании часто спрашивают три модели:

### At-most-once

Сообщение обрабатывается не более одного раза.

Возможна потеря необходимой обработки.

### At-least-once

Обработка выполняется как минимум один раз при соблюдении предпосылок надёжной доставки и восстановления.

Возможны повторы.

### Exactly-once

Результат обработки должен проявляться ровно один раз в пределах определённых гарантий системы.

В Kafka существуют транзакционные механизмы и Exactly-Once Semantics для определённых сценариев обработки потоков.

Однако это **не гарантирует автоматически**, что внешняя база данных, HTTP-сервис или платёжная система выполнит бизнес-операцию ровно один раз.

Для таких случаев могут потребоваться:

- Идемпотентные Consumer.
- Уникальные ограничения.
- Inbox pattern.
- Transactional Outbox.
- Координация сохранения данных и позиции обработки.

**Подробный разбор этих гарантий, включая сценарии падения Consumer, вынесем в отдельный файл `03-delivery-semantics.md`.**

## 19. Kafka CLI — полезные команды для QA

Примеры ниже предполагают доступ к Kafka и наличие CLI-скриптов.

### Посмотреть список топиков

```bash
bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --list
```

### Посмотреть информацию о топике

```bash
bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --topic payments.completed
```

Можно увидеть:

- Количество партиций.
- Replication Factor.
- Leader каждой партиции.
- Реплики.
- ISR.

### Читать сообщения из топика

```bash
bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic payments.completed \
  --from-beginning
```

Команда пытается читать с начала доступной истории, но фактическое поведение зависит от используемой группы и её сохранённой позиции.

### Отправить тестовое сообщение

```bash
bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic payments.completed
```

После запуска можно вводить сообщения в консоль.

### Посмотреть Consumer Groups

```bash
bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --list
```

### Посмотреть состояние группы

```bash
bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --group payments-service
```

В выводе обычно доступны:

- TOPIC.
- PARTITION.
- CURRENT-OFFSET.
- LOG-END-OFFSET.
- LAG.
- CONSUMER-ID.

### Почему эти команды полезны QA?

Они позволяют:

- Проверить наличие событий.
- Диагностировать отставание обработки.
- Убедиться в правильном количестве партиций.
- Проверить распределение Consumer.
- Найти проблемы с обработкой сообщений.

**Осторожно:** сброс offset группы, удаление топиков и отправка тестовых событий могут влиять на работу системы. Такие действия выполняют только в разрешённой среде.

## 20. Практический пример: система бонусов

Предположим, сервис платежей публикует событие:

```json
{
  "eventId": "evt-1001",
  "userId": "user-123",
  "paymentId": "payment-456",
  "amount": 250,
  "currency": "BYN"
}
```

Топик:

```text
payments.completed
```

Ключ:

```text
user-123
```

Сервис бонусов подписан на топик через Consumer Group:

```text
bonus-service
```

### Обычный сценарий

1. Producer публикует событие.
2. Kafka записывает его в партицию.
3. Consumer получает событие.
4. Проверяет данные и бизнес-условия.
5. Начисляет бонус.
6. Сохраняет результат.
7. Фиксирует offset.

### Что проверять QA?

**Позитивные сценарии**

- Событие корректно получено.
- Бонус начислен правильному пользователю.
- Сумма рассчитана корректно.
- Состояние сохранено в БД.

**Повторная доставка**

- То же событие получено повторно.
- Бонус не начисляется второй раз, если это одна логическая операция.

**Ошибка при обработке**

- База данных временно недоступна.
- Consumer не должен безвозвратно пропустить событие, требующее обработки.

**Падение Consumer**

- Consumer завершился после изменения БД, но до фиксации offset.
- После восстановления сообщение может быть доставлено повторно.
- Повторная обработка не должна нарушать бизнес-инварианты.

**Порядок сообщений**

- Для одного пользователя поступают связанные события.
- Необходимо проверить, что архитектура и обработчик обеспечивают требуемый бизнес-порядок.

**Рост Lag**

- При большом потоке платежей Consumer начинает отставать.
- Проверяем корректность обработки накопленных событий после снижения нагрузки.

## 21. Типичные вопросы на собеседовании

### 1. Что такое Kafka?

Распределённая платформа потоковой передачи событий для публикации, хранения и чтения сообщений.

### 2. Что такое Topic?

Именованный поток сообщений, состоящий из одной или нескольких партиций.

### 3. Что такое Partition?

Упорядоченная часть топика, позволяющая распределять данные и параллелить обработку.

### 4. Что такое Offset?

Позиция записи внутри конкретной партиции.

### 5. Уникален ли Offset во всей Kafka?

Нет. Он уникален в пределах партиции.

### 6. Что такое Consumer Group?

Группа Consumer, совместно распределяющих обработку партиций.

### 7. Что произойдёт, если Consumer больше, чем партиций?

В классической модели внутри одной группы часть Consumer останется без назначенных партиций этого топика.

### 8. Что такое Rebalance?

Перераспределение партиций между Consumer группы.

### 9. Что происходит при падении Consumer?

После обнаружения сбоя его партиции могут быть назначены другим участникам группы.

### 10. Может ли Kafka доставить сообщение повторно?

Да. Например, после сбоя до фиксации offset.

### 11. Что такое Consumer Lag?

Отставание позиции потребительской группы от конца потока.

### 12. Где хранятся committed offsets?

Обычно во внутреннем топике `__consumer_offsets`.

### 13. Зачем нужен Message Key?

В частности, для управления распределением сообщений по партициям и обеспечения порядка записей одной сущности.

### 14. Гарантирует ли Kafka порядок сообщений?

Внутри одной партиции — порядок записей. Глобального порядка между партициями нет.

### 15. Что такое Replication Factor?

Количество реплик партиции.

### 16. Чем Leader отличается от Follower?

Leader обслуживает основные операции с партицией, а Follower реплицирует её данные.

### 17. Что такое ISR?

Набор реплик, считающихся достаточно синхронизированными.

### 18. Чем Auto Commit отличается от Manual Commit?

При Auto Commit клиент автоматически фиксирует позицию, а при Manual Commit приложение управляет этим самостоятельно.

### 19. Удаляется ли сообщение после чтения Consumer?

Нет. Оно сохраняется согласно политике retention или compaction.

### 20. Как протестировать Kafka-интеграцию?

Проверить публикацию, структуру события, обработку, итоговые изменения данных, дубликаты, ошибки, повторы, порядок и восстановление после сбоев.

## 22. Частые ошибки на собеседовании

**Ошибка:** «Offset — это количество сообщений, обработанных Consumer».

Правильно: offset — позиция в партиции. Фиксация позиции не доказывает успешную бизнес-обработку.

**Ошибка:** «Все Consumer одного топика получают все сообщения».

Правильно: это зависит от Consumer Groups. Внутри одной классической группы партиции распределяются между участниками.

**Ошибка:** «Если Consumer прочитал сообщение, Kafka удаляет его».

Правильно: сообщения сохраняются независимо от чтения согласно политике хранения.

**Ошибка:** «Kafka гарантирует порядок сообщений во всём топике».

Правильно: порядок гарантируется внутри партиции.

**Ошибка:** «Если Producer получил подтверждение, значит Consumer обработал событие».

Правильно: подтверждение Producer относится к записи в Kafka, а не к обработке Consumer.

**Ошибка:** «Manual Commit полностью исключает дубликаты».

Правильно: при сбое после бизнес-обработки, но до фиксации offset возможно повторное чтение.

**Ошибка:** «Если Consumer упал, сообщение обязательно потеряется».

Правильно: Kafka хранит сообщения независимо от Consumer, и при сохранности данных и доступной позиции чтение может возобновиться.
