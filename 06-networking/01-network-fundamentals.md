## 1. Зачем QA нужны сетевые основы?

Допустим, клиент вызывает `GET https://api.example.com/bonuses`, но запрос не работает.

В зависимости от причины:
- Имя сервера может не преобразоваться в IP-адрес.
- До нужного IP может не быть маршрута.
- Firewall может блокировать TCP-соединение.
- TLS-сертификат может быть неправильным.
- Reverse Proxy может не суметь подключиться к Backend.
- Backend может вернуть HTTP 500, хотя с сетью всё нормально.

Если понимать устройство сети, проще определить, **к какому компоненту идти с проблемой и что сначала проверить**.

## 2. Модель OSI: семь уровней

**OSI** — учебная модель, которая помогает разделить сетевое взаимодействие на семь уровней. Это полезная схема для объяснения, но реальные протоколы не всегда строго помещаются в одну ячейку.

| Уровень | Название | За что отвечает, простыми словами | Примеры |
|---|---|---|---|
| 7 | Прикладной (Application) | Правила обмена данными между приложениями | HTTP, DNS, SMTP |
| 6 | Представления (Presentation) | Представление и преобразование данных | Кодировки, форматы данных |
| 5 | Сеансовый (Session) | Управление сеансами взаимодействия | Управление сессиями как понятие |
| 4 | Транспортный (Transport) | Передача данных между конечными участниками, порты | TCP, UDP |
| 3 | Сетевой (Network) | Доставка пакетов между сетями | IP, ICMP, маршрутизация |
| 2 | Канальный (Data Link) | Доставка кадров в пределах одного сетевого сегмента | Ethernet, MAC-адреса |
| 1 | Физический (Physical) | Передача сигналов | Кабель, оптика, радиосигнал |

**Что достаточно знать QA:** уверенно объяснять уровни 7, 4, 3 и 2, иметь общее представление об остальных.

### На каком уровне находится TLS?

На практике TLS защищает данные между приложением и транспортом (например, между HTTP и TCP). Его иногда относят к уровню представления OSI, но это упрощение. **Не стоит выдавать такое сопоставление за строгое правило.**

### Вопрос на собеседовании

**На каком уровне работают HTTP, TCP и IP?**

Короткий ответ: HTTP — прикладной, TCP — транспортный, IP — сетевой. В модели OSI это уровни 7, 4 и 3.

## 3. Модель TCP/IP и отличие от OSI

Модель **TCP/IP** ближе к тому, как обычно описывают работу интернета.

| TCP/IP | Пример | Примерное соответствие OSI |
|---|---|---|
| Прикладной | HTTP, DNS | 5–7 |
| Транспортный | TCP, UDP | 4 |
| Интернет | IP, ICMP | 3 |
| Канальный / доступ к сети | Ethernet, Wi-Fi | 1–2 |

**Разница:** OSI делит взаимодействие на семь уровней, а модель TCP/IP обычно описывают четырьмя. При этом конкретные реализации и учебные материалы могут немного отличаться.

### Что говорить на интервью

> OSI — модель из семи уровней для понимания сетевого взаимодействия. TCP/IP — более практическая модель стека протоколов интернета. Например, HTTP относится к прикладному уровню, TCP — к транспортному, IP — к интернет-уровню.

## 4. Что такое инкапсуляция?

**Инкапсуляция** — когда данные одного уровня передаются внутри данных следующего уровня.

Упрощённый пример для HTTP/1.1 поверх TLS и TCP:

```text
HTTP request
    ↓
TLS: защищает HTTP-данные
    ↓
TCP: передаёт поток байтов, использует порты
    ↓
IP: добавляет адреса отправителя и получателя
    ↓
Ethernet/Wi-Fi: передаёт кадры по локальному участку сети
    ↓
Физическая передача
```

На другой стороне информация обрабатывается в обратном порядке.

Важно:
- Один HTTP-запрос **не обязан** помещаться в один TCP-сегмент.
- Один TCP-сегмент **не обязан** совпадать с одним IP-пакетом или одним кадром.
- TCP передаёт поток байтов, а не отдельные HTTP-сообщения.
- HTTP/3 работает иначе: использует QUIC поверх UDP.

**Зачем QA это знать?** Чтобы не путать потерю сетевого пакета с ошибкой HTTP. Потеря может быть обработана транспортным протоколом, а приложение даже не узнает о ней напрямую — но заметит задержку.

## 5. IP-адрес, MAC-адрес и Port: в чём разница?

### IP-адрес

Используется для адресации и доставки **IP-пакетов между сетями**.

Пример: `192.168.10.20`.

### MAC-адрес

Адрес канального уровня, например Ethernet. Используется для передачи кадра в пределах конкретного канального сегмента.

Пример: `02:42:ac:11:00:02`.

**Важно:** MAC-адрес не является «глобальным адресом компьютера в интернете». При прохождении через маршрутизаторы канальные заголовки создаются заново для следующего участка пути.

### Порт

Позволяет отличить одно транспортное соединение или службу от другой на одном IP.

Например:
- `192.168.10.20:443` — возможный HTTPS endpoint.
- `192.168.10.20:5432` — возможный PostgreSQL endpoint.

### Упрощённая аналогия

- IP — адрес здания.
- Port — номер нужного кабинета.
- MAC — адрес для доставки на конкретном локальном участке пути.

Аналогия не описывает все детали, но помогает запомнить различия.

### Вопрос на собеседовании

**Почему недостаточно знать IP для подключения к PostgreSQL?**

Потому что нужно знать порт и параметры протокола, а затем пройти проверки доступа и аутентификацию. IP сам по себе не обозначает конкретную службу.

## 6. Как компьютер узнаёт MAC-адрес для отправки пакета?

В IPv4-сетях Ethernet часто используется **ARP (Address Resolution Protocol)**.

Допустим, компьютер `192.168.10.10` хочет отправить пакет на `192.168.10.20` в своей локальной подсети.

Упрощённо:
1. Компьютер определяет, что адрес назначения находится в локальной сети.
2. Узнаёт MAC-адрес назначения через ARP, если его нет в кэше.
3. Отправляет Ethernet-кадр.

Если адрес назначения **в другой сети**, компьютер отправляет кадр на MAC-адрес **следующего маршрутизатора**, а не ищет MAC далёкого сервера через ARP.

В IPv6 вместо ARP используется механизм Neighbor Discovery (NDP).

**Для QA достаточно понимать:** IP определяет логический адрес назначения, а на конкретном участке Ethernet доставка опирается на канальные адреса.

## 7. Подсеть, маска и CIDR

**Подсеть** — часть адресного пространства сети.

Запись **CIDR** показывает IP-адрес и количество бит сетевого префикса.

Пример:

```text
192.168.10.0/24
```

Здесь `/24` означает, что первые 24 бита IPv4-адреса относятся к сетевому префиксу.

Для обычной IPv4-подсети `192.168.10.0/24`:
- Адрес сети: `192.168.10.0`.
- Часто используемый диапазон адресов хостов: `192.168.10.1` – `192.168.10.254`.
- Broadcast: `192.168.10.255`.
- Маска: `255.255.255.0`.

**Примечание:** специальные случаи и правила в современных сетях могут отличаться; это типичный пример обычной IPv4 LAN.

### Почему два IP могут быть в разных подсетях?

```text
192.168.10.20/24
192.168.11.30/24
```

При такой маске это разные подсети. Чтобы обмениваться пакетами, обычно требуется маршрутизация.

### Что QA полезно знать

- `/24`, `/16`, `/32` — это длина префикса.
- Одинаковое начало IP ещё не гарантирует, что устройства в одной подсети: важна маска.
- Правила сетевого доступа нередко задаются для диапазонов CIDR.

### Частый вопрос

**В чём разница между IP `192.168.10.10/24` и `192.168.10.10/32`?**

Первый адрес задан с 24-битным префиксом (обычно описывает локальную сеть из множества адресов), второй — с 32-битным (один IPv4-адрес). Как конкретный адрес работает в системе, зависит также от маршрутов и конфигурации интерфейса.

## 8. Что такое Gateway и маршрутизация?

**Router (маршрутизатор)** пересылает IP-пакеты между сетями.

**Default Gateway** — следующий узел, которому компьютер обычно передаёт пакеты, если не нашёл более подходящего маршрута.

Пример:

```text
Ноутбук: 192.168.10.20
          |
          v
Gateway: 192.168.10.1
          |
          v
Другие сети / интернет
          |
          v
Backend server
```

### Что происходит при отправке запроса?

1. Компьютер знает IP назначения.
2. Смотрит таблицу маршрутов.
3. Выбирает интерфейс и следующий узел.
4. Передаёт пакет.
5. Маршрутизаторы по пути пересылают его дальше.

Для конкретного IP можно посмотреть выбранный маршрут командой `ip route get`. Подробности — в разделе Linux.

### Практический пример QA

API доступен в офисной сети, но недоступен дома без VPN.

Возможные причины:
- Backend находится во внутренней подсети.
- Маршрут до этой сети доступен только через VPN.
- Firewall разрешает доступ лишь определённым подсетям.
- DNS внутри VPN возвращает другие адреса.

То есть проблема может быть не в самом API.

## 9. Частные и публичные IP-адреса

Частные диапазоны IPv4, определённые для локальных сетей:

| Диапазон | Часто встречается |
|---|---|
| `10.0.0.0/8` | Корпоративные сети |
| `172.16.0.0/12` | Корпоративные и контейнерные сети |
| `192.168.0.0/16` | Домашние и офисные сети |

Обычные частные IPv4-адреса не маршрутизируются напрямую в публичном интернете.

**Важно:** не всякий адрес, который «не частный», автоматически является пригодным публичным адресом. Есть также loopback, link-local, документационные, multicast и другие специальные диапазоны.

### Для QA

Адрес `10.20.30.40` может быть доступен только из определённой сети, VPN или контейнерного окружения.

## 10. Что такое NAT?

**NAT (Network Address Translation)** — изменение IP-адресов при прохождении трафика через сетевое устройство. Часто NAT также меняет порты (NAPT/PAT).

Пример исходящего соединения:

```text
Рабочий компьютер
192.168.10.20:53000
        |
        v
Роутер / NAT
Публичный_IP:61000
        |
        v
API в интернете
```

Удалённый API обычно видит внешний адрес подключения, а не частный адрес компьютера.

### Зачем используется NAT?

Часто для выхода множества устройств с частными IPv4-адресами в интернет через один или несколько внешних адресов.

### Что такое Port Forwarding?

Правило, позволяющее направлять входящие подключения с адреса/порта NAT-устройства на внутренний endpoint.

Пример:

```text
203.0.113.10:8443  ->  192.168.10.20:443
```

Это учебные адреса из специальных диапазонов документации.

### Что QA полезно понимать?

- Сервер может видеть IP сетевого шлюза или Proxy, а не реальный IP клиента.
- IP Allowlist может зависеть от внешнего адреса NAT.
- Открытый порт на приложении сам по себе не означает доступность извне.
- Изменение сетевых правил может нарушить доступ к тестовому стенду.

## 11. Firewall: почему сеть «есть», а соединение не работает?

**Firewall** применяет правила к трафику: разрешает или блокирует соединения в соответствии с настройками.

Пример:

```text
QA-клиент  ---->  Firewall  ---->  Backend:8080
                       |
                       +--- правило запрещает TCP/8080
```

Возможны разные эффекты:
- **REJECT** — соединение явно отклоняется; часто видно Connection refused или другую явную ошибку.
- **DROP** — пакеты отбрасываются без ответа; нередко возникает timeout.

Реальный результат зависит от протокола и конфигурации.

### Полезные проверки

- Доступ разрешён именно из сети QA?
- Разрешён нужный порт и протокол?
- Правила применяются к входящему или исходящему трафику?
- Нет ли дополнительной фильтрации в облаке или Kubernetes?

**Важно:** успешный ping не доказывает, что TCP-порт доступен. И наоборот: отсутствие ответа на ping не доказывает недоступность API.

## 12. Proxy, Reverse Proxy и Load Balancer

Эти понятия часто встречаются рядом, но они не равны друг другу.

### Forward Proxy

Промежуточный сервер со стороны **клиента**.

```text
Client -> Forward Proxy -> External API
```

Может использоваться для корпоративного доступа в интернет, фильтрации и контроля исходящих запросов.

### Reverse Proxy

Промежуточный сервер со стороны **сервиса**.

```text
Client -> Reverse Proxy -> Bonus Service
```

Может:
- Принимать HTTPS.
- Отправлять запросы нужному Backend.
- Ограничивать доступ.
- Добавлять заголовки.
- Управлять таймаутами.

### Load Balancer

Распределяет трафик между несколькими доступными экземплярами приложения.

```text
               +--> Bonus Service A
Client -> LB --|
               +--> Bonus Service B
```

Один компонент (например, Nginx) может одновременно выполнять задачи Reverse Proxy и балансировки.

### Что важно для QA?

- HTTP 502/504 может сформировать Proxy, а не Backend.
- Один экземпляр Backend может работать неправильно, а другой — нормально.
- TLS может завершаться на Proxy, а дальше использоваться другое соединение.
- Проверки напрямую по IP и через публичный домен могут давать разные результаты.
- Таймауты разных компонентов могут отличаться.

---

## 13. Почему сервис работает локально, но не доступен через публичный адрес?

Возможная схема:

```text
Browser
   |
   v
DNS -> Public IP
   |
   v
Firewall / NAT / Load Balancer
   |
   v
Reverse Proxy
   |
   v
Backend
```

Если `localhost` работает, мы проверили только часть цепочки.

При недоступности снаружи нужно рассматривать:
- DNS.
- Внешний IP и маршрутизацию.
- Firewall.
- NAT и правила проброса портов.
- Балансировщик.
- Reverse Proxy.
- Адрес и порт, на котором слушает Backend.

Команды для проверки этих гипотез есть в [Linux Networking](../05-linux/04-linux-networking.md).

## 14. Latency, Bandwidth, Packet Loss и MTU

### Latency

Задержка передачи данных (в зависимости от измерения — в одну сторону или туда-обратно).

Для API обычно обсуждают время ответа в целом, но оно включает **не только сеть**, а ещё Backend, БД и другие зависимости.

### Bandwidth

Пропускная способность канала — какой объём данных потенциально может передаваться за единицу времени.

Важно не путать её с фактической скоростью передачи приложения: на неё влияют и другие ограничения.

### Packet Loss

Потеря пакетов. В TCP это может приводить к повторным передачам и росту задержек.

### MTU

**Maximum Transmission Unit** — максимальный размер пакета сетевого уровня, который можно передать через конкретный канал без необходимости разбивать его на части на соответствующем уровне.

В Ethernet распространено MTU 1500 байт, но в VPN и других сетях оно может отличаться.

### Почему это важно QA?

При неправильных настройках пути или MTU небольшие запросы иногда проходят, а более крупные — зависают или работают нестабильно.

Но это **одна из гипотез**, а не причина, которую следует угадывать без проверки.

### Чего НЕ нужно учить глубоко?

- Расчёт контрольных сумм.
- Поля всех IP- и TCP-заголовков.
- Настройку сложной маршрутизации.
- Подробности согласования MTU на разных устройствах.

Для собеседования QA обычно достаточно знать смысл и влияние этих понятий на доступность и скорость API.

## 15. Что происходит, когда пользователь открывает страницу?

Упрощённый пример HTTPS поверх TCP:

1. Браузер получает URL и определяет, какой ресурс требуется.
2. Если нужен сетевой запрос, определяет IP через DNS или другой механизм разрешения имени.
3. Выбирает сетевой маршрут.
4. Устанавливает соединение (для HTTP/1.1 или HTTP/2 обычно TCP, затем TLS).
5. Отправляет HTTP-запрос.
6. Запрос может пройти через Proxy, Load Balancer или API Gateway.
7. Backend обрабатывает запрос и при необходимости обращается к БД.
8. Клиент получает HTTP-ответ; браузер может дополнительно запрашивать CSS, JavaScript, изображения и другие ресурсы.

**Нюанс:** кэш, уже существующее соединение, HTTP/3 и особенности браузера могут менять порядок или пропускать отдельные шаги.

### Что может проверить QA?

- Правильность адреса и окружения.
- Доступность сервиса.
- HTTP-статус и контракт.
- TLS.
- Корректную обработку ошибок зависимостей.
- Различия между прямым запросом и запросом через Proxy.

## 16. Практические вопросы для собеседования

**1. Зачем нужна модель OSI?**  
Чтобы разделять сетевое взаимодействие по уровням и понимать, где может возникнуть ошибка. Это учебная модель, а не инструкция по устройству каждого современного протокола.

**2. Чем OSI отличается от TCP/IP?**  
OSI обычно описывается семью уровнями, TCP/IP — четырьмя. TCP/IP ближе к стеку протоколов, используемых в интернете.

**3. Где работают HTTP, TCP и IP?**  
HTTP — прикладной уровень, TCP — транспортный, IP — сетевой (интернет-уровень в TCP/IP).

**4. Что такое инкапсуляция?**  
Передача данных более высокого уровня внутри данных более низкого, например TCP внутри IP.

**5. Чем IP отличается от MAC?**  
IP используется для доставки между сетями, MAC — для передачи кадра на конкретном канальном участке, например Ethernet.

**6. Что такое ARP?**  
Механизм получения MAC-адреса для IPv4-адреса в локальной сети. В IPv6 используются другие механизмы, например NDP.

**7. Что такое маска подсети?**  
Она определяет, какие биты IP-адреса относятся к сетевому префиксу.

**8. Что означает /24?**  
Длина сетевого префикса — 24 бита. Для IPv4 обычная маска — 255.255.255.0.

**9. Что такое Default Gateway?**  
Следующий узел, через который отправляются пакеты, когда нет более подходящего маршрута.

**10. Что такое NAT?**  
Преобразование IP-адресов, а нередко и портов, при прохождении трафика через сетевое устройство.

**11. Что такое Private IP?**  
Адрес из выделенных частных диапазонов IPv4, используемый внутри частных сетей и не маршрутизируемый напрямую в публичном интернете.

**12. Чем Forward Proxy отличается от Reverse Proxy?**  
Forward Proxy стоит на стороне клиента, Reverse Proxy — на стороне сервиса.

**13. Что делает Load Balancer?**  
Распределяет запросы между несколькими экземплярами сервиса с учётом своей конфигурации и состояния узлов.

**14. Почему API доступен через VPN, но не без него?**  
Могут отличаться маршруты, DNS и правила доступа к внутренним адресам.

**15. Почему успешный ping не доказывает доступность API?**  
Ping обычно использует ICMP, а API работает поверх других протоколов и портов.

**16. Как Packet Loss влияет на TCP?**  
Может приводить к повторным передачам и увеличению задержки.

**17. Для чего нужен MTU?**  
Он определяет максимальный размер IP-пакета для передачи через соответствующий сетевой интерфейс/канал без превышения его ограничений.

**18. Где может возникнуть HTTP 502?**  
Часто в Gateway или Reverse Proxy, если ответ upstream непригоден. Нужно проверить источник ответа и логи промежуточного компонента.

## 17. Практические ситуации для QA

### Ситуация A. API работает только через VPN

**Что предположить:** внутренний адрес, различия в DNS, маршруты через VPN, firewall allowlist.

**Что объяснить:** даже если приложение работает, у клиента может не быть сетевого пути к нему.

### Ситуация B. Через один адрес API работает, через другой — нет

**Что предположить:** разные маршруты, NAT, Reverse Proxy, сертификат, разные экземпляры Backend, конфигурация балансировщика.

**Что объяснить:** разные адреса могут вести по разным сетевым путям и к разным экземплярам приложения.

### Ситуация C. Маленькие запросы проходят, большие зависают

**Что предположить:** ограничения тела запроса, проблемы сети/MTU, таймауты или нагрузка на Backend.

**Что объяснить:** сначала проверить HTTP-ограничения и логи, затем сетевые гипотезы; нельзя автоматически обвинять MTU.

### Ситуация D. Из контейнера нельзя подключиться к localhost:5432 на хосте

**Что объяснить:** у контейнера обычно отдельное сетевое пространство; `localhost` внутри контейнера — не `localhost` хоста. Нужно использовать правильный адрес и настройки сети.

### Ситуация E. После настройки Load Balancer ошибки стали периодическими

**Что предположить:** один из Backend-экземпляров работает неправильно, некорректная health check, разные версии приложений, проблемы с сессиями.

**Что объяснить:** периодическая ошибка может зависеть от того, на какой экземпляр попадает запрос.
