# Что происходит, когда вводишь адрес сайта в браузере?

## 1. Короткая карта процесса

Представь, что открываешь сайт впервые, соединение ещё не установлено и подходящих сохранённых ответов нет.

```text
Ты вводишь http://yandex.ru
            |
            v
Браузер разбирает URL и решает, использовать ли HTTPS
            |
            v
DNS: доменное имя -> IP-адрес
            |
            v
Сеть: маршрутизатор -> интернет -> входной сервер/CDN
            |
            v
Соединение: TCP (и TLS при HTTPS) либо QUIC для HTTP/3
            |
            v
HTTP-запрос -> HTTP-ответ (HTML или перенаправление)
            |
            v
Браузер находит и загружает CSS, JS, изображения, шрифты
            |
            v
DOM + CSSOM -> layout -> paint -> страница на экране
```

**Это логическая схема, а не точное расписание операций:** DNS может быть закэширован, соединение — переиспользовано, некоторые ресурсы — уже сохранены, а загрузка и отрисовка частично идут параллельно.

## 2. Браузер разбирает URL

**URL (Uniform Resource Locator — адрес ресурса)** состоит из нескольких частей:

```text
http://yandex.ru:80/search?text=qa#results
^^^^   ^^^^^^^^^ ^^ ^^^^^^ ^^^^^^^ ^^^^^^^
схема    хост   порт  путь  запрос  фрагмент
```

Здесь мы ввели только `http://yandex.ru`: схема — `http`, имя хоста — `yandex.ru`, путь по умолчанию — `/`, стандартный порт HTTP — 80. Если путь или порт указаны явно, браузер учитывает их.

**Фрагмент** после `#` обычно используется на стороне клиента: он не передаётся серверу в обычной строке HTTP-запроса.

Есть тонкость именно с `http://`: современные браузеры могут **обновить подключение до HTTPS** (например, благодаря HSTS или режиму HTTPS-First). Если такого обновления не случилось, HTTP-сервер часто возвращает редирект на HTTPS. Поэтому утверждать «браузер обязательно сначала отправляет запрос на порт 80» было бы неточно.

**HSTS (HTTP Strict Transport Security — строгая транспортная безопасность HTTP)** — механизм, позволяющий браузеру запомнить правило обращаться к сайту по HTTPS; правило может также поставляться через предварительно встроенный список.

## 3. DNS: как находится IP-адрес

**DNS (Domain Name System — система доменных имён)** переводит понятные человеку имена в адреса, используемые сетью.

Компьютер не отправляет IP-пакеты «на название `yandex.ru`». Ему нужен IP-адрес сервера или входного сетевого узла (например, CDN или балансировщика).

```text
yandex.ru -- DNS-запрос --> DNS-резолвер
          <-- ответ: IP ---
```

Адрес для примера может выглядеть как `203.0.113.10`. Это **зарезервированный учебный IP, не IP Яндекса**.

Как происходит поиск:

1. Проверяются доступные локальные источники: например, кэш DNS браузера/операционной системы и применимые настройки разрешения имён.
2. При необходимости запрос отправляется DNS-резолверу (часто настроен провайдером, корпоративной сетью или пользователем).
3. Если у рекурсивного резолвера тоже нет нужного ответа, он может пройти цепочку через корневые, TLD и авторитетные DNS-серверы.
4. Результат возвращается клиенту и может кэшироваться на время, ограниченное DNS TTL (Time To Live — сроком жизни записи).

**Пример из жизни:** ты знаешь название магазина, но для доставки нужен его адрес. DNS помогает получить сетевой адрес по имени.

**Для QA:** если DNS-разрешение не удалось, HTTP-ответа вроде `500` может вообще не быть — запрос ещё не дошёл до HTTP-сервера. Проверяем имя, резолвер и доступность сети отдельно от логики API.

## 4. Как запрос добирается до сервера

Получить IP недостаточно: пакеты ещё нужно доставить через сеть.

**IP (Internet Protocol — интернет-протокол)** отвечает за адресацию и передачу пакетов между сетями. **Маршрутизатор (router)** выбирает следующий участок пути.

Для домашнего подключения процесс упрощённо выглядит так:

```text
Браузер -> ОС -> домашний роутер -> провайдер -> сеть интернет
                                                    |
                                                    v
                                   сервер / CDN / балансировщик
```

На локальном участке сеть должна доставить кадр нужному соседнему устройству. Для IPv4 в Ethernet может использоваться **ARP (Address Resolution Protocol — протокол определения аппаратного адреса)**: он помогает узнать MAC-адрес локального узла, например шлюза. **MAC (Media Access Control — аппаратный адрес интерфейса в локальной сети)** нужен на конкретном канальном участке, но не является глобальным адресом сайта.

Если домашние устройства выходят в интернет через один публичный IPv4-адрес, роутер часто использует **NAT (Network Address Translation — преобразование сетевых адресов)**. Он меняет адреса и иногда порты при прохождении трафика.

**Необязательно рассказывать всё это сразу на собеседовании.** Достаточно сказать, что ОС отправляет трафик через маршрутизаторы к IP-адресу, а при уточнении объяснить ARP, MAC и NAT.

Подробности: [сетевые основы](01-network-fundamentals.md).

## 5. TCP, TLS и особенности HTTPS

### TCP: зачем нужно соединение

Для HTTP/1.1 и HTTP/2 обычно используется **TCP (Transmission Control Protocol — протокол управления передачей)**. Он обеспечивает упорядоченный поток байтов, подтверждения и повторную передачу потерянных данных.

Новый TCP-сеанс начинается с **Three-way Handshake (трёхэтапного рукопожатия)**:

```text
Клиент                                Сервер
   | -------- SYN -------------------> |
   | <------- SYN-ACK ---------------- |
   | -------- ACK -------------------> |
   |         TCP-соединение готово     |
```

- **SYN** — клиент предлагает начать соединение и синхронизировать параметры.
- **SYN-ACK** — сервер подтверждает запрос и отправляет свой SYN.
- **ACK** — клиент подтверждает ответ.

Это не обмен HTML. Это подготовка транспортного соединения.

### TLS: чем HTTPS отличается от HTTP

**TLS (Transport Layer Security — протокол защиты транспортного соединения)** используется для шифрования и защиты передаваемых данных. В привычном варианте HTTPS поверх TCP после TCP-рукопожатия выполняется TLS-рукопожатие.

Браузер проверяет сертификат и имя сайта, стороны согласуют криптографические параметры и получают ключи защищённой сессии. После этого HTTP-данные передаются по защищённому каналу.

**Простая аналогия:** TCP — надёжная доставка писем по порядку; TLS — запечатанный защищённый конверт и проверка, с кем общаемся; HTTP — содержание письма и правила формата.

**Но:** HTTP/3 использует **QUIC** поверх **UDP (User Datagram Protocol — протокол пользовательских датаграмм)**; QUIC включает защиту на базе TLS 1.3. Там нет отдельного TCP three-way handshake. Если браузер уже имеет пригодное соединение, все рукопожатия заново также не обязательны.

## 6. HTTP-запрос, сервер и ответ

**HTTP (Hypertext Transfer Protocol — протокол передачи гипертекста)** определяет структуру запросов и ответов клиента и сервера.

Упрощённо HTTP/1.1-запрос за главной страницей:

```http
GET / HTTP/1.1
Host: yandex.ru
Accept: text/html
User-Agent: ExampleBrowser/1.0
```

Что означает каждая часть:

- `GET` — просим получить ресурс, а не создать новый.
- `/` — путь к главной странице на данном хосте.
- `Host` — имя хоста; помогает серверу определить, какой сайт запрошен, если на одном адресе размещено несколько сайтов.
- `Accept` — клиент сообщает, какие типы представления ему подходят.

Запрос может попасть не сразу в приложение, а на **CDN (Content Delivery Network — сеть доставки контента)**, **Reverse Proxy (обратный прокси-сервер)** или **Load Balancer (балансировщик нагрузки)**. Эти компоненты могут обработать запрос сами либо передать его дальше.

Представим, что сервер перенаправляет HTTP на HTTPS:

```http
HTTP/1.1 301 Moved Permanently
Location: https://yandex.ru/
```

Тогда браузер получает новый адрес из `Location` и выполняет дальнейшую навигацию. На практике конкретный сайт может применять другие редиректы и адреса.

При успешной выдаче HTML ответ мог бы выглядеть так:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8

<!doctype html>
<html>
  <body><h1>Привет!</h1></body>
</html>
```

Здесь `200` — успешная обработка HTTP-запроса, `Content-Type` — тип тела ответа, а HTML — данные, которые будет разбирать браузер.

**Разница для QA:** HTTP `500` означает, что сервер или промежуточный узел вернул HTTP-ошибку. А ошибка DNS или отказ TCP-соединения может возникнуть **до появления любого HTTP-ответа**.

## 7. Откуда браузер знает про CSS, JavaScript и картинки

Это частый уточняющий вопрос. **Многие ссылки находятся прямо в HTML**, а остальные могут обнаружиться позже — в CSS и JavaScript.

Например, сервер вернул:

```html
<!doctype html>
<html lang="ru">
  <head>
    <meta charset="utf-8">
    <title>Бонусы</title>
    <link rel="stylesheet" href="/css/styles.css">
    <script src="/js/app.js" defer></script>
  </head>
  <body>
    <h1>Мои бонусы</h1>
    <img src="/img/bonus.png" alt="Бонус">
    <button id="load">Загрузить бонусы</button>
  </body>
</html>
```

Браузер видит:

- `<link rel="stylesheet">` → нужен CSS-файл `/css/styles.css`.
- `<script src="...">` → нужен JavaScript-файл `/js/app.js`.
- `<img src="...">` → нужно изображение `/img/bonus.png`.

Если документ открыт с `https://example.com/`, путь `/img/bonus.png` указывает на `https://example.com/img/bonus.png`. При абсолютном адресе вроде `https://cdn.example.com/img/bonus.png` ресурс берётся с другого хоста. **Тег `<base>`** в HTML также может повлиять на разрешение относительных URL.

Браузер загружает эти файлы дополнительными HTTP-запросами, часто параллельно. Парсер HTML и механизм предварительного обнаружения ресурсов (**preload scanner — предварительный сканер загрузок**) помогают найти ресурсы заранее.

### CSS может обнаружить ещё ресурсы

```css
@font-face {
  font-family: "BonusFont";
  src: url("/fonts/bonus.woff2") format("woff2");
}
.banner { background-image: url("/img/background.jpg"); }
```

Браузер может запросить шрифт и фоновую картинку при необходимости для отображения страницы. Значит, **не все ресурсы обязаны быть перечислены в исходном HTML**.

### JavaScript может запросить данные позже

```js
document.querySelector('#load').addEventListener('click', async () => {
  const response = await fetch('/api/bonuses');
  if (!response.ok) throw new Error('Не удалось получить бонусы');
  const bonuses = await response.json();
  console.log(bonuses);
});
```

Что произойдёт:

1. Браузер скачает `app.js`, потому что HTML содержит тег `<script>`.
2. JavaScript зарегистрирует обработчик кнопки.
3. Только после клика выполнится `fetch('/api/bonuses')`.
4. Браузер отправит HTTP-запрос к API и получит ответ (например, JSON).
5. Скрипт может изменить DOM и показать новые данные без полной перезагрузки страницы.

Этот API-запрос **вообще не был прямо указан в исходном HTML**. Его инициировал выполняющийся JavaScript.

**Что означает `defer`:** классический внешний скрипт загружается без остановки разбора HTML, а выполняется после его разбора, до события `DOMContentLoaded`. Без `defer`, `async` или специальных типов классический `<script>` может блокировать HTML-парсер. Не все файлы обязательно загружаются или исполняются в одном порядке.

## 8. Как браузер рисует страницу

Получить HTML — ещё не значит показать готовый сайт. Браузер должен построить представление документа и определить, что рисовать.

1. **DOM (Document Object Model — объектная модель документа)** — дерево элементов HTML в памяти. Например, `<h1>`, `<button>`, `<img>` становятся узлами.
2. **CSSOM (CSS Object Model — объектная модель CSS)** — представление правил стилей. Оно позволяет определить цвета, размеры и другие свойства элементов.
3. **Render Tree (дерево отображения)** — результат учёта структуры и вычисленных стилей, необходимый для последующих этапов отображения. Не каждый DOM-узел обязательно создаёт видимый объект.
4. **Layout (компоновка)** — вычисление размеров и положения элементов.
5. **Paint (отрисовка)** — создание команд рисования элементов.
6. **Compositing (композиция)** — объединение нарисованных слоёв там, где браузер использует слои.

```text
HTML --> DOM ---------+
                      +--> Render Tree --> Layout --> Paint --> Composite
CSS  --> CSSOM --------+
             ^
         CSS-файлы
```

**Пример:** HTML говорит, что у нас есть кнопка «Получить бонусы». CSS определяет её цвет и размер. Layout определяет, где она будет находиться. Paint и композиция помогают вывести её на экран.

**JavaScript** может изменить DOM, CSS-классы или данные на странице. После этого браузер может пересчитать часть компоновки или выполнить новую отрисовку.

**Необязательно ждать все картинки:** браузер может показать часть страницы раньше, а изображения и динамические блоки появятся позже. События `DOMContentLoaded` и `load` также означают разные стадии готовности.

## 9. Почему шаги могут отличаться: кэш, HTTP/3, редиректы

Эту главу стоит помнить, чтобы не отвечать на интервью слишком категорично.

| Ситуация | Что меняется |
|---|---|
| DNS-адрес уже известен | Не нужно снова выполнять полный поиск DNS |
| Подходящее соединение уже открыто | Не нужны новые TCP/TLS-рукопожатия для каждого запроса |
| Есть действительный кэш ресурса | Ресурс можно повторно использовать без полной загрузки |
| Сервер возвращает `304 Not Modified` | Браузер переиспользует ранее сохранённое тело после условного запроса |
| HTTPS-First или HSTS | Запрос может быть переведён на HTTPS до HTTP-подключения |
| Сервер возвращает `301` или `302` | Браузер делает переход на другой URL |
| Используется HTTP/3 | Транспортом служит QUIC поверх UDP, не TCP |
| Есть Service Worker (сервисный работник) | Скрипт может перехватывать запросы и отдавать кэшированные ответы |

**HTTP-кэш ≠ DNS-кэш:** первый хранит ответы на запросы ресурсов, второй — результаты разрешения имён. Не нужно смешивать их в одно понятие.

## 10. Как посмотреть процесс в DevTools

**DevTools (инструменты разработчика)** позволяют проверить происходящее в реальном браузере.

1. Открой Chrome DevTools → **Network (Сеть)**.
2. Включи **Preserve log (сохранять журнал)**, если хочешь увидеть цепочку перенаправлений.
3. Обнови страницу. Для отдельного эксперимента можно включить **Disable cache (отключить кэш)** при открытых DevTools.
4. Посмотри запрос первого документа (**Doc / Document**), его статус и заголовки `Location`, `Content-Type`, `Cache-Control`.
5. Отфильтруй **CSS**, **JS**, **Img**, **Font**, **Fetch/XHR**. Это покажет, какие файлы и данные загружались.
6. Открой **Initiator (инициатор)** — попробуй понять, какой HTML/CSS/JS вызвал конкретный запрос.
7. Во вкладке **Timing (временная диаграмма)** у запроса посмотри доступные этапы: DNS, подключение, SSL/TLS, ожидание ответа и получение данных. Не каждый этап обязательно появится для каждого запроса.

**Маленькое упражнение:** на тестовой странице открой Network, нажми кнопку, которая обращается к API, и найди новый Fetch/XHR. Сравни, какие запросы были при первоначальном открытии, а какие появились после клика.

## 11. Что может пойти не так и что проверит QA

| Наблюдение | Где искать причину |
|---|---|
| Домен не открывается, HTTP-статуса нет | DNS, сеть, прокси, firewall, TLS |
| `ERR_CONNECTION_REFUSED` | Соединение до сервиса/порта не устанавливается; проверка слушающего процесса и маршрута |
| Ошибка сертификата | Срок действия, доменное имя, цепочка доверия, часы устройства |
| `301/302` по кругу | Настройка HTTPS, прокси, cookies, правила редиректов |
| HTML приходит с `200`, но страница пустая | Ошибка JS, ресурсы CSS/JS, неверный Content-Type, CSP, загрузка SPA |
| Страница видна, но нет бонусов | API-запрос, авторизация, CORS, кэш, ответ Backend |
| Картинки не появились | Ошибочные URL, `404`, политики безопасности, кэш, формат |
| Всё медленно | DNS/connect/TLS, TTFB (ожидание первого байта), ресурсы, JS, layout, Backend |

**Для Backend QA:** важно различать сетевую ошибку без HTTP-ответа, HTTP-ошибку и успешный HTTP-ответ с некорректной бизнес-логикой.

## 12. Ответ на собеседовании за 2–3 минуты

> Когда я ввожу `http://yandex.ru`, браузер сначала разбирает URL: определяет схему, хост и путь. Он также может решить сразу использовать HTTPS из-за настроек безопасности или HSTS.
>
> Если нужен сетевой запрос, браузер определяет IP-адрес хоста через DNS — сначала учитывает доступные кэши, а при необходимости обращается к резолверу.
>
> После этого ОС отправляет трафик через сеть к нужному адресу. Для HTTP/1.1 или HTTP/2 браузер обычно устанавливает TCP-соединение через SYN, SYN-ACK, ACK. Для HTTPS дополнительно используется TLS с проверкой сертификата и установлением защищённого обмена.
>
> Затем отправляется HTTP GET-запрос. Он может пройти через CDN или прокси к серверу приложения. Сервер вернёт HTML, ошибку или перенаправление — например, с HTTP на HTTPS.
>
> Получив HTML, браузер начинает строить DOM и загружает указанные в документе CSS, JavaScript и изображения. Дополнительные ресурсы могут находиться в CSS; JavaScript может отправлять API-запросы и менять DOM. На основе DOM и CSSOM браузер рассчитывает расположение элементов и рисует страницу.
>
> При повторном открытии часть этапов может быть пропущена благодаря кэшу и переиспользованию соединения, а для HTTP/3 используется QUIC вместо TCP.

**Как запомнить:** `URL → DNS → сеть → TCP/TLS (или QUIC) → HTTP → HTML/CSS/JS → отрисовка`.

На собеседовании сначала дай такую последовательность, а в детали TCP, DNS, ARP/NAT, TLS, HTTP-кэширования и DOM углубляйся по уточняющим вопросам.

## 13. Уточняющие вопросы со скрытыми ответами

### 1. Почему `http://yandex.ru` может не отправлять запрос по HTTP?

<details><summary>Показать ответ</summary>

Современный браузер может повысить схему до HTTPS до сетевого запроса (HSTS, HTTPS-First). Если сначала всё же был HTTP, сервер может вернуть редирект на HTTPS.

</details>

### 2. Зачем нужен DNS, если у сайта есть имя?

<details><summary>Показать ответ</summary>

Имя удобнее людям. Для маршрутизации пакетов нужен IP-адрес. DNS помогает определить подходящий адрес по имени с учётом кэшей и DNS-записей.

</details>

### 3. Почему не всегда происходят SYN, SYN-ACK, ACK?

<details><summary>Показать ответ</summary>

Может использоваться уже установленное TCP-соединение. Кроме того, HTTP/3 работает через QUIC поверх UDP, а не через TCP.

</details>

### 4. Откуда браузер узнаёт адрес картинки?

<details><summary>Показать ответ</summary>

Из HTML-тега `<img src="...">`, CSS `url(...)` или созданного JavaScript элемента. Относительный адрес разрешается относительно базового URL документа или CSS-файла в зависимости от контекста.

</details>

### 5. Если HTML пришёл с `200`, почему сайт может быть сломан?

<details><summary>Показать ответ</summary>

Могут не загрузиться CSS/JS, JavaScript может завершиться с ошибкой, а API-запросы после загрузки страницы — возвращать ошибки или неправильные данные.

</details>

### 6. Что такое DOM и CSSOM?

<details><summary>Показать ответ</summary>

DOM — структура HTML как дерево объектов; CSSOM — структура CSS-правил. Браузер использует их для определения отображаемых элементов, стилей, размеров и расположения.

</details>

### 7. Чем отличается ошибка DNS от HTTP 500?

<details><summary>Показать ответ</summary>

При ошибке DNS браузер ещё не получил адрес, необходимый для подключения, и HTTP-ответ может отсутствовать. `500` — это уже сформированный HTTP-ответ с серверной ошибкой.

</details>

### 8. Что происходит, если после загрузки нажать кнопку «Показать бонусы»?

<details><summary>Показать ответ</summary>

JavaScript может выполнить `fetch` к API, получить JSON и обновить DOM без полной перезагрузки документа. Этот запрос может отсутствовать в исходном HTML.

</details>
